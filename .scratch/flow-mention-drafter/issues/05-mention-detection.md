## Question

[Flow 알림 API 실호출로 멘션 데이터 확인](01-flow-alarm-api-check.md)의 결과를 바탕으로, 앱이 멘션을 **어떻게 수집하고 추적할지** 정한다.

- **채팅 멘션**: 2026-10-14에 MVP에서 뺐다(지도의 Out of scope 참고). 이 티켓은 업무 멘션만 다룬다.
- **그룹 멘션 거르기**: 알림의 `mentionYn: "Y"`에는 `@전체`(`MENTIONS: ["ALL"]`)도 섞여 온다. 나를 직접 지목했는지를 무엇으로 판정할지 정한다. 후보는 두 가지다.
  - 본문 `MENTIONS` 배열에 내 ID가 있는지 본다.
  - 댓글·대댓글 `contents`의 `@[이름](ID)` 표기에 내 ID가 있는지 본다.
- **폴링**: 주기와 커서를 어떻게 쓸지 정한다. 앱이 꺼져 있던 동안 쌓인 멘션을 어디까지 거슬러 가져올지도 정한다.
- **중복 방지**: 같은 멘션을 두 번 처리하지 않는 기준(무엇을 멘션의 정체성으로 볼지)을 정한다.
- **읽음 상태**: Flow의 읽음 상태를 앱이 바꿀지, 건드리지 않을지 정한다. 알림·게시글·댓글을 GET으로 조회하는 것만으로는 읽음 상태가 바뀌지 않는다.
- **맥락 수집 범위**: 스레드가 길 때 게시물 본문과 댓글 중 어디까지 가져올지 정한다. 대댓글 멘션의 원문이 `replyYn=Y`로 받는 처음 10개 안에 없을 수 있다. 그 경우 대댓글 API로 페이지를 넘겨야 한다.

응답 형태와 필드 값은 [Flow 알림 API 실호출로 멘션 데이터 확인](01-flow-alarm-api-check.md)의 답에 있다.

## Answer

2026-10-14에 사용자와 두 라운드로 정했다. 근거로 쓴 응답은 [flow-alarm-probe-result.json](../research/flow-alarm-probe-result.json)에 있다.

- 알림은 `alarmId` 내림차순(최신순)으로 온다.
- `lastCursor`는 `size=20`에서 `20`이 왔다. ID가 아니라 순번을 가리키는 값으로 보인다.
- 송신자가 나인 멘션 알림이 있었다(알림 `9999999015`: 내가 쓴 `@전체` 게시물).
- 댓글 `999999033` 아래에서 33분 동안 멘션 알림이 4건 왔다.

용어는 [GLOSSARY.md](../../../GLOSSARY.md)에 반영했다. **멘션**의 정의를 좁혔고, **멘션 위치**, **댓글 스레드**, **멘션 묶음**을 새로 넣었다.

### 나를 지목했는지 판정

멘션된 글을 직접 조회해서 판정한다. 알림의 `content`에는 표기가 대부분 빠져 있어서 판정에 쓸 수 없다.

- **내 ID**: 알림의 `receiverId`를 쓴다. 설정에서 따로 받지 않는다.
- **댓글·대댓글 멘션**: `contents`에 `@[…](내 ID)` 표기가 있으면 멘션이다.
- **본문 멘션**: `content` JSON의 TEXT 컴포넌트에서 아래 둘 중 하나라도 맞으면 멘션이다. 개인을 지목한 본문 멘션은 아직 관찰하지 못했기 때문에 둘 다 본다.
  - `MENTIONS`에 내 ID가 있다.
  - `CONTENTS`에 `@[…](내 ID)` 표기가 있다.
- **버리는 경우**: 아래 알림은 조용히 버린다.
  - 송신자(`registerId`)가 나인 알림
  - 글이 지워졌거나(404) 권한이 없는(403) 경우
  - 글이 수정되어 내 표기가 사라진 경우

### 멘션의 식별과 멘션 묶음

- **식별**: 멘션은 멘션 위치 `(postId, remarkId, replyId)`로 식별한다. 같은 멘션 위치에서 알림이 두 번 와도 멘션은 하나다. `alarmId`는 폴링 기준점으로만 쓴다.
- **묶음**: 아직 처리하지 않은 멘션은 `(postId, remarkId)`가 같으면 하나의 멘션 묶음이 된다.
  - 댓글 멘션과 그 아래 대댓글 멘션은 한 묶음이다.
  - 본문 멘션은 게시물마다 한 묶음이다.
  - 같은 게시물이라도 다른 댓글 스레드에서 온 멘션은 다른 묶음이다.
- **초안**: 묶음마다 하나를 만든다. 초안은 가장 최근 멘션에 답하고, 앞선 멘션은 맥락으로 쓴다.
- **검토 화면**: [초안 검토 화면 프로토타입](04-draft-review-prototype.md)의 단위가 멘션에서 멘션 묶음으로 바뀐다.
  - 상태(생성 중, 준비됨 등)는 묶음에 붙는다.
  - 트레이 숫자와 대기열 위치(`3 / 4`)는 묶음 수를 센다.
  - 원문 영역에는 묶인 멘션을 시간순으로 모두 보여 주고, 머리에 "멘션 3건"을 표시한다. 화면 문구는 "멘션"을 그대로 써도 된다.
- **처리 중인 묶음에 새 멘션이 올 때**

  | 묶음 상태 | 처리 |
  | :- | :- |
  | 생성 중 | 진행 중인 실행을 취소하고, 새 멘션을 합쳐 처음부터 다시 만든다. |
  | 준비됨 (초안·요구·지시를 손대지 않음) | 합치고 자동으로 다시 만든다. |
  | 준비됨 (사용자가 하나라도 손댐) | 합치기만 한다. "새 멘션 1건" 표시와 "다시 만들기" 버튼을 띄운다. |
  | 게시 중 (5초 카운트다운) | 합치지 않는다. 게시는 그대로 진행하고, 새 멘션은 새 묶음으로 만든다. |
  | 실패 | 합치고 자동으로 다시 시도한다. |
  | 게시됨·무시함 | 새 묶음을 만든다. 나중에 무시를 되돌려도 두 묶음을 합치지 않는다. |

### Flow에서 이미 직접 답한 멘션

- **판정 기준**: 아래 글이 있으면 그 멘션은 직접 답한 것으로 본다. 시각은 각 글의 `registeredDateTime`을 그 멘션 알림의 `registeredDateTime`과 비교한다.
  - 댓글 스레드 묶음: 그 댓글 스레드 안에서 멘션보다 나중에 쓴 내 대댓글
  - 본문 묶음: 그 게시물에서 멘션보다 나중에 쓴 내 댓글. 대댓글은 넣지 않는다.
- **판정 범위를 좁게 잡은 이유**: 같은 게시물의 다른 댓글 스레드에 쓴 내 글은 답으로 치지 않는다. 잘못 건너뛰면 멘션을 놓치지만, 잘못 만든 초안은 한 번 무시하면 끝나기 때문이다.
- **처리**
  - 내가 마지막으로 답한 글보다 앞선 멘션은 묶음에서 뺀다.
  - 묶음의 멘션이 모두 빠지면 초안을 만들지 않는다. 그 묶음은 처리됨에 **"Flow에서 직접 답함"** 상태로 둔다. 이 상태는 프로토타입의 상태 목록에 새로 더한다.
  - 사용자가 되돌리면 초안을 만든다.
- **확인 시점**: 감지할 때 한 번, 초안 생성을 시작하기 직전에 한 번 확인한다. 생성 직전에는 맥락을 어차피 새로 조회하므로 추가 조회가 없다.
- 초안이 준비된 **뒤에** 직접 답한 경우는 [게시 전 스레드 변화 처리 결정](14-thread-change-before-post.md)에서 다룬다.

### 폴링

- **주기**: 60초마다 알림 목록을 조회한다. 조회 한도(분당 1,000회)에 비해 여유가 크다.
  - 앱을 시작할 때, 잠자기에서 깨어날 때, 트레이 메뉴에서 "지금 확인"을 누를 때는 바로 조회한다.
- **요청**: `GET /user/alarms?filters=MENTION&size=20`이다. `readYn`은 생략해서 읽은 알림도 받는다.
  - 앱이 조회하기 전에 모바일 등에서 알림을 열어 읽음이 되면, `readYn=N`으로는 그 멘션을 놓치기 때문이다.
- **기준점**: Flow의 `cursor`는 저장하지 않는다. 대신 이미 본 가장 큰 `alarmId`를 기준점으로 저장한다.
  - 최신순으로 페이지를 넘기다가 기준점 이하의 알림, 72시간보다 오래된 알림, `hasNext: false` 중 하나를 만나면 멈춘다.
  - 페이지를 넘기는 사이에 새 알림이 오면 항목이 밀려 중복이 생긴다. 이 중복은 멘션 위치로 거른다. 항목이 밀리기만 하므로 놓치는 알림은 생기지 않는다.
- **오류**
  - `429`: `Retry-After`만큼 기다린다.
  - 네트워크 오류: 다음 주기에 다시 시도한다.
  - `401`: 폴링을 멈추고 트레이에 "키 확인 필요"를 띄운다.

### 앱이 꺼져 있던 동안의 멘션

- **첫 실행**: 과거 멘션은 가져오지 않는다. 가장 최근 알림의 `alarmId`를 기준점으로 잡고, 그 뒤에 온 멘션만 처리한다. 오래된 멘션마다 에이전트가 한꺼번에 실행되는 것을 막기 위해서다.
- **다시 켰을 때**: 기준점 이후의 멘션 중 최근 72시간 안에 온 것만 가져온다. 72시간이면 주말에 꺼 둔 경우까지 덮는다.
- **건너뛴 멘션**: 72시간보다 오래된 멘션은 건너뛰고 표시하지 않는다. 그런 멘션은 지금처럼 Flow에서 직접 처리한다.

### 읽음 상태

앱은 Flow의 읽음 상태를 바꾸지 않는다. 앱이 Flow에 쓰는 것은 댓글 게시뿐이다.

- 단건 읽음 API(`PATCH /user/alarms/read`)는 "그 알림의 프로젝트, 게시글, 댓글 정보로" 처리한다고 되어 있어서, 다른 알림까지 함께 읽음이 될 수 있다. 이 범위는 확인하지 않았다.
- Flow 쪽 배지는 사용자가 직접 지운다.

### 맥락 수집 범위

- **항상 가져오는 것**: 게시물 제목과 본문이다.
  - 본문은 `content` JSON의 TEXT 컴포넌트에서 꺼낸다.
  - 첨부는 파일 이름만 넣고, 이미지는 넣지 않는다.
- **댓글 스레드 묶음**: 대상 댓글 스레드를 **전부** 가져온다. `replyYn=Y`로 받는 처음 10개를 넘는 대댓글은 `GET /user/comments/{postId}/replies/{commentId}`로 끝까지 페이지를 넘겨 가져온다.
- **다른 댓글**: 최근 20개까지 가져오고, 댓글마다 대댓글은 처음 10개까지만 넣는다. 본문 묶음이면 이 20개가 스레드 맥락이 된다.
- **가져오는 시점**: 초안을 만들 때마다 새로 조회한다. 재생성할 때도 마찬가지다. 감지 시점의 내용을 저장해 두고 쓰지 않는다.
- **총 길이 상한**: 정하지 않았다. 넘쳤을 때 무엇부터 뺄지도 함께 [게시 전 스레드 변화 처리 결정](14-thread-change-before-post.md)으로 넘겼다.

### 다른 티켓에 넘기는 것

- **[에이전트 실행 계약 결정](07-agent-run-contract.md)**: 이미 닫혔다. 스펙을 쓸 때 아래처럼 읽는다.
  - "멘션 원문"은 멘션 묶음의 멘션 전부다. 시간순으로 넘기고, 답할 대상인 마지막 멘션을 표시한다.
    - 07에서 넘기지 않기로 한 "같은 시점에 들어온 다른 멘션"은 다른 묶음의 멘션을 말한다.
  - 재생성 표의 "처음과 같은 입력"은 입력의 구성이 같다는 뜻이다. Flow 내용은 위 "가져오는 시점"대로 매번 새로 조회한다.
  - 07은 Flow 사용자 ID를 넘기지 않기로 했다. 그래서 앱이 본문과 댓글의 `@[이름](ID)` 표기를 이름 표기로 바꿔서 넘긴다.
- **[초안 게시 위치와 형식 결정](12-post-placement.md)**
  - 게시 위치는 멘션 묶음의 마지막 멘션을 기준으로 정한다.
  - 한 묶음에 송신자가 여러 명일 수 있다(관찰 사례: 한 댓글 스레드에서 두 사람). 다시 멘션할 대상을 정해야 한다.
- **[게시 전 스레드 변화 처리 결정](14-thread-change-before-post.md)**: 초안이 준비된 뒤의 스레드 변화와 맥락 길이 상한을 다룬다.
- **지도의 안개**
  - 온보딩: 최근 멘션 하나로 시험해 보기, 다른 계정의 키로 바꿨을 때 기준점 초기화
  - 처리한 멘션의 보관: 기준점, 처리한 멘션 위치, 멘션 묶음과 상태를 저장 대상에 추가
  - 여러 PC에서 동시 실행: 감지 방식에서 나온 사실을 덧붙임
