## Question

dmg와 exe를 내려받는 **다운로드 사이트**를 어떤 형태로 만들지 정한다.

- **호스팅 위치**: GitHub Releases와 Pages, 사내 서버, 정적 호스팅 서비스 중 어디에 둘지.
- **공개 범위**: 사내 팀원에게만 열지, 공개할지. 사내 한정이라면 접근을 어떻게 막을지.
- **설치 안내**: 미서명 앱이라 설치할 때 뜨는 경고를 넘어가는 방법을 OS별로 어떻게 안내할지. 문구는 [트레이 데스크톱 앱 프레임워크와 미서명 배포 조사](03-tray-app-framework-research.md)를 근거로 한다.
  - [서명 정책 재검토](10-signing-policy-review.md)에서 정한 제약
    - Windows 안내의 첫 단계에서 스마트 앱 컨트롤 상태를 확인하게 한다. 켜져 있으면 "이 PC에서는 아직 실행되지 않으니 배포 담당자에게 알려 달라"고 안내한다.
    - SAC를 끄라는 안내는 하지 않는다. 조사 문서 안내문 초안의 "관리자에게 문의"는 회사 관리 PC가 없다는 전제와 맞지 않으므로 바꾼다.
    - 새 버전을 설치하면 다시 확인을 받는다는 점을 안내한다. Windows는 SmartScreen 경고, macOS는 Keychain 재허용과 알림 권한이 해당한다.
- **버전 관리**: 버전을 어떻게 표시할지, 이전 버전도 내려받을 수 있게 할지.
- **산출물 연결**: [데스크톱 프레임워크와 기술 스택 결정](08-desktop-stack.md)에서 정한 빌드 산출물이 사이트에 반영되는 경로.

화면 결정에는 `ui-design` 스킬을 함께 쓴다.

## Comments

- 2026-10-16, [데스크톱 프레임워크와 기술 스택 결정](08-desktop-stack.md)에서 덧붙인다.
  - **산출물**: 태그를 푸시하면 GitHub Actions가 `stardraft` 저장소에 초안 Release를 만든다.
    - 파일은 macOS arm64 DMG, Windows x64 NSIS 설치 파일, `SHA256SUMS.txt`다.
    - 공개는 사용자가 직접 누른다.
  - **저장소 공개 범위**: `stardraft`는 개인 계정의 비공개 저장소로 시작한다. 라이선스는 MIT이고, 공개로 바꾸는 시점은 사용자가 정한다.
    - 비공개인 동안 Release 파일은 GitHub 로그인과 저장소 권한이 있어야 받을 수 있다.
    - 그래서 사이트가 파일을 어떻게 내보낼지 여기서 정한다.
    - 비공개 저장소에서 GitHub Pages를 쓸 수 있는지(요금제 조건)는 확인하지 않았다.
  - **사이트 코드 자리**: 같은 저장소에 `apps/site` 자리를 두었다. 사이트를 여기에 둘지 이 티켓에서 정한다.
  - **macOS**: Apple Silicon 전용이다. 사이트에 이 점을 표시한다. Intel Mac을 쓰는 팀원이 나오면 x64 DMG를 추가한다.
  - **Windows**: 설치 파일은 원클릭이다. 관리자 권한 없이 사용자별로 설치하고, 설치 위치는 묻지 않는다.
  - **설치 안내 문구**: 앱 이름은 `Stardraft`다. 설치 안내에 나오는 대화상자와 키체인 항목 이름(`Stardraft Safe Storage`)에 이 이름이 쓰인다.

## Answer

2026-10-16~17에 사용자와 그릴링으로 정했다.

- 근거가 된 조사
  - [다운로드 사이트 호스팅 조사](../research/download-site-hosting.md): GitHub Pages와 Release의 제한, NSIS 업데이트 동작, 최소 OS, 칩 판별, 스마트 앱 컨트롤 경로를 다뤘다. 이 세션에서 직접 확인한 사실은 문서 끝 "추가 확인"에 덧붙였다.
  - 이 티켓에서 갈라져 나와 먼저 닫힌 조사 티켓이 둘 있다. [다운로드 사이트 UI/UX 사례 조사](18-download-site-ux-research.md)와 [앱 내 업데이트 가능성 조사](20-in-app-update-research.md)다.

### 공개 범위

- 누구나 로그인 없이 받을 수 있다. 검색 노출도 막지 않는다(`noindex` 없음).
- 페이지에 회사 이름과 사람 이름은 넣지 않는다. 언어는 한국어만 쓴다.
- 처음에는 "링크를 아는 사람에게만 열고 `noindex`를 건다"로 정했다. 그 뒤 저장소를 처음부터 공개하기로 하면서(아래), 사이트의 노출 범위도 저장소에 맞췄다.
- 사내 한정(GitHub 권한, 회사 메일 인증)은 고르지 않았다. 설치 파일에도 페이지에도 감출 회사 정보가 없기 때문이다. [데스크톱 프레임워크와 기술 스택 결정](08-desktop-stack.md)에서 회사별 값을 코드에서 모두 뺐다.

### 저장소와 호스팅

- **`stardraft`는 처음부터 공개 저장소(MIT)로 만든다.** 08의 "비공개로 시작한다"를 바꾼다.
  - 처음에는 비공개 `stardraft` 하나에 모두 두기로 했다. Vercel 함수가 읽기 토큰으로 서명된 임시 URL을 받아 넘기는 구조였다.
    - 비공개 Release 파일의 서명 URL은 인증 없이 받아지고, 약 55분 동안 유효하다. 사용자 계정의 다른 비공개 저장소로 실측했다.
  - 그 뒤 사용자가 "오픈소스로 풀 생각이었다"고 밝혔고, 비공개여야 할 이유가 없었다. 그래서 비공개 기간을 위한 구조를 버렸다. 그 구조를 위해 남기려던 ADR도 남기지 않는다.
  - 업무상 저작물(저작권법 제9조)은 08에서 설명했고, 사용자는 개인 소유로 진행한다. 공개하면 회사도 이 코드를 보게 된다. 그래서 회사 시간이나 장비로 만든다면 공개 전에 회사 규정을 확인하는 편이 안전하다고 알렸다.
- **공개 저장소에서 지킬 것**
  - 첫 커밋부터 비밀값과 회사 데이터를 넣지 않는다. 비밀값은 Actions 비밀값에만 둔다.
  - 외부인이 연 PR의 워크플로는 승인해야 돌게 한다. 업데이트 서명 키 같은 비밀값을 지키기 위해서다.
  - 이 기획 저장소는 공개하지 않는다. 새 저장소로 옮기는 스펙, `GLOSSARY.md`, ADR은 회사 정보가 없는지 확인한 뒤 옮긴다.
- **사이트 코드**: `stardraft/apps/site`에 둔다.
- **호스팅**: Vercel Hobby에 둔다.
  - Root Directory는 `apps/site`다. 앱 코드만 바뀐 푸시는 Ignored Build Step으로 빌드를 건너뛴다.
  - Hobby는 비상업 개인 용도만 허용한다. 이 앱은 개인 소유이고, 무료로 배포하며, 결제나 광고가 없다. 그래서 문서의 상업적 이용 예시에 해당하지 않는다고 보고 Hobby로 시작한다. 애매해지면 Vercel 지원팀에 묻거나 Pro로 옮긴다.
  - GitHub Pages는 쓰지 않는다. 사용자가 Vercel을 골랐다.
- **도메인**: `stardraft.squadify.app`이다. 사용자가 직접 설정한다.

### 다운로드와 버전 정보

- **다운로드 링크**: `/download/mac`, `/download/windows`, `/download/<버전>/<os>`를 둔다.
  - Vercel 함수가 공개 Release에서 파일을 찾아 GitHub 파일 주소로 302 리디렉트한다. 사이트의 링크가 GitHub 주소에 직접 묶이지 않게 하려는 것이다.
  - 초안과 사전 릴리스는 고르지 않는다.
- **버전 정보**: 페이지는 같은 사이트의 `/api/releases`를 부른다.
  - 이 함수는 GitHub API 결과를 CDN에 5분 동안 캐시한다. Release를 공개하면 5분 안에 반영되므로, 다시 빌드하거나 배포 훅을 쓸 일이 없다.
  - 내주는 정보는 버전, 날짜, 파일 크기, sha256 `digest`, 릴리스 노트다.
  - 공개 정보만 읽는 토큰을 하나 둔다. Vercel 서버는 여러 고객이 IP를 나눠 쓴다. 그래서 토큰 없이 부르면 비인증 한도(IP당 시간당 60회)를 남이 다 써 버릴 수 있다.
- **이전 버전**: 사이트는 GitHub Release 목록으로 링크한다. 사례 10곳 중 7곳이 이렇게 한다.

### 릴리스 흐름과 버전

- 태그를 푸시하면 08의 워크플로가 `stardraft`에 초안 Release를 만든다.
  - 앱 내 업데이트에 필요한 파일도 함께 올라간다. macOS zip, `latest.yml`, `latest-mac.yml`, 서명 파일이다.
  - 정확한 목록은 [앱 내 업데이트 방식 결정](22-in-app-update-design.md)에서 정한다.
- 저장소 주인은 초안 상태에서 GitHub에서 직접 파일을 받아 자기 PC에 먼저 설치해 본다. 공개는 사용자가 직접 누르고, 사전 릴리스는 쓰지 않는다.
- `stardraft`에 immutable releases를 켠다.
  - 켜면 공개한 Release의 파일과 태그를 바꾸거나 지울 수 없다.
  - 미서명 앱이라 팀원들이 경고를 넘기는 데 익숙하다. 그래서 파일 바꿔치기를 막는 것이 중요하다.
- 버전은 SemVer이고 `0.1.0`에서 시작한다. 파일 이름에는 버전을 넣는다(electron-builder 기본값).
- **다운그레이드 차단**
  - 앱은 자기가 아는 것보다 새 `state.db`(`PRAGMA user_version`)나 `settings.json`(`schemaVersion`)을 만나면 실행하지 않는다.
  - 대신 "이 데이터는 더 새 버전(vX)에서 만들어졌습니다. 새 버전을 다시 설치하세요"라고 알리고, 데이터는 자동으로 지우지 않는다.
  - 앱 내 업데이트로 마이그레이션이 일어난 뒤 옛 버전으로 되돌릴 때의 처리는 22에서 정한다.

### 앱 내 업데이트

- **범위 안으로 옮긴다.**
  - 사용자가 "다른 앱은 앱 안에서 업데이트하고 다시 실행되는데, 그건 안 되느냐"고 물었다.
  - [앱 내 업데이트 가능성 조사](20-in-app-update-research.md) 결과, Windows는 가능하고 macOS는 조건부로 가능하다.
- 첫 버전(`0.1.0`)부터 업데이트 기능과 macOS 명시 DR 재서명을 넣는다. 나중에 넣으면 그 버전은 팀원 모두가 사이트에서 한 번 더 수동으로 설치해야 하기 때문이다.
- macOS는 [앱 내 업데이트 macOS 실기 검증](21-in-app-update-macos-check.md)으로 확정한다. 실패하면 macOS만 수동 업데이트와 새 버전 알림으로 돌아가고, Windows는 그대로 간다.
- 나머지 방식은 [앱 내 업데이트 방식 결정](22-in-app-update-design.md)에서 정한다. 업데이트 파일 출처(GitHub에서 직접 받을지, 우리 도메인을 거칠지), 받는 시점, 설치 전 확인, 서명 키 관리가 해당한다.
  - 우리 도메인을 거친다면 앱에 넣는 주소는 `stardraft.squadify.app`이다.
  - 도메인 갱신이 끊기면 이미 설치된 앱의 업데이트도 끊긴다. 사용자는 이 점을 알고 골랐다.
- 지도의 Out of scope에서 "앱 내 자동 업데이트"를 뺐다.

### 설치 안내

문구는 [트레이 데스크톱 앱 프레임워크와 미서명 배포 조사](03-tray-app-framework-research.md)의 안내문 초안을 바탕으로 쓰고, 아래 내용을 바꾼다.

- **macOS**
  - `xattr`로 quarantine을 지우는 최후 수단은 뺀다.
    - ad-hoc 서명한 DMG는 "열지 않음 → 그래도 열기" 경로로 간다(11 실측).
    - CI는 `codesign --verify --deep --strict`를 통과하지 못하면 빌드를 실패시킨다.
    - 그러면 정상 배포물에서 "손상됨"이 뜨는 경우는 파일이 깨졌거나 바뀐 경우뿐이다.
  - "손상되었기 때문에 열 수 없습니다"가 뜨면 이렇게 안내한다. "받는 중에 파일이 깨졌거나 바뀌었을 수 있습니다. 이 파일은 지우고 사이트에서 다시 받으세요. 다시 받아도 같으면 설치하지 마세요."
  - 지원 환경은 Apple Silicon, macOS 13 이상이다(Electron 44의 최소 버전).
    - 웹 페이지는 Safari에서 칩을 판별할 수 없다. 그래서 Intel Mac을 자동으로 막지 않고, 칩을 확인하는 방법을 적는다.
- **Windows**
  - 지원 환경은 Windows 10 이상, x64다. ARM PC에서는 에뮬레이션으로 실행된다.
  - 첫 단계에서, Windows 11이면 스마트 앱 컨트롤 상태를 확인하게 한다. Windows 10에는 이 기능이 없다.
    - **켜기**이면 "스마트 앱 컨트롤이 켜져 있으면 Stardraft는 실행되지 않습니다"라고 사실만 알린다.
    - SAC를 끄라는 안내는 하지 않는다([서명 정책 재검토](10-signing-policy-review.md)).
  - "배포 담당자에게 알려 달라" 같은 연락 절차는 넣지 않는다.
    - 사용자는 "프로그램을 쓰는 것은 본인의 선택"이라며 이 절차가 필요 없다고 했다.
    - 10과 이 티켓 본문에 있는 해당 문구를 대체한다.
  - 수동으로 새 버전을 설치할 때 앱이 켜져 있으면 "Stardraft이(가) 실행 중입니다. OK을 클릭하면 종료됩니다." 창이 뜬다. 이 점을 미리 알린다. 데이터는 유지된다.
- **스크린숏**: 사용자가 막히는 화면 네 곳에만 실제 앱으로 찍은 스크린숏을 넣는다. 나머지 단계는 버튼 이름을 굵게 인용한다.
  - 네 곳
    - macOS "'Stardraft'을(를) 열지 않음" 대화상자
    - 시스템 설정의 **그래도 열기** 위치
    - Windows "Windows의 PC 보호" 화면(**추가 정보** → **실행**)
    - 스마트 앱 컨트롤 설정 화면
  - 스크린숏은 첫 릴리스 빌드로, 한국어 OS에서 찍는다.
  - Windows 화면은 08의 "팀 배포 전 Windows 점검 목록"을 돌릴 때 찍는다. 그때 실제 메뉴 이름이 "앱 & 브라우저 컨트롤"인지 "앱 및 브라우저 컨트롤"인지도 확인한다.
  - OS 메이저 업데이트로 화면이 바뀌면 다시 찍는다.
  - 이렇게 정한 이유가 있다. 실기 검증 때 사용자가 "열지 않음" 대화상자를 보고 "다시 설치해야 하냐"고 되물었다.
- **다시 묻는 확인**
  - 업데이트 뒤 macOS가 Keychain 재허용(`Stardraft Safe Storage`)과 알림 권한을 다시 물을 수 있다고 미리 알린다.
  - 앱 밖에서 수동으로 설치하면 SmartScreen과 "그래도 열기"도 다시 거친다.

### 화면

- 화면은 [다운로드 사이트 화면 프로토타입](19-download-site-prototype.md)에서 정한다. 사용자가 비슷한 사이트 10곳을 조사해 초안을 만들고 구체화하자고 했다.
- 인터랙티브는 설치를 돕는 상호작용과 시각 연출을 **모두** 뜻한다.
- 이 사이트에서는 `ui-design`의 장식 모션 금지를 푼다. 사용자의 결정이고, 그 차이는 19에 적어 두었다.
- OS의 "동작 줄이기"(`prefers-reduced-motion`)는 지킨다.
- **담을 내용**: 아래 여덟 가지다. 배치와 표현은 19에서 바꿀 수 있다.
  1. 한 줄 소개
  2. OS별 다운로드와 지원 환경
  3. 설치 전에 필요한 것: Flow 개인 API 키, Claude Code CLI 설치와 로그인
  4. OS별 설치 안내
  5. 업데이트 방법: 보통은 앱이 알아서 하고, 안 되면 사이트에서 다시 받는다.
  6. 변경 내역
  7. 이전 버전(GitHub Release 목록 링크)과 SHA256
  8. 삭제 방법: 앱, 데이터 폴더(`~/Library/Application Support/Stardraft/`, `%APPDATA%\Stardraft\`), macOS 키체인 항목
