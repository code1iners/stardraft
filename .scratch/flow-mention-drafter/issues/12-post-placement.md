# 초안 게시 위치와 형식 결정

Map: [Flow 멘션 답변 초안 앱](../map.md)
Type: grilling
Mode: HITL
Status: resolved
Blocked by: 04

## Question

승인한 초안을 Flow의 **어디에, 어떤 형식으로 게시할지** 정한다. 근거가 되는 응답 형태는 [Flow 알림 API 실호출로 멘션 데이터 확인](01-flow-alarm-api-check.md)의 답에 있다.

- **게시 위치**: 멘션 위치(본문·댓글·대댓글)마다 초안을 게시글의 새 댓글로 달지, 대댓글로 달지 정한다.
  - Flow의 댓글은 댓글과 대댓글의 2단 구조다. 대댓글 멘션은 알림에 부모 댓글의 `remarkId`와 대댓글의 `replyId`가 함께 온다.
  - 쓰기 API는 `POST /user/comments/{postId}`(댓글)와 `POST /user/comments/{postId}/replies/{commentId}`(대댓글)다.
  - [멘션 감지 방식 결정](05-mention-detection.md)에서 초안을 멘션 묶음마다 하나씩 만들기로 했다. 그래서 게시 위치는 묶음의 마지막 멘션을 기준으로 정한다.
- **송신자 다시 멘션하기**: 게시 본문 앞에 송신자를 `@[이름](ID)` 표기로 멘션할지 정한다.
  - 한 묶음에 송신자가 여러 명일 수 있다(관찰 사례: 한 댓글 스레드에서 두 사람). 누구를 다시 멘션할지도 함께 정한다.
  - 조회 응답에서는 이 표기를 확인했다. 쓰기 API가 이 표기를 받아 실제 멘션 알림으로 처리하는지는 문서에 없다. 확인이 필요하면 별도 task 티켓으로 뺀다.
- **근거 표기**: 근거를 게시 본문에 넣을지, 검토 화면에만 둘지 정한다.
  - 검토 화면에서는 근거를 자연어 설명과 파일·줄 위치로 보여 주고, 초안 문장마다 근거 번호(①②)를 붙이기로 했다([초안 검토 화면 프로토타입](04-draft-review-prototype.md)).
  - 게시 본문에 넣는다면, 번호와 설명을 어떤 형식으로 남길지도 함께 정한다.
- **초안의 형태**: [에이전트 실행 계약 결정](07-agent-run-contract.md)에 따라 초안은 문단과 문장의 배열로 온다. 글머리표와 `@[이름](ID)` 멘션 표기가 없는 평문이다. 게시 본문으로 바꿀 때 문단 사이를 어떻게 나눌지와 멘션 표기를 어디에 넣을지는 이 티켓에서 정한다.

## Answer

2026-10-15에 사용자와 그릴링으로 정했다.

- 쓰기 API의 문서 사실은 [flow-api-facts.md](../research/flow-api-facts.md)의 "쓰기" 절에 반영했다.
- 문서로 알 수 없는 사실은 [댓글 쓰기 API 실측](15-comment-write-api-check.md)으로 분리했다. 실측 결과에 따라 적용할 규칙은 이 답의 "실측 결과에 따른 규칙"에 미리 정해 두었다.

### 멘션 묶음 유지

그릴링 중에 1문 1답(멘션 하나에 초안 하나, 게시 하나)과 비교했다. 멘션 묶음을 유지하고, [멘션 감지 방식 결정](05-mention-detection.md)은 고치지 않는다.

- [Flow 알림 API 실호출로 멘션 데이터 확인](01-flow-alarm-api-check.md)에서 받은 멘션 알림 20건 중 12건은 여러 번 멘션이 오간 댓글 스레드 3곳에서 왔다. 그중 한 스레드에서는 49분 동안 4건이 왔다.
- 1문 1답이면 이런 스레드에서 에이전트 실행과 검토할 초안이 멘션 수만큼 늘어난다. 앞선 초안은 이미 대화가 지나간 질문에 답하게 된다.
- 묶음이 더하는 구현은 묶음 키와 합치기 표 정도다.

### 게시 위치

게시 위치는 멘션 묶음의 키 `(postId, remarkId)`로 정해진다. 한 묶음의 멘션은 모두 게시 위치가 같다. 그래서 질문에 적었던 "묶음의 마지막 멘션을 기준으로 한다"는 규칙은 두지 않는다.

| 묶음 | 게시 | API |
| :- | :- | :- |
| 본문 묶음 (`remarkId`가 `-1`) | 게시물에 새 댓글 | `POST /user/comments/{postId}` |
| 댓글 스레드 묶음 | 그 댓글에 대댓글 | `POST /user/comments/{postId}/replies/{remarkId}` |

- 댓글 스레드 묶음은 멘션이 댓글에 왔든 대댓글에 왔든 같다. Flow의 댓글은 2단 구조라서 대댓글에 다시 대댓글을 달 수 없다.
- 이 위치는 05의 "Flow에서 이미 직접 답한 멘션" 판정 범위와 같다. 그래서 앱이 올린 글도 그 판정에서 내 답으로 잡힌다. 다른 PC에서 앱으로 올린 글도 마찬가지다.

### 받는 사람

게시 본문 앞에서 다시 멘션하는 Flow 구성원을 **받는 사람**이라 한다.

- **기본값**: 묶음에 남은 멘션의 송신자 전원이다.
  - 중복은 빼고, 처음 멘션한 순서로 둔다.
  - 05의 직접 답함 처리로 묶음에서 빠진 멘션의 송신자는 넣지 않는다.
  - 마지막 멘션의 송신자만 넣지 않는 이유: 게시하면 묶음 전체가 처리되므로, 기다리던 송신자 모두에게 알림이 가야 한다.
- 이름과 ID는 초안을 만들 때 새로 조회한 글의 `registerName`, `registerId`를 쓴다.
- **검토 화면**: 초안 영역 머리 바로 아래에 "받는 사람" 줄을 둔다.

  ```
  초안
  받는 사람  @김철수 ×   @이영희 ×
  ───────────────────────────────
  실제 서비스에서는 재시도를 5번 합니다. ① …
  ```

  - 항목마다 ×로 뺄 수 있다. 모두 빼면 멘션 없이 게시한다.
  - 송신자가 아닌 사람을 더하는 기능은 MVP에 넣지 않는다.
  - 항목은 테두리만 있는 작은 표시로 그린다. 알약 모양이나 색 강조는 쓰지 않는다.
  - 멘션 표기를 편집기 텍스트에 넣지 않는 이유: 사용자가 이름을 고치면 이름과 ID의 짝이 깨진다.

### 게시 본문

- **구성**: 받는 사람의 `@[이름](ID)` 표기를 공백으로 이어 맨 앞에 두고, 공백 하나 뒤에 편집기 텍스트를 같은 줄에서 잇는다. 편집기 텍스트는 앞뒤 공백을 지운다. 받는 사람이 없으면 편집기 텍스트만 올린다.
  - 예: `@[김철수](kim@…) @[이영희](lee@…) 실제 서비스에서는 재시도를 5번 합니다. …`
  - 관찰한 Flow 댓글이 표기로 시작해 같은 줄에서 본문을 잇는 모양이었다.
- **초안에서 편집기 텍스트로**: 초안 실행의 출력을 아래처럼 텍스트로 만들어 편집기에 보여 준다.
  - 같은 문단의 문장은 공백 하나로 잇는다.
  - 문단 사이에는 빈 줄 하나(`\n\n`)를 둔다.
  - 근거 번호(①②)는 화면 장식이라서 텍스트에 들어가지 않는다.
  - 그래서 편집했든 안 했든 "검토자가 본 글이 그대로 올라간다".
- **넣지 않는 것**
  - **근거와 근거 번호**: 쉬운 말 기준([초안 검토 화면 프로토타입](04-draft-review-prototype.md))과 부딪힌다. 근거 목록 없이 번호만 남으면 뜻이 없고, 저장소 내부 경로가 Flow에 남는다. 근거를 포함하는 옵션도 MVP에 두지 않는다.
  - **AI 초안 표시 꼬리말**: 사람이 검토하고 내 명의로 올리므로 넣지 않는다. 설정도 두지 않는다. 필요하면 사용자가 "추가 지침"으로 초안 안에 넣을 수 있다.
- **게시 버튼을 끄는 경우**
  - 편집기 텍스트가 비었을 때. Flow는 `contents`에 최소 1자를 요구한다.
  - 게시 본문(받는 사람 표기 포함)이 4,000을 넘을 때. 편집기 아래에 "Flow 댓글 길이 제한을 넘었습니다 (4,120 / 4,000)"를 보여 준다. 초안은 보통 5문장 이내라서 사용자가 길게 고쳤을 때만 생긴다.

### 게시 실패

REST API에는 댓글 수정·삭제가 없다. 같은 글이 두 번 올라가면 Flow 화면에서 손으로 지워야 하고, 5초 게시 취소가 앱 안의 유일한 되돌리기 수단이다. 아래 처리는 이 점을 기준으로 정했다.

- **상태**: 새 상태 **게시 실패**를 둔다.
  - 생성 실패용 "실패"와 나눈 이유: 할 수 있는 행동이 다르다. 게시 실패는 초안을 다시 만들 필요 없이 다시 게시하면 된다.
  - 상태 목록은 04의 생성 중, 준비됨, 게시 중, 게시됨, 실패, 무시함과 05의 "Flow에서 직접 답함"에 게시 실패를 더한 것이 된다.
- **알리는 방법**: 게시를 누르면 바로 다음 멘션으로 넘어가므로, 실패는 사용자가 다른 묶음을 보는 동안 일어난다. 그래서 눈에 띄게 알린다.
  - 실패한 순간 토스트를 한 번 띄운다. 예: "게시하지 못했습니다: 김철수님 멘션"
  - 트레이의 빨간 점과 펼친 창의 "실패" 묶음 목록에 넣는다.
- **화면**: 상세 머리에 쉬운 말로 된 사유 한 줄을 보여 준다. 초안과 편집한 내용은 그대로 두고, 계속 고칠 수 있다. 버튼은 "다시 게시"와 "무시"다.
- **응답별 처리**

  | 응답 | 처리 |
  | :- | :- |
  | `403` | 게시 실패. 사유: "이 글에 댓글을 쓸 권한이 없습니다" |
  | `404`, `412` | 게시 실패. 사유: "글이나 댓글이 지워졌습니다" |
  | `400`, `422` | 게시 실패. 사유: "Flow가 글을 받지 않았습니다(길이 등)" |
  | `429` | 요청이 처리되지 않은 것이 확실하다. `Retry-After`만큼 기다렸다가 자동으로 한 번 더 보낸다. 또 실패하면 게시 실패로 두고, 사유는 "Flow 요청 한도를 넘었습니다"다. |
  | `401` | 묶음 하나의 실패로 다루지 않는다. 05에서 정한 대로 폴링을 멈추고 트레이에 "키 확인 필요"를 띄운다. 묶음은 준비됨으로 남긴다. |
  | 응답 없음(타임아웃, 연결 끊김), `5xx` | 서버에 글이 올라갔는지 알 수 없다. 아래 확인을 거친다. |

  - 오류 코드 체계는 Flow 문서끼리 맞지 않는다(400과 422 등). 그래서 코드 이름보다 상태 코드로 나눈다.
- **올라갔는지 알 수 없을 때의 확인**: 그 자리를 다시 조회해서 게시 요청 뒤에 올라온 내 글을 찾는다. 본문 묶음이면 게시물의 댓글을, 댓글 스레드 묶음이면 그 스레드의 대댓글을 조회한다.
  - 찾으면 게시됨으로 둔다.
  - 못 찾으면 게시 실패로 두고, 사유는 "Flow가 응답하지 않았습니다"다.
  - 다시 조회하지 않고 그대로 재시도하면 중복 댓글이 남을 수 있기 때문이다.
- **게시 성공**: 응답의 `commentId`(새 댓글)나 `replyId`(대댓글)를 묶음에 기록한다. 쓰기 응답에는 `registeredDateTime`이 없다.

### 실측 결과에 따른 규칙

[댓글 쓰기 API 실측](15-comment-write-api-check.md)의 결과에 따라 아래처럼 적용한다.

| 실측 항목 | 결과가 이러면 | 적용 |
| :- | :- | :- |
| `@[이름](ID)` 표기가 멘션으로 처리되는가 | 멘션으로 보이지 않거나 알림이 가지 않음 | 받는 사람 줄을 숨기고 멘션 없이 게시한다. 날것의 `@[…](…)` 글자가 Flow에 보이지 않게 한다. |
| 빈 줄이 그대로 보이는가 | 빈 줄이 무너짐 | 문단 사이를 줄바꿈 하나로 바꾼다. |
| 4,000의 단위 | 글자 또는 바이트 | 게시 버튼을 끄는 기준과 글자 수 표시를 그 단위로 센다. |
| 지워진 부모 댓글에 대댓글을 달 때의 응답 | 응답 코드와 본문 | 위 응답별 처리 표에 반영한다. |

### 다른 티켓에 넘기는 것

- **[게시 전 스레드 변화 처리 결정](14-thread-change-before-post.md)**: 이 티켓이 열려 있는 동안 다른 세션이 맡아서, 질문 본문 대신 그 티켓의 Comments에 남겼다.
  - 게시 실패의 상태와 사유는 이 티켓에서 정했다. 14는 부모 댓글이 지워진 것을 게시 전에 알아챌지만 정하면 된다.
  - 준비된 묶음에 새 멘션이 합쳐지면, 새 송신자를 받는 사람에 더할지 정한다.
  - 사용자가 받는 사람에서 누군가를 뺀 것을 05 표의 "사용자가 손댐"으로 볼지 정한다.
- **[댓글 쓰기 API 실측](15-comment-write-api-check.md)**: 위 "실측 결과에 따른 규칙"의 네 항목을 확인한다.
- **지도의 안개**
  - 여러 PC에서 동시 실행: 게시 방식이 정해졌다.
  - 처리한 멘션의 보관: 게시한 글의 `commentId`·`replyId`와 받는 사람에서 뺀 사람이 저장 대상에 늘었다.
- **스펙을 쓸 때**: 04의 상태 목록에 게시 실패를 더하고, 검토 화면에 받는 사람 줄을 넣는다.
