## Question

초안이 준비된 **뒤에** 멘션 묶음이 있는 자리가 바뀌면 앱이 어떻게 할지 정한다. 여기서 "준비된 뒤"는 준비됨 상태와 게시 중 상태(5초 카운트다운)를 말한다. 아울러 에이전트에게 넘기는 스레드 맥락의 길이 상한을 정한다.

[멘션 감지 방식 결정](05-mention-detection.md)에서 이미 정한 것은 다시 다루지 않는다.

- 같은 묶음에 새 멘션이 오면 묶음 상태에 따라 합치거나 새 묶음을 만든다(05의 표).
- 생성을 시작하기 직전에 Flow에서 직접 답했는지 확인한다.
- 맥락은 초안을 만들 때마다 새로 조회한다.

정할 것은 다음과 같다.

- **멘션이 아닌 새 글**: 대상 자리에 멘션이 아닌 댓글이나 대댓글이 새로 달리면, 검토 화면에서 알릴지, 초안을 다시 만들지 정한다.
- **준비된 뒤의 직접 답**: 초안이 준비된 뒤에 Flow에서 내가 직접 답한 경우를 어떻게 처리할지 정한다. 다른 PC에서 앱으로 게시한 경우도 Flow에서는 내 글로 보인다.
- **원문의 수정과 삭제**: 멘션된 글이 수정되거나 삭제된 경우를 어떻게 처리할지 정한다. 수정되어 내 표기가 빠진 경우도 포함한다.
  - 대댓글을 달 부모 댓글이 지워지면 게시가 실패할 수 있다. 게시 위치는 [초안 게시 위치와 형식 결정](12-post-placement.md)을 따른다.
- **변화를 알아내는 시점**: 아래 중 언제 다시 조회할지 정한다. 조회 한도(분당 1,000회)와 게시 취소 시간(5초)을 함께 고려한다.
  - 폴링 주기(60초)마다 준비된 묶음의 스레드를 다시 조회한다.
  - 검토 화면에서 그 묶음을 열 때 조회한다.
  - 게시 직전에만 조회한다.
- **스레드 맥락 길이 상한**: 05에서는 맥락 범위를 대상 댓글 스레드 전체와 다른 댓글 최근 20개로 정했다. 이 맥락이 너무 길 때의 총 길이 상한과, 넘치면 무엇부터 뺄지 정한다.
  - [에이전트 실행 계약 결정](07-agent-run-contract.md)은 이 상한을 정하지 않고 닫혔다.
  - 초안 실행의 제한 시간은 10분이다.

## Answer

2026-10-15에 사용자와 그릴링으로 정했다. 진행하는 동안 [초안 게시 위치와 형식 결정](12-post-placement.md)이 해결되어, 그 티켓이 아래 Comments에 남긴 질문도 함께 정했다.

판단에 쓴 사실은 다음과 같다. 응답 예시는 [flow-alarm-probe-result.json](../research/flow-alarm-probe-result.json)에 있다.

- 댓글과 대댓글 응답에 `editedDateTime`이 있다. 그래서 다시 조회하기만 해도 수정 여부를 알 수 있다.
- 댓글 목록에 업무 상태 변경 같은 **시스템 댓글**(`systemCode`가 있는 글)이 섞여 온다.
- 멘션이 아닌 새 글에는 나에게 알림이 오지 않는다(`filters=MENTION`). 다시 조회해야만 알 수 있다.

### 다시 조회하는 시점

- **대상**: 사용자의 행동을 기다리는 묶음이다. 준비됨, 실패, 게시 실패, 저장소 확인 필요가 여기에 해당한다. 생성 중인 묶음은 생성이 끝난 뒤 첫 주기부터 본다.
- **폴링 주기마다**: 60초마다 알림을 조회한 뒤, 대상 묶음의 Flow 내용을 다시 조회한다.
  - 묶음 하나에 GET이 2~3회 든다. 기다리는 묶음이 20개여도 분당 60회 안팎이라, 조회 한도(분당 1,000회)의 6% 정도다.
  - 주기마다 조회해야 이미 답한 묶음이 트레이 숫자에서 바로 빠진다.
- **게시를 누를 때**: 한 번 더 조회한다. 자세한 처리는 아래 "게시를 누를 때의 확인"에 있다.
- **검토 화면을 열 때**: 따로 조회하지 않는다. 화면에 보이는 내용이 최대 60초 늦을 수 있다.

### 무엇을 변화로 보는가

- **비교 기준**: 지금 초안을 만들 때 에이전트에게 넘긴 Flow 내용이다. 앱은 이 내용을 초안과 함께 저장한다.
  - [멘션 감지 방식 결정](05-mention-detection.md)의 "감지 시점의 내용을 저장해 두고 쓰지 않는다"는 생성 입력에 관한 규칙이라 이 기준과 충돌하지 않는다.
- **지켜볼 범위**
  - 댓글 스레드 묶음: 그 댓글 스레드 전체(머리 댓글과 대댓글 전부)
  - 본문 묶음: 게시물 본문과 게시물의 댓글. 대댓글은 넣지 않는다. 05의 직접 답 판정 범위와 같다.
- **범위 밖**
  - 다른 댓글에 생긴 변화
  - 댓글 스레드 묶음에서 게시물 본문이 수정된 것
  - 첨부의 변화
  - 시스템 댓글
- **초안이 없는 묶음**: 실패와 저장소 확인 필요 묶음은 비교 기준이 없다. 그래서 "이미 답함"과 "원문 사라짐"만 판정한다.

### 변화별 처리

| 변화 | 처리 |
| :- | :- |
| 멘션이 아닌 새 글 | 알리기만 한다. |
| 원문 수정(내 표기는 남음) | 알리기만 한다. |
| 내 답이 생김 | 처리됨의 "이미 답함"으로 옮긴다. |
| 멘션이 사라짐 | 그 멘션을 묶음에서 뺀다. 모두 빠지면 처리됨의 "원문 사라짐"으로 옮긴다. |

#### 새 글과 원문 수정: 알리기만 한다

- 사용자가 초안을 손댔는지와 관계없이 자동으로 다시 만들지 않는다.
- **화면**
  - 초안 위에 한 줄을 띄운다. 예: "초안을 만든 뒤 새 글 2건 · 원문 수정됨". 같은 줄에 "다시 만들기" 버튼을 둔다.
  - 원문 영역에서는 새 글에 "새 글" 태그를, 수정된 원문에는 "수정됨" 태그를 붙이고 현재 내용을 보여 준다.
  - 트레이 숫자와 점은 바꾸지 않는다.
  - 이 표시를 보고도 다시 만들지 않고 그대로 게시할 수 있다.
- **알리는 이유**: 답을 바꿔야 할 정보가 멘션 없이 오는 경우가 흔하다.
  - 송신자가 "운영 환경 얘기예요", "해결됐어요" 같은 후속 글을 `@` 없이 쓴다.
  - 다른 동료가 먼저 답한다.
  - 송신자가 내 표기를 남긴 채 질문을 고친다.
  - 작은 창에서는 스레드가 접혀 있어서, 알리지 않으면 사용자가 펼쳐서 직접 비교해야 한다. 알림의 비용은 한 줄이다. 반면 놓치면 옛 질문에 대한 답이나 중복 답이 동료에게 게시된다.
  - 누가 쓴 글이 답을 바꿀지 미리 알 수 없으므로, 송신자의 글로 좁히지 않는다.
- **자동으로 다시 만들지 않는 이유**: 05 표의 새 멘션과 성격이 다르다.
  - 새 멘션은 나에게 온 요청이 바뀐 것이다.
  - 멘션이 아닌 글은 맥락이 바뀐 것이고, 초안과 관련이 있는지 알 수 없다.
  - 대화가 활발한 스레드에서 자동으로 다시 만들면, 같은 묶음의 재생성이 대기열을 계속 막고 사용량을 쓴다.

#### 이미 답함

- **판정**: 05와 같은 기준을 쓴다. 준비된 묶음의 멘션은 모두 새로 생긴 내 답보다 앞서므로, 묶음 전체를 답한 것으로 본다.
- **처리**: 처리됨의 "이미 답함"으로 자동으로 옮긴다.
  - 초안은 편집한 것까지 그대로 남긴다.
  - 되돌리면 그 초안을 가진 채 준비됨으로 돌아오고, 다시 만들지 않는다. 05의 되돌리기는 초안이 없어서 새로 만드는 것이라 처리가 다르다.
  - 보고 있던 묶음이면 화면을 다음 멘션으로 넘기지 않는다. 상태 태그만 바꾸고 "Flow에 이미 내 답이 있습니다 · 되돌리기"를 띄운다.
- **이름**: 05의 "Flow에서 직접 답함"을 "이미 답함"으로 바꾼다. 이 답이 05와 12에 적힌 상태 이름을 대체한다.
  - 다른 PC의 앱이 게시한 글도 Flow에서는 내 글로 보인다. 앱은 내 답을 Flow에서 직접 썼는지 구분할 수 없으므로, "Flow에서 직접 답함"은 틀릴 수 있다.
  - 이 PC가 게시한 묶음은 "게시됨"이 되므로 두 상태가 헷갈리지 않는다.
- **앱이 올린 글이 답한 범위**: 이 PC의 앱이 게시한 글은, **게시를 누를 때 조회한 내용에 있던 멘션에만** 답한 것으로 본다.
  - 이 PC의 게시는 12에서 기록하기로 한 `commentId`·`replyId`로 알아본다.
  - 이 규칙이 필요한 이유: 카운트다운 중에 온 멘션은 05 표대로 새 묶음이 된다. 그런데 작성 시각으로만 판정하면, 내 게시가 그 멘션보다 나중이라서 새 묶음이 감지되자마자 "이미 답함"이 된다. 그러면 새 질문이 초안 없이 숨어 버린다.
  - 시각 대신 "조회 결과에 있었는지"로 판단하므로, PC 시계와 Flow 서버 시계가 달라도 틀리지 않는다.
  - 다른 PC의 앱이 올린 글은 구분할 수 없으므로 Flow의 작성 시각으로 판정한다. 두 PC를 동시에 쓸 때만 생기는 일이라 감수한다.
  - 05에서 감지할 때와 생성을 시작하기 직전에 하는 직접 답 확인에도 이 규칙을 쓴다.

#### 원문 사라짐

- **사라진 것으로 보는 경우**
  - 그 글이 지워진 경우: 목록에 없거나 `404`가 온다.
  - 수정되어 내 표기가 빠진 경우
  - 게시물에 접근할 수 없게 된 경우: `403`이 온다.
  - 댓글 스레드의 머리 댓글이 지워진 경우: 대댓글이 남아 있어도 묶음 전체가 사라진 것으로 본다. 그 아래에는 게시할 수 없기 때문이다.
- **사라진 것으로 보지 않는 경우**: 네트워크 오류, `5xx`, `429` 같은 일시적인 오류다.
- **멘션이 일부 남은 경우**: 준비됨을 유지하고, 알림 줄에 "멘션 1건 사라짐"을 함께 띄운다.
- **멘션이 모두 사라진 경우**: 처리됨의 새 상태 "원문 사라짐"으로 옮긴다. 초안은 남기고, 되돌리기를 할 수 있다.
  - 05에서는 감지 단계에서 이런 멘션을 조용히 버렸다. 여기서 처리됨에 남기는 이유는, 사용자가 이미 트레이 숫자나 화면으로 이 묶음을 봤을 수 있기 때문이다.
- **게시 전에 알아채기**: 12가 남긴 "부모 댓글이 지워진 것을 게시 전에 알아챌지"에 대한 답이다.
  - 폴링과 게시를 누를 때의 확인에서 머리 댓글이 지워진 것을 찾으면, 묶음을 "원문 사라짐"으로 옮긴다.
  - 그 사이에 지워져 게시가 실패하면 12의 "게시 실패"를 따른다.
  - 다른 자리로 자동으로 옮겨 게시하지 않는다. 예를 들어 대댓글 대신 게시물의 새 댓글로 달면, 검토하지 않은 자리에 글이 올라간다.

#### 되돌린 뒤의 재판정

- "이미 답함"이나 "원문 사라짐"에서 되돌리면, 앱은 **그때 있던 내 답과 사라진 멘션**을 묶음에 기록한다. 이후의 판정에서는 이것들을 빼고, 그 뒤에 새로 생긴 것만 판정한다.
- 이 규칙이 필요한 이유: 규칙이 없으면 되돌린 직후 다음 폴링이 같은 내 답을 다시 찾아 처리됨으로 돌려보낸다. 게시를 눌러도 게시를 누를 때의 확인이 매번 멈춘다.
- 05에서 감지할 때 "이미 답함"이 된 묶음을 되돌릴 때도 같은 규칙을 쓴다. 그러지 않으면 생성 직전의 직접 답 확인이 같은 답을 찾아 다시 처리됨으로 보낸다.

### 게시를 누를 때의 확인

게시를 누르는 순간 Flow 내용을 조회하고, 5초 카운트다운 안에서 끝낸다. 카운트다운이 끝난 직후에만 조회하면, 사용자는 이미 다음 멘션으로 넘어간 뒤라 변화를 보여 줄 수 없다.

| 확인 결과 | 처리 |
| :- | :- |
| 이미 답함 | 멈추고 게시하지 않는다. "이미 답함"으로 옮기고, 토스트를 "게시하지 않았습니다: Flow에 이미 내 답이 있음 · 되돌리기"로 바꾼다. |
| 원문 사라짐 | 멈추고 게시하지 않는다. "원문 사라짐"으로 옮긴다. 표기만 빠지고 게시할 자리는 남아 있어도 멈춘다. 되돌리고 다시 누르면 게시된다. |
| 누를 때 화면에 없던 새 글이나 원문 수정 | 멈추고 게시하지 않는다. 준비됨으로 돌리고 알림 줄을 붙인다. 토스트는 "게시하지 않았습니다: 새 글 1건 · 보기"로 바꾼다. 나를 멘션한 글이어도 같다. |
| 이미 알림 줄에 떠 있던 변화뿐 | 그대로 게시한다. 사용자가 보고 누른 것이다. |
| 조회 실패, 또는 카운트다운이 끝난 뒤 5초가 지나도 조회가 끝나지 않음 | 그대로 게시한다. |

- **나를 멘션한 새 글도 멈추는 이유**: 멘션이 아닌 새 글로는 멈추면서, 나를 멘션한 새 글로는 멈추지 않으면 앞뒤가 맞지 않는다. 그대로 게시하면 사용자는 새 요청을 모른 채 답한 것이 된다.
  - 멈춘 뒤 다음 폴링에서 알림이 오면, 그 멘션은 05 표의 준비됨 규칙으로 합쳐진다.
  - 05 표의 게시 중 행("합치지 않고, 게시는 그대로 진행하고, 새 멘션은 새 묶음으로 만든다")은 이 확인이 **끝난 뒤** 들어온 멘션에만 적용한다.
- **조회가 실패해도 게시하는 이유**: 이 확인은 게시를 막는 관문이 아니라 안전망이다.
  - 폴링이 이미 60초 안에 확인했으므로, 이 확인을 건너뛰어도 위험은 지금까지와 같다.
  - 네트워크가 끊겼다면 게시 요청도 실패해서 12의 "게시 실패"로 간다.

### 받는 사람

[초안 게시 위치와 형식 결정](12-post-placement.md)에서 넘어온 질문이다.

- **새 멘션이 합쳐질 때**: 그 송신자를 받는 사람에 자동으로 더한다.
  - 사용자가 전에 ×로 뺀 사람이라도 다시 더한다. 뺄 때는 이 새 요청이 없었기 때문이다.
  - 새로 더한 것을 따로 표시하지 않는다. 05 표의 "새 멘션 1건" 줄로 알 수 있다.
- **멘션이 사라질 때**: 그 송신자에게 남은 멘션이 없으면 받는 사람에서 뺀다. 12의 기본값("묶음에 남은 멘션의 송신자 전원")을 그대로 적용한 결과다.
- **"사용자가 손댐"과의 관계**: 받는 사람에서 누군가를 뺀 것은 05 표의 "사용자가 손댐"으로 보지 않는다.
  - 05 표가 손댄 것을 따지는 이유는, 자동 재생성이 사용자가 고친 초안·요구·지시를 덮어쓰지 않게 하려는 것이다.
  - 받는 사람은 초안 텍스트 밖에 따로 있어서 자동 재생성이 덮어쓰지 않는다.
  - 그래서 받는 사람만 바꾼 묶음에 새 멘션이 오면 05 표대로 자동으로 다시 만든다. 이때 뺀 상태는 유지하고, 새 멘션의 송신자만 위 규칙대로 다시 더한다.

### 맥락 길이 상한

- **상한**: 30,000자다. 토큰 수는 모델마다 달라 앱이 정확히 셀 수 없으므로 글자 수로 센다. 선택 실행에도 같은 상한을 쓴다.
- **절대 빼지 않는 것**
  - 게시물 제목
  - 묶음의 멘션 전부. 본문 묶음이면 본문 전체가 여기에 해당한다.
  - 댓글 스레드 묶음의 머리 댓글
- **빼는 순서**: 상한 안에 들어올 때까지 아래 순서로 뺀다.
  1. 다른 댓글의 대댓글. 오래된 댓글부터 뺀다.
  2. 다른 댓글. 오래된 것부터 뺀다.
  3. 게시물 본문. 댓글 스레드 묶음에서만, 앞 10,000자만 남기고 자른다.
  4. 대상 댓글 스레드에서 멘션이 아닌 대댓글. 오래된 것부터 뺀다.
- **뺐다는 표시**: 뺀 자리에 "[다른 댓글 12개 생략]" 같은 표시를 넣어, 에이전트가 맥락이 잘렸다는 것을 알게 한다.
- **절대 빼지 않는 것만으로 넘칠 때**: 자르지 않고 그대로 넘긴다. 최종 안전장치는 10분 제한이다.
- **화면과 기록**: 상세 머리의 실행 줄에 "맥락 일부 생략"을 덧붙인다. 예: "Claude Code · 2분 14초 · 맥락 일부 생략". 실행 기록에는 뺀 항목 수를 남긴다.
- **30,000자인 이유**
  - 보통의 스레드는 몇천 자라 이 상한에 닿지 않는다.
  - 상한에 닿는 것은 다른 댓글 20개에 각각 대댓글 10개가 달린 붐비는 게시물이나, 본문이 아주 긴 경우다.
  - 에이전트가 쓸 수 있는 맥락의 대부분은 저장소를 읽는 데 남겨야 한다.

### 용어

- [GLOSSARY.md](../../../GLOSSARY.md)에 **맥락**을 추가했다. 티켓 질문에 쓴 "스레드 맥락"은 쓰지 않는 말로 두었다. **댓글 스레드**가 좁은 뜻으로 정해져 있는데, 이 말은 본문과 다른 댓글까지 가리켜서 헷갈리기 때문이다.
- "이미 답함"과 "원문 사라짐"은 상태 이름이므로 용어집에 넣지 않고 스펙에서만 쓴다.

### 2026-10-15, [초안 게시 위치와 형식 결정](12-post-placement.md)에서 넘어온 것

12가 해결되었다. 이 티켓을 다른 세션이 맡고 있어서 질문 본문은 고치지 않고 여기에 남긴다. 자세한 내용은 12의 답에 있다.

- **게시 실패 처리는 12에서 정했다.**
  - 새 상태 "게시 실패"를 두고, 응답별 사유를 보여 준다. 예를 들어 `404`와 `412`의 사유는 "글이나 댓글이 지워졌습니다"다.
  - 그래서 이 티켓의 "원문의 수정과 삭제"에서는 부모 댓글이 지워진 것을 **게시 전에** 알아챌지만 정하면 된다.
  - 지워진 부모 댓글에 대댓글을 달 때의 실제 응답 코드는 [댓글 쓰기 API 실측](15-comment-write-api-check.md)에서 확인한다.
- **받는 사람이 새로 생겼다.** 게시 본문 앞에서 다시 멘션하는 Flow 구성원이고, 기본값은 묶음에 남은 멘션의 송신자 전원이다. 검토 화면에서 ×로 뺄 수 있다. 준비된 뒤의 변화와 관련해 정할 것이 두 가지 생겼다.
  - 준비된 묶음에 새 멘션이 합쳐지면 새 송신자를 받는 사람에 더할지 정한다.
  - 사용자가 받는 사람에서 누군가를 뺀 것을 05 표의 "사용자가 손댐"으로 볼지 정한다.
- **게시하면 앱이 `commentId` 또는 `replyId`를 기록한다.** "준비된 뒤의 직접 답"을 판정할 때 앱이 올린 글을 구분하는 데 쓸 수 있다.
