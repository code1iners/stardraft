## Question

처리한 멘션 묶음과 그에 딸린 데이터를 `state.db`에 **얼마나 남길지**, 그리고 앱을 다시 켰을 때 **무엇을 되살릴지** 정한다. 처리한 묶음은 게시됨, 무시함, "이미 답함", "원문 사라짐" 상태다.

저장 대상은 이전 티켓들에서 정해졌다.

- [멘션 감지 방식 결정](05-mention-detection.md)
  - 폴링 기준점(`alarmId`)
  - 처리한 멘션 위치
  - 멘션 묶음과 그 상태
- [초안 게시 위치와 형식 결정](12-post-placement.md)
  - 게시한 글의 `commentId`·`replyId`
  - 받는 사람에서 뺀 사람
  - "게시 실패" 상태와 그 사유
- [게시 전 스레드 변화 처리 결정](14-thread-change-before-post.md)
  - 초안별 비교 기준: 그 초안을 만들 때 넘긴 Flow 내용이다. 상한은 30,000자다.
  - 되돌릴 때 기록한 내 답과 사라진 멘션
  - 게시를 누를 때 조회한 내용
- [에이전트 실행 계약 결정](07-agent-run-contract.md)
  - 실행 기록: 에이전트와 CLI 버전, 모델, 시각, 결과, 마지막 단계, 앱이 고친 내용 불일치, 비용
  - 보관 기간은 이 항목에서 정하기로 했다.

정할 것:

- **처리됨 목록**: 기간과 개수 중 무엇을 기준으로 얼마나 남길지. 처리됨 목록에서 무시를 되돌릴 수 있다([초안 검토 화면 프로토타입](04-draft-review-prototype.md)). 그래서 이 기준은 되돌릴 수 있는 기간도 정한다.
- **지난 묶음의 큰 데이터**: Flow 본문, 초안, 비교 기준을 계속 둘지, 아니면 기록만 남기고 지울지. 정할 때 볼 것은 두 가지다.
  - **용량**: 비교 기준 하나가 최대 약 90KB다.
  - **민감도**: 회사 글이 PC에 남는다.
- **중복 방지에 필요한 최소 기록**: 처리한 멘션 위치를 얼마나 오래 남겨야 같은 멘션을 다시 감지하지 않는지. 05의 "다시 켰을 때는 72시간 안의 멘션만 가져온다" 규칙과 맞춰 본다.
- **실행 기록의 보관 기간**
- **다시 켰을 때 되살리기**
  - 앱을 끌 때 생성 중이던 실행을 어떻게 다룰지
  - 5초 게시 카운트다운 중이던 묶음을 어떻게 다룰지
  - 응답을 받지 못한 게시를 어떻게 다룰지. 12에서 정한 다시 조회와 맞춰 본다.

## 정해진 것

이 질문의 전제다. [데스크톱 프레임워크와 기술 스택 결정](08-desktop-stack.md)에서 정했다.

- 상태는 OS 표준 앱 데이터 폴더의 `state.db`에 둔다. SQLite이고 드라이버는 better-sqlite3다.
- 마이그레이션은 `PRAGMA user_version`으로 관리하고, WAL을 켠다.
- 데이터는 PC마다 따로 두고 동기화하지 않는다.
- 진단 로그에는 API 키와 Flow 글 본문을 남기지 않는다.

## Comments

- 2026-10-18, [설정과 첫 실행 온보딩 결정](16-onboarding.md)에서 덧붙인다.
  - **계정 ID**: 키를 확인할 때 받은 `userId`를 `state.db`에 둔다. 새 키의 계정과 비교하는 데 쓴다.
  - **다른 계정의 키로 바꿀 때**: 확인을 받고 `state.db`를 통째로 비운다. 그래서 이 티켓에서 정할 보관 기간과 상관없이 모든 기록이 사라진다.
  - **시험 묶음**: 최근 멘션으로 돌린 시험 묶음은 끝내면 지운다. 처리됨 목록과 기준점에 남기지 않으므로 보관 대상이 아니다.
