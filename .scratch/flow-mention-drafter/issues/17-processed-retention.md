# 처리한 멘션의 보관 결정

Type: grilling
Mode: HITL

## Question

처리한 멘션 묶음과 그에 딸린 데이터를 `state.db`에 **얼마나 남길지**, 그리고 앱을 다시 켰을 때 **무엇을 되살릴지** 정한다. 처리한 묶음은 게시됨, 무시함, "이미 답함", "원문 사라짐" 상태다.

저장 대상은 이전 티켓들에서 정해졌다.

- [멘션 감지 방식 결정](05-mention-detection.md)
  - 폴링 기준점(`alarmId`)
  - 처리한 멘션 위치
  - 멘션 묶음과 그 상태
- [초안 게시 위치와 형식 결정](12-post-placement.md)
  - 게시한 글의 `commentId`·`replyId`
  - 받는 사람에서 뺀 사람
  - "게시 실패" 상태와 그 사유
- [게시 전 스레드 변화 처리 결정](14-thread-change-before-post.md)
  - 초안별 비교 기준: 그 초안을 만들 때 넘긴 Flow 내용이다. 상한은 30,000자다.
  - 되돌릴 때 기록한 내 답과 사라진 멘션
  - 게시를 누를 때 조회한 내용
- [에이전트 실행 계약 결정](07-agent-run-contract.md)
  - 실행 기록: 에이전트와 CLI 버전, 모델, 시각, 결과, 마지막 단계, 앱이 고친 내용 불일치, 비용
  - 보관 기간은 이 항목에서 정하기로 했다.

정할 것:

- **처리됨 목록**: 기간과 개수 중 무엇을 기준으로 얼마나 남길지. 처리됨 목록에서 무시를 되돌릴 수 있다([초안 검토 화면 프로토타입](04-draft-review-prototype.md)). 그래서 이 기준은 되돌릴 수 있는 기간도 정한다.
- **지난 묶음의 큰 데이터**: Flow 본문, 초안, 비교 기준을 계속 둘지, 아니면 기록만 남기고 지울지. 정할 때 볼 것은 두 가지다.
  - **용량**: 비교 기준 하나가 최대 약 90KB다.
  - **민감도**: 회사 글이 PC에 남는다.
- **중복 방지에 필요한 최소 기록**: 처리한 멘션 위치를 얼마나 오래 남겨야 같은 멘션을 다시 감지하지 않는지. 05의 "다시 켰을 때는 72시간 안의 멘션만 가져온다" 규칙과 맞춰 본다.
- **실행 기록의 보관 기간**
- **다시 켰을 때 되살리기**
  - 앱을 끌 때 생성 중이던 실행을 어떻게 다룰지
  - 5초 게시 카운트다운 중이던 묶음을 어떻게 다룰지
  - 응답을 받지 못한 게시를 어떻게 다룰지. 12에서 정한 다시 조회와 맞춰 본다.

## 정해진 것

이 질문의 전제다. [데스크톱 프레임워크와 기술 스택 결정](08-desktop-stack.md)에서 정했다.

- 상태는 OS 표준 앱 데이터 폴더의 `state.db`에 둔다. SQLite이고 드라이버는 better-sqlite3다.
- 마이그레이션은 `PRAGMA user_version`으로 관리하고, WAL을 켠다.
- 데이터는 PC마다 따로 두고 동기화하지 않는다.
- 진단 로그에는 API 키와 Flow 글 본문을 남기지 않는다.

## Answer

2026-10-18에 사용자와 그릴링으로 정했다. 사용자는 아홉 가지 권고안을 모두 그대로 받아들였다.

### 기록의 두 층

처리한 묶음의 데이터를 두 층으로 나눈다.

- **전체 기록**: 되돌리기에 필요한 것 전부다.
  - Flow 원문
  - 초안(원래 초안과 편집본), 요구, 근거, 지시
  - 비교 기준
  - 게시를 누를 때 조회한 내용
  - 되돌릴 때 기록한 내 답과 사라진 멘션
  - 받는 사람과 게시 본문
  - 실행 기록
- **전체 기록을 모두 남겨야 하는 이유**: 되돌리면 그 초안을 가진 채 준비됨으로 돌아오고, 비교 기준으로 변화 감지를 다시 한다([게시 전 스레드 변화 처리 결정](14-thread-change-before-post.md)). 그래서 되돌릴 수 있는 동안에는 일부만 지울 수 없다.
- **최소 기록**: ID와 상태만 둔다. 송신자 이름과 글 내용은 넣지 않는다.
  - 묶음 자리(`postId`, `remarkId`)
  - 묶음에 있던 멘션 위치
  - 마지막 상태와 처리한 시각
  - 이 PC가 게시한 글의 `commentId`·`replyId`와, 그 글이 답한 멘션 위치
- **기준점**(`alarmId` 하나)은 늘 남긴다.

### 처리됨 목록

- **기간**: 처리한 때부터 7일 남긴다. 7일이 지나면 목록에서 빠지고, 되돌릴 수 없다.
  - 되돌렸다가 다시 처리하면 7일을 새로 센다.
  - 설정에서 바꿀 수 없다.
- **기간으로 정한 이유**: 되돌릴 수 있는 기간이 묶음마다 같아서 사용자가 미리 알 수 있다. 개수 기준이면 멘션이 몰린 주에는 어제 무시한 것도 사라지고, 한가한 달에는 몇 달 전 회사 글이 남는다.
- **7일인 이유**
  - 금요일에 무시하고 월요일에 다시 보는 경우를 덮는다.
  - "이미 답함"으로 잘못 옮겨진 경우(예: 시스템 댓글을 내 답으로 판정)도 대개 며칠 안에 알아챈다.
  - 길게 둘수록 회사 글이 PC에 오래 남는다.
- **정리 시점**: 앱을 켤 때와 하루에 한 번 정리한다.
- **화면**: 펼친 창의 처리됨 묶음 아래에 "처리한 지 7일이 지나면 목록에서 사라지고 되돌릴 수 없습니다"를 작은 글씨로 둔다. 안내가 없으면 항목이 왜 사라졌는지 알 수 없다.

### 전체 기록

- **보관**: 처리됨 목록에 있는 동안만 둔다. 목록에서 빠질 때 지우고 최소 기록만 남긴다.
  - 게시됨 묶음은 되돌릴 수 없지만 같은 규칙을 쓴다. 목록에서 무엇을 올렸는지 보여 줘야 하고, 규칙을 둘로 나눌 만큼 얻는 것이 없다.
- **재생성할 때**: 이전 초안과 그 비교 기준을 바로 지운다. 이전 초안을 다시 보는 화면이 없다.
- **지운 내용**: SQLite `secure_delete`를 켠다. 이 설정이 없으면 행을 지워도 그 내용이 파일의 빈 공간에 남는다.
- **암호화**: `state.db`는 암호화하지 않는다.
  - SQLCipher 같은 네이티브 모듈이 하나 늘어난다. [데스크톱 프레임워크와 기술 스택 결정](08-desktop-stack.md)에서 `@napi-rs/keyring`을 뺀 것과 같은 이유다.
  - 짧은 보관 기간과 OS 디스크 암호화(FileVault, BitLocker)에 맡긴다.
- **용량**: 비교 기준 하나는 최대 약 90KB이고, 보통은 몇 KB에서 수십 KB다. 7일치는 몇 MB 안에 든다.

### 최소 기록

- **보관**: 기한 없이 둔다. 다른 계정의 키로 바꾸면 `state.db`를 비우므로 그때 사라진다([설정과 첫 실행 온보딩 결정](16-onboarding.md)).
- **오래 둬야 하는 이유**
  1. **같은 멘션 위치에서 새 알림이 올 때**: 기준점은 이미 본 알림만 막는다. Flow가 글을 수정할 때 멘션 알림을 다시 보내는지는 모른다.
     - 최소 기록이 지워진 뒤 그런 알림이 오면, 이미 답한 멘션의 초안이 다시 생긴다.
     - "이미 답함"으로도 막지 못한다. 새 알림의 시각이 내 답보다 나중이기 때문이다.
     - 기한 없이 두면 이 사실을 확인하지 않아도 된다.
  2. **앱이 올린 글이 답한 범위**: 카운트다운 중에 생긴 새 묶음이 오래 대기 상태로 남는 경우다.
     - 폴링할 때마다 하는 "이미 답함" 판정에 옛 게시 기록이 필요하다.
     - 기록이 지워지면 그 묶음이 갑자기 "이미 답함"으로 숨는다.
- **결과**: 처리한 멘션 위치에서 다시 온 알림은 글이 수정되었더라도 다시 감지하지 않는다. [멘션 감지 방식 결정](05-mention-detection.md)의 식별 규칙과 같다.
- **용량**: 하루 10묶음이면 1년에 1MB가 되지 않는다.

### 실행 기록

- 그 묶음의 전체 기록에 속하고, 함께 지운다.
  - 대기 중인 묶음의 실행 기록은 묶음이 남아 있는 동안 모두 둔다.
  - 시험 묶음의 실행 기록은 시험을 끝낼 때 함께 지운다.
- **함께 지우는 이유**
  - 실행 기록을 보여 주는 곳은 상세 머리의 한 줄뿐이고, 비용은 보여 주지 않는다([에이전트 실행 계약 결정](07-agent-run-contract.md)).
  - 실패 사유와 내용 불일치 목록에는 CLI 오류 원문이나 저장소 경로가 들어갈 수 있다. 그래서 회사 정보와 똑같이 다룬다.
- **사용량을 모으려고 일부만 오래 남기는 안**: 쓰지 않았다. 지금은 그 숫자를 쓰는 화면이 없다.

### 대기 중인 묶음

- 준비됨, 실패, 게시 실패, 저장소 확인 필요 묶음은 사용자가 처리할 때까지 기한 없이 둔다. 오래됐다고 처리됨으로 옮기지 않는다.
- **남아 있는 묶음의 뜻**: Flow에서 직접 답하면 폴링이 "이미 답함"으로 옮기고, 원문이 지워지면 "원문 사라짐"으로 옮긴다. 그래서 남아 있는 것은 정말 아직 답하지 않은 멘션이다.
- **"만료됨" 상태를 두는 안**: 쓰지 않았다. 상태가 하나 늘고, 답해야 할 멘션이 조용히 숨는다.
- **폴링 비용**: 대기 묶음이 20개여도 분당 60회 안팎으로, 조회 한도의 6%쯤이다(14에서 계산).

### 다시 켰을 때

#### 생성 중이던 묶음

- **끌 때**: 에이전트 프로세스 트리를 종료한다. "생성 중인 초안이 있습니다" 같은 확인 창은 띄우지 않는다.
- **다시 켤 때**: 생성 중이던 묶음(대기열에서 기다리던 것 포함)을 원래 순서대로 대기열에 넣고, 끊긴 실행을 맨 앞에 둔다. 실행은 처음부터 다시 한다.
- **끊긴 실행**: 실행 기록에 "앱 종료로 중단"으로 남긴다. 07의 자동 재시도 1회에는 세지 않는다.
- **꺼져 있던 사이에 Flow에서 답한 묶음**: 생성 직전의 직접 답 확인(05)을 그대로 거친다. 그래서 실행하지 않고 "이미 답함"이 된다.
- **시험 묶음**: 진행 중이었으면 다시 켤 때 지운다. [시험 끝내기]와 같다.
- **"앱이 종료됨" 실패로 두는 안**: 쓰지 않았다. 사용자는 다시 켜기만 하면 이어지기를 기대한다.

#### 카운트다운 중이던 묶음

- **처리**: 카운트다운 중에는 아직 게시 요청을 보내지 않은 상태다. 이때 앱이 꺼지면 정상 종료든 강제 종료든 게시하지 않는다.
  - 다시 켜면 그 묶음은 준비됨이다.
  - 상세 머리에 "앱이 꺼져서 게시하지 않았습니다"를 한 줄 띄운다.
- 게시를 누를 때 조회한 내용은 버린다. 다시 누르면 새로 조회한다.
- **게시하지 않는 이유**
  - 5초 취소가 앱 안의 유일한 되돌리기 수단이다. 댓글 수정·삭제 API가 없다([초안 게시 위치와 형식 결정](12-post-placement.md)).
  - 끄는 것을 게시로 처리하면, 취소 대신 앱을 끈 사용자에게 되돌릴 방법이 없다.
  - OS 종료나 강제 종료에서는 카운트다운 끝까지 기다릴 수 없다. 그래서 "끝까지 기다렸다가 게시한다"는 지킬 수 없는 약속이다.
- **쓰지 않은 안**: 종료를 미뤘다가 게시한 뒤 끄는 안과, 종료 확인 창을 띄우는 안이다.
- **업데이트로 다시 시작할 때**: 카운트다운과 게시 요청이 끝날 때까지 미룬다. [앱 내 업데이트 방식 결정](22-in-app-update-design.md)에 넘겼다.

#### 응답을 받지 못한 게시

- **보내기 전**: 게시 요청을 보내기 직전에 "게시 요청 보냄"과 게시 본문을 `state.db`에 먼저 적는다. 그래야 다시 켰을 때 요청을 보냈는지 안다.
- **정상 종료할 때**: 게시 요청이 진행 중이면 응답을 최대 5초 기다린 뒤 끈다.
- **다시 켰을 때**: 강제 종료, 충돌, 5초 초과로 응답을 받지 못한 경우다.
  - 그 묶음은 게시 중 상태로 두고 "게시 결과 확인 중"을 보여 준다. 게시 버튼은 막는다.
  - 첫 조회가 성공하면 12의 "올라갔는지 알 수 없을 때의 확인"을 돌린다.
    - 글을 찾으면 게시됨으로 두고 ID를 기록한다.
    - 못 찾으면 게시 실패로 두고, 사유는 "앱이 꺼져서 게시하지 못했습니다"다.
  - 조회가 실패하면 다음 폴링에서 다시 확인한다.
- **찾는 기준**: 그 자리에서 이 PC가 기록한 적 없는 내 글 가운데 게시 본문과 똑같은 글을 찾는다. 12의 "게시 요청 뒤에 올라온 내 글"을 이 기준으로 바꾼다.
  - 시각 대신 내용으로 찾는다. [댓글 쓰기 API 실측](15-comment-write-api-check.md)에서 보낸 문자열이 그대로 저장되는 것을 확인했다.
  - PC 시계와 Flow 서버 시계를 비교하지 않기로 한 14와도 맞다.
  - 앱이 켜져 있을 때 응답이 없거나 `5xx`가 온 경우의 확인에도 이 기준을 쓴다.

### 용어

- 새 용어는 없다. "게시 결과 확인 중"과 "앱 종료로 중단"은 상태 문구이므로 이전 결정들처럼 스펙에서만 쓴다.
- ADR은 만들지 않았다. 보관 기간은 코드만 고치면 바꿀 수 있어서 되돌리기 어려운 결정이 아니다.

### 다른 티켓과 지도에 넘기는 것

- **[앱 내 업데이트 방식 결정](22-in-app-update-design.md)**: 업데이트로 다시 시작하는 일을 카운트다운과 게시 요청이 끝날 때까지 미룬다. 그 티켓의 Comments에 남겼다.
- **[초안 게시 위치와 형식 결정](12-post-placement.md)**: 이미 닫혔다. 스펙을 쓸 때 "올라갔는지 알 수 없을 때의 확인"은 위 "찾는 기준"으로 읽는다.
- **스펙을 쓸 때**: [초안 검토 화면 프로토타입](04-draft-review-prototype.md)에 아래를 더한다.
  - 처리됨 목록 아래의 보관 기간 안내
  - 준비됨 상세 머리의 "앱이 꺼져서 게시하지 않았습니다"
  - 게시 중 상태의 "게시 결과 확인 중" 문구와, 그동안 막는 게시 버튼
- **지도의 안개**: 바뀌는 것이 없다.
