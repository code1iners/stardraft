# 다운로드 사이트 화면 프로토타입

Map: [Flow 멘션 답변 초안 앱](../map.md)
Type: prototype
Mode: HITL
Status: resolved
Blocked by: 18

## Question

다운로드 사이트는 어떤 모습과 흐름이어야 하는가? [다운로드 사이트 UI/UX 사례 조사](18-download-site-ux-research.md)를 근거로 인터랙티브 초안을 만들고, 사용자와 함께 다듬는다. `prototype` 스킬과 `ui-design` 스킬을 쓴다.

정할 것:

- 페이지 배치와 흐름: OS 감지, 다운로드, 단계별 설치 안내, 막힌 단계의 분기
- 상호작용과 시각 연출의 수준. 사용자는 둘 다 원했다.
- 대화상자를 HTML로 재현할지, 스크린숏으로 보여 줄지, 둘 다 쓸지. 사례 조사는 HTML 재현이 진짜 OS 창으로 오인될 위험을 지적했다.
- 사이트 기술(프레임워크). Vercel에 배포하고, 같은 사이트의 함수가 다운로드(`/download/<os>`, `/download/<버전>/<os>`)와 버전 정보(`/api/releases`)를 맡는다.

## 정해진 것

[다운로드 사이트 형태 결정](09-download-site.md)에서 정했다.

- **담을 내용**: 아래 항목을 담는다. 배치와 표현은 이 티켓에서 바꿀 수 있다.
  1. 한 줄 소개. 기능 홍보는 하지 않는다.
  2. OS별 다운로드와 지원 환경. macOS는 Apple Silicon과 macOS 13 이상, Windows는 10 이상 x64다.
  3. 설치 전에 필요한 것
  4. OS별 설치 안내
  5. 업데이트 방법: 보통은 앱이 알아서 하고, 안 되면 사이트에서 다시 받는다. 앱 내 업데이트 방식은 [앱 내 업데이트 방식 결정](22-in-app-update-design.md)에서 정하므로, 이 항목의 문구는 그 결과에 맞춘다.
  6. 변경 내역
  7. 이전 버전(GitHub Release 목록 링크)과 SHA256
  8. 삭제 방법
- **공개 범위**: 누구나 받을 수 있고, 검색 노출도 막지 않는다. 회사 이름과 사람 이름은 넣지 않는다.
- **언어**: 한국어만 쓴다.
- **스크린숏**: 막히는 화면 네 곳은 실제 앱으로 찍은 스크린숏을 쓴다.
- **설치 안내 문구**
  - `xattr` 단계는 넣지 않는다.
  - "배포 담당자에게 알려 달라" 같은 연락 절차는 넣지 않는다.
  - 스마트 앱 컨트롤이 켜져 있으면 실행되지 않는다는 사실만 알린다.
  - "손상됨"이 뜨면 다시 받으라고 하고, 다시 받아도 같으면 설치하지 말라고 안내한다.
- **모션**
  - 사용자 결정으로 이 사이트에서는 `ui-design`의 장식 모션 금지를 푼다. `ui-design`의 다른 기준은 그대로 적용한다.
  - OS의 "동작 줄이기"(`prefers-reduced-motion`)는 지킨다. 이 설정이 켜져 있으면 움직임을 멈추거나 줄인다.
  - 참고로 사례 조사에서 모션을 쓰는 다섯 곳은 모두 이 설정을 무시했다.

## Answer

2026-10-17에 사용자가 [프로토타입](../prototypes/download-site/index.html)의 변형 A·B·C를 비교한 뒤 "A에 C처럼 인터랙티브하게"를 골랐다. 고른 조합은 같은 파일의 **D 확정안**으로 그렸고, 파일을 열면 D가 기본으로 뜬다.

- 실행: `open .scratch/flow-mention-drafter/prototypes/download-site/index.html`. 변형은 `?variant=A|B|C|D`나 화면 아래 막대로 바꾼다.
  - 같은 막대에서 방문 환경(`?env=`)과 "동작 줄이기"(`?motion=`)를 흉내 낼 수 있다.
  - 버전, 날짜, SHA256, 변경 내역은 가짜 데이터다. 다운로드는 일어나지 않는다. 구현에 재사용하지 않는다.
- 비교한 변형
  - A 문서형: 한 페이지 문서다. OS 탭 안에 번호 단계를 두고, 막히는 곳만 스크린숏을 넣는다. 모션은 없다.
  - B 설치 도우미: 한 단계씩 "됐어요/안 돼요"로 진행하고, 막히면 상황을 골라 갈라진다. 설명용 모션만 쓴다.
  - C 미리 해 보기: 단계 글을 스크롤하면 옆의 예시 화면이 바뀌고, 예시 화면을 미리 눌러 볼 수 있다. 장식 모션도 쓴다.

### 페이지 배치와 흐름

- **A의 한 페이지 문서**로 만든다. 데스크톱에서는 왼쪽에 목차를 고정한다. 섹션 순서는 다운로드 → 설치 전에 필요한 것 → 설치 안내 → 업데이트 → 변경 내역 → 이전 버전과 SHA256 → 삭제다.
- **첫 화면**
  - 왼쪽에 이름, 한 줄 소개, 감지한 OS의 대표 다운로드 버튼을 둔다. 버튼 밑에는 지원 환경과 파일 크기를 한 줄로 적고, 그 밑에 다른 OS용 받기 링크를 둔다.
  - 그 밑에 버전·날짜, 변경 내역 링크, SHA256 복사를 둔다.
  - 오른쪽에는 설치하면 아이콘이 생기는 자리(메뉴 막대나 트레이)를 보여 주는 그림을 둔다.
  - 맨 아래에 서명하지 않은 이유 한 문장과 "이 주소에서 받은 파일만 설치하세요"를 둔다.
- **OS 감지 분기**
  - Chromium에서 Apple Silicon으로 확인되면 macOS 버튼을 그대로 보여 준다.
  - Safari와 Firefox처럼 칩을 알 수 없으면, 버튼 밑에 칩 확인 방법(Apple 메뉴 > 이 Mac에 관하여)을 적는다.
  - Intel Mac이면 지원하지 않는다고 알리고, 대표 버튼 대신 "그래도 macOS용 받기"와 Windows용 링크를 둔다.
  - Windows ARM이면 에뮬레이션으로 실행된다는 한 줄을 붙인다.
  - 휴대폰이면 받기 대신 "PC에서 열 링크 복사"를 둔다. 안내는 그대로 읽을 수 있다.
  - 그 밖의 OS이면 지원 OS 두 버튼을 모두 보여 준다.
- **설치 안내**
  - OS 탭의 기본값은 감지 결과다. 다른 OS용 받기를 누르면 탭도 그 OS로 바뀐다.
  - 단계는 다음과 같다.
    - macOS 5단계: DMG를 열고 옮기기 → 처음 열면 뜨는 경고 창 닫기 → 시스템 설정에서 그래도 열기 → 한 번 더 확인하고 암호 입력 → 메뉴 막대에 아이콘이 보이면 끝
    - Windows 4단계: 스마트 앱 컨트롤 확인(Windows 11) → 설치 파일을 열고 추가 정보 → 실행 → 저절로 설치되고 켜짐 → 트레이에 아이콘이 보이면 끝
  - 단계마다 담는 것
    - 제목
    - 화면에 뜨는 문구("이 문구가 보이면")
    - 한두 문장의 지시. 누를 버튼 이름은 굵게 쓴다.
    - 예시 화면
    - 완료 기준(✓)
    - "여기서 막히면" 펼침
  - 스마트 앱 컨트롤 단계는 상태별 할 일을 표로 둔다(평가·끄기 → 다음 단계, 켜기 → 실행되지 않음).
  - 막힌 경우 목록은 프로토타입의 `STEPS`에 있다. 손상됨, 휴지통으로 이동을 누름, Intel Mac, 그래도 열기 버튼이 안 보임(1시간), 노치에 아이콘이 가려짐, 알림 허용을 놓침, 실행 버튼이 없음, 스마트 앱 컨트롤 차단, "실행 중입니다" 창, 트레이 숨김 영역이 해당한다.
- **설치 뒤 섹션**
  - 업데이트: 보통은 앱이 하고, 안 되면 사이트에서 다시 받는다. 업데이트 뒤에 다시 묻는 것도 적는다.
  - 변경 내역: 최근 3개를 보여 주고 GitHub 전체 목록으로 링크한다.
  - 이전 버전과 SHA256: 현재 파일 표에 SHA256 복사를 붙이고, OS별 확인 명령을 둔다. 이전 버전은 GitHub Release 목록으로 링크하고, 다운그레이드 차단 안내를 붙인다.
  - 삭제: OS별 단계를 적고, 데이터 폴더 경로에 복사 버튼을 붙인다.
- 본문 문구는 09의 제약을 따른다. 사례 조사의 `xattr` 최후 수단과 "배포 담당자에게 알리기"는 넣지 않았다.

### 상호작용과 시각 연출

- **예시 화면은 모든 단계에 둔다.** 사용자가 "전체 단계 유지"를 골랐다.
  - 대화상자와 설정 화면을 HTML로 재현한다. 누를 곳을 직접 눌러 다음 상태로 넘어갈 수 있다. 예를 들어 "추가 정보"를 누르면 "실행"이 나타난다.
  - 화면이 보이는 위치까지 스크롤하면 커서가 누를 곳으로 움직이고, 누를 곳에 강조 테두리가 깜빡인다.
  - "휴지통으로 이동", "실행 안 함"처럼 잘못된 버튼을 누르면 실제 창에서는 누르지 말라는 경고를 띄운다.
  - "처음부터"로 되돌릴 수 있다.
- **시각 연출**
  - 설명용으로는 커서 이동, 누를 곳 강조, 장면 전환을 쓴다.
  - 장식용으로는 첫 화면 그림의 별 아이콘 반짝임을 쓴다. 사용자가 이 그림을 따로 바꾸라고 하지 않아 유지했다.
  - OS의 "동작 줄이기"가 켜져 있으면 모든 움직임을 멈추고 마지막 모습만 보여 준다. 커서는 누를 곳에 바로 놓는다.
- 고르지 않은 것
  - B의 한 단계씩 진행하는 방식과 "됐어요/안 돼요" 분기는 쓰지 않는다. 막힌 경우는 단계마다 "여기서 막히면" 펼침으로 다룬다.
  - C의 스크롤 연동 고정 화면도 쓰지 않는다. 예시 화면은 단계 안에 둔다.

### 대화상자: 재현과 스크린숏을 함께 쓴다

- 막히는 네 곳(09)은 **실제 스크린숏을 기본으로 보여 준다.** "예시"로 바꾸면 재현 화면을 눌러 볼 수 있다. 사용자가 "실제 화면 기본"을 골랐다.
- 나머지 단계에는 재현 화면만 둔다.
- 재현 화면이 진짜 OS 창으로 보이지 않게 아래처럼 구분한다.
  - 위에 노란 띠로 "예시 화면 · 눌러 볼 수 있지만 실제 창이 아닙니다"를 단다.
  - 바깥을 빗금 배경으로 감싼다.
  - 페이지 위에 떠 있지 않고, 항상 단계 안의 틀 속에 있다.
- 스크린숏은 첫 릴리스 빌드로 한국어 OS에서 찍는다(09). 재현 화면의 문구도 그때 실제 화면에 맞춘다.
  - 아직 실제 문구를 확인하지 않은 것이 있다. 시스템 설정의 차단 줄, 그래도 열기 뒤의 확인 창과 암호 창, Windows의 PC 보호와 설치 창, 스마트 앱 컨트롤 상태 이름("평가"인지 "평가 모드"인지)이다.
  - OS 메이저 업데이트로 화면이 바뀌면 스크린숏과 재현을 함께 고친다.

### 사이트 기술

- **Astro로 만들고, 예시 화면처럼 상호작용하는 부분만 React(19, TypeScript)로 만든다.** 사용자가 Astro를 골랐다.
  - 고른 이유
    - 본문이 빌드할 때 HTML로 나온다. 그래서 JS를 받기 전에도 다운로드 버튼과 안내가 보이고, 검색에도 잡힌다.
    - 상호작용하는 부분은 앱과 같은 React와 TypeScript로 만든다.
  - 비교한 대안
    - Vite + React 단일 페이지: JS가 돌아야 내용이 보인다.
    - 빌드 없는 HTML과 `api/` 함수: 예시 화면 로직을 손으로 관리해야 한다.
- **함수**: `/download/<os>`, `/download/<버전>/<os>`, `/api/releases`는 Astro 서버 엔드포인트로 만든다. 같은 Vercel 배포의 함수로 돌아간다(09).
  - 이 엔드포인트만 미리 빌드하지 않고, 나머지 페이지는 정적으로 낸다.
  - 어댑터 이름과 버전은 구현을 시작할 때의 안정판으로 정확히 고정한다. 확인하지 않았다.
- **OS 감지**: 브라우저에서 `navigator.userAgentData`(Chromium의 `architecture`)와 UA로 한다. JS가 돌기 전이나 감지하지 못했을 때는 두 OS 버튼을 모두 보여 준다(구현 기준으로 정했다).
- **동작 줄이기**: CSS는 `prefers-reduced-motion` 미디어 쿼리로, 커서처럼 JS로 움직이는 부분은 같은 미디어 쿼리 값을 읽어 멈춘다.
- 코드 자리는 `stardraft/apps/site`다(09).

### 남은 것
