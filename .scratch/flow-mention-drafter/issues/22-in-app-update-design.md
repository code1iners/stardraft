# 앱 내 업데이트 방식 결정

Map: [Flow 멘션 답변 초안 앱](../map.md)
Type: grilling
Mode: HITL
Status: resolved
Blocked by: 21

## Question

Stardraft가 앱 안에서 새 버전을 **어떻게 받고, 언제 설치하고, 어떻게 진위를 확인할지** 정한다. 근거는 [앱 내 업데이트 가능성 조사](20-in-app-update-research.md)와 [앱 내 업데이트 macOS 실기 검증](21-in-app-update-macos-check.md)이다. 트레이 메뉴처럼 화면이 걸리는 결정에는 `ui-design`을 함께 쓴다.

정할 것:

- **업데이트 파일 출처**: 아래 둘 중에서 정한다.
  - electron-updater의 `github` provider로 공개 Release에서 직접 받는다.
  - `generic` provider로 우리 도메인(`stardraft.squadify.app`)의 Vercel 함수를 거친다.
  - 비교할 점은 의존하는 것(GitHub 저장소 경로냐, Vercel과 도메인이냐), 사전 릴리스와 초안을 거르는 방법, 다중 Range 요청 문제(GitHub 자산 호스트가 `501`을 준다)다.
- **확인과 다운로드 시점**: 확인 주기를 정하고, 자동으로 받을지 사용자에게 묻고 받을지 정한다.
- **설치 시점**
  - "재시작해서 업데이트" 트레이 메뉴와 종료할 때 자동 설치 중에서 무엇을 쓸지 정한다.
  - 에이전트 실행 중이거나 게시 취소 대기(5초) 중에 재시작하면 어떻게 할지 정한다.
  - 표시 방식도 정한다. 트레이 아이콘의 점은 처리할 초안을 알리는 데 이미 쓰고 있다([초안 검토 화면 프로토타입](04-draft-review-prototype.md)).
- **진위 확인**: 업데이트 파일은 Gatekeeper나 SmartScreen의 사람 확인 없이 모든 PC에 퍼진다. 그래서 아래를 정한다.
  - Ed25519 서명 방식
  - 키를 만들고 보관하는 곳(Actions 비밀값), 회전 방법
  - 검증에 실패하면 어떻게 할지
  - 공개 저장소라 외부 PR의 워크플로는 승인해야 돌게 해 둔다(09).
- **macOS 서명**: `afterSign`에서 최상위 번들만 명시 DR로 다시 서명하는 단계를 빌드에 넣는다. 첫 버전부터 넣는다(09). 21 결과에 따라 조정한다.
- **관리자가 아닌 macOS 계정**: 업데이트할 때마다 관리자 인증을 요구한다. 아래 중에서 정한다.
  - `~/Applications`에 설치하라고 안내한다.
  - 업데이트를 끄고 수동으로 업데이트하게 한다.
  - 관리자 인증 창을 그대로 감수한다.
- **실패와 되돌리기**
  - 업데이트에 실패하면 어떻게 할지 정한다. 수동 설치 안내로 이어지는 경로가 필요하다.
  - 옛 버전으로 되돌릴 때 더 새로운 데이터를 어떻게 다룰지 정한다. 09의 다운그레이드 차단 규칙과 마이그레이션 전 사본이 걸린다.
- **차등 다운로드**: 처음에는 끌지 정한다.
- **Release 산출물 목록**: 08의 초안 Release에 무엇을 더 올릴지 확정한다(zip, `latest*.yml`, blockmap, 서명 파일).
- **Windows 점검**: 08의 "팀 배포 전 Windows 점검 목록"에 넣을 항목을 정한다. 조용한 설치와 재실행, MOTW와 SmartScreen이 뜨는지, 실패할 때의 상태다.

## 정해진 것

[다운로드 사이트 형태 결정](09-download-site.md)에서 정했다.

- 앱 내 업데이트는 범위 안이다. 첫 버전(`0.1.0`)부터 넣는다.
- `stardraft`는 공개 저장소이고, Release에 immutable releases를 켠다.
- 우리 도메인을 거친다면 앱에 넣는 주소는 `stardraft.squadify.app`이다.
- 앱은 자기보다 새 데이터를 만나면 실행하지 않고, 데이터를 자동으로 지우지 않는다.

## Answer

2026-10-19에 사용자와 그릴링으로 정했다.

- 근거
  - [앱 내 업데이트 가능성 조사](../research/in-app-update.md)
  - [앱 내 업데이트 macOS 실기 검증](21-in-app-update-macos-check.md)
  - electron-updater 6.8.10 소스: 21 프로토타입의 `node_modules`에서 직접 확인했다.
  - GitHub immutable releases 공식 문서

### 업데이트 파일 출처

- **electron-updater의 `github` provider로 공개 Release에서 직접 받는다.** 우리 도메인과 Vercel 함수는 거치지 않는다.
  - 의존하는 것은 GitHub 저장소 경로 하나다. 도메인 갱신이 끊기거나 Vercel에 문제가 생겨도 업데이트는 계속된다.
  - provider는 `github.com/<주인>/stardraft/releases.atom`과 `releases/latest`(JSON)를 읽는다. API가 아니라서 API 호출 한도와 무관하다 [소스: `GitHubProvider.js`의 `getLatestTagName`].
  - 초안은 공개되지 않아 보이지 않는다. 사전 릴리스는 `releases/latest`가 거른다(`allowPrerelease` 기본값 false).
  - provider가 다중 Range 요청을 끄도록 고정돼 있다(`isUseMultipleRangeRequest: false`). 그래서 GitHub 자산 호스트가 `501`을 주는 문제가 생기지 않는다.
  - `generic` provider와 Vercel 함수는 고르지 않았다.
    - 얻는 것: 나중에 GitHub를 떠나도 앱을 바꿀 필요가 없고, 함수에서 배포를 통제할 수 있다.
    - 잃는 것: 도메인, Vercel, 함수 코드, GitHub 토큰에 기대게 된다.
  - 보안은 두 안이 같다. 진위는 출처가 아니라 아래 서명이 지킨다.
- **잘못 나간 버전 멈추기**: 그 Release를 사전 릴리스로 바꾼다.
  - immutable releases는 자산과 태그만 잠그고, 사전 릴리스 전환과 latest 표시 변경은 허용한다.
    - 원문: "Only the assets and tag are locked. You can still edit the title and release notes of a published immutable release, and change whether it is marked as a pre-release or as the latest release." [immutable releases 문서](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
  - 사이트의 `/download/<os>`도 사전 릴리스를 고르지 않으므로 같이 멈춘다.
  - **확인하지 못한 것**: 사전 릴리스로 바꾸면 `releases/latest`가 바로 이전 버전을 가리키는지는 문서끼리 맞지 않는다. REST 문서는 생성일 정렬이라 하고, `make_latest` 문서는 표시를 따른다고 한다.
    - 첫 릴리스 전에 테스트 저장소에서 확인한다.
    - 안 되면 정상 버전에 latest 표시를 다시 지정한다.
  - Release를 삭제할 수도 있지만, 그 태그 이름은 다시 쓸 수 없다.

### 확인과 다운로드 시점

- **확인 시점**
  - 앱이 켜지고 1분 뒤 한 번, 그 뒤 4시간마다 확인한다.
  - 잠자기에서 깨어났을 때 마지막 확인이 4시간보다 오래됐으면 바로 확인한다.
  - 설정 "일반"의 [지금 확인]으로도 확인한다.
- **다운로드**: 새 버전을 찾으면 묻지 않고 받는다.
- **끄는 설정은 두지 않는다.** 확인과 다운로드 모두 해당한다. 받은 파일은 서명을 통과해야 설치 후보가 되고, 설치는 사용자가 정하기 때문이다.
- 소스에서 실행할 때(`Stardraft Dev`)는 업데이트를 끈다.

### 설치 시점

- **사용자가 [다시 시작]을 누를 때만 설치한다.**
  - 두 OS 모두 같다.
  - `autoInstallOnAppQuit = false`로 둔다.
  - 누르는 곳은 세 곳이다. 오른쪽 클릭 메뉴, 작은 창 띠, 설정 "일반"이다.
- **고르지 않은 안**: 종료할 때 설치하는 안과, 조건이 맞으면 앱이 알아서 다시 시작하는 안이다. 이유는 세 가지다.
  - **Keychain 창**: macOS는 업데이트 뒤 첫 실행에 Keychain 창(로그인 암호)을 띄운다.
    - 종료할 때 설치하면, 다음 실행에서 안내 없이 창이 뜬다.
    - 알아서 다시 시작하면, 자리에 없을 때 창이 뜬다. 그러면 답할 때까지 감지가 멈춘다.
  - **Windows 종료 중 설치**: PC를 끌 때 앱 종료와 함께 NSIS 설치가 돌 수 있다. NSIS는 옛 버전을 지운 뒤 새 파일을 푼다. 그 사이에 OS가 프로세스를 끊으면 앱이 없는 상태가 될 수 있다.
  - **서명 검증과의 충돌**: electron-updater의 종료 시 설치는 macOS에서 `update-downloaded`를 내보낸 직후 Squirrel에 파일을 넘긴다(`MacUpdater.js` L219-224). 그러면 서명 검증이 끝나기 전에 설치 대기에 들어간다.

### 다시 시작 흐름

- **macOS**: 어디서 눌러도 먼저 작은 창에 확인 화면을 띄운다. 메뉴 항목에는 안내를 담을 수 없기 때문이다.
  - 제목: "0.2.0으로 다시 시작합니다"
  - [설정과 첫 실행 온보딩 결정](16-onboarding.md)의 문구: "다시 켜지면 macOS가 'Stardraft Safe Storage' 사용을 묻습니다. Mac 로그인 암호를 넣고 '항상 허용'을 누르세요."
  - 덧붙이는 문구: "관리자 권한을 주는 창이 아닙니다. '허용'만 누르면 다음에 또 묻습니다." 21에서 사용자가 이 창을 관리자 암호 창으로 읽었기 때문이다.
  - **예시 화면**: Keychain 대화상자를 HTML로 재현해 넣고, "항상 허용"을 강조한다. [다운로드 사이트 화면 프로토타입](19-download-site-prototype.md)의 "예시 화면" 띠와 빗금 틀 규칙을 따른다.
  - 버튼: [다시 시작] [나중에]
  - 업데이트할 때마다 보여 준다. "다시 보지 않기"는 두지 않는다. 업데이트 사이 간격이 길어 잊기 쉽고, "허용"을 누르면 매번 묻게 되기 때문이다.
- **Windows**: 물을 것이 없으므로 확인 화면 없이 바로 다시 시작한다.
- **편집 중인 초안**: 다시 시작하기 전에 열린 편집기의 내용을 저장하고, 다시 켜면 그대로 보여 준다.
  - 지금까지 어느 티켓도 정하지 않았던 것이다.
  - 정상 종료에도 같은 규칙을 쓴다.
- **Keychain에서 "거부"를 누르면**: 16의 "키 확인 필요" 경로로 간다.

### 다시 시작을 미루는 조건

- **게시 카운트다운과 게시 요청**: 끝날 때까지 미룬다. [처리한 멘션의 보관 결정](17-processed-retention.md)에서 정했다.
- **에이전트 실행**: 그 실행이 끝날 때까지 미룬다. 실행 시간은 최대 10분이다.
  - 그동안 대기열의 다음 실행은 시작하지 않는다. 감지(폴링)는 계속한다.
  - 화면에는 "다시 시작 대기"를 보이고 [지금 다시 시작]과 [취소]를 둔다.
  - [지금 다시 시작]을 누르면 17대로 실행을 끊는다. 다시 켜면 그 실행이 대기열에 다시 들어가 처음부터 돈다.
- **미룰 조건이 모두 끝나면** 바로 다시 시작한다. macOS의 Keychain 안내는 누를 때 이미 보여 주었다.

### 진위 확인

- **방식**: Ed25519다. Node 내장 `crypto`를 쓰고, 외부 라이브러리는 쓰지 않는다.
- **서명 대상은 짧은 서명 문장이다.** 문장은 형식 이름, 버전, 파일 이름, sha512로 이뤄진다.
  - Ed25519는 메시지 전체를 한 번에 메모리에 올려야 한다. 그래서 100MB가 넘는 zip에 직접 서명하지 않는다.
  - 버전과 파일 이름을 함께 묶는다. 진짜 서명이 붙은 옛 파일을 새 버전인 척 내미는 공격을 막기 위해서다.
- **서명은 `latest.yml`과 `latest-mac.yml` 안의 필드로 둔다.**
  - 처음에는 `<파일 이름>.sig`를 따로 올리려 했다. Release 파일 수를 줄이려고 바꿨다.
  - electron-updater는 yml을 `js-yaml`로 읽은 결과를 그대로 넘긴다. 그래서 우리가 더한 필드도 다운로드 이벤트까지 온다 [소스: `Provider.js`의 `parseUpdateInfo`].
  - Tauri도 업데이트 안내 파일 안에 서명을 둔다.
  - **서명 필드는 처음부터 서명 목록으로 둔다.** 키를 회전할 때 두 키로 함께 서명할 수 있게 하려는 것이다(아래 "서명 키").
  - 서명하는 파일은 macOS zip과 Windows exe다. DMG는 앱이 받지 않으므로 대상이 아니다.
- **앱이 확인하는 것**: `update-downloaded`에서 아래가 모두 맞을 때만 "설치 준비됨"으로 둔다.
  - 받은 파일의 sha512를 직접 다시 계산한 값이 서명 문장과 같은지
  - 서명 목록 중 하나가 앱의 공개 키 목록 중 하나로 검증되는지
  - 서명 문장의 버전이 yml의 버전과 같고, 지금 버전보다 높은지
  - 서명 문장의 파일 이름이 받은 파일과 같은지
- **실패하면**
  - 받은 파일을 지우고 설치하지 않는다. 지금 버전을 계속 쓴다.
  - 같은 버전은 자동으로 다시 받지 않는다. 더 새 버전이 나오면 그 버전은 받는다. 사용자가 [다시 시도]를 누르면 다시 받는다.
  - yml에 서명 필드가 없거나 형식이 틀려도 같은 실패로 본다.
  - 문구: "업데이트 파일의 서명이 맞지 않아 설치하지 않았습니다. 지금 버전을 계속 씁니다."
  - **사이트에서 수동 설치하라고 권하지 않는다.**
    - 네트워크 손상은 electron-updater의 sha512 확인에서 먼저 걸린다. 그래서 서명 실패는 CI 실수이거나 Release가 조작된 경우다.
    - 조작된 경우라면 사이트의 DMG도 같은 Release에서 나온다.

### 서명 키

- **만들기**: 저장소 주인이 `pnpm release:keygen` 한 번으로 준비한다. 팀원은 터미널을 쓸 일이 없다. 스크립트는 아래를 한 번에 한다.
  1. Ed25519 키 쌍을 메모리에서 만든다. 디스크에 파일로 남기지 않는다.
  2. 공개 키를 앱 소스의 키 목록 파일에 써 넣는다. 커밋은 직접 한다.
  3. 개인 키를 `gh secret set --env release`로 Actions 환경 비밀값에 등록한다.
  4. 개인 키는 화면에 출력하지 않고 클립보드에 복사한다. 비밀번호 관리자에 붙여 넣었다는 확인(Enter)을 받은 뒤 클립보드를 비운다.
  - 전제: `gh`에 로그인되어 있어야 한다.
  - 평소 릴리스에서는 키를 만질 일이 없다. 태그를 푸시하면 CI가 서명한다.
- **개인 키 보관**
  - `release` 환경의 비밀값으로 두고, `v*` 태그에서만 읽히게 한다. [다운로드 사이트 형태 결정](09-download-site.md)의 외부 PR 워크플로 승인과 겹쳐 이중으로 막는다.
  - 비밀번호 관리자에 오프라인 사본을 둔다. Actions 비밀값은 다시 읽을 수 없다. 사본 없이 잃어버리면 새 키를 넣은 버전을 모든 PC가 사이트에서 다시 설치해야 한다.
- **공개 키**: 앱 소스에 상수 목록으로 넣는다. 지금은 하나다.
- **회전**: 정기 회전은 하지 않고, 유출이 의심될 때만 한다.
  1. `pnpm release:keygen --rotate`로 새 키를 만든다.
     - 새 공개 키를 목록에 **더한다**.
     - 새 개인 키는 두 번째 환경 비밀값으로 등록하고, 사본을 비밀번호 관리자에 둔다.
  2. 회전하는 동안 CI는 옛 키와 새 키로 함께 서명한다. 옛 버전 앱은 옛 키로, 새 공개 키를 아는 앱은 새 키로 통과한다.
  3. 팀원 PC가 새 공개 키를 넣은 버전으로 올라온 뒤, 옛 키 서명과 옛 공개 키를 뺀다.
  - 그릴링에서는 "새 공개 키를 넣은 버전 N은 옛 키로, N+1부터는 새 키로 서명한다"는 절차에 합의했다. 기록하면서 문제를 찾아 고쳤다. 앱은 늘 최신 버전만 받으므로, N을 건너뛰고 N+1을 만난 옛 앱은 검증에 실패한다. 그래서 회전 기간에는 두 키로 함께 서명하는 방식으로 바꿨다.
- **예비 키는 두지 않는다.** 처음부터 오프라인 전용 예비 공개 키를 넣어 두는 방법도 있다. 하지만 유출된 키로 공격자가 서명하는 것은 막지 못하고, 열 명 안팎 규모에서 얻는 것이 작다.

### 릴리스 전 CI 검사

아래 중 하나라도 틀리면 초안 Release를 만들지 않는다.

- **macOS 빌드 작업**
  1. `afterSign` 뒤 `.app` 최상위 DR이 정확히 `designated => identifier "app.squadify.stardraft"`인지 `codesign -d -r-`로 확인한다.
  2. 만든 zip을 `ditto -x -k`로 풀어서 같은 DR인지, `codesign --verify --deep --strict`를 통과하는지 확인한다.
     - 실제로 업데이트되는 파일은 zip이다.
     - electron-builder 26.15.0에는 zip이 서명을 깨뜨린 회귀가 있었다.
- **Release 작업**
  3. `latest*.yml`의 파일 이름, 크기, sha512가 실제 zip, exe와 맞는지 확인한다.
  4. 서명 필드를 넣은 뒤, 앱 소스의 공개 키 목록으로 다시 검증한다.
- **사람이 확인하는 것으로 두지 않는 이유**: DR이 빠진 버전이 한 번 나가면, 그 버전을 설치한 PC는 이후 업데이트가 조용히 모두 거부되고 사이트에서 다시 설치해야 풀린다(21).
- **macOS 서명 단계**: 계획대로 `afterSign`에서 최상위 번들만 다시 서명한다. 21에서 확인했고, 조정할 것은 없다.

### 앱이 스스로 바꿀 수 없는 위치

- **확인할 때마다 앱이 자기 위치를 본다.**
  - 번들과 부모 폴더에 쓸 수 있는지
  - 읽기 전용 볼륨(DMG 안, App Translocation)인지
  - Squirrel.Mac이 관리자 인증을 요구하거나 거부하는 조건과 같다.
- **쓸 수 없으면 업데이트를 받지 않는다.** 새 버전이 있다는 사실과 [사이트에서 받기]만 보여 준다.
  - 관리자 인증 창은 띄우지 않는다. 관리자 암호가 없는 사용자는 그 창에서 할 수 있는 일이 없다.
  - 사유 문구는 경우마다 다르다.
    - DMG 안이거나 번역 실행이면: "응용 프로그램 폴더로 옮긴 뒤 다시 여세요"
    - 권한이 없으면: "이 계정은 Stardraft를 바꿀 권한이 없습니다"
- 사이트의 macOS 설치 1단계는 그대로 두고 한 줄만 더한다(아래 "다운로드 사이트").
- Windows는 사용자별 설치라 해당하지 않는다.
- **고르지 않은 안**은 세 가지다.
  - `~/Applications` 설치를 기본으로 안내하는 안
  - 업데이트를 끄는 안
  - 관리자 인증 창을 감수하는 안
  - 팀원 대부분은 자기 Mac의 관리자일 것으로 봤다. 그래서 흔한 경우는 그대로 두고, 드문 경우만 수동 경로로 내려가게 했다.

### 표시

21에서 사용자가 "추가로 업데이트 진행 여부를 알 수 있었으면 좋겠음"이라고 한 데 대한 답이다.

- **트레이 아이콘은 바꾸지 않는다.**
  - 숫자, 점, "!"는 멘션과, 감지를 멈추는 문제에 쓴다([초안 검토 화면 프로토타입](04-draft-review-prototype.md), 16).
  - 업데이트는 급하지 않다.
- **OS 알림은 띄우지 않는다.**
- **작은 창의 띠 자리는 하나다.** 16의 전역 문제 띠가 있으면 업데이트 띠는 그 뒤로 미룬다.

| 상태 | 오른쪽 클릭 메뉴 | 작은 창 띠 | 설정 "일반" |
|---|---|---|---|
| 최신 / 확인 중 | - | - | "최신 버전입니다 · 마지막 확인 10:20" [지금 확인] / "확인 중…" |
| 받는 중 | "0.2.0 받는 중… 45%"(누를 수 없음) | - | 진행 막대와 % |
| 설치 준비됨 | "다시 시작해서 업데이트 (0.2.0)" | "새 버전 0.2.0이 준비됐습니다" [다시 시작] [변경 내역] | 같은 문구와 [다시 시작] [변경 내역] |
| 다시 시작 대기 | "다시 시작 대기 중…" | "초안 생성이 끝나면 다시 시작합니다" [지금 다시 시작] [취소] | 같은 문구 |
| 스스로 바꿀 수 없는 위치 | "새 버전 0.2.0 · 사이트에서 받기" | 사유와 [사이트에서 받기] | 사유와 [사이트에서 받기] |
| 서명 검증 실패 | - | 서명 실패 문구 [닫기] | 서명 실패 문구와 [다시 시도] |
| 설치 실패 | - | 설치 실패 문구와 버튼 | 설치 실패 문구와 버튼 |
| 확인·다운로드 실패(네트워크) | - | - | "마지막 확인 실패 · 3시간 전" [지금 확인] |
| 업데이트 직후 첫 실행 | - | "0.2.0으로 업데이트했습니다" [변경 내역], 한 번만 | 버전 |

- 네트워크 실패는 다음 확인에서 저절로 다시 시도한다. 그래서 설정에만 적는다.
- 버튼이 여는 곳
  - [변경 내역]: 사이트의 변경 내역 섹션
  - [사이트에서 받기]: 사이트의 업데이트 섹션
- 16이 남겨 둔 설정 "일반"의 업데이트 자리는 위 표의 설정 열이다. 지금 버전, 상태 문구, [지금 확인], 상태별 버튼이 들어간다.

### 설치 실패

- **기록**: 다시 시작하기 직전에 "업데이트 시도"를 기록한다. 지금 버전, 새 버전, 시각이다. 17의 "보내기 전에 남긴 기록"과 같은 방식이다.
- **판정**: 다시 켰을 때 버전이 그대로면 설치 실패로 본다.
  - 문구: "0.2.0으로 업데이트하지 못했습니다"
  - 버튼: [다시 시도] [사이트에서 받기]
- **Squirrel.Mac이 앱 안에서 거부한 경우**(`did not pass validation`)는 다시 시도해도 소용이 없다.
  - 문구: "이 버전은 앱 안에서 업데이트할 수 없습니다. 사이트에서 받아 설치하세요."
  - 버튼: [사이트에서 받기]만 둔다.
- **Windows에서 NSIS가 중간에 멈춰 앱이 없어진 경우**에는 앱이 아무것도 보여 줄 수 없다. 그래서 사이트의 업데이트 섹션에 적는다.
- **진단 로그**: electron-updater 로그를 남긴다. macOS는 ShipIt 로그 위치(`~/Library/Caches/app.squadify.stardraft.ShipIt/`)도 남긴다.

### 옛 버전으로 되돌리기와 데이터

- **고칠 때는 새 버전으로 덮는다.** 옛 버전 재설치는 지원 경로로 두지 않는다.
  - 사이트에서 옛 버전을 깔아도, 앱 내 업데이트가 곧 같은 최신 버전을 다시 받는다(`allowDowngrade` 기본값 false).
- **09 규칙은 그대로다.** 옛 앱은 자기보다 새 데이터를 만나면 실행하지 않고, 데이터를 자동으로 지우지 않는다.
- **마이그레이션 전 사본**
  - 마이그레이션 직전에 `state.db`와 `settings.json`의 사본을 버전 이름으로 남긴다.
  - **새 버전이 정상으로 뜬 지 7일이 지나면 지운다.** 사본에는 Flow 원문과 초안이 들어 있다. 오래 두면 17의 "처리됨 7일 뒤 전체 기록 삭제"를 사본이 깨뜨린다.
  - 사본을 복원하는 버튼은 두지 않는다. 개발자가 직접 복구할 때만 쓴다.

### 차등 다운로드

- **처음에는 끈다**(`disableDifferentialDownload: true`).
  - macOS는 DMG로 처음 설치한 뒤의 첫 업데이트가 어차피 전체 다운로드다.
  - 인원도 열 명 안팎이다.
- **blockmap도 올리지 않는다.**
  - 나중에 버전 N부터 올리기 시작하면, N에서 N+1로 가는 업데이트부터 차등으로 받는다.
  - N보다 옛 버전에서 오는 업데이트는 전체를 받는다. 지금과 같으므로 잃는 것이 없다.
  - 그릴링 중에 "지금 올려 두어야 나중에 켤 수 있다"고 잘못 설명했다가 바로잡았다.

### Release 산출물

[데스크톱 프레임워크와 기술 스택 결정](08-desktop-stack.md)의 초안 Release에는 다섯 개만 올린다.

| 파일 | 쓰는 쪽 | 이유 |
|---|---|---|
| `Stardraft-<v>-arm64.dmg` | 사람(사이트) | Mac에 처음 설치할 때 받는다 |
| `Stardraft-<v>-arm64-mac.zip` | 앱 | Squirrel.Mac은 DMG를 쓰지 못하고 zip만 받는다. 없으면 `ERR_UPDATER_ZIP_FILE_NOT_FOUND`다 |
| `latest-mac.yml` | 앱 | 새 버전이 있는지 묻는 안내 파일이다. 버전, zip 이름, 크기, sha512, 우리 서명이 들어 있다 |
| `Stardraft-Setup-<v>.exe` | 사람과 앱 | Windows는 같은 파일로 처음 설치와 업데이트를 모두 한다 |
| `latest.yml` | 앱 | Windows용 안내 파일이다 |

- **사람은 지금처럼 DMG나 exe만 받는다.**
  - zip과 yml은 앱이 Release에서 직접 읽는다.
  - 사이트의 다운로드 버튼도 DMG와 exe만 가리킨다.
- **릴리스할 때 손으로 만드는 파일은 없다.** 태그를 푸시하면 CI가 다섯 개를 만들고 서명해서 초안에 올린다.
- **08의 `SHA256SUMS.txt`는 뺀다.** GitHub가 Release 파일마다 sha256 `digest`를 보여 주고, 09의 `/api/releases`도 이 값을 내보낸다.
- **blockmap과 `.sig` 파일은 올리지 않는다.** 이유는 위 "차등 다운로드"와 "진위 확인"에 있다.
- **파일 이름에서 공백을 뺀다.**
  - NSIS 기본 이름은 `Stardraft Setup <v>.exe`다.
  - GitHub는 올릴 때 공백을 `.`으로 바꾸고, `latest.yml`은 공백을 `-`로 본다. 그래서 이름이 어긋난다.
  - `nsis.artifactName`을 `${productName}-Setup-${version}.${ext}`로 둔다.
- **빌드 설정**
  - `mac.target: ["dmg", "zip"]`
  - `publish: { provider: "github", owner: <주인>, repo: "stardraft" }`
  - `--publish never`로 빌드한다. 업로드는 08대로 마지막 작업 하나가 한다.

### 다운로드 사이트

[다운로드 사이트 화면 프로토타입](19-download-site-prototype.md)의 자리 표시 "새 버전이 나오면 Stardraft가 받아서 설치하고 다시 켭니다"는 맞지 않는다. 설치는 사용자가 누를 때만 하기 때문이다. 아래로 바꾼다.

> **업데이트**
> Stardraft는 새 버전을 스스로 확인하고 받아 둡니다. 준비되면 트레이 메뉴와 Stardraft 창에 **다시 시작**이 나타나고, 누르면 새 버전으로 다시 켜집니다.
>
> - **Mac**: 다시 켜지면 macOS가 'Stardraft Safe Storage' 사용을 묻습니다. Mac 로그인 암호를 넣고 **항상 허용**을 누르세요. 관리자 권한을 주는 창이 아닙니다. **허용**만 누르면 다음에 또 묻습니다. *(예시 화면)*
> - **앱이 스스로 업데이트하지 못할 때**: 이 페이지에서 새 버전을 받아 덮어 설치하세요. 데이터는 그대로 남습니다. Mac은 **그래도 열기**와 키체인 확인을, Windows는 SmartScreen 확인을 다시 거칩니다.
> - **Windows에서 앱이 사라졌거나 켜지지 않을 때**: 이 페이지에서 다시 설치하세요. 데이터는 그대로입니다.

- **macOS 설치 1단계**(응용 프로그램 폴더로 옮기기)에는 아래 한 줄만 더한다. 예시 화면은 바꾸지 않는다.
  > 관리자가 아닌 계정이면 홈 폴더의 응용 프로그램(`~/Applications`)에 두세요. 그래야 앱이 스스로 업데이트됩니다.
- **Keychain 예시 화면**: 앱의 다시 시작 확인 화면과 같은 것을 쓴다.
- **서버 엔드포인트**: 업데이트 파일은 앱이 GitHub에서 직접 받으므로, 사이트에 업데이트용 엔드포인트를 만들지 않는다.

### "팀 배포 전 Windows 점검 목록"에 더한 것

08의 점검 목록에 아래 다섯 가지를 더한다.

1. `quitAndInstall(true, true)`가 창과 UAC 없이 설치하고, 새 버전으로 다시 켜지는지
2. 앱이 받은 설치 파일에 MOTW(`Zone.Identifier`)가 없는지, 설치할 때 SmartScreen이 뜨지 않는지
3. 설치 도중 프로세스를 강제로 끊었을 때 어떤 상태가 되는지, 사이트에서 다시 설치하면 데이터가 남는지
4. 업데이트 뒤에도 아래가 유지되는지
   - 알림
   - 로그인 시 자동 시작
   - 바로가기의 AppUserModelID
   - 트레이 아이콘을 숨김 영역 밖으로 꺼내 둔 상태
   - DPAPI 키 복호화
5. 버전이 그대로일 때 설치 실패 띠가 뜨는지

### 구현 후 확인

- **사전 릴리스 전환**: 공개한 immutable Release를 사전 릴리스로 바꿨을 때, `releases/latest`와 앱의 업데이트 확인이 바로 이전 버전으로 돌아가는지. 첫 릴리스 전에 테스트 저장소에서 확인한다.
- **macOS 표준 계정과 `~/Applications`**
  - 21에서 하지 않은 실험이다.
  - 표준 계정에서 위치 확인이 "쓸 수 없음"으로 판정하는지도 본다.
- **오류 경로와 표시**: 두 경우를 각각 본다. yml의 sha512를 틀리게 고친 경우와 서명 필드를 틀리게 고친 경우다.
- **업데이트 뒤 자동 시작**: 실제로 로그아웃했다가 로그인할 때 자동 시작되는지. 21에서는 상태 값만 봤다.
- **Windows 실기**: 위 점검 목록으로 본다.

### 용어

- 새 용어는 없다. 업데이트는 앱 운영에 관한 것이고, 멘션과 초안 도메인 밖이다.
- "설치 준비됨", "다시 시작 대기" 같은 상태 문구는 이전 결정들처럼 스펙에서만 쓴다.

  - 되돌리기 어렵고, 맥락 없이는 의아하며, 실제 트레이드오프가 있었다.
  - 09대로 새 앱 저장소로 옮길 문서다.

- 2026-10-18, [처리한 멘션의 보관 결정](17-processed-retention.md)에서 덧붙인다.
  - **재시작을 미루는 조건**: 업데이트로 다시 시작하는 일은 게시 카운트다운과 게시 요청이 끝날 때까지 미룬다. 질문의 "게시 취소 대기 중에 재시작하면 어떻게 할지"에 대한 답이다.
  - **미루지 않을 때 일어나는 일**: 17에서 앱이 꺼질 때의 처리를 정했다. 업데이트 재시작도 이 규칙을 따른다.
    - 카운트다운 중이던 묶음은 게시하지 않고 준비됨으로 돌아간다.
    - 진행 중인 게시 요청은 응답을 최대 5초 기다리고, 그래도 응답이 없으면 다시 켰을 때 결과를 확인한다.
    - 생성 중이던 묶음은 다시 켜면 대기열에 다시 들어가 처음부터 실행한다. 그래서 에이전트 실행 중에도 재시작할 수는 있다. 사용량을 아끼려고 실행이 끝날 때까지 미룰지는 이 티켓에서 정한다.
- 2026-10-19, [앱 내 업데이트 macOS 실기 검증](21-in-app-update-macos-check.md)에서 덧붙인다.
  - **macOS 채택**: 변형 B(최상위 명시 DR)로 업데이트와 재실행이 성공했다. macOS도 앱 내 업데이트를 채택한다. "macOS 서명" 항목은 계획대로 `afterSign`에서 최상위 번들만 다시 서명하며, 조정할 것은 없다.
  - **진행과 실패 표시**: 서명 검증 실패는 `error` 이벤트로만 끝났고 화면에는 아무것도 뜨지 않았다. 사용자는 "추가로 업데이트 진행 여부를 알 수 있었으면 좋겠음"이라고 했다. 확인 중, 받는 중, 설치 대기, 실패를 어디에 어떻게 보여 줄지 정한다.
  - **DR 누락 방지**: Squirrel.Mac은 설치된 옛 번들의 DR로 새 번들을 검증한다. 그래서 명시 DR이 빠진 버전을 설치한 PC는 이후 업데이트가 모두 조용히 거부되고, 사이트에서 다시 설치해야 풀린다. 빌드에서 최상위 DR이 `designated => identifier "app.squadify.stardraft"`인지 검사하고, 다르면 Release를 만들지 않을지 정한다.
  - **Keychain 안내 문구**: "허용"만 누르면 다음 실행에 또 묻는다. 그래서 16에서 정한 "'항상 허용'을 누르세요" 문구가 꼭 필요하다. 사용자는 이 창을 관리자 암호 창으로 읽었다. 관리자 인증이 아니라 Keychain 창이라는 것을 문구나 그림으로 구분하면 좋다. 사이트에서 받아 수동으로 업데이트해도 똑같이 물으므로, 다운로드 사이트의 업데이트 섹션도 같은 안내를 쓴다.
  - **관리자 인증**: 관리자 계정이 직접 `/Applications`에 끌어다 놓은 경우에는 관리자 인증 창이 뜨지 않았다. 표준 계정과 `~/Applications`는 확인하지 않았다.
