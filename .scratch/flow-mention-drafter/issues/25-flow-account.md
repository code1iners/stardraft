# 25: Flow 계정 연결과 키 보관

**Spec:** [스펙](../spec.md) 3절, 13절 "개인 API 키"

**What to build:** 설정 창 "Flow 계정" 칸에 개인 API 키를 넣고 [확인]을 누르면 이름·소속·이메일 계정 카드와 "연결됨"이 보인다. 키는 OS 키 보관소로 보호되어 저장된다. 다른 계정의 키로 바꾸면 확인을 받고 기록을 비운다.

**Blocked by:** 24

**Status:** resolved

- [x] 입력 칸 위에 "Flow 웹의 내 API 키에서 발급합니다. 메뉴가 보이지 않으면 회사 관리자가 개인 키 발급을 허용해야 합니다."가 있고 링크는 없다.
- [x] [확인]은 `GET /user/employees/me`를 `x-flow-api-key` 헤더로 부른다. API 주소 `https://api.flow.team`는 코드 한 곳에만 있다. Flow 어댑터의 첫 조각이다.
- [x] 성공하면 계정 카드와 "연결됨"을 보이고, 그때만 `safeStorage` 비동기 API로 암호화해 데이터 폴더의 파일에 저장한다. `shouldReEncrypt`면 다시 암호화한다. 실패하면 옛 키와 계정을 그대로 둔다.
- [x] 실패 문구: `401` "키가 맞지 않습니다. Flow에서 다시 복사해 붙여 넣어 주세요.", 네트워크 오류 "Flow에 연결할 수 없습니다"와 다시 시도, `429`는 잠시 뒤 자동 재시도.

- [x] `.env`나 환경 변수로 키를 받는 경로가 없다. 개발 모드의 키체인 항목 이름이 `Stardraft Dev Safe Storage`로 분리되는지 확인해 기록한다.
- [x] 가짜 `fetch`로 성공·401·네트워크·429 경로와 계정 비교가 테스트된다.

## Comments

### 2026-10-20 구현과 검증 기록

**구조**

- Flow 어댑터의 첫 조각은 `src/core/flow/http-flow-api.ts`의 `HttpFlowApi`다. Flow API 포트를 구현한다.
  - API 주소 `https://api.flow.team`은 이 파일의 상수 하나에만 있다. 어댑터 테스트는 실제로 부르는 주소를 문자열로 확인한다.
  - 요청에는 `x-flow-api-key` 헤더를 싣고, 20초 제한 시간(시계 포트)을 둔다. 함께 거는 조건은 셋이다.
    - `cache: 'no-store'`: Flow 글이 HTTP 디스크 캐시에 남지 않게 한다.
    - `credentials: 'omit'`: 키 인증이라 쿠키를 싣거나 받지 않는다.
    - `redirect: 'error'`: 리디렉트를 따라가면 키 헤더가 다른 출처로 갈 수 있다.
  - 응답은 실호출에서 본 봉투 `response.data`에서 읽는다.
    - 문서는 `/user/employees/me`의 응답 필드(`userId`, `fullname`, `divisionName`, `email`)만 밝히고 data 안의 위치는 밝히지 않는다. 그래서 data 자체와 data 바로 아래 객체 가운데 `userId`가 있는 것을 읽는다.
    - 이름이나 이메일이 비면 사용자 ID로 대신 보인다.
  - 실패는 아래처럼 나눈다.
    - `401`: 키 거부
    - `429`: 한도. `Retry-After`는 초와 HTTP 날짜를 모두 읽는다.
    - 응답 없음, 제한 시간 초과, 리디렉트: 연결 실패
    - 그 밖의 응답 코드: 코드를 담아 돌려준다.
    - 모양이 다른 성공 응답: `unexpected-response`. Flow API 포트에 새로 더한 실패 종류다.
    - 헤더에 실을 수 없는 키(공백, 줄바꿈, 한글 등): 보내지 않고 키 거부로 본다.
  - 사용자 ID 비교 규칙(`isSameFlowUser`)은 `src/core/flow/user-id.ts`에 있다.
- 비밀 저장소는 `src/core/storage/file-secret-store.ts`의 `FileSecretStore`다.
  - 암호화는 `safeStorage` 비동기 API 모양(`encryptStringAsync`, `decryptStringAsync`)만 받는 `AsyncStringEncryption`으로 주입한다. main은 `safeStorage`를 그대로 넘긴다. 동기 API는 받지 않는다.
  - 암호문은 데이터 폴더의 `flow-api-key.bin`(0600)에 임시 파일을 거쳐 원자적으로 쓴다.
  - 읽을 때 `shouldReEncrypt`면 새 열쇠로 다시 저장한다. 다시 저장하지 못해도 이번에 푼 키는 돌려준다.
  - 복호화에 실패하거나 파일을 읽을 수 없으면 `unreadable`이다.
  - 읽기·쓰기·지우기는 맡긴 순서대로 하나씩 한다(`src/core/serial-queue.ts`). 다시 암호화한 옛 키가 그 사이에 저장한 새 키를 덮지 않게 하기 위해서다.
  - `openAppData`가 데이터 폴더의 다른 파일과 함께 이 저장소를 만든다. 키 파일은 형식 검사와 마이그레이션 사본에 넣지 않는다.
- `state.db`는 마이그레이션 2를 더했다.
  - `account` 표에 `name`, `division`, `email`을 더했다. 사용자 ID만 있던 행은 이름과 이메일 자리를 사용자 ID로 채운다.
  - 상태 저장소 포트의 `getAccountUserId`/`setAccountUserId`를 `getAccount`/`setAccount`/`resetForAccount`로 바꿨다.
  - `resetForAccount`는 `app_meta`만 남기고 DB에 있는 모든 표를 비운 뒤 새 계정을 넣는다.
    - 한 트랜잭션으로 하고, 외래 키 검사는 커밋 때로 미룬다.
    - 표 목록을 코드에 적지 않고 DB에서 읽으므로 뒤 티켓이 더하는 표도 지워진다.
    - 끝나면 `wal_checkpoint(TRUNCATE)`로 옛 계정의 글이 WAL 파일에 남지 않게 한다.
- core의 `src/core/account/flow-account.ts`(`FlowAccount`)가 키 확인과 계정 비교를 맡는다.
  - 붙여 넣은 키의 앞뒤 공백을 뺀다.
  - `429`면 `Retry-After`만큼(없으면 10초, 짧으면 1초) 기다렸다가 최대 3번 다시 확인한다.
  - 처음이거나 같은 계정이면 키를 저장하고 계정을 남긴다. 다른 계정이면 저장하지 않고 확인(`confirmSwitch`/`cancelKeyCheck`)을 기다린다.
  - 새 확인은 앞 확인을 대신한다. 계정 비교와 저장은 한 차례씩 해서, 앞 확인이 저장하는 사이에 다른 계정의 키가 확인 없이 저장되지 않게 했다.
  - 저장 순서는 키(실패하기 쉬운 암호화) → 계정이다.
    - 키를 저장하지 못하면 옛 키와 계정, 기록이 모두 그대로다.
    - 다른 사람의 계정을 남기지 못하면 키를 바꾸기 전으로 되돌린다.
    - 같은 사람의 이름·소속만 남기지 못하면 새 키로 연결된 채 끝난다.
- main
  - Flow 요청은 `net.fetch`(Chromium 네트워크: OS 프록시와 인증서 설정을 따름)로 보낸다.
  - 설정 창을 닫으면 진행 중인 확인과 확인을 기다리는 계정 바꾸기를 그만둔다.
- IPC
  - 스냅숏에 `flowAccount`를 더했다. 계정의 이름·소속·이메일과 확인 진행 상태를 담고, 사용자 ID는 렌더러에 넘기지 않는다.
  - 이벤트 `flow-account-changed`, `flow-key-check-finished`를 더했다.
  - 명령 `check-flow-key`(빈 값과 512자를 넘는 값 거부), `confirm-flow-account-switch`, `cancel-flow-key-check`를 더했다.
- 렌더러
  - "Flow 계정" 칸: 안내 한 줄, 입력 칸 위 안내 문장(링크 없음), 비밀번호 입력, [확인]/[취소]. 실패하면 문구와 [다시 시도]를 보이고, `429`로 기다리는 동안 대기 문구를 보인다.
  - 계정 카드: 이름 · 소속, 이메일, "✓ 연결됨", [키 바꾸기], "키는 이 PC에만 암호화해 보관합니다."

    - 저장 실패: "키를 이 PC에 저장하지 못했습니다. 다시 시도해 주세요."
  - `429`로 기다리는 동안: "Flow 요청이 많아 잠시 뒤 다시 확인합니다."
  - 확인 시트의 둘째 줄 "작업 폴더, 저장소 매핑, 에이전트, 지침 같은 설정은 그대로 둡니다."와 버튼 [취소]/[지우고 바꾸기]는 프로토타입 문구다.
- `429` 자동 재시도의 상한
  - 최대 3번 다시 시도한다.
  - `Retry-After`가 60초보다 길면 기다리지 않고 바로 한도 실패로 끝낸다. 서버가 정한 시각보다 일찍 부르지 않으면서, 화면이 오래 멈춘 것처럼 보이지 않게 하기 위해서다.

- 설정 창을 닫으면 진행 중인 확인을 그만둔다. 창이 없는데 확인 시트를 기다리거나, 닫힌 뒤에 다시 확인하지 않게 하기 위해서다.

    - 가짜 서버가 `x-flow-api-key` 헤더로 `GET /user/employees/me`를 받았다.
    - `401` 문구. 입력한 키는 남고, [다시 시도]는 없다.
    - 연결 끊김: 문구와 [다시 시도]. [다시 시도]는 같은 키로 다시 요청한다.
    - `429`: 대기 문구가 보이고, `Retry-After: 2`대로 2초 뒤 다시 확인해 계정 카드가 보인다.
    - 응답 없는 서버: 20초 뒤 연결 실패. `net.fetch`가 중단 신호를 따른다.
    - 리디렉트: 따라가지 않고 연결 실패.
    - 쿠키: 성공 응답의 `Set-Cookie`가 다음 요청에 실리지 않고, 쿠키 저장소도 비어 있다.
    - 키 파일 `flow-api-key.bin`: 0600, `v10`으로 시작하는 암호문, 평문 없음. `state.db`에는 계정 행이 있다.
    - 같은 계정의 새 키: 시트 없이 연결되고, 직접 넣어 둔 기준점 9001이 남는다.
    - 다른 계정: 시트 문구, 뒤 화면 `inert`, [취소]에 초점. Esc로 취소하면 그대로이고 초점이 입력 칸으로 돌아온다.
    - [지우고 바꾸기]: 계정이 바뀌고 기준점이 지워진다. `app_meta`는 남고, `settings.json` 해시는 그대로이며, `state.db-wal`은 0바이트다.
    - `429`로 기다리는 동안 설정 창을 닫으면 다시 확인하지 않는다.
    - 앱을 다시 켜도 계정 카드가 그대로다.
    - 진단 로그에 키와 사용자 ID 문자열이 없다.
- 개발 모드 키체인 항목
  - 키를 처음 저장한 순간 로그인 키체인에 서비스 `Stardraft Dev Safe Storage`, 계정 `Stardraft Dev Key` 항목이 생겼다.
  - 설치본 이름 `Stardraft Safe Storage` 항목은 생기지 않았다. `applyAppIdentity`가 `ready` 전에 앱 이름을 바꾸므로 Electron이 키체인 항목 이름을 정할 때 개발 이름이 쓰인다.
  - 확인 뒤 이 검증이 만든 항목은 지웠다(시작 전에는 없었다).

**사용자 확인이 필요한 것** (체크 항목에는 없지만 코드로 확인할 수 없는 것)

- 실제 Flow 계정의 개인 API 키로 연결하는 것: 이름·소속·이메일이 맞게 보이는지와, 응답 봉투에서 구성원 정보가 실제로 어디에 있는지. 두 모양을 모두 읽게 했지만 실제 응답으로는 확인하지 못했다.
