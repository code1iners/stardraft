# 32: 알림 폴링과 멘션 판정

**Spec:** [스펙](../spec.md) 4절 "폴링", "나를 지목했는지 판정"

**What to build:** 감지를 시작하면 60초마다 Flow 알림을 조회해 나를 직접 지목한 업무 멘션만 골라내고, 새 멘션이 생기면 트레이 숫자가 오르고 OS 알림이 뜬다. `@전체`, 담당자 지정, 내가 쓴 글, 72시간보다 오래된 알림은 걸러진다. Flow의 읽음 상태는 바뀌지 않는다.

**Blocked by:** 31

**Status:** resolved

- [x] `GET /user/alarms?filters=MENTION&size=20`(`readYn` 생략)을 60초마다, 그리고 앱 시작·잠자기에서 깨어남·"지금 확인" 때 바로 조회한다. 읽음 처리 API는 절대 부르지 않는다.
- [x] 기준점(가장 큰 `alarmId`)을 쓰고, 기준점 이하·72시간 초과·`hasNext: false` 중 하나를 만나면 페이지 넘기기를 멈춘다. 페이지 사이의 중복은 멘션 위치로 거른다. 기준점은 조회 뒤 갱신된다.
- [x] 오류: `429`는 `Retry-After`, 네트워크 오류는 다음 주기, `401`은 폴링을 멈추고 "키 확인 필요"(26).
- [x] 멘션 위치 구분(본문·댓글·대댓글)과 판정: 댓글·대댓글은 `contents`의 `@[…](내 ID)`, 본문은 `content` JSON TEXT 컴포넌트의 `MENTIONS` 또는 `CONTENTS` 표기. 대댓글이 처음 10개에 없으면 대댓글 API로 페이지를 넘긴다. 내 ID는 `receiverId`이며 25의 `userId`와 같아야 한다.
- [x] 버리는 알림: 송신자가 나, `404`/`403`, 수정되어 표기 사라짐, 72시간 초과, 최소 기록에 있는 멘션 위치의 재알림(최소 기록 자체는 47이 완성하되 판정 입구는 여기서 둔다).
- [x] 판정을 통과한 멘션은 멘션 위치로 식별되어 `state.db`에 저장되고, 트레이 숫자와 OS 알림이 뜬다(작은 창 표시는 33).
- [x] 가짜 Flow API와 가짜 시계로 기준점, 72시간, 페이지 넘김 중 중복, 판정 규칙 전부, 오류 경로가 테스트된다. 픽스처는 가짜 데이터다.

**결정과 이유**

- 기준점
  - 판정은 오래된 알림부터 한다.
  - 판정하지 못한 알림을 만나면 거기서 멈춘다. 기준점은 판정을 마친 알림까지만 옮겨, 다음 조회에서 나머지를 다시 판정한다.
  - 기준점이 없으면 가장 최근 `alarmId`를 기준점으로 잡고 과거 멘션은 가져오지 않는다. 다른 계정의 키로 바꿔 `state.db`를 비운 경우다.
- 72시간과 시간대
  - Flow 시각(`yyyyMMddHHmmss`)은 한국 표준시로 읽는다. 실호출(01)에서 방금 온 알림의 시각이 조회 시각(UTC)보다 9시간 앞서 있었다.
  - 정확히 72시간 전인 알림은 범위 안이다.
  - 시각을 읽을 수 없는 알림은 범위 안으로 본다.
- 중복: 같은 `alarmId`와 같은 멘션 위치는 한 번의 조회에서 한 번만 판정한다. 같은 위치의 알림이 여럿이면 가장 먼저 온 알림으로 저장한다.
- 내 ID
  - 스펙대로 알림의 `receiverId`를 쓴다.
  - 키 확인 때 얻은 `userId`와 다르면 버리지 않고 `detection.receiver-mismatch` 경고만 남긴다. 둘이 같다는 것은 아직 실호출로 확인하지 않았다. 다를 때 버리면 모든 멘션을 조용히 잃는다.
  - 송신자가 둘 중 어느 ID와 같아도 "송신자가 나"로 버린다.
- 오류
  - `401`(목록·판정 어디서든): 키 거부를 알리고 폴링을 멈춘다. "지금 확인"과 깨어남도 조회하지 않는다.
  - `429`: `Retry-After`만큼 기다린다. 그동안 "지금 확인"도 앞당기지 않는다. 헤더가 없으면 다음 주기다.
  - 연결 실패: 다음 주기에 다시 조회한다.
  - 조회하는 사이에 키를 새로 확인해 다시 시작했으면, 옛 키로 받은 `401`로는 멈추지 않는다.
- 판정에서 버리는 알림
  - 스펙 목록: 송신자가 나, `404`·`403`, 표기 사라짐, 72시간 초과, 이미 기록한 멘션 위치.
  - 댓글·대댓글이 목록에 없으면 지워진 것(`404`와 같음)으로 본다.
  - 서버 오류, 그 밖의 응답 코드, 모르는 응답 모양은 다음 조회에서 다시 판정한다. 같은 알림이 3번 이어서 실패하면 `detection.alarm-given-up` 경고를 남기고 넘어간다. 판정은 실패한 알림에서 멈추므로, 한 글 때문에 뒤의 멘션이 72시간 동안 막히지 않게 하려는 것이다.
- 대댓글 목록 응답 모양은 실호출로 확인하지 않았다. 그래서 두 모양을 모두 읽는다.
  - `data` 바로 아래에서 `replyId`가 든 배열
  - 알림 목록처럼 `data.replies` 아래에 `hasNext`·`lastCursor`·`replies[]`가 한 겹 더 오는 모양
- 쪽 수 상한(50쪽, 알림 1,000건)을 둔다. 서버가 다음 쪽이 있다고 계속 답할 때의 방어다. 닿으면 `detection.page-limit` 경고를 남긴다.
- 트레이 숫자와 알림
  - 트레이 숫자는 저장한 멘션 수다. 묶음 단위(준비됨 + 저장소 확인 필요)로 세는 것은 33이 바꾼다.
  - Windows 숫자 배지는 33의 몫이다. 그전까지 Windows는 툴팁에 "멘션 N건"을 보인다.
  - 새 멘션 OS 알림은 조회 한 번에 하나다("새 멘션" / "새 멘션 N건"). 본문에는 송신자 이름만 넣는다.
- 트레이 메뉴에 "지금 확인"을 더했다. 감지를 시작하기 전에는 꺼 둔다.
- 최소 기록: 판정 입구 `hasMentionLocation`은 지금은 저장한 멘션을 본다. 47이 최소 기록 표를 더할 때 이 메서드에서 함께 본다.
