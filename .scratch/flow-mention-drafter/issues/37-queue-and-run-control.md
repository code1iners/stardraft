# 37: 대기열과 실행 제어

**Spec:** [스펙](../spec.md) 6절 "실행 제어", "공통 실행 규칙"(버전 확인·점검 실행)

**What to build:** 여러 묶음이 한꺼번에 와도 에이전트는 한 번에 하나만 돌고, 사용자가 누른 재생성과 다시 시도는 맨 앞에 들어간다. 일시적인 실패는 한 번 자동으로 다시 시도한다. CLI가 사라지거나 로그아웃되면 대기열 전체가 멈추고 전역 문제로 한 번만 알리며, 해결되면 저절로 다시 돈다.

**Blocked by:** 35

**Status:** resolved

- [x] 직렬 대기열에 우선순위가 있다. 사용자 행동(재생성·다시 시도)은 맨 앞, 한 묶음의 선택 실행 뒤 초안 실행은 맨 앞(38에서 사용).
- [x] 자동 재시도는 일시적 실패(구조화 출력 없음, 모델 과부하, 네트워크 오류)에만 1회이고, 타임아웃·취소·형식 위반·앱 종료 중단은 세지 않는다.
- [x] 전역 실패(CLI 없음, 미로그인, 버전 낮음, 점검 실행 실패)는 묶음을 실패 처리하지 않고 대기열을 멈춘 뒤 26의 전역 문제로 알린다. 원인이 해결되면 자동으로 재개한다. 로그인 사전 점검은 시작 시와 전역 실패 의심 시에만 한다.
- [x] 실행 전에 CLI 버전이 바뀐 것을 알아채면 점검 실행을 먼저 돌리고, 실패하면 대기열을 멈춘다.
- [x] 설정 변경 반영: 에이전트·모델·추가 지침·작업 폴더는 다음 실행부터, 비밀 파일 패턴 추가는 50에서 다룬다.
- [x] 가짜 실행기·가짜 시계로 순서, 우선순위, 재시도 조건, 전역 실패 멈춤과 재개가 테스트된다.

**스펙과 다르거나 스펙에 없던 결정** (검토 대상)

- 되돌리기도 사용자 행동 자리에 넣었다. 스펙은 "재생성과 다시 시도"만 들지만, 초안 없이 되돌린 묶음은 사용자가 눌러 새로 만드는 것이라 같은 자리로 봤다.
- "맨 앞"을 이렇게 해석했다.
  - 끊긴 생성을 처음부터 다시 하는 묶음이 사용자 행동보다 앞이다. 그 묶음은 이미 차례가 와서 돌던 것이다.
  - 사용자 행동끼리는 누른 순서다. 마지막에 누른 것이 먼저 돌면 여러 개를 눌렀을 때 순서가 뒤집힌다.
- 전역 실패가 의심됐는데 재확인이 통과하면 일시적 실패처럼 1회 더 실행한다. 스펙의 일시적 실패 목록을 이 경우에 넓혔다.
  - 실패로 두면 CLI 교체 경합에서 정상인데도 묶음이 실패한다.
  - 계속 다시 넣으면 작동 확인(사용량)이 끝없이 돈다.
- 자동 재시도는 기다리지 않고 바로 한다. CLI가 이미 안에서 여러 번 재시도한다(28 실측: 연결 거부를 10회, 171초).
- Flow 쪽은 키 거부·쓸 키 없음과 네트워크 오류·429면 대기열을 멈추고, 5xx 등은 묶음 실패로 둔다(위 구조).
  - 네트워크 오류는 전역 문제로 띄우지 않는다(스펙에 없음).
  - 멈춘 동안 묶음은 "차례를 기다리는 중"이다.

  - "로그인 사전 점검은 시작 시와 전역 실패 의심 시에만"은 매 실행 전에 로그인을 확인하지 않는다는 뜻으로 지켰다.

- 대기열을 시작하는 시점을 저장된 키를 읽은 뒤로 옮겼다. 업데이트 뒤 키체인 확인 창에 답하기 전에는 맥락을 조회할 수 없어, 생성 중 묶음이 실패로 떨어지는 경합이 있었다.
- 실패 문구: 과부하·네트워크 오류에 "두 번 시도했습니다."를 더했다.
- 체크리스트 5의 "작업 폴더": 작업 폴더를 읽는 실행은 선택 실행(38)뿐이다. 이 티켓의 대기열은 설정을 실행마다 새로 읽고, 설정이 바뀌어도 실행 중인 실행을 끊지 않는다. 38이 선택 실행 요청을 만들 때 작업 폴더를 읽으면 다음 실행부터 반영된다.

**리뷰 반영** (Standards·Spec 두 축)

- 반영한 것
  - Spec
    - Flow 네트워크 오류·429의 처리를 정했다(멈췄다가 다시 조회).
    - 재확인이 통과한 실패는 한 번 더 실행한다.
    - 다시 넣는 사이의 [취소]를 지킨다.
  - Standards
    - 호출 횟수를 세던 테스트를 "실행이 일어나지 않는다"로 바꿨다. 이제 그 변이가 멈추지 않고 깨끗하게 실패한다.
    - 버전 변화 테스트의 명령 순서 고정을 풀었다.
    - 실행 직전 확인의 단계 주석과 두 번째 기다림의 이유를 적었다.
    - 시작 조건을 하나로 모았고, `DraftAgent`가 `RunnableAgent`를 넓히게 했고, main의 구독 묶기를 한 함수로 모았다.
    - 이름을 바꿨다: `reservedPriorities`, `changeCounts`, 테스트 도우미 `targetMentionOf`·`addThreadMention`.
    - `auth status` 가짜 출력을 `fakes/fake-claude-stream.ts`의 `fakeClaudeAuthStatus`로 모았다.
- 반영하지 않은 것
  - `suspectsGlobalFailure(reason: string)`의 넓은 인자 타입. 호출하는 쪽이 서로 다른 두 실패 유니온(실행기 결과, 실행 실패 사유)을 넘긴다. 목록 자체는 `ExecutorFailureReason`으로 타입을 검사한다.
  - 일시적 실패 목록과 화면 문구("두 번 시도했습니다.")를 한 곳에 두는 것. 렌더러는 core를 import할 수 없고(ESLint 경계), 문구는 사유마다 따로 쓴다.
  - (값, 변경 알림) 옵션 쌍을 한 객체로 묶는 것. 35의 `agent`·`onAgentChange`와 같은 모양을 지켰다.
  - 멈춤 장치를 클래스로 떼어 내는 것. 대기열 말고 쓰는 곳이 없어 간접만 늘어난다.

**사용자 확인이 필요한 것** (실제 화면·실제 CLI·실제 네트워크·실기기)

- 실제 Claude Code
  - 로그아웃(`claude auth logout`)한 뒤 멘션이 오면 묶음이 "차례를 기다리는 중"으로 남는지, "에이전트 확인 필요" 띠·트레이 "!"·OS 알림이 한 번 뜨는지 본다.
  - 다시 로그인하고 [에이전트 확인]으로 다시 확인하면 그 묶음부터 저절로 다시 도는지 본다.
  - Claude Code가 스스로 업데이트된 뒤 첫 실행 전에 작동 확인이 한 번 도는지 본다(진단 로그 `agent.cli-version-changed`).
  - 이유: 실제 CLI와 계정, 사용량이 필요하다. 이 티켓은 스펙대로 가짜 실행기와 가짜 stream-json으로 검사했다.
- 실제 네트워크(59): Wi-Fi를 끈 채 멘션 묶음의 생성 차례가 오면 실패로 떨어지지 않고 기다리는지, 다시 켜면 1분 안에 이어 도는지 본다.
- 실제 화면(59): 멈춘 동안의 생성 중 묶음 표시와 일시적 실패 문구를 본다.
- Windows(60): 위와 같다.
