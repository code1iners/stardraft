# 38: 자동 선택

**Spec:** [스펙](../spec.md) 5절 "자동 선택의 흐름", "매핑이 있는데 코드와 무관한 멘션", 6절 "선택 실행의 스키마"와 선택 실행 불일치 표

**What to build:** 저장소 매핑이 없는 묶음은 작업 폴더에서 찾은 후보를 놓고 선택 실행이 먼저 돌고, 고른 저장소로 초안 실행이 바로 이어진다. 화면에는 "생성 중" 하나로 보이고 진행 단계만 "저장소 고르는 중" → "초안 쓰는 중"으로 바뀐다. 확신하지 못하거나 코드와 무관하면 초안 없이 "저장소 확인 필요"에 에이전트의 사유와 후보가 보인다.

**Blocked by:** 29, 35

**Status:** resolved

- [x] 후보가 1개면 선택 실행을 건너뛰고 그 저장소를 쓴다. 0개(작업 폴더 없음·비어 있음)면 저장소 확인 필요.
- [x] 선택 실행: 입력은 초안 실행과 같은 맥락 + Flow 프로젝트 이름 + 후보 목록, 읽기 범위는 작업 폴더 전부(첫 폴더 cwd, 나머지 `--add-dir`), 선택 실행 전용 지침, 타임아웃 5분, 같은 맥락 길이 상한.
- [x] 출력 스키마: 판정(`chosen`/`unsure`/`unrelated`), 후보 `enum` 배열, 이유. 불일치 표(0개면 확신 못함, 4개 이상이면 앞 3개, 빈 이유는 "이유 없음").
- [x] 고름이 아니면 저장소 확인 필요 상태로 사유·후보를 보이고 [저장소를 골라 만들기](창은 39) [Flow에서 열기] [무시]를 둔다. OS 알림을 띄우고 트레이 숫자에 센다.
- [x] 저장소 영역에 자동으로 고른 이유를 보인다. 자동 선택 결과를 매핑으로 자동 저장하지 않는다.
- [x] 가짜 실행기로 세 판정과 불일치 표, 후보 0·1·여럿 경로, 잇기 순서가 테스트된다.

### 2026-10-21 구현과 검증 기록

**구조**

- 자동 선택의 흐름 `src/core/drafts/draft-queue.ts`(`DraftQueue.generate`, `selectRepos`)
  - 순서: 저장소 매핑 확인 → 맥락 조회와 "이미 답함" 확인 → (매핑이 없으면) 자동 선택 → 초안 실행
  - 매핑이 없는 묶음은 감지·되돌리기 때 저장소 확인 필요가 아니라 생성 중이 된다(`statusWithoutDraft`). 매핑된 폴더가 하나라도 없으면 35대로 자동 선택으로 넘어가지 않는다.
  - 후보 찾기: 생성마다 설정의 작업 폴더를 읽고 `findSelectionScope`(`src/core/repos/repo-candidates.ts`)로 다시 훑는다.
    - 없는 작업 폴더는 읽기 범위에서도 뺀다.
    - 겹친 작업 폴더에서 같은 저장소가 나오면 한 번만 센다.
  - 후보 0개: 실행 없이 `no-candidates` 사유로 저장소 확인 필요가 되고 OS 알림을 띄운다. 1개: 선택 실행 없이 그 저장소로 초안 실행을 돌린다.
  - 후보 여럿: 선택 실행이 고르면 같은 생성 안에서 그 묶음의 초안 실행을 바로 잇는다.
    - 그사이 들어온 사용자 행동(다시 시도)과 감지한 묶음은 그 뒤에 돈다.
    - 초안 실행은 새 실행이라 실행 직전 확인을 다시 거친다.
- 실행 단계 `runPhase`: 선택 실행과 초안 실행이 같은 코드로 다음을 거친다.
  - 실행 직전 확인
  - 일시적 실패 1회 재시도
  - 전역 실패 의심 시 연결 확인과 대기열 멈춤
  - [취소]와 새 멘션으로 멈춤
  - 37의 인계("선택 실행의 실패에도 같은 재시도·전역 실패 규칙")를 이렇게 지켰다.
- 선택 실행 `src/core/drafts/repo-selection.ts`
  - 지침 `SELECTION_INSTRUCTIONS`
    - 데이터 구획 규칙은 초안 실행과 같다.
    - 판정 세 가지의 뜻과 "확신이 낮다고 후보를 모두 넣지 않습니다"를 적었다.
    - 이유는 쉬운 말·합니다체로 쓰게 했다.
  - 입력 문서: "# 후보 저장소"(절대 경로) 뒤에 초안 실행과 같은 "# 데이터" 구획(`dataSectionLines`)을 둔다. 맥락 문서도 길이 상한(30,000자)을 적용한 같은 것이다.
  - 스키마: `verdict`(`chosen`/`unsure`/`unrelated`), `repositories`(후보 경로 `enum` 배열), `reason`이다. 모두 `required`이고 다른 속성은 받지 않는다.
  - 요청
    - 읽기 범위는 있는 작업 폴더 전부다(첫 폴더가 cwd, 나머지 `--add-dir`).
    - 제한 시간 5분(`SELECTION_TIMEOUT_MS`), 턴 상한 40(35에서 정한 `CLAUDE_MAX_TURNS.selection`)이다.
    - 모델과 추가 비밀 파일 패턴은 초안 실행과 같다.
  - 구조 실패: 판정이 세 값이 아니거나 후보가 아닌 저장소를 고르면 구조 실패라 한 번 더 실행한다.
  - 내용 불일치(`readSelectionOutput`)는 고쳐서 실행 기록 `fixes`에만 남긴다.
    - 고름인데 0개면 확신 못함으로 다룬다.
    - 4개 이상이면 앞 3개만 쓴다.
    - 같은 저장소가 거듭 나오면 한 번만 센다.
    - 이유가 비어 있으면 빈 문자열로 두고, 화면에는 "이유 없음"으로 보인다.
- 저장소 확인 필요 `src/core/bundles/`
  - 사유(`RepoCheck`)에 `no-candidates`와 `unsure`·`unrelated`를 더했다.
    - `unsure`·`unrelated`에는 이유, 작업 폴더의 후보 전부(`candidates`), 에이전트가 짚은 저장소(`picked`)가 든다.
  - `MentionBundles.markRepoCheckNeeded`: 생성 중 묶음을 옮기고 실행 기록을 더하며 OS 알림을 띄운다.
    - 옮기는 순간 멘션 위치가 바뀌었으면(새 멘션이 합쳐짐) 처음부터 다시 만든다.
    - 트레이 숫자는 기존대로 저장소 확인 필요를 센다.
- 초안과 실패
  - `Draft.autoSelection`: `single-candidate` 또는 `chosen`과 이유. 매핑으로 만들었으면 `null`이다.
  - `DraftFailure.runKind`: 실패한 실행의 종류(`selection`/`draft`). 실행 전에 실패했으면 `null`이다.
  - `state.db` 형식 8에서 이미 있던 초안과 실패에 두 값을 `null`로 넣었다. 자동 선택 결과는 저장소 매핑으로 저장하지 않는다.

      - 에이전트가 코드와 무관한 멘션으로 판정함
    - 에이전트의 이유
    - "에이전트가 짚은 후보"와 "작업 폴더의 (다른) 후보 N개"

**스펙과 다르거나 스펙에 없던 결정** (검토 대상)

- [저장소를 골라 만들기]: 저장소 확인 필요 화면에 두되 꺼 둔다. 티켓 항목 4가 "(창은 39)"라 누를 곳이 아직 없다. 마우스를 올리면 "저장소 선택 창은 아직 준비되지 않았습니다."가 보인다.
- 후보 표시: 스펙의 "후보"는 작업 폴더에서 찾은 후보라 그 전부를 보인다. 에이전트가 짚은 저장소는 따로 앞에 둔다.
  - 지침에 다음을 적었다.
    - 확신 못함이면 가능성이 있는 저장소를 3개까지 넣는다.
    - 코드와 무관이면 빈 배열로 둔다.
  - 확신 못함의 짚은 저장소도 3개로 자른다.
- 후보 0개 판정의 시점: 맥락 조회와 "이미 답함" 확인 뒤에 판정한다.
  - 이미 답한 묶음에 저장소 확인 필요 알림을 띄우지 않으려는 것이다.
  - 저장소 확인 필요 묶음의 "스레드 보기"에 맥락을 남기려는 것이기도 하다.
  - 매핑된 폴더가 사라진 경우는 35대로 맥락 조회 전에 판정한다.
- 작업 폴더를 읽는 시점: 생성마다 한 번이다.
  - 같은 생성 안의 자동 재시도는 같은 후보로 다시 묻는다. 후보 `enum`과 입력이 실행마다 달라지지 않게 하려는 것이다.
  - 저장소 매핑도 생성을 시작할 때 한 번 읽는 것과 같다. 바꾼 작업 폴더는 다음 생성부터 쓴다.
- 자동 재시도 1회를 생성 한 번이 아니라 실행 단계마다 센다. 선택 실행과 초안 실행은 서로 다른 실행이다.
- 선택 실행에는 추가 지침을 붙이지 않는다. 설정의 추가 지침은 "모든 초안에 적용할" 어조·길이·호칭·맺음말이다.
- 실패한 실행의 종류(`runKind`)를 더했다. 선택 실행의 시간 초과가 "10분"으로 잘못 보이지 않게 하려는 것이다.
- 실행 줄: 준비됨은 초안 실행의 시간만 보이고 선택 실행의 시간은 더하지 않는다. 두 시간을 합칠지는 스펙에 없다.
- [다시 시도]는 선택 실행부터 다시 한다. 실패한 생성의 선택 결과는 저장하지 않는다.
- 자동 선택 전에 사유 없이 저장소 확인 필요가 된 옛 묶음(`repoCheck`가 `null`)은 그대로 둔다.
  - 형식 8에서 생성 중으로 올리면 올린 직후 에이전트 실행이 몰린다.
  - 아직 배포 전이라 실제로 남은 묶음도 없다.
  - 무시한 뒤 되돌리면 자동 선택을 탄다.

**리뷰 반영** (Standards·Spec 두 축)

- 반영한 것
  - Spec
    - 저장소 확인 필요에 작업 폴더의 후보 전부를 담는다. 에이전트가 짚은 저장소만 보이면 코드와 무관 판정에서 후보가 하나도 보이지 않았다.
    - 선택 실행만 돈 저장소 확인 필요 묶음의 실행 줄을 보인다.
  - Standards
    - 결과를 저장하지 못했을 때 처음부터 다시 만드는 코드를 `restartUnlessFinished` 하나로 모았다.
    - 진행 단계를 실행마다 한 곳에서 처음으로 돌린다.
    - 후보 경로를 한 번만 만든다. 매핑 확인 결과의 이름을 `mapping`으로 바꿨다.
    - 스냅숏이 저장소 확인 필요 사유를 필드를 밝혀 옮긴다. 실패 종류에 `GenerationRunKindSnapshot` 이름을 붙였다.
    - 렌더러는 사유 첫 줄을 한 곳에서 그리고, 사유 내용 컴포넌트에 자기 Props를 둔다.
- 반영하지 않은 것
  - 선택 실행 요청과 초안 실행 요청 만들기를 한 함수로 합치는 것. 지침·스키마·읽기 범위·제한 시간이 모두 달라, 합치면 인자만 늘어난다.
  - `DraftAgent`·`RunningDraft`·`draft.*` 로그 이름을 선택 실행까지 아우르게 바꾸는 것. 이 티켓의 범위를 넘는 이름 바꾸기다.
  - 옛 사유 없는 저장소 확인 필요 분기를 지우는 것. 위 결정대로 둔다.
  - 문구의 "5분"·"10분"을 상수에서 만드는 것. 렌더러는 core를 import할 수 없고(ESLint 경계), 35의 "10분" 문구와 같은 방식이다.
- 용어집의 빈틈(`docs/agents/domain.md`): 다음 말이 스펙에는 있지만 `GLOSSARY.md`에는 없다.
  - "선택 실행"·"초안 실행"
  - 선택 실행의 "후보"·"판정"
  - 화면에는 "저장소 고르는 중"과 판정 문장만 나온다. 용어집에 넣을지는 용어를 정리할 때 정한다.

**사용자 확인이 필요한 것** (실제 화면·실제 CLI·실기기)

- 실제 화면(59)
  - 저장소 확인 필요 묶음의 저장소 영역: 사유, 짚은 후보와 다른 후보, 꺼진 [저장소를 골라 만들기], [Flow에서 열기], [무시]
  - 준비됨 묶음의 "자동으로 고른 이유"
  - 생성 중 진행 단계가 "저장소 고르는 중"에서 "초안 쓰는 중"으로 바뀌는 것
  - 저장소 확인 필요 OS 알림, 트레이 숫자
  - 이유: 렌더러 테스트는 정적 렌더링만 하고, 알림과 트레이는 실제 Electron 실행이 필요하다.
- 실제 Claude Code CLI
  - 선택 실행 스키마(`enum` 배열)로 `structured_output`이 오는지
  - 5분·40턴 안에 판정하는지
  - 지침대로 후보를 모두 넣지 않는지
  - 이유: 실제 실행은 사용자의 사용량을 쓴다. 이 티켓은 항목 6대로 가짜 실행기로 검사했다.
- Windows(60): 후보가 아주 많으면 `--json-schema` 인수가 길어진다. Windows 명령줄 상한(32,767자) 안에서 도는지 확인이 필요하다.
  - 예: 경로 80자 저장소가 300개면 스키마만 24,000자를 넘는다.
  - macOS는 인수 상한이 훨씬 커서 문제가 없다.
