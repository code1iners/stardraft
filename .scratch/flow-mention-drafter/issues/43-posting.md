# 43: 게시

**Spec:** [스펙](../spec.md) 9절 "게시 위치", "게시 본문", "게시 성공", "보내기 전 기록", 7절의 게시 중 상태

**What to build:** [게시]를 누르면 5초 카운트다운 토스트가 뜨고 그동안 취소할 수 있다. 끝나면 받는 사람 멘션 표기 뒤에 편집기 텍스트를 이은 게시 본문이 본문 묶음은 새 댓글로, 댓글 스레드 묶음은 그 댓글의 대댓글로 올라간다. 게시됨이 되면 바로 다음 묶음으로 넘어간다.

**Blocked by:** 40

**Status:** resolved

- [x] 게시 본문: `@[이름](ID)` 표기를 공백으로 이어 맨 앞에 두고 공백 하나 뒤에 편집기 텍스트(앞뒤 공백 제거)를 같은 줄에서 잇는다. 받는 사람이 없으면 텍스트만. 근거·번호·AI 표시는 없다.
- [x] 위치: `remarkId`가 `-1`이면 `POST /user/comments/{postId}`, 아니면 `POST /user/comments/{postId}/replies/{remarkId}`.
- [x] [게시]는 텍스트가 비었거나 4,000자를 넘거나 게시 결과 확인 중이면 꺼진다. 확인 창은 없다.
- [x] 보내기 직전에 "게시 요청 보냄"과 게시 본문을 `state.db`에 먼저 적는다. 성공하면 `commentId`/`replyId`를 기록하고 게시됨으로 둔다.
- [x] 카운트다운 중 들어온 새 멘션은 합치지 않고 새 묶음이 된다(게시 전 확인이 끝난 뒤 기준은 46에서 정밀화).
- [x] 게시하거나 무시하면 다음 준비된 묶음으로 넘어간다. 게시 중 상태는 검토 대기 목록에 남되 트레이 숫자에서는 빠진다.
- [x] 가짜 Flow API와 가짜 시계로 본문 조립, 위치, 카운트다운과 취소, 보내기 전 기록, 성공 기록이 테스트된다.

## Comments

### 2026-10-22 구현과 검증 기록

**구조**

- Flow 어댑터와 포트
  - `FlowApi.createComment(postId, contents)`: `POST /user/comments/{postId}`, 본문 `{ contents }` JSON, 응답의 `commentId`를 읽는다.
  - `FlowApi.createReply(postId, commentId, contents)`: `POST /user/comments/{postId}/replies/{commentId}`, 응답의 `replyId`를 읽는다.
  - 조회와 같은 요청 설정(캐시·쿠키·리디렉트 없음, 20초 응답 제한)을 쓴다. 만든 글의 ID가 없는 성공 응답은 `unexpected-response`다.
- 묶음(`MentionBundle`)
  - 상태 `posting`(게시 중)과 `posted`(게시됨)를 더했다. 게시 중은 검토 대기 목록에 남고 트레이 숫자에서 빠지며, 게시됨은 처리됨이고 되돌릴 수 없다.
  - 게시 기록 `posting: { body, sentAt, postedId }`. 게시 요청을 보내기 직전에 `body`와 `sentAt`을 먼저 적고, 성공하면 `postedId`(본문 묶음은 `commentId`, 댓글 스레드 묶음은 `replyId`)를 더한다. `state.db` 형식 12에 `posting` 열(JSON)을 더했다.
  - 게시 중 묶음은 무시·편집·받는 사람 빼기·재생성을 받지 않고, 새 멘션을 합치지 않는다. 같은 자리의 새 멘션은 새 묶음이 된다.
- 게시 본문과 [게시] 판정(`core/drafts/post-body.ts`)
  - `postableBody`: 편집기 텍스트가 비지 않고 받는 사람 표기를 포함한 게시 본문이 4,000자(`String.length`) 이하일 때의 게시 본문.
  - `isPostable`: 준비됨이고 `postableBody`가 있을 때. main의 [게시] 시작과 렌더러 스냅숏의 `canPost`가 같은 판정을 쓴다.
- 게시(`core/posting/posting.ts`의 `Posting`)
  - `post`: 준비됨 묶음을 게시 중으로 두고 시계 포트로 5초를 센다. `cancel`: 카운트다운 중에만 준비됨으로 돌린다. 확인 창은 없다.
  - 5초가 지나면 보내기 전 기록 → 본문 묶음(`remarkId`가 `-1`)은 새 댓글, 댓글 스레드 묶음은 대댓글 → 성공하면 게시됨과 `postedId` 기록.
  - 로그에는 묶음 ID와 결과 종류만 남기고 게시 본문과 예외 문구는 남기지 않는다.
- 화면
  - 준비됨 바닥 줄 오른쪽에 재생성 메뉴와 [게시]. `canPost`가 거짓이면 [게시]를 끈다.
  - [게시]를 누르면 다음 준비된 묶음으로 넘어가고, 창 아래에 "5초 뒤 게시합니다: 김철수님 멘션 · 취소" 토스트가 뜬다. 토스트는 main의 묶음 상태를 따르므로 다른 묶음을 보거나 창을 바꿔도 카운트다운 동안 보인다. [취소]를 누르면 그 묶음으로 돌아간다.
  - 게시 중 묶음을 보면 "게시 중" 태그와 바닥 줄에 남은 초와 [취소]만 있다. 게시 요청을 보낸 뒤에는 "게시 결과 확인 중입니다."와 꺼진 [게시]만 있다.
  - 넘어갈 묶음: 대기열에서 떠나는 묶음 뒤의 첫 준비됨·저장소 확인 필요 묶음, 뒤에 없으면 앞에서 찾고, 그것도 없으면 바로 뒤·앞 묶음이다. 무시도 같은 규칙을 쓴다.
  - 토스트 여러 개(카운트다운, 무시)를 쌓을 수 있게 토스트 자리(`.toast-stack`)를 두었다.

**스펙과 다르거나 스펙에 없던 결정** (검토 대상)

- 게시 실패 상태(44)가 생기기 전의 임시 처리
  - 처리되지 않은 것이 확실한 실패(`429`, `4xx` 거절)는 준비됨으로 돌리고 게시 기록을 지운다. `401`은 "키 확인 필요"도 알린다.
  - 올라갔는지 알 수 없는 실패(응답 없음, `5xx`, 만든 글의 ID가 없는 성공 응답, 예외)는 보내기 전 기록을 둔 채 게시 중("게시 결과 확인 중", [게시] 꺼짐)으로 둔다. 다시 게시하면 중복 댓글이 남을 수 있기 때문이다. 44의 내용 일치 확인이 이 상태를 게시됨이나 게시 실패로 정해야 한다.
- 이 PC가 게시한 글의 답 범위
  - 스펙 4절은 "게시를 누를 때 조회한 내용에 있던 멘션에만" 답한 것으로 본다. 그 조회(46)가 아직 없어 "그 글을 올린 묶음의 멘션에만" 답한 것으로 보고 다른 묶음의 이미 답함 판정(감지, 초안 실행 직전)에서 뺀다.
  - 넣지 않으면 카운트다운 중 새 묶음이 된 멘션이 게시 직후 바로 이미 답함으로 숨어, 체크리스트의 "새 묶음이 된다"가 의미를 잃는다.
  - 같은 댓글 스레드에 열린 묶음이 둘(되돌린 묶음과 새 묶음 등)일 때는 스펙과 결과가 다를 수 있다. 45·46에서 조회한 내용으로 바꿀 때 `MentionBundles.notPostedByOtherBundles`를 고친다.
- [게시]를 누르면 main이 받아들였는지 기다리지 않고 다음 묶음으로 넘어간다. 렌더러는 `canPost`일 때만 [게시]를 켜므로 거절되는 경우는 그사이 상태가 바뀐 드문 경우뿐이다.
- "다음 준비된 묶음"을 준비됨·저장소 확인 필요로 보고, 없으면 예전처럼 바로 뒤·앞 묶음으로 넘어간다. 무시에도 같은 규칙을 적용했다.
