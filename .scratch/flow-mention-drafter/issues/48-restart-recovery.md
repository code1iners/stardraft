# 48: 다시 켜기

**Spec:** [스펙](../spec.md) 12절 "끌 때", "다시 켤 때", 8절 상세 머리 문구

**What to build:** 앱을 껐다 켜면 생성 중이던 묶음이 원래 순서로 대기열에 돌아와 처음부터 실행된다. 카운트다운 중에 꺼졌으면 게시하지 않고 준비됨으로 돌아오며 "앱이 꺼져서 게시하지 않았습니다"가 보인다. 게시 응답을 못 받고 꺼졌으면 "게시 결과 확인 중"으로 두고 첫 조회 뒤 게시됨 또는 게시 실패로 정한다. 편집 중이던 초안은 그대로 보인다.

**Blocked by:** 37, 44

**Status:** resolved

- [x] 끊긴 실행은 "앱 종료로 중단"으로 기록하고 자동 재시도 1회에 세지 않으며, 다시 켜면 맨 앞에서 처음부터 돈다. 생성 직전 이미 답함 확인을 거친다.
- [x] 카운트다운 중 종료 → 준비됨, 조회한 내용 버림, 안내 한 줄.
- [x] 보내기 전 기록만 있고 결과가 없는 묶음 → 게시 중("게시 결과 확인 중", 게시 버튼 막음) → 44의 내용 일치 확인으로 게시됨 또는 게시 실패("앱이 꺼져서 게시하지 못했습니다"). 조회 실패면 다음 폴링에서 다시.

  - 순서: 폴링과 보관 정리 예약을 멈춘다 → 초안 대기열과 게시를 함께 멈춘다 → 묶음 저장 줄이 빌 때까지 기다린다(`MentionBundles.whenIdle`).
  - 초안 대기열(`DraftQueue.stop`)
    - 실행을 끊어 프로세스 트리를 끝낸다. 끊은 실행은 실행 기록에 결과 `app-quit`("앱 종료로 중단")으로 남는다. 묶음은 생성 중으로 둔다.
    - 그 기록이 남기를 최대 5초 기다린다(시계 포트).
  - 게시(`Posting.stop`)
    - 카운트다운과 기다리던 일(`429` 뒤 다시 보내기, 다시 확인)을 지운다. 카운트다운 중이던 묶음은 게시 중으로 남는다.
    - 보낸 게시 요청의 응답과 그 기록을 최대 5초 기다린다. 그래도 없으면 보내기 전 기록을 둔 채 끝낸다.
  - 편집기는 친 글자마다 `edit-draft`로 저장하므로, 끌 때는 그 저장이 끝나기를 기다린다.
- 초안 대기열의 순서
  - 대기열(실행 중인 묶음은 맨 앞 `resume`, 그 뒤 기다리는 묶음과 자리)을 바뀔 때마다 `state.db`에 남긴다.
  - 그래서 끌 때의 정리 없이 꺼져도(강제 종료, Windows 종료·로그아웃) 다시 켤 때 같은 순서로 돈다.
  - 다시 켜면 `DraftQueue.start()`가 남긴 순서와 자리 그대로 먼저 넣고, 남긴 것에 없는 생성 중 묶음은 작은 창 순서로 끝에 넣는다.
  - 실행은 처음부터 하고, 재시도 횟수는 새로 센다. 생성 직전 확인(`prepareRun`)이 꺼져 있던 사이의 내 답을 찾아 "이미 답함"으로 옮긴다.
- 다시 켤 때(`MentionBundles.recoverAfterRestart`, 저장한 묶음을 읽은 직후)

  - 보내기 전 기록만 있고 결과가 없는 게시 중 묶음마다 44의 내용 일치 확인(`checkOutcome`)을 돌린다.

  - 조회하지 못하면 게시 중으로 둔 채 60초 뒤 다시 확인한다. 다시 확인해도 사유는 `app-quit`이다.

**사용자가 확인할 항목** (실제 앱·OS·CLI가 필요해 코드로 확인하지 못함. 실제 확인은 59·60에서)

- 실제 앱에서 생성 중에 트레이 "종료"·Cmd+Q로 끄면 확인 창 없이 몇 초 안에 끝나고, `claude` 프로세스가 남지 않는지
- 다시 켜면 그 묶음이 "차례를 기다리는 중"에서 먼저 도는지
- 카운트다운 중에 끄고 켜면 상세 머리에 "앱이 꺼져서 게시하지 않았습니다"가 보이는지
- 편집기에 친 마지막 글자가 다시 켠 뒤에도 남는지(마지막 입력이 끄기 전에 main에 닿는지)

**스펙과 다르거나 스펙에 없던 결정** (검토 대상)

- "원래 순서": 끌 때의 대기열(자리 포함)을 그대로 복원한다. 37은 다시 켤 때 모두 작은 창 순서로 넣었다.
- 대기열은 바뀔 때마다 남긴다. Windows 종료·로그아웃에서는 `before-quit`이 오지 않기 때문이다.
- "앱 종료로 중단" 기록은 끌 때의 정리를 거친 경우에만 남는다. 강제 종료·Windows 종료에서는 실행 기록이 없고 순서만 유지된다.
- 끊은 실행의 기록을 최대 5초 기다린다(스펙에 없음).
  - 게시 응답 대기와 함께 돌아 전체는 약 5초 안이다.
  - Flow 조회 중에 끊긴 생성은 기록할 실행이 없어 기다리지 않는다.
  - 5초를 넘겨 늦게 끝난 기록이나 게시 결과는 `state.db`를 닫은 뒤라 로그만 남는다. 게시는 다시 켤 때 확인으로 회복된다.
- 결과 모름 확인
  - 조회 실패면 44대로 60초 타이머로 다시 확인한다. 스펙의 "다음 폴링에서"와 간격은 같다.
  - 다시 조회했을 때 자리가 지워졌거나 볼 수 없으면 44대로 "글이나 댓글이 지워졌습니다"·"이 글에 댓글을 쓸 권한이 없습니다"다. 스펙 12절은 "앱이 꺼져서 게시하지 못했습니다" 하나만 적었지만, 원인을 더 정확히 알리는 쪽을 택했다.
- "앱이 꺼져서 게시하지 않았습니다" 표시
  - 준비됨일 때만 보인다.
  - 다시 [게시]를 누르면(취소해도) 지운다. 다시 만들거나, 처리됨에서 되돌려도 지운다.
  - 손댄 초안에 새 멘션이 합쳐져도 그대로 둔다.
- "게시 결과 확인 중"은 8절대로 상세 머리에 두고, 43의 바닥 줄 문구는 빼서 겹치지 않게 했다.
- 시험 묶음
  - 49가 아직 없어 묶음의 `trial` 표시와 `StateStore.deleteBundles`를 먼저 더했다.
  - 시작할 때 `trial`인 묶음을 모두 지운다. 끝낸 시험 묶음은 이미 지워졌으므로 남은 것은 진행 중이던 것이다.
