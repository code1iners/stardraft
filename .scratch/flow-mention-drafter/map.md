## Destination

스펙이 다루는 대상은 두 가지다.

- **트레이/메뉴바 데스크톱 앱**(미서명 dmg/exe)

스펙만 보고 티켓을 나눠 바로 구현에 들어갈 수 있으면 도착이다.

### 차팅 중 확정된 전제

티켓 없이 정한 사항이다. 바꾸려면 지도를 다시 그려야 한다.

- **사용자**: 내가 먼저 써 보고, 괜찮으면 팀원에게 배포한다. 배포는 dmg/exe를 내려받는 웹사이트로 한다.
- **플랫폼**: Mac과 Windows 둘 다 지원한다. MVP 검증은 Mac에서 하고, 기술 선택은 Windows에서도 동작하는 것으로 한정한다.
- **앱 형태**: 트레이/메뉴바 데스크톱 앱. 돈이나 신원 확인이 드는 서명은 하지 않고, 설치할 때 뜨는 경고는 사용자가 동의하고 넘어간다.
  - macOS는 번들 전체에 ad-hoc 서명을 한다. 무료이고, Apple Silicon에서 실행하려면 필요하다.
  - 자세한 내용은 [서명 정책 재검토](issues/10-signing-policy-review.md)에 있다.
- **감지**: 개인 API 키로 폴링한다. 허용 지연은 1~5분이다.
- **감지 범위**: 업무에서 나를 `@`로 직접 지목한 멘션만 감지한다. 채팅 멘션은 MVP에서 뺐다(Out of scope 참고).
- **에이전트**: 내 PC에 설치된 CLI를 비대화형으로 호출한다. 실행기는 교체할 수 있게 만든다.
- **안전 장치**: 에이전트는 읽기 전용으로 실행하고, 비밀 파일은 탐색에서 뺀다. 초안은 반드시 사람이 검토한다.
- **저장소 선택**: 직접 등록한 저장소 매핑을 먼저 쓴다. 매핑이 없으면 에이전트가 작업 폴더에서 저장소를 고른다.
- **맥락과 생성**: 에이전트에게 게시물 본문과 댓글 스레드를 맥락으로 준다. 초안은 자동으로 생성하고, 요구와 근거를 함께 표시한다.
- **알림**: 초안이 준비되면 OS 알림을 띄우고, 알림을 클릭하면 검토 화면이 열린다.
  - macOS에서는 ad-hoc 서명한 Electron 44 앱으로 알림 표시와 클릭 전달을 확인했다([미서명 앱 macOS 실기 검증](issues/11-tauri-macos-unsigned-check.md)). Windows는 아직 확인하지 않았다.
- **데이터 반출**: 회사 코드와 Flow 메시지를 에이전트 제공사로 보내는 것은 기존 Claude Code/Codex 사용 범위 안에서 허용된 것으로 본다.

- [CLI 에이전트 비대화형 실행 능력 조사](issues/02-cli-agent-headless-research.md): Claude Code(`claude -p --json-schema`)와 Codex(`codex exec --output-schema`) 모두 비대화형 구조화 출력과 읽기 전용 실행이 되지만, 비밀 파일 제외는 Codex에서 베타 기능에 의존하고, `claude -p`는 저장소 훅을 막는 플래그가 필수다.
- [트레이 데스크톱 앱 프레임워크와 미서명 배포 조사](issues/03-tray-app-framework-research.md): 미서명 전제에서는 Tauri v2가 유리하다(Electron 42 이상은 macOS 알림과 로그인 항목에 서명이 필요하다). 다만 Tauri의 macOS 알림 클릭은 폐기 예정 API에 기대 실기 검증이 필요하고, Apple Silicon에는 ad-hoc 서명이 필수이며, Windows 스마트 앱 컨트롤이 켜진 PC에서는 미서명 앱이 실행되지 않는다.
- [Flow 알림 API 실호출로 멘션 데이터 확인](issues/01-flow-alarm-api-check.md): 업무 멘션 알림은 `mentionYn`으로만 구분되고(`alarmType`은 `null`), `@전체`도 섞여 온다. 그래서 게시글·댓글의 `@[이름](ID)` 표기에 내 ID가 있는지로 걸러야 한다. 게시글·댓글 API로 맥락을 가져올 수 있지만, 대댓글이 10개를 넘으면 대댓글 API로 페이지를 더 넘겨야 한다. GET 조회는 읽음 상태를 바꾸지 않는다. 채팅 멘션 확인은 구현 후로 넘겼다.
- [초안 검토 화면 프로토타입](issues/04-draft-review-prototype.md): 트레이 아이콘을 누르면 멘션을 하나씩 보는 작은 창이 뜨고, "펼쳐 보기"로 목록+상세 창이 된다. 근거는 코드 대신 자연어 설명과 파일·줄 위치로 보여 주고, 초안 문장마다 근거 번호를 붙인다. 초안과 근거 설명은 개발자가 아닌 사람도 이해할 수 있는 쉬운 말로 쓴다. 재생성은 요구 고치기, 지시 덧붙이기, 저장소 바꾸기로 한다. 게시는 5초 동안 취소할 수 있고, 게시하거나 무시하면 다음 멘션으로 넘어간다. 알림 없이도 트레이 아이콘의 숫자와 점으로 찾아온다.
- [저장소 매핑과 자동 선택 규칙 결정](issues/06-repo-mapping.md): Flow 프로젝트 하나에 저장소를 여러 개 연결하고, 모두 읽기 범위로 넘긴다. 매핑이 없으면 앱이 작업 폴더에서 찾은 git 저장소 후보 중에서 선택 실행이 1~3개를 고르고, 그다음 초안 실행을 돌린다. 확신하지 못하거나 코드와 무관한 멘션, 매핑된 폴더가 없는 경우는 초안 없이 "저장소 확인 필요" 상태로 올린다. 자동 선택 결과는 사용자가 연결 버튼을 누를 때만 매핑으로 저장한다. 작업 폴더는 여러 개 둘 수 있고, 설정은 PC마다 따로 두며, 네트워크·WSL 경로는 받지 않는다.
- [에이전트 실행 계약 결정](issues/07-agent-run-contract.md): 쓰기·명령 실행·웹 접근 차단, 읽기 범위 제한, 비밀 파일 차단을 모두 강제할 수 있는 실행기만 쓴다. 지금은 Claude Code만 해당하며(필수 플래그 묶음 고정, `stream-json` 출력), Codex는 [비밀 파일 제외 실측](issues/13-secret-exclusion-check.md) 결과로 정한다. 지침은 시스템 프롬프트 자리에, Flow 내용은 stdin의 데이터 구획에 넣는다. 초안 실행은 요구, 문장별 근거 번호를 단 문단, 근거(저장소·경로·줄과 설명)를 출력한다. 선택 실행도 같은 계약을 따른다. 실행은 한 번에 하나이고 10분 제한이며, 내용 불일치는 앱이 고쳐서 보여 주고 문체 위반은 경고로 표시한다.
- [멘션 감지 방식 결정](issues/05-mention-detection.md): 60초마다 `filters=MENTION`으로 읽은 알림까지 조회하고, 이미 본 가장 큰 `alarmId`를 기준점으로 저장한다. 멘션된 글을 직접 조회해 `@[…](내 ID)` 표기로 판정하고, 송신자가 나인 알림은 뺀다. 멘션은 멘션 위치로 식별한다. 같은 댓글 스레드나 같은 본문의 미처리 멘션은 멘션 묶음으로 합쳐 초안을 하나만 만든다. 첫 실행에는 과거 멘션을 가져오지 않고, 다시 켰을 때는 72시간 안의 멘션만 가져온다. Flow에서 이미 직접 답한 멘션은 초안 없이 "Flow에서 직접 답함"으로 둔다. 읽음 상태는 바꾸지 않는다. 맥락은 본문, 대상 댓글 스레드 전체, 다른 댓글 최근 20개이고, 초안을 만들 때마다 새로 조회한다.
- [서명 정책 재검토](issues/10-signing-policy-review.md): 돈이나 신원 확인이 드는 서명은 하지 않고, 무료 서명은 허용한다. macOS는 ad-hoc 서명이 빌드 필수 단계다. 자체 서명 인증서는 Electron 알림을 살릴 때만 쓴다. Windows는 미서명으로 배포하고, 스마트 앱 컨트롤이 켜진 PC는 지원하지 않는다. 설치 안내에서 SAC 상태를 확인하게 하되, SAC를 끄라고 안내하지는 않는다. 나중에 Artifact Signing을 붙일 수 있도록 빌드에 서명 자리를 둔다. 업데이트 때마다 다시 뜨는 SmartScreen 경고와 Keychain 재허용은 감수한다.
- [미서명 앱 macOS 실기 검증](issues/11-tauri-macos-unsigned-check.md): macOS 27, Apple Silicon에서 ad-hoc 서명한 Electron 44 앱으로 네 가지를 확인했다. 브라우저로 받은 DMG는 "손상됨"이 아니라 "열지 않음 → 그래도 열기" 경로로 열리고, 알림 표시, 클릭 전달(배너와 알림 센터 모두), 로그인 시 자동 시작(`setLoginItemSettings`)이 모두 동작했다. 그래서 알림과 자동 시작은 더 이상 Tauri가 앞서는 근거가 아니며, Tauri는 실기 검증하지 않았다.
- [초안 게시 위치와 형식 결정](issues/12-post-placement.md): 본문 묶음은 새 댓글로, 댓글 스레드 묶음은 그 댓글에 대댓글로 게시한다. 게시 본문은 받는 사람(묶음에 남은 멘션의 송신자 전원, 검토 화면에서 뺄 수 있음)의 `@[이름](ID)` 표기 뒤에 편집기 텍스트를 그대로 잇고, 근거·근거 번호·AI 표시는 넣지 않는다. 게시 실패는 별도 상태로 사유와 함께 알리고, 자동 재시도는 `429`일 때만 한다. 응답이 없으면 실제로 올라갔는지 다시 조회한다. REST에 댓글 수정·삭제 API가 없기 때문이다. 멘션 묶음은 1문 1답과 비교한 뒤 유지했다. 표기가 실제 멘션이 되는지 등은 [댓글 쓰기 API 실측](issues/15-comment-write-api-check.md)에서 확인한다.
- [게시 전 스레드 변화 처리 결정](issues/14-thread-change-before-post.md): 사용자 행동을 기다리는 묶음은 60초 폴링마다, 그리고 게시를 누를 때 다시 조회해 초안을 만들 때의 내용과 비교한다. 멘션이 아닌 새 글과 원문 수정은 알리기만 하고, 내 답이 생기면 "이미 답함"(05의 "Flow에서 직접 답함"을 대체), 멘션이 모두 사라지면 "원문 사라짐"으로 처리됨에 옮기며 초안은 보존한다. 게시를 누를 때 화면에 없던 변화가 있으면 멈추고, 이 PC가 올린 글은 그때 조회한 멘션까지만 답한 것으로 본다. 되돌린 묶음은 같은 이유로 다시 옮기지 않는다. 맥락은 30,000자 상한을 두고 다른 댓글부터 뺀다.
- [댓글 쓰기 API 실측](issues/15-comment-write-api-check.md): API로 올린 `@[이름](ID)` 표기는 Flow 화면에서 멘션으로 보이고, 줄바꿈과 빈 줄도 그대로 보인다. 보낸 문자열은 그대로 저장된다. 그래서 12의 게시 본문 형식을 유지한다. 받는 사람에게 알림이 가는지는 구현한 앱으로 확인한다. `contents` 4,000은 글자 단위이고, 초과하면 `400` `VALIDATION_ERROR`가 온다. 지운 댓글에 대댓글을 달면 `412` `NOT_EXISTS_ERROR`가 오고, 지운 댓글의 대댓글 목록도 `412`를 준다. 댓글 목록에 `systemCode`가 있는 시스템 댓글(제목·상태 변경)이 행동한 사람 명의로 섞여 오므로, "이미 답함" 판정에서 빼야 한다.
- [데스크톱 프레임워크와 기술 스택 결정](issues/08-desktop-stack.md): Electron + TypeScript로 만들고, UI는 React 19다. 앱 이름은 `Stardraft`(`app.squadify.stardraft`)다. 핵심 로직은 main 프로세스에서 Electron 없는 TS 모듈로 돌리고, Flow 전용 코드는 Flow 어댑터에 모은다. 데이터는 OS 표준 앱 데이터 폴더에 PC마다 따로 둔다. 설정은 `settings.json`, 상태는 better-sqlite3 `state.db`, 개인 API 키는 `safeStorage`로 암호화해 나눠 저장한다. electron-builder 26.17.0으로 macOS arm64 DMG(ad-hoc 서명)와 Windows x64 NSIS 설치 파일을 만든다. 태그를 푸시하면 GitHub Actions가 초안 Release를 만든다. 앱 코드는 회사 데이터가 없는 개인 계정의 새 저장소 `stardraft`(MIT)에 둔다. 처음에는 비공개로 시작하기로 했으나, 다운로드 사이트 형태 결정에서 처음부터 공개하기로 바꿨다.
- [앱 내 업데이트 가능성 조사](issues/20-in-app-update-research.md): Windows는 미서명 그대로 electron-updater로 조용히 설치하고 다시 실행할 수 있다(소스 근거, 실기 미확인). macOS는 조건부로 가능하다. 기본 ad-hoc 서명은 Squirrel.Mac 검증에서 거부되고, 최상위 번들만 `identifier` 명시 DR로 다시 서명하면 통과한다(실측). 실제 설치·재실행은 실험이 남았다. 업데이트가 Gatekeeper·SmartScreen 확인 없이 퍼지므로 앱이 Ed25519 서명을 직접 검증해야 한다.
- [다운로드 사이트 UI/UX 사례 조사](issues/18-download-site-ux-research.md): 10곳(Raycast, Rectangle, Maccy, Espanso, Stretchly, Flameshot, AeroSpace, Cursor, LM Studio, Zed)을 봤다. 감지한 OS의 대표 버튼과 지원 환경 한 줄이 공통이다. 대화상자 재현, 설치를 설명하는 모션, 스마트 앱 컨트롤 안내, 업데이트 재확인 안내는 10곳 모두 하지 않아 Stardraft가 새로 채운다. 구성은 문서형, 단계 체크리스트형, 체크리스트에 대화상자 재현을 더한 안을 제안했다.
- [다운로드 사이트 형태 결정](issues/09-download-site.md): `stardraft`는 처음부터 공개 저장소(오픈소스)로 만들고, 소스·Release·`apps/site`를 함께 둔다. 사이트는 Vercel(`stardraft.squadify.app`)에 두고 누구나 받을 수 있게 열며, 회사·사람 이름은 넣지 않는다. `/download/<os>`와 `/api/releases`(CDN 5분 캐시) 함수가 공개 Release를 내보낸다. 초안 상태에서 내 PC에 먼저 설치해 본 뒤 직접 공개하고, immutable releases를 켠다. 이전 버전은 GitHub Release 목록으로 링크하고, 앱은 자기보다 새 데이터면 실행하지 않는다. 설치 안내에서 `xattr`와 연락 절차는 빼고, 막히는 화면 네 곳에 스크린숏을 넣는다. 스마트 앱 컨트롤이 켜진 경우는 실행되지 않는다는 사실만 알린다. 앱 내 업데이트는 범위 안으로 옮기고 첫 버전부터 넣는다. 화면은 상호작용과 장식 연출을 모두 쓰되 "동작 줄이기" 설정을 지키며, 자세한 모습은 프로토타입 티켓에서 정한다.
- [다운로드 사이트 화면 프로토타입](issues/19-download-site-prototype.md): 왼쪽 목차가 있는 한 페이지 문서로 만들고, 모든 설치 단계에 눌러 볼 수 있는 예시 화면(HTML 재현)을 넣는다. 막히는 네 곳은 실제 스크린숏을 먼저 보여 주고 예시로 바꿀 수 있다. 재현 화면은 "예시 화면" 띠와 빗금 틀로 실제 창과 구분한다. 커서 이동과 강조, 첫 화면 별 아이콘 반짝임을 쓰고, "동작 줄이기"가 켜지면 모두 멈춘다. 사이트는 Astro로 만들고 상호작용하는 부분만 React로 만들며, 다운로드와 버전 정보 함수는 Astro 서버 엔드포인트다.
- [설정과 첫 실행 온보딩 결정](issues/16-onboarding.md): 시작하기 전용 창은 두지 않는다. 첫 실행에 트레이 옆 작은 창이 필수 세 가지(Flow 키, 에이전트 연결, 작업 폴더)를 보여 주고, 설정 창에서 채운다. 다 되면 [감지 시작]으로 기준점을 잡고, 그때 띄우는 알림으로 macOS 알림 권한을 묻는다. 다른 계정의 키면 확인을 받고 `state.db`를 비운다. 에이전트는 찾기·버전·로그인·작동 확인을 자동으로 돌려 연결선 그림으로 보여 주고, 실패하면 고치는 방법을 그림 카드로 보여 준다. CLI는 로그인 셸 PATH로 찾아 절대 경로를 저장하고, 모델은 선택 상자로 고른다. 키·CLI 문제는 트레이 "!"와 OS 알림 한 번으로 알린다. 지난 멘션으로 게시 없이 돌려 보는 시험을 둔다.
- [처리한 멘션의 보관 결정](issues/17-processed-retention.md): 처리됨 목록은 처리한 때부터 7일 남기고, 그동안만 되돌릴 수 있다. Flow 원문, 초안, 비교 기준, 실행 기록 같은 전체 기록은 목록에서 빠질 때 지우고, 재생성할 때는 이전 초안을 바로 지운다. `secure_delete`를 켜고 `state.db`는 암호화하지 않는다. ID와 상태만 담은 최소 기록(멘션 위치, 이 PC가 게시한 글과 그 글이 답한 멘션)은 계정을 바꿀 때까지 둔다. 대기 중인 묶음에는 기한이 없다. 다시 켜면 생성 중이던 묶음은 대기열에 다시 넣고, 카운트다운 중이던 묶음은 게시하지 않고 준비됨으로 돌린다. 응답을 받지 못한 게시는 보내기 전에 남긴 기록으로 알아채고, 그 자리에서 게시 본문과 같은 내 글을 찾아 게시됨이나 게시 실패로 정한다.
- [앱 내 업데이트 macOS 실기 검증](issues/21-in-app-update-macos-check.md): macOS 27, Apple Silicon, 관리자 계정에서 최상위 번들만 명시 DR로 다시 서명한 ad-hoc Electron 앱이 electron-updater로 업데이트되고 다시 실행됐다. Gatekeeper, 앱 수정 보호, 관리자 인증 창은 뜨지 않았고, 알림 권한과 로그인 항목은 유지됐다. Keychain만 다시 묻는다. "항상 허용"을 눌러야 다음 실행부터 묻지 않고, 사용자는 이 창을 관리자 암호 창으로 읽었다. 처음 설치한 뒤 첫 실행에는 묻지 않았다. 기본 ad-hoc 서명은 예상대로 설치 전에 거부됐고, 화면에는 아무것도 뜨지 않았다. 그래서 macOS도 앱 내 업데이트를 채택한다.

## Not yet specified

- **여러 PC에서 동시 실행**: 같은 Flow 계정으로 Mac과 Windows에서 앱을 함께 켜면, 두 PC가 같은 멘션을 각각 감지해 초안을 만들고 둘 다 게시할 수 있다. 설정과 매핑은 PC마다 따로 두기로 했다([저장소 매핑과 자동 선택 규칙 결정](issues/06-repo-mapping.md)). 막을지, 막는다면 PC끼리 처리 상태를 어떻게 알릴지 정해야 한다.
  - 게시 방식은 [초안 게시 위치와 형식 결정](issues/12-post-placement.md)에서 정해졌다. 앱이 올린 글은 묶음 자리에 놓이므로 다른 PC의 "이미 답함" 판정에 잡히고, 게시하면 `commentId`·`replyId`가 기록된다.
  - [멘션 감지 방식 결정](issues/05-mention-detection.md)에서 나온 사실이 두 가지 있다.
    - 앱이 Flow의 읽음 상태를 바꾸지 않으므로, Flow를 통해 PC끼리 처리 상태가 전해지지 않는다.
    - 한 PC가 먼저 게시하면, 다른 PC는 생성을 시작하기 직전의 직접 답 확인에서 그 게시를 내 글로 보고 걸러 낸다.
  - [게시 전 스레드 변화 처리 결정](issues/14-thread-change-before-post.md)으로, 두 PC 모두 초안이 준비된 상태여도 한쪽이 게시하면 다른 쪽이 60초 안의 폴링이나 게시를 누를 때의 확인에서 "이미 답함"으로 알아챈다. 그래서 두 번 게시되는 경우는 두 PC에서 몇 초 사이에 게시를 누를 때로 좁혀졌다.
  - 남은 문제는 두 가지다. 몇 초 사이의 중복 게시, 그리고 두 PC가 같은 멘션에 에이전트를 각각 실행해 사용량을 두 번 쓰는 것이다. 이를 막을지 정해야 한다.
  - [데스크톱 프레임워크와 기술 스택 결정](issues/08-desktop-stack.md)에서 데이터는 PC마다 로컬에 두고, 공유 저장소(Supabase 등)는 쓰지 않기로 했다. 공유 저장소로 PC끼리 처리 상태를 나누려면, Flow 글과 초안이 새 외부 서비스로 나간다. 그러려면 지도의 데이터 반출 전제를 바꿔야 한다.

## Out of scope

- **돈이나 신원 확인이 드는 서명과 공증**: Apple Developer ID와 공증, Windows Artifact Signing과 OV 인증서가 해당한다. 설치 경고는 사용자가 동의하고 넘어간다. 무료 서명(macOS ad-hoc 서명)은 범위 안이다. 자세한 내용은 [서명 정책 재검토](issues/10-signing-policy-review.md)에 있다.
  - Windows 스마트 앱 컨트롤이 켜진 팀원 PC가 실제로 나오면 Artifact Signing 도입을 검토한다. 이 검토는 스펙 밖의 운영 판단이다. 스펙에는 서명 자리만 둔다.
- **서버형 중앙 처리**: 저장소와 에이전트가 각자의 PC에 있어서 중앙 서버로는 처리할 수 없다.
- **검토 없는 자동 게시**: 동료에게 나가는 글이므로 사람이 반드시 검토한다.
- **담당자 지정과 그룹 멘션 감지**: 잡음이 많아 멘션의 정의에서 뺐다.
- **채팅 멘션**: 2026-10-14에 사용자가 MVP에서 빼기로 했다.
  - 이유: 업무 멘션만으로 MVP를 확정하면, 알림 목록에 채팅 멘션이 들어오는지 확인하는 일을 구현 뒤로 미뤄도 비용이 거의 없다. 이 확인에는 동료의 협조도 필요하다.
  - 구현 후에 [Flow 알림 API 실호출로 멘션 데이터 확인](issues/01-flow-alarm-api-check.md)의 점검 스크립트에 `PROBE-GROUP`·`PROBE-DM` 표지 멘션을 넣어 확인한다.
  - 알림 목록에 채팅 멘션이 없으면 다른 감지 경로(Flow MCP의 `flow_search`, OS 알림 읽기)를 찾아야 한다. 이 경로 탐색도 함께 미뤘다.
