# 내 담당 신규 업무의 최초 게시글 초안 가능성 재조사

- 조사일: 2026-10-29
- 범위: Flow 공식 공개 도움말·개발자 명세 재조회, 현재 코드와 기존 마스킹 응답 검토. 인증된 실호출, 외부 업무 생성·수정, 구현 변경은 하지 않았다.
- 이전 조사: [담당자 지정 감지 검토](flow-task-assignment-detection.md). 이번 문서는 사용자가 다시 설명한 **업무 최초 게시글에 대한 초안**을 기준으로 결론을 좁힌다.

## 결론

**구현 가능한 방향이다. 생성하면서 나를 담당자로 넣은 업무와, 생성 후 나를 담당자로 추가한 업무 모두 그 업무의 제목·본문을 가져와 초안 대상으로 삼을 수 있다.** 필요한 핵심은 정확한 지정 이벤트 종류를 복원하는 것이 아니라, 대상 업무를 발견하고 현재 내가 담당자인지 확인한 뒤 업무 본문에 대한 초안을 만드는 것이다. 공개 명세의 알림·업무 목록·게시글 상세 조회와 기존 담당자 응답을 결합한 설계 판단이며, 현재 구현은 이를 지원하지 않으며, 두 시나리오의 실제 자동 감지는 아직 검증하지 않았다. [공식 게시글 명세](https://api.flow.team/docs/api/user/posts), [공식 알림 명세](https://api.flow.team/docs/api/user/alarms), [기존 응답](flow-alarm-probe-result.json)

사용자가 말한 “최초 게시글”은 **담당자 변경 알림이나 댓글이 아니라 업무를 만든 제목·본문**으로 해석한다. 조회 시점의 업무 본문을 사용하면 된다. “생성 순간의 수정 전 본문을 복원”하라는 요구로 해석하지 않는다. 공개 조회 명세는 현재 본문·작성 시각·수정 시각을 제공하지만, 과거 버전 복원 기능은 검토한 명세에서 확인하지 못했다. [공식 개인용 게시글 명세 번들](https://api.flow.team/_app/immutable/nodes/26.027ae61c.js)

**업무별 최초 초안 1회**를 권장한다. 이렇게 하면 이후 일반 댓글·상태 변경·재지정마다 같은 원문 초안을 새로 만들 필요가 없다. 이는 자동 중복 생성을 막자는 제안이며 사용자의 수동 재생성 금지를 뜻하지 않는다. 과거 업무 제외 정책까지 사용자가 승인했다는 의미도 아니다.

## 두 경우와 자기 지정

| 경우 | 조사 결과 | 남은 실제 검증 |
| --- | --- | --- |
| 업무 작성 시 나를 담당자로 넣고 등록 | 공식 도움말에 업무 등록 시 지정 담당자에게 알림을 전송한다고 명시돼 있다. 알림의 게시글 식별자로 제목·본문을 가져오는 구조가 가능하다. | 실제 `WORKER` 조회에 나타나는지, 현재 담당자 구조와 업무·게시글 식별자 매핑 |
| 업무 생성 후 나를 담당자로 추가 | 공식 API (Application Programming Interface: 프로그램 간 연동 인터페이스)가 기존 업무 담당자 변경을 지원한다. 업무가 생성 후 지정되더라도 게시글 상세를 조회해 본문을 대상으로 삼을 수 있다. | 지정 변경의 알림 발생·지연·형태는 문서만으로 확정되지 않는다. 목록 조회 보완 시 실제 담당자 판별 검증 |
| 내가 업무를 만들면서 나 자신을 담당자로 지정 | 목록에서 현재 담당 업무를 확인하는 방식이라면 본인 작성 여부 때문에 제외할 이유가 없다. | 자기 자신이 수행한 생성·지정에도 내 알림이 생기는지는 미확인이다. 기존 `sent-by-me` 멘션 필터를 재사용하면 누락된다. |

첫 행의 알림 근거는 [업무 게시물 공식 도움말](https://support.flow.team/ko/flow/task), 두 번째 행의 변경·조회 근거는 [개인용 게시글 명세](https://api.flow.team/docs/api/user/posts)다. 자기 지정 지원은 이 명세로부터의 설계 추론이며, 현재 제외 동작은 [mention-judgement.ts](../../../apps/desktop/src/core/flow/mention-judgement.ts)의 `judge`에서 확인했다.

## 공식 명세에서 확인한 수집·조회 수단

### 알림으로 후보를 빠르게 발견

`GET /user/alarms?filters=WORKER`를 사용할 수 있다. 알림에는 `projectId`, `postId`, `alarmId`, `workerYn` 등이 있다. `workerYn`의 의미는 내 담당 업무 알림이며, 반드시 신규 지정 이벤트라는 뜻은 아니다. 따라서 알림은 **업무를 발견하는 계기**로 사용하고, 알림 문구 자체를 초안 대상으로 삼지 않는 것이 적합하다. 읽은 알림을 일괄 배제하면 사용자가 Flow에서 먼저 읽은 업무를 놓칠 수 있으므로 읽음 여부에 의존하지 않는 수집이 필요하다. [공식 알림 명세 번들](https://api.flow.team/_app/immutable/nodes/19.d44ad53c.js)

이전 조사에서 “일반 알림과 정확한 지정 이벤트를 구분해야 진행할 수 있다”고 제시한 조건은 이번 목표에는 지나치게 강하다. 아래의 신규 업무 범위와 업무별 처리 기록이 있으면, 일반 댓글 알림으로 발견했더라도 **아직 처리하지 않은 적격 업무 본문**을 대상으로 삼을 수 있다. 다만 신규 업무 범위를 정하지 않고 `WORKER`의 첫 관측만 사용하면, 예전부터 담당하던 업무의 새 댓글로 초안을 만들 수 있다. 이는 명세와 중복 정책에서 도출한 설계상 위험이다.

### 업무 목록으로 알림 의존을 보완

`GET /user/posts/projects/{projectId}/tasks/filter`는 참여 프로젝트의 업무 목록을 반환한다. 응답에 `taskId`, `postId`, `projectId`, `columns`, `hasNext`, `lastCursor`가 있다. 따라서 알려진 대상 프로젝트의 업무를 주기적으로 확인하고 상세 조회로 담당자를 판별하는 보완 경로가 가능하다. 이 방식은 자기 알림이 없는 경우에도 활용할 수 있지만, 실제 해당 업무가 목록과 상세에 노출되는지는 검증해야 한다. [공식 개인용 게시글 명세 번들](https://api.flow.team/_app/immutable/nodes/26.027ae61c.js)

필터 `filterRecords`는 컬럼 식별자·연산자·값을 받는다. 공개 예시는 상태 필터이며, **담당자 전용 `workerId` 쿼리나 담당자 컬럼의 확정된 필터 예시를 확인하지 못했다.** 따라서 “내 업무만 서버에서 바로 조회 가능하다”고 단정하지 않는다. 초기 검증은 목록 조회 후 상세 담당자 확인으로 할 수 있고, 담당자 필터 최적화는 컬럼 구조 확인 이후의 일이다. 같은 명세의 `updatedSince`는 페이지별 수정 시각 필터이며, 완전한 변경 이력·스냅샷이 아니다. 조회 중 페이지 간 중복·누락 가능성이 명시되어 있고, 빈 페이지여도 `hasNext`가 참이면 계속 조회해야 한다. 수정 시각 필터만으로 무누락 감지를 보장할 수 없다. [공식 개인용 게시글 명세 번들](https://api.flow.team/_app/immutable/nodes/26.027ae61c.js)

### 제목·본문과 현재 담당자를 확인

`GET /user/posts/{postId}`에는 `title`, `content`, `htmlContent`, `registeredDateTime`(작성 일시), `editedDateTime`(수정 일시), `tasks`가 문서화되어 있다. 다만 `tasks` 내부 상세 필드는 공개 명세에서 원본 배열로만 설명한다. 기존 마스킹 응답에는 `tasks[].TASK_SRNO`와 `tasks[].WORKER_REC[].WORKER_ID`가 있다. 현재 담당자 확인의 구체적 근거는 있지만, 최신 서버의 모든 업무 유형에서 동일하다고 확정할 수 없다. [공식 개인용 게시글 명세 번들](https://api.flow.team/_app/immutable/nodes/26.027ae61c.js), [기존 응답](flow-alarm-probe-result.json)

## “새로운 업무”의 범위

아래는 선택 가능한 정책이며 이번 조사에서 확정하지 않는다.

| 해석 | 판정 방향 | 주의점 |
| --- | --- | --- |
| 기능을 켠 뒤 새로 생성된 업무 | 게시글 `registeredDateTime`이 활성화 기준 이후이고 현재 내가 담당자일 때 처리 | 생성 후 늦게 나를 지정해도 대상이다. 과거 생성 업무에 신규 지정되는 경우는 제외된다. 서버 작성 시각의 시간대와 경계를 확인해야 한다. |
| 나에게 새롭게 배정된 업무 | 최초 동기화에서 현재 내 담당 목록을 기준 상태로 저장한 뒤, 이후 처음 내 담당으로 관측되는 미처리 업무를 처리 | 오래전에 생성된 업무도 이후 나에게 배정되면 포함된다. 정확한 지정 순간을 보장하는 방식은 아니며, 조회 사이에 지정·해제가 끝나면 놓칠 수 있다. |

“새로운 업무”라는 표현에 가장 좁게 맞는 출발점은 첫 번째지만, 사용자의 기존 업무 신규 배정까지 제외하겠다는 동의를 받은 것은 아니다. 어느 정책이든 **처음 본 알림 시간과 업무 생성 시간을 같다고 취급하면 안 된다.** 작성 시각은 상세 조회 필드이며 알림 시각은 해당 알림의 시각이다. [게시글 명세 번들](https://api.flow.team/_app/immutable/nodes/26.027ae61c.js), [알림 명세 번들](https://api.flow.team/_app/immutable/nodes/19.d44ad53c.js)

## 현재 Stardraft와 연결하는 최소 설계

아래는 구현안 검토이며 코드 변경이나 제품 결정의 승인을 뜻하지 않는다.

1. `WORKER` 알림으로 업무 후보를 모으고, 대상 프로젝트 업무 목록을 보완 조회한다. 목록 경로에서는 `taskId`와 `postId`를 함께 확보하며 둘이 같다고 가정하지 않는다.
2. 현재 담당자에 내 계정이 있는지와 신규 업무 범위를 확인한다. 담당자 필드 조회 실패는 미담당으로 확정하지 않고 재시도 대상으로 둔다.
3. 계정·프로젝트·업무 식별자 단위로 초기 초안 처리 기록을 유지한다. 알림 식별자는 수집 중복 제거에 사용하되, 업무별 1회 여부를 알림 식별자로 판정하지 않는다. 처리 실패 후 재시도가 가능하도록 발견·진행·완료 상태를 구분한다.
4. 대상은 업무 제목·본문으로 고정한다. 댓글은 보조 맥락으로 전달할 수 있지만 신규 댓글 때문에 초기 업무 초안을 다시 만들지는 않는다. 기존 직접 멘션 응답은 별도 흐름으로 유지하며, 동일 본문에서 멘션과 할당 후보가 겹칠 때 한 초안으로 합칠지는 구현 전에 정한다.
5. 기존 저장소 연결·코드 확인·초안 생성·검토 흐름을 연결한다. 이번 사용자 요구는 초안을 받아보는 데까지이며 댓글 자동 게시나 코드 자동 수정의 승인이 아니다.

현재 `http-flow-api.ts`는 `MENTION` 알림만 조회한다. `mention-judgement.ts`는 본인이 보낸 알림과 직접 멘션이 없는 본문을 제외한다. `bundle-context.ts`도 직접 멘션 존재를 다시 검사한다. `draft-input.ts`는 마지막 멘션을 답변 대상으로 안내한다. 따라서 알림 필터만 추가해서는 업무 본문 초안으로 이어지지 않고, **담당 업무용 판정·대상 입력을 분리**해야 한다. 기존 맥락 구조에는 `post`와 `otherComments`가 있어 본문과 보조 댓글을 나눠 전달할 수 있다. [http-flow-api.ts](../../../apps/desktop/src/core/flow/http-flow-api.ts), [mention-judgement.ts](../../../apps/desktop/src/core/flow/mention-judgement.ts), [bundle-context.ts](../../../apps/desktop/src/core/flow/bundle-context.ts), [draft-input.ts](../../../apps/desktop/src/core/drafts/draft-input.ts)

현재 중복 판정은 `hasMentionLocation`에 의존하는 멘션 위치 기준이다. 이를 담당 업무의 최초 처리 기록으로 그대로 사용하면 다른 의미가 섞이므로 계정·프로젝트·업무 단위 기록이 필요하다는 설계 판단이다. [mention-detection.ts](../../../apps/desktop/src/core/detection/mention-detection.ts)

## 가장 작은 검증과 완료 경계

우선 사용자가 이미 접근 가능한 실제 사례를 읽기 전용으로 확인하면 된다. 새 업무를 외부에 만들거나 담당자를 조작하는 실험은 이번 조사에서 실행하지 않았다.

| 확인 사례 | 필요한 증거 |
| --- | --- |
| 생성 시 나 지정 | `WORKER` 알림 또는 목록에서 발견, 업무·게시글 식별자, 현재 담당자, 제목·본문 |
| 생성 후 나 추가 | 동일 업무 본문을 조회할 수 있음, 알림이 없어도 목록 조회로 발견 가능한지 |
| 본인이 생성하고 자기 지정 | 자기 알림 유무 및 목록 조회 가능 여부, 자기 작성 제외 필터 없이 처리 가능 |
| 이미 처리한 업무의 댓글·상태 변경 | 같은 업무 키를 재사용하고 초기 초안을 중복 생성하지 않음 |
| 예전부터 내 담당인 업무의 새 댓글 | 선택한 신규 업무 범위에 따라 의도대로 제외되거나 포함됨 |
| 멘션과 담당 지정 동시 발생 | 초기 본문 초안이 의도치 않게 두 개 생기지 않음 |

실제 담당자 필드와 두 생성·지정 사례를 확인하면 구현을 구체화할 수 있다. **“담당자 변경 이벤트를 완벽히 구별할 수 없으므로 본문 초안도 불가능하다”는 결론은 맞지 않는다.** 반대로 공개 명세만으로 모든 지정 사건의 즉시·무누락 감지를 보장할 수도 없다. 조회 주기·프로젝트 접근 범위·일시적 지정 및 해제에 따라 감지 경계가 남는다. 담당자 식별을 안정적으로 검증하지 못하면 자동 초안 대상으로 확정하지 않고, 목록 조회 범위·빈도는 호출 제한과 실제 비용을 본 뒤 정하는 것이 적절하다. 이번에는 무료 사용 조건이나 모든 참여 프로젝트 전량 조회의 비용을 확인하지 않았으므로, 목록 보완만으로 안정성을 무조건 보장하지 않는다.
