# 01: Flow 신규 배정 판별 근거 검증

Status: needs-info
Blocked by: 없음 (즉시 착수 가능)

**What to build:** 생성 시 지정과 생성 후 지정된 업무를 실제로 발견하고, 현재 담당자·배정 시점·완료 상태를 확인할 수 있다는 근거를 확보한다. 자동 초안이 잘못된 업무를 대상으로 삼지 않도록 구현 전 판별 계약을 검증하는 선행 티켓이다.

스펙: [담당 업무 최초 초안](../spec.md)
연결 요구: Q1, Q4, Q9, Q10 및 스펙의 실제 Flow 검증 경계.

- [ ] 접근 가능한 실제 사례에서 생성 시 나 지정과 생성 후 나 추가를 각각 확인하고, 관측 날짜·조회 방법·결과를 기록한다. 실제 사례를 확인하지 못한 것을 문서나 가짜 응답만으로 통과시키지 않는다.
- [ ] 업무와 게시글 식별자의 관계, 업무 작성자, 현재 담당자 배열과 복수 담당자 표현을 확인한다. 두 식별자가 같다고 가정하지 않는다.
- [ ] 담당 업무 알림과 일반 변경 알림을 비교하고, 알림만으로 신규 배정을 단정하지 않는 발견·판정 방법을 정리한다.
- [ ] 기능 시작 전 담당 업무를 기준 상태로 구분하는 방법과 이후 새 배정을 발견하는 방법을 확인한다. 초기 조회 도중 발생하는 배정과 불완전한 조회의 처리 경계를 기록한다.
- [ ] 배정 이후 작성한 내 댓글을 판정할 수 있는 시각 근거와 시간대를 확인한다. 최초 관측 시각·업무 작성 시각을 실제 배정 시각으로 대체하지 않는다.
- [ ] 완료 여부와 담당 해제의 실제 표현을 확인한다. 사용자 정의 상태 이름만으로 완료를 판정하지 않는다.
- [ ] 알림 누락 보완이 필요하면 프로젝트 업무 목록의 접근 범위·쪽 나눔·담당자 확인·호출 비용과 한계를 검증하고 수집 방안을 정리한다.
- [ ] 계정 비밀값과 업무 내용을 가린 최소 응답 사례를 확보한다. 기존 Flow 어댑터 검증 구조에서 재사용할 수 있게 정상·누락·불명확한 응답을 구분한다.
- [ ] 조회 실패와 담당자 정보 부재를 구분한다. 합의된 판별이 불가능하면 미확인 항목과 대안을 보고하고, 제품 기준을 임의로 완화하거나 이 티켓을 완료 처리하지 않는다.
- [ ] 외부 업무 생성·변경·게시는 이 티켓만으로 실행 승인된 것으로 보지 않는다. 가능한 읽기 전용 사례부터 검증하고 추가 외부 조작이 필요하면 실행 범위를 확인한다.

## Comments

### 2026-10-29 — 읽기 전용 실제 화면 조사

**부분 확인이며 완료 아님.** 열려 있던 로그인된 Flow 웹 화면을 읽어 생성 후 본인 추가 사례를 확인했다. 공개 API (영문 원문: Application Programming Interface: 프로그램 간 연동 인터페이스) 실응답은 이번에 확보하지 못했다. 현재 셸의 `FLOW_API_KEY`와 `FLOW_PERSONAL_API_KEY`는 모두 없었다. 기존 앱의 암호화된 키를 추출하지 않았으며, 사용 가능한 인증 경로를 사용자에게 요청했다. 업무 생성·담당 변경·댓글 게시·읽음 처리 호출은 실행하지 않았다.

#### 실제 관측 A: 생성 후 본인 추가

- 관측일: 2026-10-29, 기존 Chrome의 `https://flow.team/main.act?detail#` 업무 상세 및 피드에서 화면 접근성 트리를 읽었다. 기존에 열려 있던 업무를 그대로 관측했다.
- 아래는 화면 관측을 가린 기록이다. API 응답이나 자동 테스트용 원본 응답으로 취급하지 않는다. 사람은 `작성자 A`, `담당자 B/C`, `본인`, `변경자 D`로 가렸고 업무 제목·본문·답글 내용·실제 식별자는 저장하지 않는다.
- 업무 작성: `2026-09-30 16:38`, 작성자 A. 프로젝트 참여자 목록에서 본인에게 `(나)`가 표시되어 있었다.
- 담당 변경 시스템 기록: `2026-10-29 10:24`, 변경자 D, `B, C → B, C, 본인`. 현재 담당자 표시도 B/C/본인 3명이었다. **오래된 업무에 생성 후 본인이 추가된 사례**를 화면에서 확인했다. 작성자와 담당 변경자는 서로 달랐다.
- 본인 답글: `2026-10-29 10:51`. 같은 업무의 일반 댓글 아래 답글로 표시되었다. 본인 추가 기록보다 뒤라는 화면상 선후 관계는 확인했다. 답글까지 ‘이미 답함’에 포함할 구현 범위와 공개 응답의 시간·작성자 매핑은 별도로 확인해야 한다.
- 상태 기록: `2026-10-14 16:48`에 `진행 → 완료`, `2026-10-29 10:24`에 `완료 → 확인 요청`. 현재 상태 표시가 `확인 요청`인데 진척도는 `100%`였다. **진척도 100%만으로 완료 판정하면 안 된다.** 표시 이름으로 완료 코드를 확정한 것은 아니다.
- 담당 변경과 상태 변경이 같은 분으로 표시돼 초 단위 순서는 알 수 없다. 화면에는 시간대 표기가 없다. 배정 순간의 완료 여부, 서버 배정 시각 및 시간대는 미확인이다.
- 화면의 업무번호와 피드의 게시글 DOM (영문 원문: Document Object Model: 웹 문서 구조) 식별자는 서로 달랐다. 업무번호를 공개 API의 `taskId`라고 확정할 수 없으므로 `taskId`·`postId` 매핑 검증은 미완료다.

#### 초기 기준 상태와 실패 경계

아래는 스펙으로부터 도출한 구현 전 검증 조건이며, 실환경에서 검증한 수집 알고리즘이 아니다.

1. 초기 동기화에서 계정·조회 대상 프로젝트·업무/게시글 식별자·현재 담당자·페이지 완료 여부와 조회 구간을 함께 기록해야 한다. 초기 조회가 끝나지 않았거나 실패한 프로젝트는 ‘본인이 담당하지 않음’으로 기록할 수 없다.
2. 초기 목록에 없는 업무를 나중에 발견한 것만으로 신규 배정을 확정할 수 없다. 초기 조회 누락·권한 변경·조회 중 배정과 구별할 근거가 필요하다. 초기 조회 구간의 사건은 보류하고, 변경 이력 또는 서버 시각 근거로 경계를 확인해야 한다. 단순 재조회만으로 일관된 초기 스냅샷을 보장하지 않는다.
3. 초기 기준 이후 확실한 미담당→담당 전환은 후보 근거지만 정확한 배정 시각을 제공하지 않는다. 두 관측 사이에 작성한 본인 댓글은 실제 배정 전후가 불명확할 수 있다. 최초 관측 시각·업무 작성 시각으로 대체하지 않는다.
4. 통신/인증/접근 실패, 성공 응답의 담당자 필드 부재, 명시적인 빈 담당자 배열을 각각 구분해야 한다. 빈 배열도 검증된 스키마와 해당 업무 매핑이 있어야 해제로 해석할 수 있다. 미확인 상태에서는 자동 제외·완료 처리하지 않는다.
5. 목록 조회를 도입하려면 페이지 상한·반복 커서·빈 페이지의 `hasNext`·중복 항목·중간 실패를 검증해야 한다. 호출량은 대상 프로젝트별 목록 페이지 수와 상세/댓글 페이지 수의 합으로 측정하고 실제 한도 확인 전 주기를 확정하지 않는다.

#### 재개 조건과 대안

- 기존 인증 경로가 준비되면 읽기 전용으로 `WORKER` 및 일반 알림, 관측 A의 상세·댓글/대댓글, 해당 프로젝트 업무 목록을 한정 조회한다. 계정 키·본문·이름·메일·사내 주소를 제외한 최소 응답을 확보한 뒤 기존 `http-flow-api.test.ts`의 보조 검증 경계에 연결한다.
- 생성 시 지정 사례는 생성 당시 담당자를 입증할 이력 또는 실제 관측이 필요하다. 접근 가능한 기존 사례로 확인할 수 없다면, 지정한 테스트 프로젝트에서 생성 시 지정 1건과 생성 후 지정 1건을 재현할 외부 변경 범위를 별도로 합의한다. 이 티켓은 그 변경을 승인하지 않는다.
- 배정 시각 또는 완료 코드가 공개 응답으로 확인되지 않으면 공식 지원을 통한 계약 확인이 대안이다. ‘이미 답함’을 관측 시각 기준으로 완화하거나 완료 이름을 추측하는 변경은 하지 않는다.
- 후속 구현 티켓은 본 티켓의 미확인 조건을 해소하기 전 완료 근거로 삼지 않는다.
