# 04: 담당자 지정과 본문 멘션의 중복 통합

Status: resolved
Blocked by: 없음 (02 해결)

**What to build:** 같은 업무 본문에 나를 직접 멘션하면서 담당자로도 지정한 경우 초안 하나만 받아 검토·게시한다. 이후 댓글 멘션은 기존처럼 별도로 처리한다.

스펙: [담당 업무 최초 초안](../spec.md)
연결 요구: Q3, Q5. 사용자 이야기 11, 12, 16, 17.

- [x] 동일 업무 본문의 직접 멘션과 담당자 지정 후보가 하나의 검토 대상과 초기 초안으로 합쳐진다. 업무 식별자와 본문 위치의 관계는 검증된 계약을 따른다.
- [x] 멘션 먼저·지정 먼저·같은 조회에서 함께 수집되는 경우와 중복 알림을 검증한다. 대기 중·생성 중·검토 중인 동일 본문에 두 번째 감지 사유가 들어와도 별도 초기 초안을 만들지 않는다.
- [x] 합쳐진 초안에도 각 감지 사유를 보존한다. 담당 업무의 현재 담당 여부와 직접 멘션 존재를 혼동하지 않는다.
- [x] 합쳐진 초안은 최신 업무 제목·본문에 답하고, 검토·수정·받는 사람 제거·승인 후 댓글 게시까지 기존 흐름으로 이어진다. 이중 게시가 발생하지 않는다.
- [x] 같은 업무의 이후 댓글·대댓글 직접 멘션은 기존 멘션 위치와 댓글 스레드 기준으로 처리된다. 업무별 최초 초안 기록이 후속 멘션을 막지 않는다.
- [x] 이미 초기 초안을 생성·처리한 동일 본문에 뒤늦게 중복 알림이 도착해도 또 다른 초기 초안을 생성하지 않는다.
- [x] 기존 통합 테스트에서 알림 순서와 진행 상태별 초안 수·검토 대상 수·게시 결과를 검증한다. 기존 본문 및 댓글 멘션 회귀 검증도 통과한다.
- [x] 마지막 변경 이후 정적 검사·관련 자동 테스트와 데스크톱의 단일 검토 대상 표시를 확인한다.

## Comments


### 2026-10-30 — 구현 및 검증

사용자가 `/implement`로 실행을 승인했다.

#### 합치는 규칙

- **본문 자리.** 담당 업무 묶음의 자리는 게시물 ID와 `remarkId = "-1"`이다. 01번 검증대로 업무 ID(`TASK_SRNO`)와 게시물 ID는 다르다고 보고, 업무 ID로 자리를 찾지 않는다. 같은 자리의 본문 멘션 위치는 `(postId, -1, -1)` 하나뿐이다.
- **멘션 먼저.** 담당자 지정이 확정되면 같은 본문의 가장 최근 실제 묶음에 배정 자료만 더한다. 묶음 상태는 대기·생성 중·검토 중·게시 중·처리됨 모두 그대로 둔다. 업무 처리 기록(`assignment_record`)은 그 묶음을 가리킨다. 멘션 묶음이 최소 기록만 남은 본문이면 새 묶음을 만들지 않는다.
- **지정 먼저.** 본문 멘션은 같은 본문의 담당 업무 묶음에 합친다. 처리됨이나 게시 중이어도 합친다. 합친 멘션은 이미 답할 대상인 본문이라 새 요청으로 세지 않는다. 그래서 재생성, “새 멘션” 수, 뺀 받는 사람 복원, 게시 확인 중단이 일어나지 않는다. 담당 업무 묶음이 최소 기록만 남은 본문의 늦은 멘션도 새 묶음을 만들지 않는다.
- **생성 중 합치기.** 실행 재시작 판단 키(`mentionSetKey`)에서 본문 멘션을 뺐다. 본문 자리에는 멘션이 하나뿐이라 기존 멘션 묶음의 동작은 같다.
- **사유 보존.** 합친 묶음은 `mentions`(본문 멘션)와 `assignment`(배정 자료)를 따로 갖는다. 본문에서 내 멘션 표기가 빠져도 담당 업무 사유로 남는다. 생성 직전 ‘이미 답함’, 받는 사람(업무 작성자), 변화 감시는 기존 담당 업무 규칙을 따른다.
- **화면.** 원문은 업무 본문으로 한 번만 보이고, 출처는 “담당 업무 초안 · 본문 멘션”으로 보인다.

#### 판단이 남은 지점

- 본문 멘션에 배정 **전에** 내가 답해 멘션 묶음이 이미 답함으로 처리된 뒤 배정되면, 새 담당 업무 초안을 만들지 않는다. 티켓의 “이미 초기 초안을 생성·처리한 동일 본문” 조항을 따랐다. 스펙의 “배정 전 댓글은 답변으로 취급하지 않는다”와 다르게 읽힐 수 있다. 다르게 처리하려면 사용자 결정이 필요하다.
- 합친 묶음은 판정에서 담당 업무 규칙이 앞선다. 05번에서 담당 해제로 게시를 막을 때, 직접 멘션이 남아 있는 합친 묶음을 어떻게 다룰지 정해야 한다. 05번 Comments에 남겼다.
- “본문 멘션” 표시는 감지 사유 기록이다. 멘션 표기가 나중에 빠져도 남는다.

#### 검증 경계

- **주 경계(`draft-queue.test.ts`, ‘본문 멘션과 담당자 지정의 합치기’ 12건).**
  - 멘션 먼저: 검토 중, 저장소 확인 대기, 생성 중(실행 중 합침), 게시 후, 최소 기록 보관 후.
  - 지정 먼저: 생성 중, 검토 중, 저장소 확인 대기, 게시 후, 무시 후 보관.
  - 같은 주기의 동시 수집과 반복 알림. 모두 초안 실행 1회, 검토 대상 1건이다.
  - 합친 초안의 본문 입력, 작성자 받는 사람 제거, 편집, 승인 후 게시 1회. 이후 같은 업무의 댓글 멘션은 댓글 스레드 묶음으로 따로 생성된다.
  - 본문 멘션 표기 제거 뒤 담당 업무 사유 유지.
- **보조 경계.**
  - 실제 SQLite: 기존 멘션 묶음에 배정 자료를 더해 저장한다. 재시작 뒤 한 묶음에 두 사유가 복원되고, 업무 처리 기록이 중복 생성을 막는다.
