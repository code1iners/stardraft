# 05: 담당 해제 시 생성 중단과 게시 차단

Status: resolved
Blocked by: 02 (생성 시 배정된 업무의 최초 초안과 게시)

**What to build:** 담당 업무 초안을 만드는 중 내가 담당자에서 제외되면 생성을 중단한다. 이미 만들어진 초안은 제외 사유와 함께 남기고 게시를 막아, 더 이상 맡지 않은 업무에 답변하지 않도록 한다.

스펙: [담당 업무 최초 초안](../spec.md)
연결 요구: Q7. 사용자 이야기 22, 23, 27.

- [x] 생성 직전과 생성 중 확인된 담당 해제로 불필요한 실행을 진행하지 않는다. 이미 실행 중이면 중단하며 뒤늦게 도착한 실행 결과가 게시 가능한 초안으로 되살아나지 않는다.
- [x] 검토 중 담당 해제를 확인하면 기존 초안과 사용자 편집 내용을 보존하고, 화면에 제외 사유와 게시 불가 상태를 표시한다.
- [x] 게시 직전 담당 상태를 다시 확인하여 확인된 해제 상태에서는 게시 요청을 보내지 않는다. 실제 확인과 게시 사이에 가능한 외부 변경 경계를 기록하고 완전한 원자성을 주장하지 않는다.
- [x] 조회 실패를 담당 해제로 기록하지 않는다. 확인 실패 시 기존 게시 전 확인의 실패 처리를 따르며, 실패를 정상 확인으로 취급해 게시하지 않는다.
- [x] 여러 담당자 중 다른 사람이 빠진 경우와 내가 빠진 경우를 구분한다. 현재 내 담당 여부를 기준으로 처리한다.
- [x] 기존 직접 멘션만으로 생성된 초안의 유효성 판정을 담당 업무 해제 규칙으로 대체하지 않는다. 담당 업무 초안의 해제 사유와 생성 상태를 구분하여 저장한다.
- [x] 기존 변화 감시·게시 전 확인과 통합 테스트에서 생성 중 해제, 준비 후 해제, 게시 직전 해제, 조회 실패, 취소 후 늦은 실행 결과를 검증한다.
- [x] 마지막 변경 이후 정적 검사·관련 자동 테스트를 실행하고, 실제 데스크톱에서 초안 보존·제외 사유·게시 차단을 확인한다. 멘션 통합 사례와의 결합 검증은 06에서 수행한다.

## Comments


### 2026-10-30 — 04번에서 넘긴 고려 사항

04번에서 같은 본문의 멘션과 담당자 지정을 한 묶음으로 합쳤다. 합친 묶음은 `mentions`(본문 멘션)와 `assignment`를 함께 갖는다. 지금은 생성 직전 ‘이미 답함’·변화 감시·받는 사람이 `assignment`가 있으면 담당 업무 규칙만 쓴다. 담당 해제로 생성을 멈추거나 게시를 막을 때, 본문의 직접 멘션이 남아 있는 합친 묶음은 “기존 직접 멘션만으로 생성된 초안의 유효성 판정을 담당 업무 해제 규칙으로 대체하지 않는다”에 따라 따로 정해야 한다. [04번 기록](04-merge-body-mention.md)


### 2026-10-30 — 구현 및 검증

사용자가 `/implement`로 실행을 승인했다. 구현 중 세 가지를 사용자에게 확인했고, 사용자는 모두 권장안을 골랐다.

#### 사용자 결정

1. **초안이 생기기 전 해제.** 생성 중, 초안 없는 실패, 저장소 확인 필요 상태에서 해제를 확인하면 실행을 멈추고 새 처리됨 상태 ‘담당 해제’(`unassigned`)로 옮긴다. 7일 안에는 되돌릴 수 있다. 되돌리면 생성 직전에 담당 여부를 다시 확인한다.
2. **검토 중 해제.** 묶음은 준비됨에 그대로 둔다. 초안과 편집본은 보존하고 편집도 할 수 있다. 게시와 다시 만들기만 막는다. 다시 담당자로 확인되면 해제 표시를 지운다.
3. **합친 묶음(04번).** 본문 직접 멘션이 남아 있으면 담당이 해제돼도 생성과 게시를 막지 않고 해제 사실만 기록한다. 멘션도 사라지거나 내 답으로 빠지면 그때부터 담당 해제 규칙으로 막는다.

#### 판정 규칙

- **담당 여부 확인.** 맥락 조회(`collectBundleContext`)가 같은 게시물 상세에서 해당 업무 ID의 담당자 배열을 본다. 결과는 세 가지다.
  - 내 ID가 있으면 담당.
  - 배열이 있는데 내 ID가 없으면(빈 배열 포함) 해제.
  - 업무를 찾지 못했거나 담당자 배열이 누락됐거나 조회가 실패하면 알 수 없음(`null`). 이 경우 해제로 기록하지 않는다.
- **해제 사유 저장.** 사유는 묶음 상태와 따로 `assignment.unassignedAt`에 둔다. Flow가 해제 시각을 주지 않으므로 해제를 확인한 PC 시각이다. ‘알 수 없음’이면 이전 값을 그대로 두므로, 한 번 확인한 해제는 다시 담당으로 확인될 때까지 게시를 계속 막는다.
- **차단 판정.** `isUnassignedBlocked`가 참일 때 막는다. 조건은 해제가 기록돼 있고 묶음에 남은 직접 멘션이 없는 것이다. 게시 본문 계산(`postableBody`)이 이 판정을 따르므로, 게시 시작과 게시 요청 기록 모두 막힌다.
- **확인 시점.**
  - 생성 직전: `prepareRun`. ‘이미 답함’이 먼저 판정된다.
  - 생성 중: 매 폴링의 변화 감시가 생성 중 담당 업무 묶음도 조회한다. 상태가 바뀌면 초안 대기열이 실행을 끊는다. 늦게 끝난 실행의 결과는 생성 중이 아닌 묶음에 저장되지 않는다.
  - 검토 중: 기존 변화 감시가 확인한다.
  - 게시 직전: `checkBeforePost`가 해제를 찾으면 준비됨으로 되돌리고, 토스트로 ‘게시하지 않았습니다: 담당자에서 제외됨’을 띄운다.
- **게시 직전 확인의 한계.** 완전한 원자성을 주장하지 않는다. 아래 경우에는 해제를 막지 못한다.
  - 확인과 게시 요청 사이에 Flow에서 담당자가 바뀐 경우.
  - 확인이 늦어 결과 없이 게시한 경우(`endPostCheck`).
  - 확인 조회가 실패해 기존 규칙대로 그대로 게시한 경우(`unchecked`).
- **저장.** 마이그레이션 20에서 최소 기록 표의 상태 CHECK에 `unassigned`를 넣었다. SQLite는 CHECK를 바꿀 수 없어 표를 새로 만들어 옮겼고, 기존 기록은 보존했다.

#### 남은 판단과 한계

- **합친 묶음의 받는 사람.** 담당이 해제된 뒤 직접 멘션으로 게시하는 합친 묶음도 받는 사람을 담당 업무 규칙(업무 작성자)으로 정한다. 본문 멘션의 송신자는 보통 업무 작성자와 같다. 다르게 정하려면 사용자 결정이 필요하다. [06번](06-recovery-and-final-verification.md)에서 결합 검증과 함께 본다.
- **조회 비용.** 생성 중 담당 업무 묶음은 폴링마다 맥락 전체(댓글 포함)를 다시 조회한다. 한 번에 하나만 생성하므로 늘어나는 호출은 많지 않다고 보았다.
- **처리됨 묶음은 다시 감시하지 않는다.** 재지정되어도 자동으로 다시 만들지 않는다(사용자 이야기 13).
- **글로서리.** ‘담당 해제’를 용어로 등재하지 않았다. `/domain-modeling` 후보로 남긴다.
