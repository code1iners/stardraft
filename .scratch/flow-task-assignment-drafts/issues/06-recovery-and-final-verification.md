# 06: 재시작·재시도·재지정 복구와 최종 검증

Status: resolved
Blocked by: 03 (기존 업무의 신규 배정과 ‘이미 답함’ 처리), 04 (담당자 지정과 본문 멘션의 중복 통합), 05 (담당 해제 시 생성 중단과 게시 차단)

**What to build:** 앱 재시작과 재지정에도 같은 업무의 초기 초안이 중복되지 않고, 실패 재시도와 사용자 요청 재생성은 정상적으로 이어진다. 모든 감지·검토·게시 규칙이 함께 동작하는지 실제 사용 흐름으로 확인한다.

스펙: [담당 업무 최초 초안](../spec.md)
연결 요구: Q1~Q10 종합. 사용자 이야기 13~15, 26 및 전체 기능의 완료 검증.

- [x] 앱 재시작 후 초기 담당 기준과 업무별 처리 기록을 복원한다. 같은 업무의 반복 알림·일반 변경·담당 해제 후 재지정으로 초기 초안을 자동 재생성하지 않는다.
- [x] 생성 실패·진행 중 종료·성공 완료를 구분한다. 실패한 작업은 기존 재시도 흐름으로 복구할 수 있고, 실패를 성공한 최초 생성으로 취급하거나 중복 실행하지 않는다.
- [x] 사용자가 지시를 덧붙여 재생성할 수 있다. 자동 중복 방지는 수동 재생성을 막지 않으며 기존 초안 교체 동작을 유지한다.
- [x] 기존 저장 데이터에서의 이전과 재시작 지속성을 실제 데이터베이스 테스트로 검증한다. 계정 전환 후 다른 계정의 담당 업무 기록·초안·처리 기준이 섞이지 않는다.
- [x] 멘션과 담당자 지정이 합쳐진 상태에서 재시작·담당 해제·조회 실패·후속 댓글 멘션을 함께 검증한다. 담당 업무 초안의 게시 차단과 기존 직접 멘션 흐름을 무심코 덮어쓰지 않는다. 합의된 규칙만으로 충돌을 해소할 수 없으면 임의 정책을 추가하지 않고 보고한다.
- [x] 생성 시 지정과 생성 후 지정 각각에서 업무 발견 → 최신 제목·본문 및 코드 기반 초안 → 검토·수정 → 사용자 승인 후 업무 댓글 게시를 통합 검증한다. 작성자 기본 멘션과 제거를 포함한다.
- [x] 자기 작성 업무·초기 담당 업무·완료 업무 제외, 복수 담당자 포함, 배정 전후 내 댓글, 중복 알림과 담당 해제의 모든 합의 사례를 검증한다.
- [x] 마지막 변경 이후 정적 검사와 관련 자동 테스트를 실행한다. 기존 서비스 통합 경계와 필요한 어댑터·데이터베이스·화면 검증을 활용하고 구현 내부를 그대로 따라가는 테스트를 추가하지 않는다.
- [x] (2026-10-30 사용자 결정: 사람 확인은 [07번](07-human-verification.md)으로 이관. 이 티켓은 에이전트 화면 검증으로 대신한다) 실제 데스크톱에서 초안 출처·수정·받는 사람 제거·이미 답함·담당 해제 사유·게시 차단·복구 상태를 확인한다. 자동 서비스 검증을 실제 화면 검증으로 대신하지 않는다.
- [x] (2026-10-30 사용자 결정: [07번](07-human-verification.md)으로 이관) 실제 Flow의 생성 시 지정·생성 후 지정·담당 해제·완료 상태·배정 시점 판단에 대한 근거를 최종 구현과 대조한다. 실제 게시까지 확인했다면 그 실행 범위와 결과를 별도로 남기고, 외부 조작이 필요한 경우 승인된 범위 안에서만 수행한다.
- [x] 자동 테스트·데스크톱 확인·실제 Flow 증거를 구분한 완료 보고를 작성한다. 실제 연동의 필수 미검증 항목이 남으면 전체 기능 완료로 표현하지 않는다. 이번 티켓은 배포나 코드 자동 수정 기능을 포함하지 않는다.

### 2026-10-30 — 자동 검증과 남은 사람 확인

사용자가 `/implement`로 실행을 승인했다. 확인해 보니 03~05번 구현이 이미 이 티켓의 복구 동작을 만족했다. 그래서 제품 코드는 바꾸지 않았고, 비어 있던 검증 경계만 테스트로 채웠다. 실제 데스크톱 확인과 실제 Flow 확인은 하지 않았으므로 **전체 기능 완료가 아니다**. 남은 일은 사람이 직접 확인해야 하므로 상태를 `ready-for-human`으로 바꾼다.

#### 추가한 자동 검증

- **실제 SQLite 위의 서비스 재시작** (`draft-queue.test.ts`, ‘재시작·재시도·재지정 복구’ 4건). 임시 `state.db`를 열고 앱 시작 순서대로 묶음 → 재시작 복구 → 초안 대기열 → 담당 업무·멘션 감지 → 게시를 연결했다. 그다음 DB를 닫고 다시 여는 방식으로 재시작을 재현했다. Flow·시계·에이전트만 대역이다.
  1. 생성 중 종료: 실행이 ‘앱 종료로 중단’으로 남는다. 다시 켜면 같은 묶음을 이어 만든다(`app-quit` → `succeeded`). 기능 시작 시각은 유지된다. 반복 알림과 일반 댓글로 다시 만들지 않는다. 해제는 재시작 뒤에도 남고 그동안 게시가 막힌다. 담당 변경 기록(S41)을 갖춘 재지정 알림으로 다시 만들지 않으며, 다시 담당자로 확인되면 작성자 멘션으로 게시한다.
  2. 생성 실패: 재시작 뒤에도 실패로 남고 저절로 다시 돌지 않는다. 반복 알림도 무시한다. [다시 시도]와 지시를 덧붙인 재생성은 같은 묶음에서 이어진다. 지시는 입력에 들어가고 업무 본문은 계속 답변 대상이다. 받는 사람에서 뺀 사람은 빠진 채로 남고, 재시작 뒤에도 그대로다.
  3. 계정 전환: 이전 계정의 담당 업무 묶음과 기준을 지운다. 새 계정은 자기 기능 시작 시각으로 다시 시작해, 이미 맡던 업무는 제외하고 이후 새 배정만 만든다.
  4. 합친 묶음: 재시작 뒤에도 두 감지 사유를 지킨다. 맥락 조회 실패(503)는 해제로 기록하지 않는다. 실패한 요청이 실제로 일어났는지도 단언한다. 담당만 해제되고 본문 멘션이 남으면 게시하며, 같은 업무의 후속 댓글 멘션은 댓글 스레드 묶음으로 따로 만든다.
- **실제 DB 마이그레이션** (`state-database.test.ts`): 형식 18(담당 업무 구조 이전)에서 올린 경우를 검증했다. 기존 묶음은 배정 자료 없이 남고, 감지 기준도 없다. 그 본문에 더한 배정은 재시작 뒤에도 한 번만 기록된다.
- **테스트가 헛돌지 않는지 확인.** 임시로 동작을 깨 보고 테스트가 실패하는지 본 뒤 되돌렸다.
  - 중복 방지(처리 기록 검사, 같은 본문 합치기)를 끄면 1번 테스트가 묶음 3개로 실패한다.
  - 해제 차단을 멘션 유무와 상관없이 막도록 바꾸면 4번 테스트가 실패한다.

#### 합의 규칙으로 정하지 못한 점 (임의 정책 없음)

- **합친 묶음의 받는 사람.** 담당만 해제되고 본문 멘션이 남아 게시하는 경우에도 받는 사람은 업무 작성자다(05번에서 넘어온 점). 본문 멘션의 송신자는 본문 작성자이므로 실제로는 둘이 같다고 본다. 다르게 정할 필요가 생기면 사용자 결정이 필요하다.
- **실패 화면 문구.** 담당 업무 묶음이 실패하면 기존 직접 멘션용 문구가 그대로 보인다. ‘Flow에서 멘션 내용을 가져오지 못했습니다.’와 저장소 확인 필요 사유의 ‘코드와 무관한 멘션으로 판정함’이 그렇다. 기존 스펙이 정한 문구라 바꾸지 않았다. 담당 업무용 문구가 필요한지는 사용자 결정 사항이다.
- **계정 전환 경로.** 테스트는 키 확인이 부르는 `resetForAccount`를 직접 호출한다. 키 확인 서비스부터 거치는 전환은 기존 계정 테스트가 맡는 범위이며, 이번에 결합해 검증하지 않았다.
- **재시작과 생성 중단의 조합.** 생성 중 해제로 처리됨 ‘담당 해제’가 된 묶음을 재시작한 뒤 재지정하는 조합은 05번에서 재시작 없이만 검증했다. 처리 기록이 DB에 남는 것은 위 테스트로 확인했다.

#### 보완한 자동 검증

앞 기록에서 한계로 남긴 두 조합을 테스트로 채웠다(‘재시작·재시도·재지정 복구’ 5건).

- **재시작과 생성 중단의 조합.** 생성 중 담당 해제로 처리됨 ‘담당 해제’가 된 묶음을 검증했다.
  - 재시작 뒤에도 그 상태로 남는다.
  - S41 근거를 갖춘 재지정 알림으로 다시 만들지 않는다.
  - 되돌리면 담당 여부를 다시 확인해 같은 묶음에서 만든다.
- **키 확인 경로의 계정 전환.** `resetForAccount`를 직접 부르지 않는다. 켜 둔 앱에서 `FlowAccount.checkKey`로 다른 사람의 키를 확인하고 `confirmSwitch`로 승인한다. 그러면 앱처럼 묶음을 새 기록으로 다시 읽는다.
  - 이전 계정의 초안이 사라지고, 다음 폴링에서 새 계정 기준이 생긴다.
  - 이미 맡던 업무는 초기 업무로 제외된다.
  - 재시작 뒤에도 새 계정의 기능 시작 시각이 유지된다.

#### 에이전트 화면 검증 (대역 연결)

화면 입력은 실제 서비스로 만들었다. 실제 SQLite와 재시작 경로로 아래 네 상태를 만들고, 그 묶음을 `main/review-snapshot.ts`의 `reviewSnapshot`으로 변환했다. 화면 쪽은 `pnpm build`로 만든 실제 렌더러(`out/renderer/index.html`, `main.tsx` → `ReviewView`/`PopoverView`, `styles.css`)를 macOS Electron 44.9.0 창에 띄웠다. 프리로드 대역으로 그 스냅숏만 넣었다.

| 상태 | 확인한 것 |
| --- | --- |
| 재시작 뒤 실패 | ‘에이전트가 10분 안에 끝내지 못해 멈췄습니다.’, [다시 시도] 클릭 시 `retry-bundle` 명령 |
| 재시작 뒤 게시 차단 | ‘담당자에서 제외되어 게시할 수 없습니다…’, 재시작 전 편집본 보존, 받는 사람 ‘@업무 작성자’ ×, [게시] 꺼짐, 다시 만들기 없음 |
| 합친 묶음과 후속 멘션 | 출처 ‘담당 업무 초안 · 본문 멘션’, 해제 경고 없이 [게시] 클릭 시 `post-bundle`, 후속 댓글 멘션은 별도 묶음 |
| 처리된 담당 해제 | 작은 창의 ‘담당 해제’ 태그, ‘담당자에서 제외되어 초안을 만들지 않았습니다.’, [되돌리기] 클릭 시 `restore-bundle` |

- 창 크기: 펼친 창 1100×850과 최소 크기 720×460, 작은 창 420×760. 모든 크기에서 가로 넘침이 없었다.
- 관찰: 합친 묶음의 원문 영역은 후속 댓글 멘션을 ‘초안을 만든 뒤 새 글 1건’으로도 보인다. 기존 변화 감시 동작이며 게시를 막지 않는다. 같은 멘션이 별도 묶음에도 있으므로 07번 실제 사용에서 혼동이 없는지 본다.
- 앱 연결은 대역이다. 실제 설치본, 실제 Flow 응답, 게시를 검증한 것이 아니다.
- 임시 생성 코드는 저장소에서 지웠다. 스크린샷과 스냅숏은 저장소 밖 세션 임시 폴더에 두었다.
