# 07: 실제 응답 대조와 남은 화면의 에이전트 최종 검증

Status: resolved
Blocked by: 06 (재시작·재시도·재지정 복구와 최종 검증)

**What to build:** 새 기능을 만들지 않는다. 06번까지 비어 있던 경계를 에이전트가 확인할 수 있는 방법으로 검증하고, 담당 업무 최초 초안의 최종 완료를 보고한다.

2026-10-30 사용자 결정: “에이전트 검증으로 변경한다. 사용자는 모든 구현이 완료되고 그 이후 별도 통합 테스트로 진행하며 사용자 검증은 완료 조건에서 제외한다.” 그래서 이 티켓의 완료 조건에서 아래를 뺐다. 실제 설치본의 화면 확인, 다른 사람이 만든 실제 배정 사례, 실제 업무 댓글 게시, 실사용 관찰이 그 대상이다. 이 항목들은 사용자의 별도 통합 테스트로 넘긴다. 에이전트는 실제 Flow를 호출하거나 외부 업무를 바꾸지 않는다.

스펙: [담당 업무 최초 초안](../spec.md)
연결 요구: 스펙 Testing Decisions의 “실제 Flow 검증은 별도 증거”, 데스크톱 화면 확인. 01번 미검증 경계, 02·03번 실제 사용 검증 경계, 06번 남은 사용자 결정.

- [x] **실응답 대조.** 01번에서 확보한 마스킹 실응답(사례 A: 생성 후 지정)을 실제 HTTP 어댑터와 최종 감지 서비스에 함께 통과시킨다. 담당자·완료 상태·배정 시점 근거의 최종 판정을 확인한다. 실응답에 없는 상태를 가정한 변형은 변형이라고 표시한다.
- [x] **조회 호출량.** 대역 Flow로 감지 주기마다 생기는 담당 업무 조회 호출 수를 측정해 기록한다. 보류 후보가 쌓일 때 늘어나는 양도 포함한다(03번 기록).
- [x] **보류·감지 지연 경계.** 동명이인·이름 변경·새 S41 형식, 알림 누락, 수정 후 최초 발견, 초기 조회 중 사건이 어떻게 처리되는지 최종 구현과 기존 테스트로 대조해 기록한다.
- [x] **남은 화면 상태.** 06번 화면 검증에서 다루지 않은 상태를 실제 렌더러와 Electron 창으로 확인한다. 실제 서비스로 만든 스냅숏을 대역 프리로드로 넣는다.
  - 준비된 담당 업무 초안의 출처 표시, 편집, 받는 사람 제거.
  - 이미 답함.
  - 앱 종료로 중단된 생성이 재시작 뒤 이어지는 상태.
- [x] **06번 사용자 결정 두 가지.** 합친 묶음의 받는 사람과 담당 업무 실패 화면의 직접 멘션용 문구를 기록한다. 현재 동작은 유지하고, 판단은 사용자의 통합 테스트로 넘긴다.
- [x] 마지막 변경 이후 정적 검사와 전체 자동 테스트를 실행한다. 자동 검증, 에이전트 화면 검증, 사용자 통합 테스트로 넘긴 항목을 구분해 최종 완료를 보고한다.

## Comments

### 2026-10-30 — 사람 확인에서 에이전트 검증으로 전환

이전 판은 `ready-for-human`이었다. 실제 설치본 화면, 실제 생성 시·생성 후 지정 사례, 실제 담당 해제·완료·배정 시점 근거, 실제 게시, 06번 사용자 결정 두 가지를 사람이 확인하는 티켓이었다. 위 사용자 결정에 따라 실제 사용 확인은 구현 완료 뒤 사용자의 별도 통합 테스트로 옮겼고, 이 티켓은 에이전트 검증으로 바꿨다. 다른 티켓의 링크를 지키려고 파일 이름은 그대로 두었다.

### 2026-10-30 — 에이전트 최종 검증 결과

제품 코드는 바꾸지 않았다. 테스트 5건을 더했고, 측정과 화면 확인은 임시 코드로 하고 지웠다. 실제 Flow 호출, 외부 업무 변경, 실제 설치본 실행은 하지 않았다.

#### 1. 실응답 대조 (자동 테스트로 남김)

`draft-queue.test.ts`의 ‘마스킹한 실응답 사례 A의 최종 판정’ 3건. 01번 fixture(`assignment-post-2026-10-29.json`, `assignment-comments-2026-10-29.json`)를 `FakeFlowServer` → 실제 `HttpFlowApi` → `AssignmentDetection` → 실제 묶음 서비스로 통과시켰다.

| 입력 | 최종 판정 |
| --- | --- |
| 관측 그대로(상태 범주 `2`) | 완료로 제외한다. 댓글은 받지 않는다. 요청은 알림 2회와 상세 1회다. |
| 변형: 범주 `0` | S41 기록(`id-40`, `20261029102448`)을 배정 시각으로 확정한다. 그 뒤 내 답글(`id-38`, 10:51:02) 때문에 ‘이미 답함’으로 처리하고 에이전트를 부르지 않는다. |
| 변형: 범주 `1` | ‘미확인’으로 보류한다. 다음 주기에도 상세를 다시 받는다. |

- 보정한 점이 둘 있다. 실응답은 담당자 컬럼 이름(`USER_NM`)을 `[redacted]`로, S41 속 이름을 사용자 별칭으로 따로 가렸다. 같은 사람이 같은 이름이 되도록 `USER_NM`을 별칭으로 바꿨다. 이 보정을 빼면 범주 `0` 변형이 실패하는 것을 확인했다. 알림은 01번 투영본의 필드를 마지막 실행 별칭으로 옮겨 만들었다(원 응답이 아님).
- **발견: 진행 중 업무의 신규 배정이 초안 없이 보류된다.** 구현은 범주 `0`(요청)만 미완료로 본다. 02번 근거(`common.min.js`)에서 진행·피드백은 범주 `1`이다. 그래서 진행·피드백 상태 업무에 나중에 배정되면 초안을 만들지 않고, 그 업무를 주기마다 다시 조회한다. 사례 A도 배정 당시 상태가 ‘확인 요청’(사용자 정의 상태, 범주 미확인)이었다. 스펙의 “상태 표시 이름만으로 완료를 추정하지 않는다”를 지킨 보수적 판단이라 바꾸지 않았다. 범주 `1`을 미완료로 넓힐지는 사용자가 결정할 일이다.

#### 2. 조회 호출량 (대역 측정, 저장소에 남기지 않음)

`FakeFlowApi.requests`로 담당 업무 감지 한 주기(60초)의 요청을 셌다. 대역의 쪽 크기(알림 20, 댓글 100, 대댓글 20)는 실제 Flow와 다를 수 있다.

| 상황 | 주기당 요청 |
| --- | --- |
| 새 알림 없음 | 1 (알림) |
| 생성 후 배정 1건이 처음 들어온 주기 | 7 (알림 1, 상세 2, 댓글 3, 프로젝트 1). 감지와 초안 맥락 수집을 합친 수다. 다음 주기는 1. |
| 위와 같고 대댓글 더보기 스레드 3개 | 13 (대댓글 6 추가) |
| 완료 범주 미확인 보류 K건 | 1 + K. 처음 주기와 이후 주기가 같다(K = 1, 5, 20에서 2, 6, 21). |
| 댓글 조회 실패 보류 1건 | 3이 매 주기 반복 |
| 댓글이 쪽 상한(50쪽)을 넘는 보류 1건 | 52가 매 주기 반복 |

- **발견: 보류 후보 수와 그 재조회에 상한이 없다.** 1번의 범주 `1` 업무처럼 다시 조회해도 결과가 같을 수 있는 보류도 `pending`에 남는다. 그런 업무가 쌓이면 분당 상세 조회가 그만큼 늘어난다. 실제 호출 한도는 확인한 적이 없다(01번). 상한이나 간격을 정하는 것은 정책 결정이라 추가하지 않았다.

#### 4. 남은 화면 상태 (에이전트 화면 검증, 대역 연결)

06번과 같은 방법을 썼다. 실제 서비스(가짜 Flow·시계·에이전트, 재시작은 실제 SQLite)로 상태를 만들고 `reviewSnapshot`으로 변환했다. 화면은 `pnpm build`로 만든 실제 렌더러를 Electron 44.9.0 창에 띄우고, 프리로드 대역으로 그 스냅숏만 넣었다. 창 크기는 1100×850, 720×460, 작은 창 420×760이며 모든 크기에서 가로 넘침이 없었다.

| 상태 | 확인한 것 |
| --- | --- |
| 준비된 담당 업무 초안 | 목록과 머리에 ‘담당 업무 초안’, 원문 ‘담당 업무 본문’에 최신 본문, 받는 사람 ‘@업무 작성자 ×’. × 클릭 시 `remove-recipient`, 편집기 입력 시 `edit-draft`, [게시] 클릭 시 `post-bundle`이 나간다. |
| 편집하고 받는 사람을 뺀 뒤 | 편집본이 편집기에 보이고 ‘받는 사람 없음 · 멘션 없이 올립니다’, ‘원래 초안으로 되돌리기’, 글자 수 28이 보인다. [게시]는 켜져 있다. |
| 이미 답함 | 처리됨 목록과 머리에 ‘이미 답함’, 하단에 ‘배정 이후 Flow에 내 답이 있어 초안 없이 처리했습니다.’가 보인다. [되돌리기] 클릭 시 `restore-bundle`이 나간다. |
| 앱 종료로 중단 뒤 재시작 | 같은 묶음이 ‘생성 중’이고 진행에 ‘초안 쓰는 중’, [취소]가 보인다. 끝나면 준비됨이 되고 실행 기록은 `app-quit` → `succeeded`다. 실행 기록의 `app-quit`은 화면에 따로 표시하지 않는다(현재 설계). |

- **발견: 이미 답함 화면의 원문 칸이 비어 보인다.** 감지 단계에서 바로 ‘이미 답함’이 된 담당 업무 묶음은 맥락을 받기 전이라 `assignment.text`가 빈 배열이다. 그래서 ‘원문 · 담당 업무 본문’ 아래에 빈 인용 칸이 나온다. 기존 화면 테스트는 본문이 든 가짜 스냅숏을 써서 이 상태를 잡지 못했다. 출처와 처리 사유는 보이므로 스펙의 표시 요구는 충족한다. 다만 본문을 보일지 칸을 숨길지는 화면 결정이라 고치지 않았다.
- 스크린숏과 스냅숏은 저장소 밖 세션 임시 폴더에 두었다. 실제 설치본, 실제 Flow 응답, 실제 게시를 검증한 것은 아니다.

#### 5. 06번에서 넘어온 사용자 결정 두 가지

현재 동작을 유지하고 사용자의 통합 테스트로 넘긴다.
- **합친 묶음의 받는 사람.** 담당만 해제되고 본문 멘션이 남아 게시하면 받는 사람은 업무 작성자다. 본문 멘션의 송신자도 본문 작성자이므로 둘은 같다고 본다.
- **담당 업무 실패 화면 문구.** 직접 멘션용 문구(‘Flow에서 멘션 내용을 가져오지 못했습니다.’, ‘코드와 무관한 멘션으로 판정함’)가 그대로 보인다.

| 사용자 결정이 필요한 발견 | ① 진행·피드백(범주 `1`) 업무가 보류되는 문제, ② 보류 재조회에 상한이 없는 문제, ③ 이미 답함 화면의 빈 원문 칸. [08번](08-verification-findings.md)으로 분리했다. |

에이전트 검증 범위의 담당 업무 최초 초안 구현은 완료다. 위 사용자 통합 테스트와 발견 3건의 결정은 남아 있다.

#### 리뷰 반영

`code-review` 두 축.
- Spec: 3절 ‘수정 후 최초 발견’ 행이 틀렸다는 지적을 받았다. 처음 기록에는 `@$%` 기록을 해석하지 않아 초안을 만들지 않는다고 적었다. 실제로는 `parseWorkerChange`가 이 형식을 최초 지정으로 읽는다. 처음 넣은 테스트는 담당자 이름이 없어서 우연히 초안이 없었던 것이다. 테스트를 이름이 있을 때와 없을 때 2건으로 다시 쓰고 기록을 고쳤다. 실제 Flow를 사용자 통합 테스트로 넘긴 사실은 스펙 Testing Decisions에도 적었다. 스크린숏을 저장소 밖에 두는 방식은 06번과 같아 유지했다.
- Standards: hard 위반은 없었다.
  - 테스트 주석의 티켓 번호 참조를 관측 날짜로 바꿨다.
  - 발견 3건은 별도 티켓으로 분리했다.
  - `(env, server)` 묶음, 범주 문자열, 파일 이름은 기존 관례와 링크 보존을 이유로 두었다.
