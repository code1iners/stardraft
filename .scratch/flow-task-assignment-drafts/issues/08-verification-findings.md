# 08: 최종 검증에서 나온 담당 업무 판정·조회·화면 결정 사항

Status: resolved

**What to build:** 아직 정하지 않았다. [07번](07-human-verification.md) 에이전트 최종 검증에서 나온 발견 3건이다. 모두 합의된 규칙을 지킨 결과이거나 화면 결정이 필요한 것이라 임의로 고치지 않았다. 사용자의 통합 테스트 결과와 함께 처리 여부를 정한다.

스펙: [담당 업무 최초 초안](../spec.md)

1. **진행·피드백 상태 업무의 신규 배정이 보류된다.** 구현은 상태 범주 `0`(요청)만 미완료, `2`만 완료로 본다. 02번 공개 클라이언트 근거에서 진행·피드백은 범주 `1`인데, 이 범주는 ‘미확인’으로 남는다. 그래서 진행 중 업무에 나중에 배정되면 초안이 만들어지지 않는다. 범주 `1`(필요하면 `3` 보류도)을 미완료로 넓힐지 정해야 한다. 근거: 07번 1절, `draft-queue.test.ts`의 ‘변형: 진행·피드백 범주(1)…’.
2. **보류 후보 재조회에 상한이 없다.** 다시 조회해도 결과가 같을 수 있는 보류(범주 미확인 등)도 `pending`에 남는다. 그래서 60초마다 후보 수만큼 상세를 다시 받는다. 댓글이 쪽 상한을 넘는 후보는 한 건에 주기마다 52회를 호출한다. 후보 수 상한, 재조회 간격, 포기 조건 중 무엇을 둘지 정해야 한다. 근거: 07번 2절.
3. **이미 답함 화면의 원문 칸이 비어 보인다.** 감지 단계에서 바로 ‘이미 답함’이 된 담당 업무 묶음은 맥락을 받지 않아 `assignment.text`가 비어 있다. 그래서 빈 인용 칸이 나온다. 감지 때 받은 업무 본문을 보일지, 칸을 숨길지 정해야 한다. 근거: 07번 4절.

## Comments

### 2026-10-31 결정과 처리

사용자 결정:

1. 진행·피드백 범주(`1`) 업무는 초안이 생기지 않아도 된다.
2. 제안 A를 채택한다. 다시 조회해도 결과가 같은 보류는 후보에서 빼고, 새 알림이 오면 다시 판정한다. 제안 B(일시적 실패의 재조회 간격 늘리기)는 이번에 하지 않는다.
3. 버튼 대신, 감지 때 이미 받은 업무 본문을 묶음에 저장해 원문 칸에 보인다.

구현:

- `assignment-detection.ts`
  - 범주가 `active`가 아니면(완료, 진행·피드백, 보류, 범주 누락) 후보에서 뺀다. 전에는 `unknown`이면 보류했다.
  - 댓글이 쪽 상한을 넘어 끝까지 받지 못하면 후보에서 뺀다. 답이 없다고 단정하지 않는 규칙은 그대로다.
  - 상세·댓글 조회 실패, 담당자 필드 누락, 현재 담당자에 내가 없는 경우는 그대로 보류한다.
- `mention-bundles.ts`의 `addAssignment`: 감지 단계에서 ‘이미 답함’이 된 새 묶음에 `context`를 저장한다. 감지 때 받은 상세의 제목·본문·첨부만 넣고, 댓글은 넣지 않는다. Flow 추가 호출은 없다.
- `bundle-context.ts`: 게시물 맥락을 만드는 부분을 `contextPostOf`로 꺼내 두 곳이 같이 쓴다.
- 스펙 Implementation Decisions에 이 결정을 한 줄 추가했다.

테스트(`draft-queue.test.ts`):

- ‘담당 업무 제외 또는 보류: unknown’: `pending`이 비는지 확인한다.
- ‘댓글을 쪽 상한까지 받아도 끝나지 않으면…’: `pending`이 비고, 다음 주기에는 알림 목록만 받는다.
- 사례 A ‘변형: 진행·피드백 범주(1)…’: 초안이 없고, 다음 주기에 상세를 다시 받지 않는다.
- ‘배정 후 이미 쓴 내 comment/reply…’: 묶음의 `context.post`에 제목·본문이 들어 있다.

검사: typecheck·lint 통과, 데스크톱 69개 파일 1,292개 테스트 통과, `git diff --check` 통과. 화면은 다시 띄워 보지 않았다. 원문 칸은 `review-snapshot.ts`가 `context.post.contents`를 읽으므로 저장된 본문이 보일 것으로 보지만, 화면 확인은 사용자 통합 테스트에 맡긴다.
