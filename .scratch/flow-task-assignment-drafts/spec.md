# 담당 업무 최초 초안

Status: ready-for-agent
작성일: 2026-10-29

## Problem Statement

Stardraft는 직접 멘션에 대한 초안을 만들지만, 업무 담당자로 지정된 것만으로는 초안을 만들지 않는다. 사용자는 다른 사람이 작성한 업무가 자신에게 새로 배정되면, 업무의 제목·본문과 관련 코드를 바탕으로 답변 초안을 받아 기존 검토·게시 흐름으로 처리하고 싶다. 업무가 생성될 때 지정된 경우와 생성 후 지정된 경우 모두 필요하다.

## Solution

기능을 켠 이후 자신에게 새로 배정된 업무를 발견하고, 업무별 최초 초안을 한 번 자동 생성한다. 업무 작성일은 신규 배정의 기준이 아니다. 기능 시작 전부터 담당하던 업무, 자신이 만든 업무에 자신을 담당자로 넣은 경우, 새 배정 시 이미 완료된 업무는 제외한다.

초안은 생성 시 조회한 최신 업무 제목·본문을 대상으로 하며 댓글은 보조 맥락으로 사용한다. 사용자는 기존 검토 화면에서 초안을 수정하고 승인하여 업무 댓글로 게시한다. 담당 업무 초안의 기본 받는 사람은 업무 작성자다.

## User Stories

1. 사용자로서, 업무 생성 시 내가 담당자로 지정되면 초안을 받고 싶다. 직접 멘션이 없어도 요청을 검토할 수 있기 때문이다.
2. 사용자로서, 생성된 업무에 나중에 담당자로 추가되어도 초안을 받고 싶다. 나중에 배정된 요청도 처리할 수 있기 때문이다.
3. 사용자로서, 오래전에 작성된 업무도 기능 시작 후 새로 배정되면 받고 싶다. 작성일과 배정일이 다르기 때문이다.
4. 사용자로서, 기능 시작 전부터 맡던 업무는 자동 초안에서 제외하고 싶다. 기존 업무가 한꺼번에 들어오는 일을 피할 수 있기 때문이다.
5. 사용자로서, 내가 만든 업무에 나를 담당자로 넣은 경우는 제외하고 싶다. 내가 작성한 요청에 불필요한 답변 초안을 받지 않기 위해서다.
6. 사용자로서, 여러 담당자 중 나도 포함되면 초안을 받고 싶다. 공동 담당 업무도 검토해야 하기 때문이다.
7. 사용자로서, 완료된 업무의 신규 배정은 제외하고 싶다. 끝난 업무에 불필요한 초안이 생기지 않기 위해서다.
8. 사용자로서, 최신 업무 제목·본문에 대한 초안을 받고 싶다. 수정된 요청 내용을 반영할 수 있기 때문이다.
9. 사용자로서, 댓글을 보조 맥락으로 참고하되 업무 본문에 답하고 싶다. 담당자 변경 알림 자체에 답하는 일을 피할 수 있기 때문이다.
10. 사용자로서, 기존 저장소 매핑과 자동 선택을 활용하고 싶다. 관련 코드에 근거한 초안을 받을 수 있기 때문이다.
11. 사용자로서, 같은 업무의 초기 초안은 한 번만 자동 생성되기를 원한다. 반복 알림으로 중복 작업이 생기지 않기 위해서다.
12. 사용자로서, 일반 댓글이나 상태 변경만으로 초기 초안이 다시 생성되지 않기를 원한다. 이미 검토한 요청이 반복되지 않기 위해서다.
13. 사용자로서, 담당 해제 후 재지정되어도 이미 생성한 초기 초안이 자동 재생성되지 않기를 원한다. 같은 업무를 중복 처리하지 않기 위해서다.
14. 사용자로서, 초안 생성 실패를 재시도하고 싶다. 일시적인 오류 때문에 업무를 놓치지 않기 위해서다.
15. 사용자로서, 필요한 경우 직접 초안 재생성을 요청하고 싶다. 자동 중복 방지와 별개로 초안을 개선할 수 있기 때문이다.
16. 사용자로서, 같은 업무 본문에서 멘션과 담당자 지정이 겹치면 초안 하나를 받고 싶다. 동일한 요청을 두 번 검토하지 않기 위해서다.
17. 사용자로서, 이후 댓글 멘션은 기존 방식대로 처리하고 싶다. 후속 질문을 계속 받을 수 있기 때문이다.
18. 사용자로서, 기존 검토 화면에서 초안을 확인하고 수정하고 싶다. 익숙한 흐름으로 답변을 다듬을 수 있기 때문이다.
19. 사용자로서, 승인한 초안을 해당 업무의 댓글로 게시하고 싶다. 원래 요청이 있는 곳에서 답변할 수 있기 때문이다.
20. 사용자로서, 업무 작성자를 기본 받는 사람으로 삼고 싶다. 담당자를 지정한 사람과 작성자가 달라도 본문 요청자에게 답할 수 있기 때문이다.
21. 사용자로서, 기본 받는 사람을 검토 중 뺄 수 있기를 원한다. 불필요한 멘션을 방지할 수 있기 때문이다.
22. 사용자로서, 생성 중 담당자에서 제외되면 생성을 중단하고 싶다. 더 이상 맡지 않은 업무에 대한 작업을 멈출 수 있기 때문이다.
23. 사용자로서, 초안이 준비된 뒤 담당자에서 제외되면 사유와 초안을 확인하되 게시가 차단되기를 원한다. 변경된 담당 상태를 알고 잘못 게시하지 않기 위해서다.
24. 사용자로서, 배정 이후 이미 작성한 내 업무 댓글이 있으면 ‘이미 답함’으로 처리하고 싶다. 답한 요청에 초안이 또 생기는 것을 피하기 위해서다.
25. 사용자로서, 배정 전에 작성한 내 댓글 때문에 새 초안이 생략되지 않기를 원한다. 과거 대화와 새 배정에 대한 답변을 구분하기 위해서다.
26. 사용자로서, 앱을 다시 켜도 업무별 처리 기록이 유지되기를 원한다. 재시작으로 초기 초안이 중복 생성되지 않기 위해서다.
27. 사용자로서, Flow 조회 실패를 담당 해제나 업무 완료로 오판하지 않기를 원한다. 연결 문제 때문에 요청이 잘못 제외되지 않기 위해서다.

## Implementation Decisions

- 담당자 지정은 직접 멘션과 다른 감지 사유다. 기존 멘션 판정의 직접 지목 확인을 우회해 가짜 멘션으로 저장하는 방식은 사용하지 않는다.
- 알림 수집, 담당 업무 판정, 초안 대기열, 맥락 수집, 변화 감시, 게시 전 확인, 상태 저장과 검토 화면에 담당 업무 초안의 의미를 연결한다. 기존 저장소 선택·초안 실행·검토·승인 후 게시 동작을 재사용한다.
- 개인용 Flow 알림 조회의 `WORKER` 필터는 업무 후보 발견 수단이다. `workerYn`이나 일반 알림 발생만으로 신규 배정이라고 판정하지 않는다. 현재 담당자와 초기 기준 상태, 업무별 처리 기록을 함께 확인한다.
- 생성 시 지정과 생성 후 지정 모두 대상이며, 업무 생성 시각을 배정 시각으로 대체하지 않는다. 최초 동기화에서는 기존 담당 업무를 자동 초안 대상에서 제외하기 위한 기준을 마련한다.
- 알림 누락을 보완하는 프로젝트 업무 목록 조회는 조사된 구현 후보다. 담당자 필터·담당자 원본 구조·호출 범위를 실제 응답으로 확인한 뒤 조회 방식을 확정한다. 전체 프로젝트를 무제한으로 조회하거나 즉시·무누락 감지를 보장하는 계약은 두지 않는다.
- Flow 연동 인터페이스에는 업무와 게시글 식별자, 현재 담당자, 업무 작성자, 완료 상태, 배정 시점 판단 근거가 필요하다. 업무 식별자와 게시글 식별자가 같다고 가정하지 않는다. 공개 문서에 세부 구조가 없는 값은 실응답으로 검증한다.
- 업무별 최초 처리 기록은 계정·업무를 구분하며 재시작 후에도 유지한다. 필요한 프로젝트 식별자를 함께 보존한다. 알림 중복 제거와 업무별 최초 초안 생성 여부를 분리한다.
- 발견·진행·실패·완료를 구분하여 실패를 성공적인 최초 생성으로 기록하지 않는다. 기존 저장 데이터의 호환성과 계정 전환 시 기록 격리를 유지한다. 구체적인 저장 구조는 기존 상태 저장 계층을 확장한다.
- 같은 업무 본문의 멘션과 담당자 지정은 초안 하나로 합친다. 합쳐진 상태에서도 각 감지 사유를 구분할 수 있어야 하며 이후 댓글 멘션은 기존 흐름으로 처리한다.
- 초안 입력의 답변 대상은 최신 제목·본문이고 댓글은 보조 맥락이다. 과거 생성 시점 본문 복원은 하지 않는다. 담당자 변경 시스템 문구를 사용자의 요청 본문으로 사용하지 않는다.
- 담당 업무 초안은 업무 작성자를 기본 받는 사람으로 사용하고 사용자가 제거할 수 있다. 담당자 지정자의 신원은 기본 받는 사람을 바꾸지 않는다.
- 생성 중 담당 해제를 확인하면 실행을 중단한다. 준비된 초안은 해제 사유와 함께 보존하고 게시를 막는다. 조회 실패를 담당 해제로 단정하지 않는다. 기존 변화 감시와 게시 전 확인에 이 조건을 반영한다.
- 배정 이후 작성한 내 업무 댓글이 있으면 생성 전에 ‘이미 답함’으로 처리한다. 배정 전 댓글과 시스템 변경 기록은 답변으로 취급하지 않는다. 배정 시점 근거가 불명확한 사례를 임의 시각으로 확정하지 않는다.
- 새 배정 시 이미 완료된 업무는 자동 초안 대상에서 제외한다. 사용자 정의 상태 표시 이름만으로 완료 여부를 추정하지 않고 Flow의 실제 상태 표현을 확인한다.
- 검토 화면은 담당 업무 초안의 출처와 제외 사유를 구분해 보여 주고, 기존 수정·받는 사람 제거·게시 동작을 유지한다. 새로운 별도 검토 화면이나 전면 재설계는 요구하지 않는다.
- 기존 Electron 기반 구조와 업데이트 신뢰 계약은 유지한다. 기술 검증이 합의된 동작을 뒷받침하지 못하면 제약을 보고하고, 제품 기준을 임의로 완화하지 않는다.

## Testing Decisions

아래 검증 경계는 2026-10-29 사용자 확인을 받아 확정했다.

2026-10-30 변경: 다른 사람이 업무를 생성하면서 본인을 담당자로 지정한 실제 사례는 사용자 합의에 따라 구현 후 사용하면서 검증한다. 이 사례의 확보는 구현 착수의 선행 조건에서 제외하고 06번 최종 검증에서 추적한다. 실제 검증 완료로 표시하지 않으며, 생성 시 지정의 자동 테스트와 나머지 판별 계약 검증은 유지한다.

- **주된 자동 검증 경계 하나:** 기존 초안 대기열 통합 테스트 구조에서 실제 감지·업무 묶음 처리·맥락 수집·저장소 연결·초안 생성·게시 서비스를 함께 실행한다. Flow, 시계와 에이전트 실행만 기존 대역으로 제어하고, 외부에서 관찰되는 초안 수·입력 대상·상태·게시 결과를 검증한다. 내부 함수 호출 순서나 사설 필드 구조를 고정하는 테스트는 작성하지 않는다.
- 선행 사례는 기존 초안 대기열 테스트의 감지부터 게시까지 이어지는 서비스 조합이다. 담당 해제와 게시 차단은 기존 변화 감시·게시 전 확인 사례, 이미 답함은 기존 댓글 판정 사례를 확장한다.
- 생성 시 지정, 생성 후 지정, 오래된 업무 신규 배정, 기능 시작 전 담당 업무 제외, 자기 작성 업무 제외, 복수 담당자 포함, 완료 업무 제외를 검증한다.
- 반복 알림·일반 댓글·상태 변경·해제 후 재지정에 대한 중복 방지, 멘션 동시 발생의 초안 합치기, 후속 댓글 멘션의 독립 처리를 검증한다. 수동 재생성과 실패 재시도를 자동 중복 방지와 구분한다.
- 생성·검토·게시 직전의 담당 해제, 배정 전후 내 댓글, 조회 실패 시 잘못된 제외 방지, 작성자 멘션 기본값과 제거를 검증한다.
- **필요한 보조 검증:** 외부 응답 해석은 기존 Flow 어댑터 테스트에 마스킹된 실제 응답 사례를 추가한다. 새 저장 필드와 중복 방지의 재시작 지속성은 기존 실제 데이터베이스·마이그레이션 테스트를 확장한다. 새 테스트 계층을 만들지 않는다.
- 검토 화면 변경은 기존 화면 테스트를 확장하고 실제 데스크톱 앱에서 초안 표시·해제 사유·게시 불가 상태를 확인한다. 서비스 테스트 통과를 화면 검증으로 대신하지 않는다.
- **실제 Flow 검증은 별도 증거:** 생성 시 지정과 생성 후 지정의 실제 후보 발견, 담당자·완료 상태·배정 시점 근거를 접근 가능한 사례에서 확인한다. 가짜 응답의 통합 테스트 통과만으로 실제 Flow 감지 완료를 선언하지 않는다. 외부 업무 생성·변경·게시가 필요한 재현은 해당 실행 범위를 확인한 뒤 수행한다.
- 구현 완료 시 마지막 변경 이후의 정적 검사·관련 자동 테스트·필요한 데스크톱 및 실제 Flow 검증 결과를 구분해 보고한다. 이 스펙 작성 자체는 테스트 실행이나 제품 검증을 뜻하지 않는다.

## Out of Scope

- 코드 자동 수정·커밋·배포 및 사용자 승인 없는 댓글 게시.
- 기능 시작 전부터 담당하던 업무의 일괄 초안 생성.
- 생성 당시 수정 전 본문 복원과 담당자 변경의 전체 이력 복원.
- 담당 재지정·일반 댓글·상태 변경마다 초기 초안을 자동으로 다시 만드는 기능.
- 직접 멘션의 기존 의미 변경, 후속 댓글 멘션의 제거, 기존 저장소 선택 흐름의 교체.
- 전면 화면 재설계, 앱 배포·업데이트 구조 변경, 이번 스펙 발행과 동시에 구현 티켓 생성 또는 구현 시작.
