# 최근 멘션 확인: 감지에서 빠진 멘션·담당 업무 수동 진행

Status: ready-for-agent
작성일: 2026-11-13

## Problem Statement

Stardraft는 Flow 알림을 60초마다 조회해 새 멘션과 담당 업무를 자동 감지하고 초안을 만든다. 그런데 자동 감지 목록에 오르지 않는 항목이 생긴다. 72시간이 지난 멘션, 앱이 꺼져 있던 동안의 멘션, 감지 기준점 앞의 항목, 기능을 켜기 전 업무, 판정 규칙이 잘못 걸러 낸 멘션(예: 사람이 쓴 멘션인데 시스템 댓글로 오인된 경우)이 그렇다. 사용자는 이런 항목을 직접 골라 초안을 만들고 평소처럼 검토·게시하고 싶다.

지금은 설정과 빈 화면의 [최근 멘션으로 시험]만 있다. 이 경로는 고른 멘션을 "시험 묶음"으로 만들기 때문에 Flow에 게시할 수 없고, 끝내거나 무시하면 기록째 지워진다. 한 번에 하나만 만들 수 있고 담당 업무는 고를 수 없다. 버튼도 묶음이 없는 빈 화면에만 보여서 이미 묶음이 있으면 설정까지 들어가야 한다. 사용자는 시험으로 멘션 댓글 초안을 써 본 뒤, 같은 방식으로 담당 업무도 진행하고 싶어 했다.

## Solution

시험 기능을 없애고 **최근 멘션 확인**으로 합친다. 작은 창 머리의 ⋯ 메뉴에서 열고, 멘션과 담당 업무를 탭으로 나눠 최근 항목을 보여 준다. 사용자가 하나를 고르면 게시할 수 있는 실제 묶음이 만들어져 기존 검토 흐름으로 이어진다. 게시 버튼을 누르기 전에는 Flow에 아무것도 올라가지 않는다.

- 목록은 최신순이고 "더 보기"로 10건씩 이어서 불러온다.
- 감지의 72시간 제한, 기준점, 기존 기록 여부는 보지 않는다. 멘션은 기존 판정 규칙(내게 온 멘션인지 등)만 통과하면 나온다. 담당 업무는 내가 담당자인 활성(요청) 업무만 나오고, 기능 시작 전 업무와 기능 시작 전 배정, 자기 작성 업무, 배정 근거가 없는 업무도 고를 수 있다.
- 각 줄에 이미 묶음이 있는지, 이미 답했는지, 감지에서 빠진 이유가 무엇인지를 태그로 보여 준다.
- 이미 묶음이 있는 항목을 고르면 새로 만들지 않고 그 묶음으로 이동한다.
- 수동으로 만든 묶음은 감지 기준점을 옮기지 않는다.

## User Stories

1. 사용자로서, 작은 창 머리의 ⋯ 메뉴에서 "최근 멘션 확인"을 열고 싶다. 묶음이 있을 때도 설정에 들어가지 않고 쓸 수 있기 때문이다.
2. 사용자로서, 묶음이 없는 빈 화면과 설정 "초안" 칸에서도 같은 "최근 멘션 확인"을 열고 싶다. 기존에 찾던 자리에서 계속 쓸 수 있기 때문이다.
3. 사용자로서, "펼쳐 보기"도 같은 ⋯ 메뉴 안에서 찾고 싶다. 머리가 깔끔하게 유지되기 때문이다.
4. 사용자로서, 감지를 시작하지 않았거나 Flow 키가 없으면 이 기능이 막혀 있고 이유가 보이기를 원한다. 왜 목록이 안 열리는지 알 수 있기 때문이다.
5. 사용자로서, 멘션과 담당 업무를 탭으로 나눠 보고 싶다. 찾는 종류만 훑을 수 있기 때문이다.
6. 사용자로서, 멘션 탭이 먼저 열리기를 원한다. 가장 자주 쓰는 목록이기 때문이다.
7. 사용자로서, 담당 업무 탭은 열 때만 불러오기를 원한다. 쓰지 않는 조회로 Flow 사용량을 낭비하지 않기 때문이다.
8. 사용자로서, 최근 항목을 최신순으로 10건씩 보고 싶다. 필요한 항목이 위쪽에 있기 때문이다.
9. 사용자로서, "더 보기"로 10건씩 이어서 불러오고 싶다. 더 오래된 항목이 필요할 때만 조회 비용을 쓸 수 있기 때문이다.
10. 사용자로서, 더 보기에 끝이 있으면 "더 이상 없음"을 알고 싶다. 계속 눌러 보지 않기 위해서다.
11. 사용자로서, 72시간이 지난 멘션도 목록에서 보고 싶다. 앱이 꺼져 있던 동안 온 멘션을 진행할 수 있기 때문이다.
12. 사용자로서, 감지 기준점 앞의 멘션도 목록에서 보고 싶다. 기준점이 정해지던 때 놓친 항목을 진행할 수 있기 때문이다.
13. 사용자로서, 감지 규칙이 잘못 걸러 낸 멘션도 목록에 나오기를 원한다. 규칙 결함이 있어도 수동으로 처리할 길이 있기 때문이다.
14. 사용자로서, 나에게 온 멘션이 아닌 알림(`@전체` 등)은 목록에 나오지 않기를 원한다. 고를 필요가 없는 항목에 묻히지 않기 위해서다.
15. 사용자로서, 담당 업무 탭에서 내가 담당자이고 활성(요청) 상태인 업무를 보고 싶다. 초안을 만들 대상이 분명하기 때문이다.
16. 사용자로서, 기능 시작 전부터 맡던 업무도 담당 업무 탭에서 보고 싶다. 자동 감지에서 제외된 업무를 직접 진행할 수 있기 때문이다.
17. 사용자로서, 기능 시작 전에 배정된 업무와 내가 만든 업무도 담당 업무 탭에서 고를 수 있기를 원한다. 자동 규칙의 제외를 내 판단으로 풀 수 있기 때문이다.
18. 사용자로서, 배정 시점 근거가 없는 업무도 고를 수 있기를 원한다. 근거 때문에 막히지 않기 위해서다. 이때 배정 시각은 알림 시각이고 추정이라는 표시가 있어야 한다.
19. 사용자로서, 진행·피드백·보류·완료 상태의 업무는 목록에 나오지 않기를 원한다. 답변이 필요한 요청만 고르기 위해서다.
20. 사용자로서, 업무가 여럿인 게시글은 목록에 나오지 않기를 원한다. 어느 업무에 대한 배정인지 모호하기 때문이다.
21. 사용자로서, 담당 업무 탭에서 알림이 없는 업무는 나오지 않는다는 한계를 안내 문구에서 알고 싶다. 목록에 없는 이유를 이해할 수 있기 때문이다.
22. 사용자로서, 각 줄에서 보낸 사람, Flow 프로젝트, 첫 줄, 시각을 보고 싶다. 어떤 요청인지 알아보고 고를 수 있기 때문이다.
23. 사용자로서, 담당 업무 줄에서 "기능 시작 전 업무" 같은 감지에서 빠진 이유를 태그로 보고 싶다. 왜 자동으로 안 왔는지 알 수 있기 때문이다.
24. 사용자로서, 이미 답한 항목에 "답함" 태그를 보고 싶다. 그래도 고를 수 있어야 한다. 답을 알고도 새 초안을 만들 때가 있기 때문이다.
25. 사용자로서, 이미 묶음이 있는 항목에 "이미 묶음 있음"과 그 묶음의 상태(검토 중, 게시됨, 무시함 등)를 보고 싶다. 중복으로 만들지 않기 위해서다.
26. 사용자로서, 이미 묶음이 있는 항목을 고르면 새로 만들지 않고 그 묶음으로 이동하고 싶다. 같은 요청에 초안이 둘 생기지 않기 위해서다.
27. 사용자로서, 이동한 묶음에서 상태에 맞는 [다시 시도]나 [되돌리기]를 쓰고 싶다. 기존 복구 경로를 그대로 쓸 수 있기 때문이다.
28. 사용자로서, 처리한 지 7일이 지나 최소 기록만 남은 항목은 수동으로 새 묶음을 만들고 싶다. 되돌릴 수 없는 항목도 다시 진행할 수 있기 때문이다.
29. 사용자로서, 항목을 고르면 게시할 수 있는 실제 묶음이 만들어지기를 원한다. 이 초안을 Flow에 올릴 수 있어야 하기 때문이다.
30. 사용자로서, 게시 버튼을 누르기 전에는 Flow에 아무것도 올라가지 않는다는 점을 목록에서 안내받고 싶다. 안심하고 고를 수 있기 때문이다.
31. 사용자로서, 고른 멘션이 이미 답한 것이어도 "이미 답함"으로 조용히 처리되지 않고 초안이 만들어지기를 원한다. 눌렀는데 아무 일도 없는 상황을 피하기 위해서다.
32. 사용자로서, 만든 묶음이 게시 직전의 변화 감시(그사이 내가 답했는지 등)는 일반 묶음처럼 받기를 원한다. 게시 안전장치가 같기 때문이다.
33. 사용자로서, 하나를 만든 뒤 이어서 다른 멘션이나 업무를 더 고르고 싶다. 여러 항목을 연달아 진행할 수 있기 때문이다.
34. 사용자로서, 여러 항목을 만들면 초안이 한 번에 하나씩 순서대로 만들어지기를 원한다. 에이전트 사용량이 고른 만큼만 쓰이기 때문이다.
35. 사용자로서, 수동으로 만든 묶음이 저장소 매핑이 없는 프로젝트면 일반 묶음처럼 "저장소 확인 필요"로 올라오기를 원한다. 기존 저장소 선택 흐름을 그대로 쓰기 위해서다.
36. 사용자로서, 수동으로 만든 묶음이 일반 묶음처럼 초안 준비됨 알림과 트레이 검토 수에 잡히기를 원한다. 검토할 항목을 놓치지 않기 위해서다.
37. 사용자로서, 수동 묶음이 "수동 요청"으로 표시되기를 원한다. 자동 감지로 온 묶음과 구분할 수 있기 때문이다.
38. 사용자로서, 수동으로 만든 묶음이 감지 기준점을 옮기지 않기를 원한다. 그 사이의 다른 미감지 멘션이 영구히 사라지지 않기 위해서다.
39. 사용자로서, 수동으로 만든 뒤 같은 위치의 새 알림이 와도 자동 감지가 묶음을 또 만들지 않기를 원한다. 중복 초안을 막기 위해서다.
40. 사용자로서, 목록을 불러오지 못하면 이유(키 없음, 키 거부, 연결 실패, 요청 한도)를 쉬운 말로 보고 [다시 불러오기]를 누르고 싶다. 원인을 알고 다시 시도할 수 있기 때문이다.
41. 사용자로서, 목록을 불러오는 동안 진행 중임이 보이기를 원한다. 멈춘 줄 알고 닫지 않기 위해서다.
42. 사용자로서, 목록에서 Esc로 닫고 싶다. 키보드로 빠르게 닫을 수 있기 때문이다.
43. 사용자로서, 이 기능이 Flow의 읽음 상태를 바꾸지 않기를 원한다. 목록을 훑어도 모바일 알림 상태가 달라지지 않기 위해서다.
44. 사용자로서, 시험 묶음과 "[시험] …" 알림, [시험 끝내기], "시험" 태그가 앱에서 사라지기를 원한다. 같은 기능이 두 이름으로 남지 않기 위해서다.
45. 사용자로서, 업데이트 직후 진행 중이던 시험 묶음이 남아 있지 않기를 원한다. 게시할 수 없는 묶음이 목록에 남지 않기 위해서다.
46. 사용자로서, 트레이 "알림 확인"과 설정 "지금 확인"(업데이트)은 그대로이기를 원한다. 익숙한 동작이 바뀌지 않기 위해서다.

## Implementation Decisions

- **용어**: 앞으로 "시험"과 "시험 묶음"은 쓰지 않는다. 새 용어는 "최근 멘션 확인"(기능), "수동 요청 묶음"(이 기능으로 만든 실제 묶음)이다. 이 저장소에는 `GLOSSARY.md`가 없으므로 용어는 이 스펙과 `flow-mention-drafter` 스펙 갱신으로 정리한다.
- **시험 기능 폐지**: 시험 묶음 표시, [시험 끝내기], 시험 묶음 삭제 규칙, 시험 전용 대기열 우선순위, "[시험] …" 알림, 시험 진행 상태와 그 IPC 명령을 모두 정리한다. 업데이트 후 첫 실행에서 남아 있는 시험 묶음은 기존 "진행 중이던 시험 묶음 삭제" 규칙대로 지운다.
- **입구**: 작은 창 머리에 아이콘 ⋯ 메뉴를 두고 "최근 멘션 확인"과 "펼쳐 보기"를 그 안에 둔다. 빈 화면과 설정 "초안" 칸의 기존 버튼 자리는 새 이름으로 유지한다. 열려면 감지를 시작했고 쓸 수 있는 Flow 키가 있어야 한다(기존 시험과 같은 조건). 목록 창은 시험 고르기 시트와 같은 방식으로 현재 창 위에 시트로 연다.
- **목록 구성**: 시트 제목은 "확인할 항목 고르기"이고 위쪽에 "멘션 | 담당 업무" 탭이 있다. 멘션 탭이 기본이다. 담당 업무 탭은 처음 열 때 조회한다. 각 탭은 자기 "더 보기" 커서와 "다시 불러오기"를 가진다.
- **멘션 목록 조회**: 기존 최근 멘션 조회를 이어 쓴다. 기존 판정 규칙을 그대로 적용하고 72시간 제한, 기준점, 기존 기록 여부는 보지 않는다. 상한 10건은 "한 번에 불러오는 개수"로 바꾸고, 이어 불러오기는 직전 알림 쪽 커서에서 이어 간다. 한 번에 훑는 쪽 수 상한은 유지한다. Flow 읽음 상태는 바꾸지 않는다.
- **담당 업무 목록 조회**: 최근 WORKER 알림을 최신순으로 받아 게시글별로 가장 최근 알림을 남기고, 게시글 상세를 조회해 후보를 정한다.
  - 후보 조건(유지하는 규칙): 업무가 하나뿐인 게시글, 내가 담당자, 활성(요청) 상태. 내 계정의 알림만 본다.
  - 풀어 주는 규칙: 기능 시작 전 업무, 기능 시작 전 배정, 자기 작성 업무, 배정 근거 없음. 배정 시점 근거는 목록에서 판정하지 않는다. 근거가 있으면 그 시각을, 없으면 알림 시각을 "배정 시각(추정)"으로 쓴다. 추정임을 묶음 상세에 표시한다.
  - 알림이 없는 업무(알림이 오기 전에 배정된 업무)는 목록에 나오지 않으며, 목록 안내 문구에 이 한계를 적는다.
  - 감지에서 빠진 이유는 줄 태그로 보인다. 기능 시작 전 업무, 기능 시작 전 배정, 자기 작성 업무, 배정 근거 없음 네 가지다.
- **줄 상태 태그**: 줄마다 "답함"(내 답이 묶음 자리에 있음), "이미 묶음 있음"과 그 묶음 상태, "처리됨"(최소 기록만 남음)을 보인다. 묶음이나 최소 기록은 멘션 위치(멘션)와 본문 자리(업무) 기준으로 찾는다.
- **고르기 동작(멘션과 업무 공통)**:

  - 기록이 전혀 없으면 새 묶음을 만든다.
  - 한 번에 하나만 고르며, 고른 뒤 목록 시트는 닫는다. 연달아 쓰려면 다시 연다.
- **수동 요청 묶음**: 게시할 수 있는 실제 묶음이다. 만들 때 "이미 답함" 판정을 하지 않는다. 일반 묶음과 같은 저장소 매핑·자동 선택 규칙을 따르고, 대기열에는 사용자가 누른 작업이므로 기존 사용자 우선 규칙(재시도·재생성과 같은 줄)을 따른다. 초안 실행 직전의 "이미 답함" 재판정은 수동 요청 묶음에서도 건너뛴다. 게시 직전 확인과 변화 감시는 일반 묶음과 같다. 수동 요청 여부는 묶음에 표시로 남기고 상세 머리에 "수동 요청" 태그를 보인다.

## Testing Decisions

아래 검증 경계는 이 대화에서 제안한 것이다. 사용자가 확정하기 전까지는 제안이다.

- **좋은 테스트의 기준**: 외부에서 관찰되는 결과만 검증한다. 만들어진 묶음 수, 묶음 상태, 초안 입력 대상, 목록에 보이는 줄과 태그, 기준점과 기존 기록이 바뀌었는지 여부, 게시 가능 여부다. 내부 함수 호출 순서나 사설 필드 구조를 고정하는 테스트는 쓰지 않는다.
- **주된 자동 검증 경계 하나**: 기존 묶음 서비스·초안 대기열 통합 테스트 구조에서, 수동 확인 목록 조회와 수동 요청 묶음 생성을 함께 실행한다. Flow, 시계, 에이전트 실행만 기존 대역으로 제어한다. 선행 사례는 기존 묶음 서비스 테스트의 감지부터 묶음 생성까지 이어지는 조합과 초안 대기열 테스트다.
- **검증할 동작**
  - 멘션: 72시간이 지난 멘션과 기준점 앞의 멘션이 목록에 나오고 고르면 게시할 수 있는 묶음이 된다. 나에게 온 멘션이 아닌 알림은 나오지 않는다. "더 보기"가 다음 10건을 이어서 불러오고 끝에서 멈춘다.
  - 담당 업무: 활성 업무가 나온다. 진행·완료 업무, 업무가 여럿인 게시글, 내가 담당자가 아닌 업무는 나오지 않는다. 기능 시작 전 업무, 시작 전 배정, 자기 작성, 배정 근거 없음은 나오고 올바른 "빠진 이유" 태그가 붙는다. 근거 없는 업무의 배정 시각은 추정으로 표시된다.
  - 이미 묶음이 있는 항목은 새 묶음이 만들어지지 않고 기존 묶음이 열린다. 7일이 지나 최소 기록만 남은 항목은 새 묶음이 만들어지고 최소 기록이 사라진다.
  - "이미 답함"인 항목도 초안이 만들어지고, 초안 실행 직전에도 이미 답함으로 처리되지 않는다. 게시 직전 확인은 일반 묶음처럼 동작한다.
  - 수동 묶음을 만든 뒤 감지 기준점과 담당 업무 감지 상태가 그대로이고, 같은 위치의 알림이 와도 자동 감지가 묶음을 만들지 않는다. 담당 업무는 같은 본문 자리가 중복되지 않는다.
  - 목록 조회 실패(키 없음, 키 거부, 연결 실패, 요청 한도)가 사용자 문구로 나오고 다시 불러올 수 있다. Flow의 읽음 상태는 바뀌지 않는다.
  - 시험 폐지: 시험 묶음 표시, [시험 끝내기], "[시험] …" 알림이 더 이상 만들어지지 않는다. 업데이트 후 첫 실행에서 시험 묶음이 정리된다.
- **필요한 보조 검증**: 외부 응답 해석(WORKER 알림 쪽 커서, 게시글 상세의 업무·담당자·상태)은 기존 Flow 어댑터 테스트에 마스킹된 실제 응답 사례를 추가한다. 새 저장 필드(수동 요청 표시)와 시험 묶음 정리의 재시작 지속성은 기존 실제 데이터베이스·마이그레이션 테스트를 확장한다. 새 테스트 계층을 만들지 않는다.
- **화면 검증**: 작은 창 ⋯ 메뉴, 시트의 탭·줄 태그·더 보기·실패 문구는 기존 화면 테스트를 확장한다. 서비스 테스트 통과를 화면 검증으로 대신하지 않고, 실제 데스크톱 앱에서 ⋯ 메뉴와 목록이 설계대로 보이는지 확인한다.
- **실제 Flow 검증은 별도 증거**: 실제 Flow에서 최근 WORKER 알림과 게시글 상세가 목록 조건대로 해석되는지, 목록에서 고른 항목이 실제로 게시되는지는 사용자의 수동 통합 테스트로 확인한다. 가짜 응답의 통합 테스트 통과만으로 실제 Flow 동작 완료를 선언하지 않는다.
- 구현 완료 시 마지막 변경 이후의 정적 검사·관련 자동 테스트·필요한 데스크톱 검증 결과를 구분해 보고한다. 이 스펙 작성 자체는 테스트 실행이나 제품 검증을 뜻하지 않는다.

## Out of Scope

- 기간을 지정해 놓친 항목을 한꺼번에 다시 스캔하는 백필과 일괄 초안 생성.
- 알림이 없는 담당 업무(알림이 오기 전에 배정된 업무)를 직접 조회하는 경로.
- 여러 항목을 체크해 한 번에 만드는 다중 선택.
- 에이전트 실패 묶음의 일괄 다시 시도, 전역 실패를 묶음 실패가 아닌 대기열 멈춤으로 다루는 변경(조사 문서의 (c)안).
- 자동 감지 규칙 자체의 변경. 감지가 잘못 걸러 낸 멘션은 규칙을 고치는 별도 작업으로 다룬다.
- 트레이 "알림 확인"과 설정 "지금 확인"의 이름 변경.
- 업무가 여럿인 게시글과 요청이 아닌 업무 범주(진행·피드백·보류·완료)의 수동 진행.
- 실제 Flow 감지·게시의 에이전트 검증. 이 부분은 구현 뒤 사용자의 수동 통합 테스트로 옮긴다.
