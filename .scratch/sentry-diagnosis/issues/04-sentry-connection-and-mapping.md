# Sentry 계정 연결, 진단 대상 필터, 저장소 매핑 설정

Status: resolved
Blocked by: 01

## Question

사용자가 Sentry를 연결하고 진단 대상을 정하는 흐름을 확정한다.

- 어떤 토큰을 어떤 scope로 받고 어디에 저장하는지(Flow 개인 키처럼 safeStorage를 쓸지), 연결 확인은 무엇으로 하는지.
- 조직이 여럿일 때의 처리, 프로젝트를 등록하는 단위.
- 환경·레벨 필터를 프로젝트마다 둘지 전체에 하나 둘지, 기본값.
- Sentry 프로젝트와 저장소를 잇는 **저장소 매핑**을 설정하는 화면과 시점(Flow 매핑 화면과 합칠지).
- 연결을 처음 했을 때 이미 열려 있던 오류 이슈를 기준 상태로 보고 건너뛸지.

## Answer

2026-11-12 grilling 세션에서 정했다. 근거 사실은 [API 조사](../research/sentry-api-facts.md)와 Flow 쪽 코드(`core/account/flow-account.ts`, `core/repos/repo-mappings.ts`, `core/onboarding/onboarding.ts`, `core/detection/mention-detection.ts`)다.

### 토큰과 연결 확인

- **개인 토큰(User Auth Token)** 하나만 받는다. 안내할 scope는 `org:read` + `event:read`다. 회사 조직도 본인 Sentry 계정이 그 조직의 구성원이면 쓸 수 있다. 조직 토큰(`org:ci` 고정)과 OAuth는 쓰지 않는다.
- 연결 확인은 두 단계다.
  1. `GET /api/0/organizations/`를 불러 조직이 하나 이상 나오는지 본다(`org:read` 확인).
  2. 프로젝트를 등록할 때 그 프로젝트로 오류 이슈 목록을 `limit=1`로 한 번 불러 본다(`event:read` 확인).
  - 실패하면 빠진 scope를 짚어 알린다.
- 토큰은 Flow 키처럼 safeStorage로 암호화해 별도 파일(`sentry-token.bin`)에 둔다.
- 401·403이 오거나 저장된 토큰을 풀 수 없으면 전역 문제 `sentry-token`("토큰 확인 필요")을 올리고 **Sentry 감지만** 멈춘다. 이유(거부·scope 부족·읽기 불가)는 구분해 표시한다. Flow 키 문제와 Sentry 토큰 문제는 서로의 감지·대기열을 멈추지 않는다. 새 토큰이 확인되면 문제를 해제한다.

### 조직과 프로젝트 등록

- 토큰 하나로 보이는 여러 조직을 모두 허용한다. 조직마다 조직 목록 응답의 `links.regionUrl`을 저장해 이후 호출의 기준 주소로 쓴다.
- 진단 대상은 사용자가 명시적으로 등록한 Sentry 프로젝트만이다(옵트인, 기본은 미등록). 등록 단위는 "조직/프로젝트"이고, 이름(slug)이 바뀌어도 끊기지 않게 프로젝트 `id`를 키로 쓴다.
- 등록한 프로젝트가 삭제되거나 권한을 잃어 404·접근 거부가 나면 **그 프로젝트만** 감지를 멈추고 설정 화면의 해당 줄에 "접근 불가"를 표시한다. 다른 프로젝트·조직은 계속 돈다. 토큰 자체가 무효(401)일 때만 전역 문제로 올린다.

### 진단 대상 필터

- 환경·레벨 필터는 **프로젝트마다** 둔다.
- 환경은 프로젝트 목록 응답의 `environments`에서 고른다. 기본값은 `production`이 있으면 그것이고, 없으면 사용자가 고른다.
- 레벨 기본값은 `error`·`fatal`이다.
- 환경은 쿼리 파라미터라서 폴링 호출이 프로젝트마다 나뉜다. 한도 안이라 받아들인다.

### 기준 시각

- 프로젝트를 **등록한 시각**을 그 프로젝트의 기준 시각으로 저장한다. 신규는 `firstSeen`이 기준 시각보다 뒤인 것만, 재발은 기준 시각 뒤에 재발한 것만 진단한다. 등록할 때 이미 열려 있거나 재발 상태였던 오류 이슈는 건너뛴다. 과거 오류 이슈를 골라 진단하는 기능은 두지 않는다.
- 등록을 해제했다가 다시 등록하면 기준 시각을 새로 잡는다(해제 기간의 오류 이슈는 진단하지 않음). 필터를 바꿀 때는 기준 시각을 유지한다.

### 저장 위치

- 등록 목록, 조직별 `regionUrl`, 필터, 기준 시각, Sentry 저장소 매핑은 Flow 저장소 매핑과 같은 `settings.json`에 둔다. 매핑 키는 Flow 프로젝트 id와 겹치지 않게 프로바이더를 구분한다(예: `sentry:{조직}/{프로젝트 id}`). 그래서 Flow 계정 리셋(`resetForAccount`, state.db만 지움)에도 남는다.
- 감지 체크포인트·중복 억제·진단 상태처럼 실행 중에 바뀌는 상태의 위치는 이 티켓에서 정하지 않았다(지도의 Not yet specified).

### 화면

- 설정 창에 `Sentry` 칸을 새로 둔다. 여기서 토큰 입력, 조직/프로젝트 등록, 환경·레벨 필터를 다룬다.
- 저장소 매핑은 `저장소` 칸 한 곳에 "Flow 프로젝트"와 "Sentry 프로젝트" 묶음으로 나눠 모은다. 매핑은 등록할 때 필수가 아니다(매핑이 없을 때의 처리는 [06](06-unmapped-sentry-project.md)).
- 구체적인 UI는 시안을 보고 정한다: [09 Sentry 설정 칸·저장소 매핑·온보딩 화면 시안](09-sentry-settings-ui-prototype.md).

### 서버

- 공식 sentry.io만 지원한다. 서버 주소 설정은 두지 않는다. 미국·독일 지역 주소는 `regionUrl`로 자동 처리한다. 차팅 때 지도에 남은 "서버 주소만 설정으로 바꿀 수 있게 열어 둔다" 전제는 사용자와의 이전 합의와 어긋나 있어 지도에서 고쳤다.

### 온보딩: 모든 프로바이더는 선택

- 어떤 프로바이더도 필수가 아니다. 지금 코드의 필수 항목(`SETUP_REQUIREMENTS = ['flow-key','agent','work-folders']`)에서 `flow-key`를 빼서 **에이전트 연결과 작업 폴더**만 필수로 둔다.
- 체크리스트에서 Flow·Sentry 연결은 "선택" 항목으로 보인다. 각 프로바이더의 감지는 그 프로바이더를 연결했을 때 시작한다.
- 필수 항목을 마쳤는데 연결된 프로바이더가 없으면 막지 않고 "감지할 대상이 없다"는 안내만 띄운다.
- Flow 필수 해제(온보딩, `SetupBand`, 감지 시작 조건 변경)는 스펙 범위에 들어간다.
