# 저장소 매핑이 없는 Sentry 프로젝트의 오류 이슈 처리

Map: [Sentry 오류 이슈 진단 보고서](../map.md)
Type: grilling
Mode: HITL
Status: resolved
Blocked by: 01, 03

## Question

저장소 매핑이 없는 Sentry 프로젝트에서 오류 이슈가 왔을 때 어떻게 할지 정한다.

- 선택지: 건너뛰고 매핑을 요청하는 알림만 띄우기, 작업 폴더에서 **자동 선택**(Flow와 같은 방식), 스택트레이스 파일 경로·release로 저장소를 추정하기.
- 자동 선택이나 추정 결과를 사용자가 저장해 저장소 매핑으로 굳히는 흐름을 Flow와 같게 둘지.
- 매핑된 저장소가 여럿일 때 스택트레이스로 범위를 좁힐지.

## Answer

2026-11-12 grilling 세션에서 정했다. 근거는 Flow 쪽 코드(`core/repos/repo-mappings.ts`, `core/drafts/draft-queue.ts`의 자동 선택, `core/bundles/mention-bundle.ts`의 `RepoCheck`·`userRepos`)와 사용자의 `~/workspace` 저장소 점검 결과다.

### 매핑이 없으면 추측하지 않는다

- 저장소 매핑이 없는 Sentry 프로젝트의 오류 이슈는 진단하지 않고 **저장소 매핑 필요** 상태로 남긴다.
- **자동 선택**(작업 폴더에서 에이전트가 고르기)과, 스택트레이스 경로·release로 앱이 저장소를 추정하는 방식은 모두 쓰지 않는다. 사용자가 정하지 않은 저장소로 진단하지 않는다.
- 저장소 매핑 필요 상태의 오류 이슈는 버리지 않는다. 그 Sentry 프로젝트에 매핑을 저장하면 기다리던 오류 이슈를 진단 대기열에 자동으로 넣는다. 기준 시각이 이미 지났기 때문에 버리면 다시 잡을 수 없다. 오래 묵은 오류 이슈가 한꺼번에 몰리는 문제는 지도의 "따라잡기와 중복 억제"에서 함께 다룬다.
- 해결 수단은 **그 Sentry 프로젝트의 저장소 매핑을 저장하는 것** 하나뿐이다. Flow의 "이 묶음만 고르기"(`userRepos`)에 해당하는, 오류 이슈 하나에만 저장소를 고르는 경로는 두지 않는다. 저장소 매핑 필요 상태의 오류 이슈 화면에 있는 버튼은 그 프로젝트의 매핑 편집으로 이동한다.

### 매핑 하나에 저장소 하나

- Sentry 프로젝트 하나에는 저장소를 **하나만** 매핑한다. 그 저장소가 cwd이자 재현 사본 대상이고, 재현 여부는 그 저장소의 **재현 허용**을 따른다. 스택트레이스로 범위를 좁히는 문제는 생기지 않는다.
- 반대 방향은 막지 않는다. 같은 저장소를 여러 Sentry 프로젝트에 매핑할 수 있다. 사용자 workspace에서 Sentry를 실제로 연동한 곳은 모노레포(`apps/`마다 다른 Sentry 프로젝트) 하나였고, Sentry 프로젝트 하나가 여러 저장소에 걸친 경우는 없었다.
- 실제로 여러 저장소가 필요한 사례가 생기면 그때 여러 개로 넓힌다. 저장 형태는 Flow 매핑과 같은 배열로 두어 나중에 넓히기 쉽게 한다. 이것은 구현 재량이다.

### 매핑된 폴더가 사라졌을 때

- 매핑된 저장소 폴더가 없으면 Flow의 `missing-folders`와 같이 다른 곳으로 넘어가지 않고 **저장소 확인 필요**로 멈춘다. 폴더가 다시 생기거나 매핑을 고치면 저장소 매핑 필요와 같은 방식으로 자동 재개한다.

### 설정 화면 표시

- 등록할 때 매핑은 계속 선택이다. 대신 `Sentry` 칸의 프로젝트 줄과 `저장소` 칸에 "저장소 매핑 없음 · 진단 보류"를 표시한다. 등록과 매핑을 한 흐름으로 묶을지는 [09 Sentry 설정 칸·저장소 매핑·온보딩 화면 시안](09-sentry-settings-ui-prototype.md)에서 정한다.
- 알림을 띄우는 방식(트레이 알림, 묶어서 알릴지 등)은 지도의 "검토 화면과 알림"에서 정한다.
