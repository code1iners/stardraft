# 진단 실행 큐의 동시 실행과 우선순위

Map: [Sentry 오류 이슈 진단 보고서](../map.md)
Type: grilling
Mode: HITL
Status: resolved
Blocked by: 08

## Question

[프로바이더 공통 경계 결정](08-provider-seam-decision.md)에서 Flow와 Sentry가 하나의 **생성 대기열**을 쓰고 대상만 어댑터로 나누기로 했다. 그 대기열이 진단 실행(`RunKind` `'diagnosis'`, 상한 20분)을 Flow 초안과 함께 어떻게 돌릴지 정한다.

- **직렬 여부**: 지금은 직렬 하나다(`draft-queue.ts:207-208,221-224`). 진단 하나가 Flow 초안을 최대 20분 늦춰도 되는지, 아니면 진단 전용 슬롯을 두어 초안과 동시에 돌릴지 정한다. 같은 CLI 에이전트를 동시에 돌리면 로그인 세션과 사용량 한도를 함께 쓴다.
- **진단끼리 동시 실행**: 재현 실행은 시뮬레이터·dev 서버 포트를 나눠 쓴다. 진단을 한 번에 하나만 돌릴지 정한다.
- **우선순위**: 지금 `resume` > `user` > `auto`다. 진단은 모두 자동으로 들어온다. Flow 자동 초안과 진단 사이의 순서, 사용자가 다시 진단(지시)을 요청했을 때의 순서를 정한다.
- **시간 상한과 일시적 실패 재시도**: 종류별 `timeoutMs`(진단 20분)를 어댑터가 정하는 것은 확정이다. 20분짜리 실행이 일시적 실패로 끝났을 때도 1회 자동 재시도할지 정한다.
- **취소·앱 종료**: 재현 중 취소나 앱 종료 때 사본·새로 켠 시뮬레이터 정리를 기다릴지(지금은 최대 5초, `draft-queue.ts:48-52`) 정한다. Codex MCP 프로세스 정리는 [재현용 MCP 적용 방식 결정](11-reproduction-mcp-wiring.md)의 범위다.

## Answer

2026-11-23 grilling 세션에서 정했다. 근거 코드는 `apps/desktop/src/core/drafts/draft-queue.ts`다. 실행 자리는 `running` 하나이고, 칸은 `resume` > `user` > `auto`다. 일시적 실패(`invalid-output`·`overloaded`·`network`)는 즉시 1회 다시 실행하고, 앱 종료 때는 기록을 최대 5초(`QUIT_RECORD_WAIT_MS`) 기다린다. [경계 결정](08-provider-seam-decision.md)과 [ADR 0004](../../../docs/adr/0004-generation-queue-with-provider-adapters.md)의 "직렬 실행"을 이 답이 바꾼다.

### 동시 실행

- 생성 대기열은 최대 n개를 동시에 돌린다. n은 앱 전체 설정인 **병렬 작업 수**로, 1~5 사이 정수를 슬라이더로 고른다. 기본값은 1이고 지금과 같은 직렬이다.
- 값을 바꾸면 돌던 실행은 그대로 두고, 다음 실행을 꺼낼 때부터 새 값을 쓴다. 값을 줄여도 돌던 실행을 끊지 않는다.
- 종류별 제한은 하나뿐이다. **재현 허용**이 켜진 진단은 한 번에 하나만 돈다. 시뮬레이터와 dev 서버 포트가 한 벌이고, "새로 켜진 시뮬레이터만 정리" 규칙이 두 실행이 겹치면 성립하지 않기 때문이다. 재현하는 진단이 이미 돌고 있으면 다음 재현 진단은 자리를 지키며 기다리고, 대기열은 그 뒤에서 돌 수 있는 것을 꺼낸다.
- 재현이 꺼진 진단(읽기 전용)과 Flow 초안에는 제한이 없다. "진단 전체를 n−1개로 묶어 Flow 몫 자리를 남기는" 제한은 두지 않는다.
- 슬라이더의 자리와 문구는 [병렬 작업 수 설정 화면 시안](14-concurrency-setting-ui-prototype.md)에서 정한다.

### 순서

- 칸은 지금의 `resume` > `user` > `auto` 그대로다. 진단을 위한 칸은 더하지 않는다.
- 감지로 들어온 진단은 Flow 자동 초안과 같은 `auto` 칸에 들어온 순서대로 선다. 사용자가 요청한 진단(실패한 진단의 재시도, **지시**를 붙인 다시 진단)은 종류와 무관하게 `user` 칸이다. 다시 진단 흐름을 둘지는 지도의 "검토 화면과 알림"에서 정한다.
- 돌고 있는 실행을 다른 실행이 끊는 선점은 두지 않는다.
- 받아들인 대가: 병렬 작업 수가 1일 때 오류 이슈가 몰리면 Flow 자동 초안이 앞선 진단 수 × 최대 20분을 기다릴 수 있다. 줄이려면 사용자가 병렬 작업 수를 올린다.

### 일시적 실패 재시도

- 진단도 지금 규칙 그대로다. 구조화 출력 없음·모델 과부하·네트워크 오류면 즉시 1회 다시 실행하고, 시간 초과(20분 상한)·취소는 다시 실행하지 않는다. 종류별 예외는 없다.
- 받아들인 대가: 20분 가까이 돈 뒤 구조화 출력이 없으면 한 오류 이슈가 자리를 40분까지 잡는다.

### 전역 실패

- 한 실행의 실패가 전역 실패로 의심되어 연결 확인까지 실패하면, 대기열은 새 실행을 꺼내지 않고 멈춘다. 함께 돌던 실행은 끊지 않는다. 성공하면 결과를 저장하고, 실패하면 같은 판정을 거쳐 대기열로 돌아간다.

### 취소와 시간 상한

- 화면에는 바로 "취소함"(시간 상한이면 진단 실패의 "시간 초과")으로 보인다. 재현하는 진단은 상한 전에 사용자에게 연장을 묻고, 전달이 되는 에이전트에게는 끊기 전에 마무리를 시킨다([진단 실패와 데이터 부족의 처리](18-diagnosis-failure-handling.md)).
- 다음 재현 진단은 프로세스 종료와 새로 켠 시뮬레이터·에뮬레이터 끄기가 끝난 뒤에 시작한다. 다른 자리의 실행은 영향받지 않는다.
- 사본 삭제는 기다리지 않고 뒤에서 한다. 사본은 실행마다 경로가 달라 겹치지 않는다.

### 앱 종료

- 돌던 실행을 모두 끊고 시뮬레이터 종료 명령을 보낸 뒤, 합쳐서 최대 5초 기다리고 끈다.
- 남은 사본은 다음 시작 때 사본 폴더를 비워 지운다.
- 5초 안에 꺼지지 않은 시뮬레이터는 그대로 두고, 다음 시작 때 찾아서 끄지 않는다. 그사이 사용자가 직접 켠 것과 구분할 수 없기 때문이다.
- 끊긴 실행들은 다음 시작 때 원래 시작한 순서대로 `resume` 칸 맨 앞에 서고, 처음부터 다시 돈다.

### 구현 메모

- 실행 자리(`running`)를 여러 개로 바꾸면서 손댈 곳: 대기열 저장(끊긴 실행 하나가 맨 앞이라는 가정), 전역 실패 판정, 앱 종료 대기, 진행 단계 알림.
- 재현 진단 제한은 대기열이 종류를 알지 않도록, 어댑터의 `prepare`가 "함께 돌 수 없는 자원"을 알려 주는 식으로 받을 수 있다. 모양은 구현 재량이다.

### 스펙에 적을 실측 항목

- Claude Code·Codex를 같은 로그인으로 2~5개 동시에 돌렸을 때 세션 파일·인증 갱신이 충돌하지 않는지, 사용량 한도 오류가 어떻게 나오는지. 문제가 있으면 상한 5를 낮춘다.
