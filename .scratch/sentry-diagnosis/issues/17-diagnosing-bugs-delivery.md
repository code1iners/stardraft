# `diagnosing-bugs` 절차의 전달 방식

## Question

차팅 전제는 "앱이 에이전트에게 `diagnosing-bugs` 절차와 재현 도구 사용을 허용한 **지침**을 넘긴다"이다. 지침은 Sentry 대상 어댑터가 만든다([경계 결정](08-provider-seam-decision.md)). 그 절차를 에이전트에게 어떻게 전달할지 정한다.

- **스킬 가정인가, 지침에 직접 넣는가**: 사용자 에이전트에 `diagnosing-bugs` 스킬이 설치되어 있다고 가정할지, 절차 본문을 앱이 지침에 넣을지. Claude는 `--restricted`, Codex는 `--ignore-user-config`로 돌므로 사용자 스킬이 실리는지부터 확인한다.
- **절차의 출처와 갱신**: 직접 넣는다면 원문을 앱에 싣는 방식(복사본, 버전), 앱에 맞게 줄이거나 고칠 부분(대화형 단계, 사람에게 묻는 단계는 무인 실행에서 쓸 수 없다).
- **읽기 전용 진단의 지침**: **재현 허용**이 꺼진 진단은 읽기 전용으로 낮춘다. 그때 절차의 어느 부분을 빼는지.
- **결과 스키마와의 연결**: 절차의 산출(재현 성공·실패·불가, 원인, 확신도)이 [보고서 형식](07-diagnosis-report-format.md)의 에이전트 결과 스키마에 어떻게 대응하는지.

## Answer

2026-11-24 grilling 세션에서 정했다. 질문 열한 개 모두 추천안대로 확정했다.

### 확인한 사실

- Claude Code의 `--restricted`는 CLAUDE.md·스킬·플러그인·훅을 모두 끈다(`claude --help`, 2.1.331). 사용자가 `diagnosing-bugs`를 설치했어도 진단 실행에는 실리지 않는다.
- Codex의 `--ignore-user-config`는 `config.toml`만 건너뛴다. 사용자 홈의 스킬 목록은 모델 요청에 그대로 들어간다([MCP 조사](../research/reproduction-mcp.md)의 범위 밖 관찰, 실측).
- Flow 초안 지침은 코드 상수다(`draftInstructions`, `apps/desktop/src/core/drafts/draft-input.ts`). Claude에는 `--append-system-prompt-file`로 넘긴다.
- 스킬 원문은 여섯 단계(피드백 루프 → 재현·최소화 → 가설 → 계측 → 수정·회귀 테스트 → 정리)이고, 사람에게 묻는 곳이 세 군데 있다.

### 전달 방식

- 스킬 설치를 가정하지 않는다. 앱이 절차 본문을 지침에 직접 넣는다. 두 CLI가 같은 절차를 받는다.
- 원문을 복사해 싣지 않는다. 앱이 무인 진단용으로 다시 쓴 **진단 절차**를 Flow 지침처럼 코드 상수로 두고, Sentry 대상 어댑터의 `prepare`가 지침으로 낸다([경계 결정](08-provider-seam-decision.md)). 원문과 자동으로 맞추지 않고 앱 버전과 함께만 바뀐다.
- 차팅 전제의 "`diagnosing-bugs` 절차"는 이제 **진단 절차**를 가리킨다. `diagnosing-bugs`는 출처다.
- Codex 실행에 사용자 홈의 스킬 목록이 실리는 것은 이번에 막지 않는다(Flow 초안 실행도 같다). 스펙에 알려진 차이로 적는다.

### 진단 절차의 내용 (재현하는 진단)

- 원문의 1~4단계와 비밀 가리기 규칙을 남긴다: 피드백 루프 만들기, 재현과 최소화, 가설 3~5개와 각 가설의 예측, 예측에 맞춘 계측.
- 5단계(수정·회귀 테스트)와 6단계(정리)는 뺀다. 고치는 일은 지도의 범위 밖이고, 재현 사본은 끝나면 지운다.
- 사람에게 묻는 단계는 "묻지 말고 `open_questions`에 적는다"로 바꾼다. 사람이 끼는 루프(HITL 스크립트)는 뺀다.
- **사본 안에서 코드 고치기**를 허용한다. 로그를 넣거나 의심 가는 줄을 바꿔 루프가 초록이 되는지 본다. 고친 내용은 사본과 함께 버리고, 보고서에는 "이렇게 바꾸니 사라졌다"를 근거로만 적는다. 패치 파일을 첨부로 남기지 않는다.
- **루프를 못 만들어도 멈추지 않는다**. 코드 읽기로 원인을 추정해 보고서를 끝까지 쓴다. 재현 없이는 확신도에 `high`를 쓰지 않는다. 스택트레이스와 코드만으로 원인이 한 줄로 드러나는 경우는 예외다. 이 규칙은 지침의 문구이고 앱이 확신도를 강제로 낮추지 않는다.
- **시간 배분**: 지침에 상한 20분을 알리고, 재현 시도는 10분쯤에서 끊고 남은 시간에 원인 분석과 보고서를 쓰게 한다. 시간 초과 때 부분 결과를 남길지는 [진단 실패와 데이터 부족의 처리](18-diagnosis-failure-handling.md)에서 정한다.
- **저장소의 안내 문서**: 먼저 README·`AGENTS.md`·`CLAUDE.md`·패키지 스크립트를 읽어 실행·테스트 방법을 찾게 한다. 실행 방법을 찾는 자료로만 쓰고, 그 문서의 다른 지시(커밋, 게시 등)는 따르지 않는다.
- **언어**: 보고서 본문은 한국어로 쓰고, 코드 식별자·오류 원문·명령어는 원문 그대로 둔다.
- [재현 실행의 보안 경계](05-reproduction-security-boundary.md)에서 정한 문구("운영 서버로 데이터를 바꾸는 요청을 보내지 말 것", "외부로 보내거나 쓰는 도구를 쓰지 말 것")도 같은 지침에 들어간다.

### 결과 스키마와의 연결

스키마는 [보고서 형식](07-diagnosis-report-format.md)의 것이다.

- `reproduction.result`의 기준
  - **성공**(`success`): Sentry 오류 이슈와 같은 예외 종류가 같은 자리에서 한 번 이상 났다. 가끔만 나는 오류는 몇 번 중 몇 번인지 `method`에 적는다.
  - **실패**(`failure`): 환경은 돌았고 시도했지만 그 증상이 나지 않았다. 근처의 다른 오류만 난 경우도 실패다.
  - **불가**(`impossible`): 시도 자체를 못 했다(`no_tool`·`insufficient_data`·`env_failed`).
- `reproduction.steps`: 성공이면 최소화한 재현 순서, 실패·불가면 시도한 것.
- `cause`: 채택한 가설과 확신도. 채택하지 않은 가설은 표로 만들지 않고 `open_questions`에 남긴다.
- 사본에서 고쳐 확인한 결과는 `cause`의 근거와 `improvements`에 글로 적는다.

### 읽기 전용 진단

- **재현 허용**이 꺼진 진단의 지침에서는 루프·재현·계측을 통째로 뺀다. "스택트레이스에서 코드를 따라가 가설을 세우고 원인을 추정한다"만 남긴다.
- 출력 스키마에서도 `reproduction`을 뺀다. 재현 칸은 앱이 "불가(허용 안 됨)"로 채운다.
- 확신도 규칙과 언어 규칙은 재현하는 진단과 같다. 지침과 스키마가 실행 종류마다 둘씩 있는 셈이다.

### 글로서리

- **진단 절차**를 더했다.
