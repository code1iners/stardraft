## Question

**저장소 매핑 필요**·**저장소 확인 필요** 상태를 화면과 알림으로 어떻게 보일지 시안으로 정한다. 두 상태는 Sentry 오류 이슈([매핑 없는 프로젝트](06-unmapped-sentry-project.md))와 Flow 묶음([Flow 전환](13-flow-without-work-folders.md))이 함께 쓴다.

- **알림 단위**: 오류 이슈마다 알릴지, 프로젝트 단위로 묶어 알릴지. Flow 묶음은 어떻게 할지.
- **저장소 매핑 필요 묶음의 버튼 배치**: 주 버튼 [저장소 매핑하기], 보조 [저장소를 골라 만들기](Flow 묶음에만 있다).
- **막힌 초안의 이유 문구**: 저장소가 정해지지 않아 다시 만들기·지시가 막힌 초안에 보일 문구.
- **트레이 알림**: 진단 보고서가 준비됐을 때, 진단이 실패했을 때, 저장소 대기 상태가 생겼을 때 트레이·시스템 알림을 띄우는 기준. 지금 Flow 초안 알림 규칙과 맞춘다.
- **시간 연장을 묻는 알림**: 재현하는 진단의 상한 5분 전에 띄우는 시스템 알림의 문구와, 알림에서 바로 답할 수 있게 할지([진단 실패와 데이터 부족의 처리](18-diagnosis-failure-handling.md)). 창을 강제로 앞에 띄우지 않는 것은 정해졌다.

진단 보고서 검토 화면 자체는 [진단 보고서 검토 화면 시안](20-diagnosis-review-ui-prototype.md)에서 다룬다.

## Answer

2026-11-24 시안 비교로 정했다. 사용자가 **안 B**를 골랐고, 시간 연장 알림만 알림의 버튼이 아니라 **눌러서 앱에서 답하기**로 정했다. 시안은 `~/.claude-mukkebi/mockups/stardraft/repo-blocked-and-notifications.html`의 `?variant=B`다. 색·간격·클래스는 지금 `styles.css`를 따른다.

### 저장소 매핑 필요·저장소 확인 필요의 화면

- 목록은 [진단 보고서 검토 화면 시안](20-diagnosis-review-ui-prototype.md) 그대로 건마다 한 줄이고, 노란 태그(`저장소 매핑 필요`·`저장소 확인 필요`)를 붙인다. 프로젝트로 접지 않는다.
- 상세 몸통에는 이유 상자를 두지 않는다. 진단은 `오류 정보`, 초안은 `원문`만 보인다.
- 이유와 버튼은 **노란 바닥 줄**에 둔다. 시간 연장 묻기와 같은 틀(`.review-foot`에 `--warn-bg`)이다. 끝내는 버튼은 왼쪽, 나아가는 버튼은 오른쪽이다.

| 상태 | 왼쪽 | 글 | 오른쪽 |
|---|---|---|---|
| 매핑 필요 · 진단 | 없음 | "**이 프로젝트에 연결한 저장소가 없습니다.** 매핑하면 기다리는 오류 n건을 진단합니다." | **[저장소 매핑하기]** |
| 매핑 필요 · 초안 | [무시] | "**이 프로젝트에 연결한 저장소가 없습니다.** 매핑하면 기다리는 멘션 n건의 초안을 만듭니다." | [저장소를 골라 만들기] · **[저장소 매핑하기]** |
| 확인 필요 · 진단 | 없음 | "**연결한 저장소 폴더를 찾을 수 없습니다.** `<경로>` 폴더가 돌아오거나 매핑을 고치면 이어 갑니다." | **[매핑 고치기]** |
| 확인 필요 · 초안 | [무시] | 위와 같다 | [저장소를 골라 만들기] · **[매핑 고치기]** |

- [저장소 매핑하기]·[매핑 고치기]는 그 프로젝트의 매핑 편집으로 이동한다([매핑 없는 프로젝트](06-unmapped-sentry-project.md) 그대로). 검토 화면 안에서 폴더를 고르지 않는다.
- 진단에는 치우는 버튼이 없다. 벗어나는 길은 매핑 저장뿐이다([진단 실패와 데이터 부족의 처리](18-diagnosis-failure-handling.md)의 상태 목록 그대로).
- 작은 창에서는 바닥 줄의 글을 윗줄에, 버튼을 아랫줄에 둔다.

### 저장소가 정해지지 않은 초안

- 몸통 맨 위 알림 줄(노랑)에 "이 초안에 쓸 저장소가 정해지지 않아 다시 만들 수 없습니다. 프로젝트에 저장소를 매핑하거나 "다른 저장소로 다시 만들기"를 쓰세요."를 적고 오른쪽에 [저장소 매핑하기]를 둔다. [다시 진단하지 못하고 돌아왔을 때](20-diagnosis-review-ui-prototype.md)의 알림 줄과 같은 모양이다.
- [다시 만들기 ▾]의 "다시 만들기"와 "지시를 덧붙여 다시 만들기"는 끄고, "다른 저장소로 다시 만들기"는 둔다. 메뉴 항목에는 이유를 따로 적지 않는다.
- `저장소` 구역에는 "정해진 저장소가 없습니다."만 적는다.

### OS 알림과 트레이

| 일 | OS 알림 | 트레이 |
|---|---|---|
| 초안 준비됨 | 건마다(지금 그대로) | 검토 대기 수에 더함 |
| 진단 보고서 준비됨 | 건마다 | 검토 대기 수에 더함 |
| 초안 실패 · 진단 실패 | 없음(지금 초안 실패 그대로) | "!" 실패 있음 |
| 저장소 매핑 필요 · 저장소 확인 필요 | 프로젝트가 그 상태가 될 때 한 번 | 프로젝트마다 1로 셈 |
| 시간 연장 묻기 | 한 번, 눌러서 앱에서 답함 | 바뀌지 않음 |

- **저장소 대기 알림의 단위**: 오류 이슈·Flow 묶음 모두 프로젝트 단위다. 풀리기 전에 같은 프로젝트에 또 오면 알리지 않고 목록의 수만 늘어난다. 풀린 뒤 다시 그 상태가 되면 다시 알린다(전역 문제 알림과 같은 방식). 알림을 누르면 그 프로젝트의 첫 건을 연다.
- **지금 Flow 동작에서 바뀌는 것**: 저장소 확인 필요 알림이 건마다(한 번에 온 것은 "n건"으로 묶음)에서 프로젝트에 한 번으로, 트레이 검토 수가 건마다에서 프로젝트마다 1로 바뀐다(`core/bundles/mention-bundles.ts`의 `repoCheckNotification`, `countsForReview`).
- **시간 연장 알림**: 알림에 버튼을 달지 않는다. 누르면 그 진단을 열고, 답은 노란 바닥 줄의 [멈추기]·[계속 진행]으로 한다. 창을 억지로 앞에 띄우지 않는다.
- 알림 본문에는 프로젝트 이름과 재현 결과만 넣고 오류 메시지·글 본문은 넣지 않는다.

| 알림 | 제목 | 본문 |
|---|---|---|
| 진단 보고서 준비됨 | 진단 보고서 준비됨 | `<프로젝트>`의 오류를 진단했습니다. 재현 성공. |
| 저장소 매핑 필요 | 저장소 매핑 필요 | `<프로젝트>`에 연결한 저장소가 없습니다. 매핑하면 기다리는 오류를 진단합니다. |
| 시간 연장 묻기 | 진단이 5분 뒤 멈춥니다 | `<프로젝트>`의 오류를 재현하는 중입니다. 계속하려면 눌러서 답해 주세요. |

### 사용자가 따로 답하지 않아 시안대로 적은 것

시안과 함께 물었지만 답이 없어 시안에 그린 대로 적었다. 스펙을 쓰기 전에 뒤집을 수 있다.

- 알림 본문에 오류 제목을 넣지 않는다.
- 위 화면·알림 문구.

### 스펙에서 채울 것

- 저장소 확인 필요 알림의 제목·본문, 초안(멘션·담당 업무) 쪽 저장소 대기 알림의 본문, 재현 결과가 실패·안 함일 때의 준비됨 본문은 시안에 그리지 않았다. 위 문구의 틀에 맞춰 쓴다.
- Windows는 어느 알림을 눌렀는지 알 수 없어 마지막 묶음 알림의 묶음을 연다(`main/os-notifier.ts`, 실기 미확인). 진단 알림이 더해지면 알림이 가리키는 대상을 묶음 ID에서 넓혀야 한다(`AppNotification.bundleId`).
- 폴더가 돌아온 것을 언제 알아차리는지(다시 확인하는 시점)는 정하지 않았다.
