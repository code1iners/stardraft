## Question

닫힌 티켓의 결정을 모아 구현 착수용 스펙 `.scratch/sentry-diagnosis/spec.md`를 쓴다. 이 지도의 목적지다.

- **틀**: 어떤 틀로 쓸지. 처음 Flow 스펙(`.scratch/flow-mention-drafter/spec.md`)의 짜임을 따를지 먼저 정한다.
- **어긋남 맞추기**: 뒤 티켓이 앞 티켓의 결정을 바꾼 곳(작업 폴더 폐지, 병렬 작업 수, 목적지에 더한 Flow 기록의 계정별 보관 등)을 찾아 최신 결정으로 맞춘다. 서로 부딪히는 결정이 남아 있으면 사용자에게 묻는다.
- **답 없이 시안대로 적은 것**: [진단 보고서 검토 화면 시안](20-diagnosis-review-ui-prototype.md)과 [저장소 대기 상태 표시와 알림 시안](21-repo-blocked-and-notification-ui-prototype.md)에 "답 없이 시안대로 적었다"고 남긴 항목을 스펙에 넣기 전에 확인받는다.
- **스펙에서 채울 것**: 각 티켓이 "스펙에서 정한다"로 미룬 항목(알림 문구, 표마다의 계정 열 등)을 채운다.
- **처음 Flow 스펙과의 관계**: 이 스펙이 바꾸는 Flow 동작(작업 폴더·자동 선택 폐지, 계정을 바꿀 때의 기록 보관, 알림 규칙)을 어디에 적을지 정한다.

## Answer

2026-11-25에 [스펙](../spec.md)을 썼다. 이 지도의 목적지다.

- **틀**: 처음 Flow 스펙의 짜임(문제 정의 → 해결 방안 → 사용자 스토리 → 번호 붙인 구현 결정 → 테스트 결정 → 범위 밖 → 추가 참고)을 따랐다. 사용자가 틀을 따로 고르지 않아 추천안으로 썼다.
- **어긋남 맞추기**: 뒤 티켓이 바꾼 결정은 최종 규칙만 적었다. 필수 설정은 에이전트 연결 하나(04 → 09), 시간 초과는 진단 실패이고 "불가(시간 초과)"는 재현 없이 다시 시도한 보고서에만(05·07 → 18), 직렬 대기열은 병렬 작업 수로(08 → 12·14), Flow의 자동 선택은 폐지(08 → 09·13), 계정을 바꿀 때 지우기는 보관으로(15 → 22). 사용자에게 물어야 할 만큼 서로 부딪히는 결정은 남아 있지 않았다.
- **새로 정한 것**: 재현은 macOS에서만 한다. Windows는 감지와 읽기 전용 진단만 된다.
- **답 없이 시안대로 적은 것**: 앞선 두 시안의 네 가지는 사용자가 시안대로 확정했다.
- **처음 Flow 스펙과의 관계**: 바뀌는 Flow 동작은 스펙 15절에 모았고, 처음 Flow 스펙에는 머리에 고지 블록만 달았다.
- **확인받지 않고 기본값으로 적은 것**: 위 Comments의 화면 항목 넷(추천안으로 적음)과 티켓에 답이 없던 빈 곳이다. 스펙의 "미결 사항과 구현 기본값"에 모두 적었다.
- 글로서리에 더한 용어는 없다. ADR도 새로 쓰지 않았다.
