## Comments

### 2026-11-26 실측 결과와 막힌 것

결과는 [조사 문서의 "실측 (2026-11-26)" 절](../research/sentry-api-facts.md)에 있다. 읽기 호출만으로 확인되는 것은 끝냈고, **시험 이벤트가 필요한 두 항목(첫째·둘째)은 못 했다.** 스펙과 다른 사실은 아직 없다(확인 못 한 것이 있을 뿐이다). 그래서 `blocked`로 남긴다.

**왜 막혔나**
- 시험 이벤트를 보내려면 프로젝트의 DSN이 필요한데, 토큰(`org:read`·`event:read`)으로는 프로젝트 키 조회가 403이다(필요 scope `project:read`). DSN은 재현 저장소 `.env`에만 있고, 이 티켓은 그 파일을 쓰도록 허락받지 않았다. 열어 보지 않았다.
- 오류 이슈를 해결 처리하려면 `event:write`가 필요한데 토큰에 없고, 이 세션에서 쓸 수 있는 Sentry 도구도 없다. 해결 처리 없이는 재발을 만들 수 없고, 시험 이벤트를 끝낸 뒤 정리도 못 한다. 정리할 수 없는 시험 이벤트를 회사 프로젝트에 보내지 않았다.

**실측으로 새로 알게 된 것(구현 티켓에 영향)**
- 감지 조회에 `collapse=stats`를 쓰면 `firstSeen`·`lastSeen`·`count`가 응답에서 사라진다. 쓰지 않는다.
- 쿼리에 날 `>`를 넣으면 HTML 400이 온다. `%3E`로 인코딩한다.
- `level:[error,fatal]` 목록 문법이 된다. `OR`는 400이다.
- 최신 이벤트: 환경·레벨은 `tags`, 소스맵 흔적은 프레임 `map`·`origFilename`과 `rawStacktrace`(프레임 `data.symbolicated`는 없음).
- 오류 이슈 상세 호출의 한도는 초당 5로 목록(10)보다 낮다. 재발 키를 읽으려는 상세 호출을 몰아 부르지 않는다.
- 403에 필요한 scope 이름이 `WWW-Authenticate` 헤더로 온다. 연결 확인의 "빠진 scope 안내"에 쓸 수 있다.
- 한도 헤더는 정상 응답에 붙고 `Retry-After`는 없다. `Reset`은 UTC epoch 초다.

**사용자가 정해 줄 것(이어가려면 하나)**
1. 새 개인 토큰을 `org:read`·`event:read`에 `event:write`와 `project:read`를 더해 만들고(scope는 만든 뒤 못 바꾼다) 같은 파일 위치에 넣는다. 그러면 DSN 조회, 시험 이벤트 전송, 해결 처리까지 이 티켓에서 끝낼 수 있다. 시험이 끝나면 토큰을 회수해도 된다.
2. 또는 재현 저장소 `.env`의 `NEXT_PUBLIC_SENTRY_DSN`을 이 실측에 쓰도록 허락하고, 시험 이슈의 해결 처리는 사용자가 Sentry 화면에서 직접 한다(재발을 만들려면 "이벤트 → 해결 → 같은 이벤트 한 번 더" 순서에서 해결 단계에 사람이 필요하다).
3. 또는 재발 실측을 건너뛰고 스펙 5절의 낮춘 규칙("재발 목록에서 사라졌다가 다시 나타나면 새 재발")으로 가기로 하고 사용자에게 알린다. 이 경우 이 티켓은 읽기 실측 결과만으로 닫을 수 있다.

시험 이벤트를 보내지 않았으므로 Sentry 쪽에 남긴 것이 없다. 이 실측으로 프로젝트에 생긴 변화는 없다.

### 2026-11-26 정리(closeout) 판정

- 재확인: `is:regressed`를 다시 불렀고 재발 이슈는 여전히 0건이다. 에이전트가 더 할 수 있는 읽기 실측은 없다.
- 완료 3 / 미완료 3(체크 안 함). 비필수로 제외한 항목은 없다.
- 미완료 셋은 모두 **사용자 협조가 있어야 에이전트가 끝낼 수 있다.** 에이전트가 직접 못 하는 이유: 해결 처리는 `event:write` scope가 필요한데 토큰에 없고, 시험 이벤트의 DSN은 `project:read` 또는 재현 저장소 `.env`에만 있어서 이 실행의 허락 범위 밖이다.
- Status는 `blocked`로 둔다. 구현 티켓은 이 티켓의 "실측" 절을 근거로 쓸 수 있지만, 재발 키(이벤트 ID)를 쓸지 낮춘 규칙으로 갈지는 아래 결정이 나온 뒤 정해진다.

**사용자가 할 일(하나만 고르면 된다)**
1. 새 개인 토큰 발급: Sentry 사용자 설정 > Personal Tokens에서 `org:read`, `event:read`, `event:write`, `project:read`로 만들어 `~/.config/stardraft/sentry-token`에 덮어쓴다. 이어서 에이전트가 DSN을 조회해 시험 이벤트를 보내고(시험용 표시 포함), 해결 → 재발 순서를 직접 돌린 뒤 해결 처리로 정리한다. 끝나면 토큰을 회수한다. 필요한 증거: 상세 응답의 `set_regression` 활동과 `data.event_id`.
2. 또는 `.env`의 `NEXT_PUBLIC_SENTRY_DSN` 사용을 허락하고, "이벤트 1회 → Sentry 화면에서 시험 이슈 해결 → 같은 이벤트 1회"의 해결 단계를 사람이 한다. 시험 이슈 정리(해결 처리)도 사람이 한다.
3. 또는 재발 실측을 하지 않기로 하고 스펙 5절의 낮춘 규칙으로 간다. 이 경우 이 티켓의 둘째 항목을 "비필수로 제외(근거: 사용자 결정, 날짜)"로 옮기고 첫째 항목은 신규 조회만으로 닫는다.
- 넷째 항목(모든 지역 조직)은 계정에 독일 조직이 없어 이 계정으로는 확인할 수 없다. 스펙이 `regionUrl` 저장에만 기대므로 비필수로 제외해도 되는지 알려 주면 그렇게 정리한다.

### 2026-11-26 재시도: 시험 이벤트 실측 완료

사용자가 11:28에 `event:write`·`project:read`를 더한 새 토큰을 같은 위치에 넣었다. 새로 호출해 확인했다(토큰 값은 출력하지 않았다). 프로젝트 키 조회가 200이어서 DSN을 API로 얻었고, 재현 저장소 `.env`는 열지 않았다. 결과는 [조사 문서의 "시험 이벤트로 확인한 것"](../research/sentry-api-facts.md)에 있다.

**한 일**: 시험 표시(예외 타입·메시지의 시험 문구, 태그 `stardraft_test:yes`, 시험 전용 환경 이름 둘)를 붙인 이벤트를 하나의 시험 오류 이슈로 묶어 보냈다. 이벤트 1(환경 A) → 이벤트 2(환경 B) → 해결 처리 → 이벤트 3(환경 A, 재발) → 해결 처리 순서다. 시험 오류 이슈는 해결 상태로 두었다.

**스펙과 맞는 것**
- 재발 활동 `set_regression`이 상세 `activity`에 나오고 `data.event_id`가 재발을 일으킨 이벤트 ID와 같다. 스펙 5절의 재발 키를 그대로 쓴다. 낮춘 규칙은 필요 없다.
- 환경을 주면 처음 보인 시각이 그 환경 기준이다. 다른 환경에서 먼저 생긴 오류 이슈가 등록한 환경에 처음 나타나면 신규로 잡힌다(사용자 이야기 14).
- `is:regressed`가 재발한 오류 이슈를 돌려준다.

**사용자에게 알릴 것(스펙 결정과 어긋나지는 않음, 구현에 참고)**
- 재발 조회에 환경을 주면 "그 환경에서 재발했다"가 아니라 "그 환경의 이벤트가 있는 오류 이슈가 재발했다"로 거른다. 환경 A의 이벤트로 일어난 재발이 환경 B로 불러도 나왔다. 그래서 `production`으로 등록해도 운영 이벤트가 한 번이라도 있던 오류 이슈가 개발 환경에서 재발하면 진단 대상이 된다. 스펙 5절은 재발 조회의 환경 필터 방식까지만 정했고 이 경우를 다루지 않는다. 막을 필요가 있다면 `data.event_id`의 이벤트를 불러 환경 태그를 확인하는 단계를 더해야 하고, 이는 스펙 변경이다. 이 티켓에서는 정하지 않았다.
- `environment`에 조직에 없는(이벤트가 아직 없는) 환경 이름을 주면 `404`가 오고 본문이 프로젝트 없음과 같다. 스펙은 환경을 프로젝트 목록에서 고르게 하므로 정상 흐름에서는 생기지 않는다.

**프로젝트에 남은 것**: 해결 상태의 시험 오류 이슈 하나, 프로젝트 환경 목록의 시험 환경 이름 둘(`stardraft-test-a`, `stardraft-test-b`). 환경 숨기기는 허락 범위 밖이라 하지 않았다. 필요하면 Sentry 프로젝트 설정의 환경 화면에서 숨긴다. 실측이 끝났으니 토큰을 회수해도 된다(이후 구현 티켓의 실기 확인에 쓸 계획이면 두면 된다).
