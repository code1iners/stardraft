# 33: Flow 기록의 계정별 보관

**Spec:** [스펙](../spec.md) 15절 "Flow 기록의 계정별 보관"

**What to build:** 다른 Flow 계정의 키로 바꿔도 기록이 지워지지 않고 계정별로 보관된다. 원래 계정의 키를 다시 넣으면 기록과 준비된 초안이 그대로 돌아온다.

**Blocked by:** 27, 28

**Status:** resolved

- [x] 스키마 이전이 계정 표를 계정마다 한 줄로 바꾸고, 감지 기준점·담당 업무 감지 상태·멘션 묶음·최소 기록·담당 업무 기록·대기열의 Flow 줄을 계정에 맨다. 기존 줄은 모두 현재 계정의 것으로 채워진다. 실제 SQLite 파일로 테스트된다.
- [x] "이미 본 것" 조회와 유일성 제약이 계정을 포함해, 두 계정에 같은 ID가 있어도 섞이지 않는다.
- [x] 화면과 감지, 초안 생성, 게시는 움직이는 계정의 기록만 다룬다.
- [x] 떠날 때: 생성 중이던 Flow 실행은 취소되고, 카운트다운은 게시 없이 준비됨으로 돌아가며, 줄 서 있던 Flow 초안은 대기열에서 빠진다. 대기열의 다른 종류 줄은 그대로다.
- [x] 돌아왔을 때: 그 계정의 기준점 이후 중 72시간 안의 멘션만 가져오고, 끊긴 생성은 대기열에 다시 서며, 응답을 못 받은 게시는 실제로 올라갔는지 확인한다. 준비됨 초안은 그대로 보이고, 떠나 있던 동안 비밀 패턴이 추가됐을 때만 게시 전 초안을 다시 만든다.
- [x] 처리한 묶음의 7일 규칙이 보관 중인 계정에도 적용된다.
- [x] 마지막으로 쓴 지 30일이 지난 계정은 기록 전체가 지워지고(덮어쓰기와 WAL 비우기 포함), 그 뒤 그 키를 넣으면 처음 넣는 계정처럼 시작한다.
- [x] 확인 창의 제목에 이름과 이메일이 함께 나오고, 본문이 처음 넣는 계정과 보관해 둔 계정에서 스펙의 문구대로 갈린다. 버튼은 [취소] · [계정 바꾸기]이고 처음 초점은 [취소]다.
- [x] 상태 DB를 비우던 계정 리셋 경로가 남아 있지 않다.
- [x] `pnpm lint`, `pnpm typecheck`, `pnpm test`가 통과한다.

## Comments

- 구현 메모: `state.db` 형식 24가 계정 표를 계정마다 한 줄(움직이는 계정 표시, 마지막으로 쓴 시각, 떠날 때의 비밀 파일 패턴)로 바꾸고, 기준점·담당 업무 감지 상태·묶음·멘션·최소 기록·최소 기록의 멘션 위치·담당 업무 기록·대기열의 Flow 줄에 `account_id`를 둔다. 멘션과 최소 기록의 멘션 위치는 "이미 본 것"의 유일성을 계정 안에 걸려고 뿌리의 계정을 함께 적는다. 계정을 넣은 적 없는 설치본의 줄은 빈 계정(`''`)으로 두고 처음 넣는 계정이 이어받는다.
- 떠날 때와 돌아올 때: `AccountRecords`(core/account)가 게시 대기 멈춤(카운트다운은 앱 종료 표시 없이 준비됨) → 생성 대기열의 Flow 종류 멈춤(`suspendKind`, 실행 기록 결과 `account-left`) → 저장소 계정 바꾸기를 하고, 새 키를 쓰게 된 뒤 끊긴 게시 정리 → 비밀 패턴 재검사 → Flow 대기열 복원(`resumeKind`) → 응답 못 받은 게시 확인을 한다. 72시간 규칙은 계정마다 보관한 기준점에 기존 감지가 그대로 적용된다.
- 해석(확인 바람): 스펙 15절 "떠나 있던 동안 비밀 패턴이 추가됐을 때만 게시 전 초안을 지금 규칙대로 다시 만든다"는 패턴을 추가했을 때의 지금 규칙(`discardSecretEvidenceDrafts`: 근거가 새 패턴에 걸린 게시 전 초안만 버리고 "비밀 파일을 근거로 듦" 실패로 둠, 끊긴 생성은 처음부터 새 패턴으로 다시 만듦)을 돌아올 때 적용하는 것으로 구현했다. 걸린 초안을 자동으로 새로 생성하지는 않는다(사용자가 [다시 시도]). 글자 그대로 "모두 다시 생성"을 뜻했다면 후속 변경이 필요하다.
- 해석: 확인 창 본문의 `{지금 계정의 소속}`이 빈 문자열이면 지금 계정의 이메일로 대신 적는다. 처음 초점 [취소]는 기존 `useEffect` 그대로이고, 렌더러 테스트 환경이 DOM이 없어 초점은 자동 테스트로 확인하지 못했다(버튼 순서·문구만 검사).
- 리뷰에서 고친 결함: 처음 넣는 계정의 기준점을 잡는 조회 중에 계정을 바꾸면 떠난 계정의 최신 알림 ID가 돌아온 계정의 기준점을 덮을 수 있었다. 기준점 저장에 계정을 넘겨 움직이는 계정일 때만 저장하게 했다.
- 리뷰 참고(고치지 않음): 계정을 바꾸는 동안의 종류별 멈춤(`suspendKind`)은 ADR-0004의 "멈춤은 두 층"(전역·어댑터)과 다른 장치다. 앱 종료를 한 종류에만 적용한 것이라 실패 멈춤 층으로 보지 않았고, ADR 보강은 문서 정리 티켓(45번)에서 판단하도록 남긴다.
- 검증: `pnpm lint`·`pnpm typecheck` 통과. desktop 전체 테스트 1403개 중 1402개 통과, 실패 1건은 결정 #7·#8의 아이콘 프레임 부하 테스트로 단독 재실행 통과. site 테스트 1건(index-page)은 결정 #6의 환경성 실패. 새 테스트: 실제 SQLite로 형식 23→24 이전·계정별 유일성·대기열 Flow 줄·보관 계정의 7일 정리·30일 삭제(파일과 WAL에 글이 남지 않음), core 포트 경계로 떠날 때·돌아올 때·게시 결과 확인·비밀 패턴 재검사·감지 경합, 생성 대기열의 종류 멈춤, 확인 창 두 문구. 실기(실제 앱에서 두 Flow 키를 오가기)는 하지 않았다.
- 통합 브랜치 병합: 작업을 마칠 때 `ticket-loop/sentry-diagnosis-20261126-104938/integration`에 새 커밋이 없어 병합할 것이 없었다.
