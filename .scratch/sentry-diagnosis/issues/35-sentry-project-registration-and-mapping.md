# 35: 프로젝트 등록과 Sentry 저장소 매핑

**Spec:** [스펙](../spec.md) 4절 "등록", "필터", "기준 시각", 6절 "Sentry 매핑", 14절 "Sentry 칸", "저장소 칸"

**What to build:** Sentry 칸에서 진단할 프로젝트를 등록하고 환경·레벨 필터와 저장소를 정한다. 저장소 칸의 매핑이 `Flow` | `Sentry` 탭으로 나뉜다. 이 티켓까지는 감지가 돌지 않는다.

**Blocked by:** 34

**Status:** resolved

- [x] [프로젝트 추가…] 모달에서 조직의 프로젝트를 골라 등록한다. 등록할 때 그 프로젝트의 오류 이슈 목록을 한 건 불러 `event:read`를 확인하고, 실패하면 빠진 scope를 알린다.
- [x] 등록은 프로젝트 `id`를 키로 설정에 저장되고, 등록한 시각이 기준 시각이 된다. 필터를 바꿔도 기준 시각은 그대로이고, 등록을 풀었다가 다시 등록하면 새로 잡힌다.
- [x] 환경은 프로젝트의 환경 목록에서 고르고 `production`이 있으면 기본값이다. 레벨 기본값은 `error`와 `fatal`이다.
- [x] Sentry 매핑은 프로젝트 하나에 저장소 하나이고, 같은 저장소를 여러 프로젝트에 매핑할 수 있다. Flow 매핑과 키가 겹치지 않는다. 매핑은 등록할 때 필수가 아니다.
- [x] "진단할 프로젝트" 줄에 `조직 / 프로젝트`, `환경 · 레벨 · 저장소 이름`, 상태가 보인다. [편집] 모달에 필터, 저장소, [등록 해제]가 있다. "토큰 확인 필요"이면 [프로젝트 추가…]가 막힌다.
- [x] 저장소 칸의 "저장소 매핑"에 `Flow` | `Sentry` 탭이 있고 두 탭의 줄 모양이 같다. Sentry 탭에는 등록한 프로젝트가 모두 오르고 [폴더 추가…] 대신 [바꾸기…]가 있다. Sentry 칸 모달의 저장소와 같은 값이다.
- [x] 매핑이 없는 등록 프로젝트는 탭 맨 위에 "저장소 매핑 없음"과 [폴더 고르기…]로 보이고 탭에 점이 찍힌다. 매핑된 폴더가 없으면 "폴더를 찾을 수 없음"이 보인다.
- [x] 등록한 프로젝트가 404이거나 접근이 거부되면 그 줄만 "접근 불가"가 된다(등록 확인 호출 기준. 폴링에서의 처리는 36번).
- [x] `pnpm lint`, `pnpm typecheck`, `pnpm test`가 통과한다.


## Comments

- 구현 메모: 등록·매핑은 `core/sentry/sentry-projects.ts`(`SentryProjects`)가 맡는다. 설정에는 `sentryProjects`(프로젝트 ID → 등록: 조직·프로젝트 id/slug/이름, 환경, 레벨, `registeredAt`)와 `sentryRepoMappings`(프로젝트 ID → 경로 배열)를 새 키로 더했다(스키마 버전은 그대로). Flow `repoMappings`와 다른 필드라 키가 겹치지 않는다. Sentry API 포트에 `listProjects`(조직 지역 주소로 호출, `environments` 포함)와 `probeErrorIssues`(`issues/?project=ID&limit=1`, 환경을 걸지 않음: 25번 실측에서 이벤트 없는 환경 이름은 404이기 때문)를 더했고, 어댑터는 404를 `not-found`로 구분한다.
- 등록 확인에서 401·403은 `SentryConnection.reportApiFailure`로 "토큰 확인 필요"를 올리고(403은 `event:read` 부족으로 안내), 404는 "프로젝트를 찾을 수 없음"으로 알리며 아무것도 저장하지 않는다.
- 해석으로 정한 것: (1) 환경 선택지에 "모든 환경"(`null`)을 항상 둔다. 새 프로젝트처럼 환경 목록이 비면 고를 것이 없기 때문이다. `production`이 있으면 기본값이다. (2) 이미 등록된 프로젝트를 다시 열어 확인하는 호출(설정 Sentry·저장소 칸을 열 때 `refresh`)에서 404와 403은 그 줄만 "접근 불가"로 본다. 등록 때 `event:read`가 확인됐으므로 이후 403은 프로젝트 접근 거부로 보았다. 토큰을 바꿔 scope가 줄어든 경우의 전역 처리는 폴링을 만드는 36번이 정한다. 401만 전역 문제로 올린다. (3) 등록을 풀면 그 프로젝트의 Sentry 저장소 매핑도 지운다(Sentry 탭에는 등록한 프로젝트만 오르므로). (4) 줄 상태 "감지 중"은 스펙 14절 문구 그대로 쓰지만, 감지는 36번에서 생긴다. 그 전에는 매핑된 줄도 "감지 중"으로 보이니 36번이 상태 판단에 실제 감지 여부를 더해야 한다. "저장소 매핑 없음 · n건 대기"의 건수도 36번 이후에 붙인다.
- 34번 보강: `useSnapshot`이 `sentry-changed` 이벤트를 받지 않아 토큰 카드가 갱신되지 않던 것을 함께 고쳤다.
- 리뷰에서 남긴 것: 레벨 목록과 환경 이름 길이 상수가 core·shared에 따로 있다(shared는 core를 가져오지 않는 기존 구조 때문). 값이 바뀌면 함께 고쳐야 한다.
- 검증: `pnpm lint`, `pnpm typecheck` 통과. desktop 테스트 1541개 모두 통과. 루트 `pnpm test`의 site는 이 워크트리에 vitest가 없어 실행되지 않는다(결정 #6의 환경성 문제).
- 확인 못 함: 독일 등 다른 지역 조직의 실호출, 실제 sentry.io 계정으로의 등록 호출(가짜 서버 테스트만).
