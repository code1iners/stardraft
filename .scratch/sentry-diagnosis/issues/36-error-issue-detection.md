# 36: 오류 이슈 감지

**Spec:** [스펙](../spec.md) 5절, 6절, 3절 "상태 DB", 9절의 저장소 대기·대기 상태

**What to build:** 등록한 프로젝트에서 **신규**와 **재발** 오류 이슈가 감지되어 검토 목록의 `진단` 묶음에 나타난다. 매핑이 있으면 `대기`, 없으면 `저장소 매핑 필요`, 폴더가 없으면 `저장소 확인 필요`다. 이 티켓까지는 진단이 실행되지 않는다. 25번의 실측 결과에 맞춰 구현한다.

**Blocked by:** 25, 32, 35

**Status:** ready-for-agent

- [ ] `sentry_`로 시작하는 표(프로젝트별 체크포인트, 중복 억제 기록, 진단)를 더하는 이전이 있다. Sentry 전용 저장 포트 뒤에 있고, 지금의 상태 저장소 포트에 Sentry 메서드가 없다.
- [ ] 5분마다, 앱을 켤 때, 절전에서 깰 때 조회한다. 프로젝트마다 환경과 레벨 필터로 신규와 재발을 조회하고 쪽을 끝까지 넘긴다.
- [ ] 기준 시각보다 앞선 신규와 재발은 건너뛴다. 신규는 최근 7일 안의 것만 진단 대상이고, 더 오래된 것은 체크포인트만 옮기고 로그에 개수를 적는다.
- [ ] 체크포인트는 조회를 시작한 시각으로 옮기고, 다음 조회는 10분 앞에서 겹쳐 조회하며 겹친 것은 중복 억제 기록으로 걸러진다.
- [ ] 신규의 키는 오류 이슈 ID, 재발의 키는 오류 이슈 ID와 재발을 일으킨 이벤트 ID다. 같은 재발은 한 번만 진단 대상이 된다.
- [ ] 같은 오류 이슈의 진단이 이미 있을 때의 재발이 스펙 5절의 표대로 처리된다(대기 중이면 키만 기록. 검토 대기·진단 실패·완료의 갈래는 그 상태를 만드는 37·38번이 테스트를 더한다).
- [ ] 한 프로젝트의 실패가 다른 프로젝트를 막지 않고 실패한 프로젝트의 체크포인트는 옮겨지지 않는다. 404·접근 거부는 그 프로젝트만 "접근 불가", 401은 전역 문제다. `429`는 한도 초기화 시각까지(없으면 다음 주기까지) Sentry 감지만 미룬다.
- [ ] 검토 스냅숏에 진단 배열이 따로 있고, 목록의 `진단 n` 묶음에 오류 제목, 감지 시각, `프로젝트 · 자리`, 상태 태그가 보인다. Sentry 프로젝트의 저장소 대기도 프로젝트 단위 알림과 트레이 수를 따른다.
- [ ] 저장소 대기 진단의 상세에 `오류 정보`와 노란 바닥 줄(진단용 글, 주 버튼 하나, 치우는 버튼 없음)이 보인다. Sentry 칸과 저장소 칸의 프로젝트 줄에 "저장소 매핑 없음 · n건 대기"가 보인다.
- [ ] 프로젝트 등록을 풀면 그 프로젝트의 체크포인트와 중복 억제 기록이 지워지고 기다리던 진단이 목록에서 빠진다.
- [ ] 가짜 Sentry API와 가짜 시계로 위 규칙이 테스트된다.
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test`가 통과한다.
