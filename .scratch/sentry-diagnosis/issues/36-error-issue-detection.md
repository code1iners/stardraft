# 36: 오류 이슈 감지

**Spec:** [스펙](../spec.md) 5절, 6절, 3절 "상태 DB", 9절의 저장소 대기·대기 상태

**What to build:** 등록한 프로젝트에서 **신규**와 **재발** 오류 이슈가 감지되어 검토 목록의 `진단` 묶음에 나타난다. 매핑이 있으면 `대기`, 없으면 `저장소 매핑 필요`, 폴더가 없으면 `저장소 확인 필요`다. 이 티켓까지는 진단이 실행되지 않는다. 25번의 실측 결과에 맞춰 구현한다.

**Blocked by:** 25, 32, 35

**Status:** resolved

- [x] `sentry_`로 시작하는 표(프로젝트별 체크포인트, 중복 억제 기록, 진단)를 더하는 이전이 있다. Sentry 전용 저장 포트 뒤에 있고, 지금의 상태 저장소 포트에 Sentry 메서드가 없다.
- [x] 5분마다, 앱을 켤 때, 절전에서 깰 때 조회한다. 프로젝트마다 환경과 레벨 필터로 신규와 재발을 조회하고 쪽을 끝까지 넘긴다.
- [x] 기준 시각보다 앞선 신규와 재발은 건너뛴다. 신규는 최근 7일 안의 것만 진단 대상이고, 더 오래된 것은 체크포인트만 옮기고 로그에 개수를 적는다.
- [x] 체크포인트는 조회를 시작한 시각으로 옮기고, 다음 조회는 10분 앞에서 겹쳐 조회하며 겹친 것은 중복 억제 기록으로 걸러진다.
- [x] 신규의 키는 오류 이슈 ID, 재발의 키는 오류 이슈 ID와 재발을 일으킨 이벤트 ID다. 같은 재발은 한 번만 진단 대상이 된다.
- [x] 같은 오류 이슈의 진단이 이미 있을 때의 재발이 스펙 5절의 표대로 처리된다(대기 중이면 키만 기록. 검토 대기·진단 실패·완료의 갈래는 그 상태를 만드는 37·38번이 테스트를 더한다).
- [x] 한 프로젝트의 실패가 다른 프로젝트를 막지 않고 실패한 프로젝트의 체크포인트는 옮겨지지 않는다. 404·접근 거부는 그 프로젝트만 "접근 불가", 401은 전역 문제다. `429`는 한도 초기화 시각까지(없으면 다음 주기까지) Sentry 감지만 미룬다.
- [x] 검토 스냅숏에 진단 배열이 따로 있고, 목록의 `진단 n` 묶음에 오류 제목, 감지 시각, `프로젝트 · 자리`, 상태 태그가 보인다. Sentry 프로젝트의 저장소 대기도 프로젝트 단위 알림과 트레이 수를 따른다.
- [x] 저장소 대기 진단의 상세에 `오류 정보`와 노란 바닥 줄(진단용 글, 주 버튼 하나, 치우는 버튼 없음)이 보인다. Sentry 칸과 저장소 칸의 프로젝트 줄에 "저장소 매핑 없음 · n건 대기"가 보인다.
- [x] 프로젝트 등록을 풀면 그 프로젝트의 체크포인트와 중복 억제 기록이 지워지고 기다리던 진단이 목록에서 빠진다.
- [x] 가짜 Sentry API와 가짜 시계로 위 규칙이 테스트된다.
- [x] `pnpm lint`, `pnpm typecheck`, `pnpm test`가 통과한다.

## Comments

- 구현 메모: 감지는 `core/sentry/sentry-detection.ts`(`SentryDetection`), 진단 목록·중복 억제·저장소 대기 알림과 재개는 `core/sentry/sentry-diagnoses.ts`(`SentryDiagnoses`), 도메인 타입은 `core/sentry/sentry-diagnosis.ts`다. 저장은 전용 포트 `core/ports/sentry-store.ts`(`SentryStore`)와 `core/storage/sqlite-sentry-store.ts`이고, 지금의 상태 저장소 포트에는 메서드를 더하지 않았다. 이전 25번이 `sentry_checkpoint`, `sentry_detection_key`(신규는 이벤트 ID 열이 빈 문자열), `sentry_diagnosis`를 더한다. 계정 열을 두지 않아 계정 이어받기·30일 삭제가 건드리지 않는다(실제 SQLite 테스트로 확인).
- Sentry API 포트에 `listNewErrorIssues`(`is:unresolved firstSeen:>{ISO} level:…`, `sort=new`), `listRegressedErrorIssues`(`is:regressed level:…`, `sort=date`), `latestRegression`(상세 `activity`의 가장 최근 `set_regression`의 `data.event_id`와 `dateCreated`)을 더했다. 쿼리는 `encodeURIComponent`로 보낸다. `429`는 `X-Sentry-Rate-Limit-Reset`을 `resetAt`(밀리초)으로 읽는다.
- 상태는 이 단계에서 `queued`(대기)와 `repo-check-needed`(사유 `unmapped`·`missing-folder`)뿐이다. 진단은 생성 대기열에 들어가지 않는다(Sentry 어댑터는 37번). 5절 표는 대기·저장소 대기면 키만 기록하는 갈래만 구현했고, 진행 중·검토 대기·진단 실패·완료 갈래는 그 상태를 만드는 37·38번이 `absorbsRegression`과 `STATUSES_REMOVED_ON_UNREGISTER`(`sentry-diagnosis.ts`)를 넓혀 더한다.
- 저장소 대기 진단은 Flow와 같은 `RepoWaitMonitor`를 하나 더 만들어 앱을 켤 때·매핑이 바뀔 때·절전에서 깰 때·폴더 없음이 있는 동안 60초마다 다시 판정한다. 진단 알림을 누르면 작은 창이 아직 진단을 그리지 않으므로 펼친 창에 그 진단을 연다. [저장소 매핑하기]·[매핑 고치기]는 설정 "저장소" 칸 `Sentry` 탭에서 그 프로젝트 줄을 짚는다.
- 해석으로 정한 것: (1) 감지 중 `403`은 티켓대로 그 프로젝트만 "접근 불가"로 둔다(35번 해석과 같음). 스펙 4절은 401·403을 토큰 문제로 묶어 적고 있어 문서끼리 다르다. (2) 저장소 대기 알림은 Flow와 같게 "프로젝트에 이미 저장소 대기가 있으면 알리지 않음"으로 해서, 매핑 필요로 기다리는 중 사유만 확인 필요로 바뀌면 다시 알리지 않는다. (3) 오류 이슈 목록은 쪽 수 상한(50쪽, 5,000건)에서 멈추고 성공으로 본다. 넘으면 그 뒤를 놓친다. (4) 재발 활동이 없는 재발 목록 항목은 로그만 남기고 건너뛴다(25번 실측으로 낮춘 규칙은 쓰지 않음). (5) 진단을 보다가 [접어 보기]를 누르면 작은 창은 첫 초안을 연다(작은 창의 진단은 38번).
- 알려진 한계: 재발 조회는 5분마다 `is:regressed`인 오류 이슈마다 상세를 한 번씩 부른다(상세 한도 초당 5회). 재발이 많으면 `429`로 Sentry 감지가 미뤄질 수 있다. 재발 조회의 환경 필터 한계(결정 #4)는 그대로다. 펼친 창 빈 상태 문구 "아직 멘션이 없습니다."는 Flow 쪽 말이 남아 있다(32번 문구, 손대지 않음). 설정 칸 줄 상태 "감지 중"은 감지 시작 여부를 보지 않는다(35번 메모의 (4)는 "n건 대기"만 반영).
- 리뷰에서 고친 것: 진단을 보는 중 토스트([되돌리기] 등)가 묶음을 골라도 진단 화면에 머물던 것, 같은 Sentry 프로젝트를 다시 짚으면 탭이 바뀌지 않던 것(짚기 요청마다 저장소 칸을 새로 그림), 밀려난 타입 주석과 빠진 주석. 이 두 화면 수정은 이벤트를 흉내 내는 렌더러 테스트 틀이 없어 자동 테스트로 검사하지 못했다.
- 리뷰에서 남긴 것(판단 사항): 오류 이슈 필드가 포트·도메인·스냅숏 세 곳에 복사된다. `repoCheck.kind` 분기가 여러 곳에 있다. 두 `RepoWaitMonitor`의 옵션 이름이 `bundles`이고 로그 이름이 같다.
- 검증: `pnpm lint`, `pnpm typecheck` 통과. desktop 전체를 두 번 돌려 두 번 모두 1590개 통과·1개 실패였다. 첫 번째 실패는 결정 #6의 `zsh rc 멈춤 5초`(이 PC 설정)이고, 리뷰 반영 뒤 마지막 실행의 실패는 `scripts/tray-icons.test.ts`의 시간 초과였다. 후자는 단독 실행 두 번 모두 통과했고 그때 부하 평균이 22여서 결정 #7~#10과 같은 부하성 실패로 본다. 둘 다 이 티켓이 건드리지 않은 파일이다. 루트 `pnpm test`의 site 실패 1건도 결정 #6의 워크트리 환경성 실패다. 가짜 Sentry API(포트)·가짜 시계·실제 SQLite로 감지 규칙 25개, 주입 fetch로 어댑터 조회 10개, 진단 스냅숏·렌더러 화면 테스트를 더했고, 핵심 규칙마다 변이를 넣어 테스트가 잡는 것을 확인했다.
