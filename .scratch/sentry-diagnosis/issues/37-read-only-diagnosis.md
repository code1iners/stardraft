# 37: 읽기 전용 진단

**Spec:** [스펙](../spec.md) 7절(실행 종류, 지침과 진단 절차의 읽기 전용, 입력, 출력), 8절, 9절, 11절 "앱이 채우는 것"

**What to build:** 감지된 오류 이슈를 에이전트가 매핑된 저장소를 읽어 진단하고, 진단 보고서가 저장되어 상세에 보인다. 보고서 없이 끝나면 **진단 실패**로 남고 다시 시도하거나 완료로 치울 수 있다. 이 티켓의 상세 화면은 보고서 내용을 한 화면에 순서대로 보이는 최소 모양이고, 탭과 상태별 바닥 줄은 38번이 한다.

**Blocked by:** 36

**Status:** resolved

- [x] Sentry 어댑터가 생성 대기열에 붙는다. 감지된 진단은 `auto` 칸에, [다시 시도]는 `user` 칸에 선다. 매핑을 저장하거나 폴더가 돌아오면 저장소 대기 진단이 처음 보인 순서대로 재개된다.
- [x] 실행 종류 `diagnosis`가 있고 두 실행기가 지금의 읽기 전용 경계 그대로 돈다(MCP 없음, 시간 상한 20분, 묻지 않고 끊음). 사용자 추가 지침은 붙지 않는다.
- [x] 시작 직전에 오류 이슈 상태를 확인해 해결·보관·삭제·병합이면 조용히 빼고 로그에 적는다. 중복 억제 기록은 남는다.
- [x] 이벤트 데이터는 시작할 때 받는다. 일시적 실패와 토큰 문제는 진단 실패가 아니라 Sentry 어댑터 멈춤이고, 그 진단은 줄에 남으며 Flow 초안은 그 앞으로 지나간다.
- [x] 지침에 읽기 전용 **진단 절차**(코드 상수), 확신도 규칙, 한국어 규칙, 없는 데이터 항목이 들어간다. 출력 스키마에 재현이 없다.
- [x] 에이전트 결과가 스키마대로 읽히고, 근거 위치 검사와 비밀 파일 근거 검사가 Flow 초안과 같은 것으로 돈다. 보고서의 재현 칸은 앱이 "불가(허용 안 됨)"로 채운다.
- [x] 앱이 오류 이슈 정보와 실행 정보(저장소 경로, HEAD 해시, 커밋하지 않은 변경 유무, 에이전트와 버전, 걸린 시간, 생성 시각)를 채운다.
- [x] 재시도 뒤에도 실패했거나 취소한 진단은 사유가 붙은 진단 실패가 되고 자동으로 더 재시도하지 않는다. [다시 시도]와 [완료](확인 없이 최소 기록으로)가 된다. 진단 실패가 남은 오류 이슈에 새 재발이 오면 새 진단으로 바뀐다.
- [x] 상세에 대기("앞에 n개가 있습니다."), 진행(단계와 읽은 파일 수), 보고서, 실패 사유가 보이고 줄 서 있거나 진행 중인 진단을 취소할 수 있다.
- [x] 가짜 Sentry API와 가짜 실행기로 위 흐름이 테스트되고, 실행기 어댑터 테스트가 진단의 인수 묶음이 읽기 전용 경계임을 검사한다.
- [x] `pnpm lint`, `pnpm typecheck`, `pnpm test`가 통과한다.

## Comments

- 구현 메모: Sentry 어댑터는 `core/sentry/sentry-target-adapter.ts`(`SentryTargetAdapter`, 대상 종류 `sentry`)이고, 초안 대기열의 생성 대기열에 `extraAdapters`로 Flow 어댑터 뒤에 붙는다. 지침·출력 스키마·입력 문서·결과 읽기·오류 이슈 정보(없는 데이터, 소스맵, 스택 앞부분)는 `core/sentry/diagnosis-run.ts`다. 실행 종류 `diagnosis`를 더했고 두 실행기는 초안 실행과 같은 인수 묶음으로 돈다(Claude Code `--max-turns`만 120). 시간 상한은 20분(`DIAGNOSIS_TIMEOUT_MS`)이다. Sentry API 포트에 `errorIssueState`(상세 조회, 리디렉트를 따라가지 않고 병합됨으로 봄)와 `latestEvent`를 더했다. 이전 26번이 `sentry_diagnosis`에 `report`·`failure`·`runs`·`completed_at` 열을 더한다. 근거 위치 검사와 비밀 파일 근거 검사는 `draft-check.ts`의 `checkEvidence`로 Flow 초안과 같은 것을 쓴다. HEAD 해시는 `.git`을 직접 읽고(`core/repos/repo-git-state.ts`), 커밋하지 않은 변경은 `git status --porcelain`으로 본다(macOS는 `xcode-select -p`가 될 때만 불러 설치 창을 띄우지 않음).
- 상태: `queued`(대기, 진행 중은 대기열이 진행하는지로 가림) · `repo-check-needed` · `ready`(검토 대기) · `failed`(진단 실패) · `completed`(완료). 5절 표의 진행 중(흡수)·진단 실패(새 진단으로 교체, 같은 트랜잭션에서 지움)·완료(새 진단) 갈래를 구현했다. 등록 해제 때 빼는 상태에 진단 실패를 더했다.
- 해석으로 정한 것: (1) 시작 직전 확인의 실패 분류. 스펙 7절의 "일시적 실패(네트워크, 5xx, 429)와 토큰 문제"만 Sentry 어댑터 멈춤으로 두고, 기다려도 풀리지 않을 실패(403, 최신 이벤트 404, 그 밖의 4xx, 앱이 모르는 응답, 조직 목록에 없음)는 그 진단만 진단 실패 `sentry-unavailable`("Sentry에서 오류 데이터를 가져오지 못했습니다")로 둔다. Flow 어댑터의 `flow-unavailable`과 같은 자리다. 멈추면 그 진단이 대기열 맨 앞에서 다른 진단까지 막기 때문이다(리뷰에서 찾음). 시작 직전 상세 조회의 404만 "삭제됨"으로 조용히 뺀다. (2) 화면의 "실행 정보"는 "실행"을 화면에 쓰지 않는 규칙에 따라 `정보` 탭 표기와 같은 "진단 정보"로 보인다. (3) 진단 실패 사유 문장은 Flow 문장을 쓰되 초안·10분을 가리키는 셋(취소함, 시간 초과, 앱 오류)만 진단용으로 바꿨다. (4) 대기의 "앞에 n개"는 진행 중인 수 + 대기열에서 앞에 선 수이고, 0이면 "곧 진단을 시작합니다."다. (5) 보고서 release는 "이벤트 · 최초 · 최근"이다. 재발 활동의 release는 읽지 않는다. (6) [완료]는 진단 실패에만 둔다. 검토 대기 보고서의 [완료](확인 포함)는 38번이다.
