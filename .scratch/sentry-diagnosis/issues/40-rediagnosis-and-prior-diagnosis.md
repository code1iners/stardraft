# 40: 다시 진단과 앞선 진단 참고

**Spec:** [스펙](../spec.md) 10절, 7절 "앞선 진단의 참고", 11절 "앞선 진단 표시", 12절 "지시 입력"

**What to build:** 검토 대기인 보고서를 지시 없이 또는 **지시**를 덧붙여 다시 진단한다. 새 보고서가 나오면 앞선 것을 바꾸고, 실패하거나 취소하면 앞선 보고서로 돌아간다. 재발한 오류 이슈의 새 진단은 앞선 진단을 참고하고 보고서에 표시한다. 이 티켓의 다시 진단은 읽기 전용으로 돌고, "재현도 다시 하기"는 42번이 더한다.

**Status:** resolved

- [x] 지시 없이: 앞선 보고서를 넘기지 않고 쌓인 지시를 비운다. 지시를 덧붙여: 앞선 보고서(결과 스키마의 칸)와 쌓인 지시 전부를 넘긴다. 첨부는 넘기지 않는다. 이벤트 데이터는 새로 받는다.

- [x] 실패하거나 취소하면 진단 실패가 아니라 앞선 보고서의 검토 대기로 돌아가고, 알림 줄에 사유와 [다시 걸기]가 보인다. 쌓인 지시는 남는다.

## Comments

### 구현 결과 (2026-11-26)
- 검증: `pnpm lint`, `pnpm typecheck` 통과. desktop `pnpm test`는 1803개 중 1802개 통과. 실패 1개는 이 티켓과 무관한 기존 환경 문제(`node-process-runner` "zsh rc 멈춤 5초"). site `index-page` 실패도 이 PC의 기존 실패다.
- 상태 모델: 다시 진단은 새 상태가 아니라 "대기(`queued`)인데 앞선 보고서(`report`)를 보관한 진단"(`isRediagnosing`)이다. 그래서 대기열·재발 흡수(키만 기록)·재시작 복원은 기존 경로를 그대로 쓴다.
- 새 칸: 진단에 `directives`(쌓인 지시), `rediagnosisFailure`(돌아온 사유), 보고서에 `priorDiagnosis`. 마이그레이션 28이 `directives`·`rediagnosis_failure` 열을 더한다.
- 해석으로 정한 것(스펙이 말하지 않은 곳):
  1. 다시 진단 중 저장소 매핑·폴더가 사라지면 저장소 대기로 가지 않고 앞선 보고서로 돌아와 사유 `repository-unavailable`("연결한 저장소를 찾을 수 없습니다.")을 알린다.
  2. 사용자가 요청한 다시 진단은 시작 직전 확인에서 해결·보관돼도 조용히 빼지 않고 진단한다. 오류 이슈가 삭제(404)됐으면 앞선 보고서로 돌아와 `sentry-unavailable`을 알린다.
  3. 다시 진단 중 프로젝트 등록을 풀면 다시 진단만 취소(`cancelled`)해 앞선 보고서를 남긴다(검토 대기 보고서는 등록 해제에도 남는다는 규칙).
  4. 지시 없는 다시 진단은 시작할 때 쌓인 지시를 비운다(스펙 "쌓인 지시는 비운다"). 그래서 그 다시 진단이 실패해도 비운 지시는 돌아오지 않는다. 지시를 덧붙인 다시 진단은 실패해도 지시가 남는다.
  5. 앞선 진단 참고는 진단 시작 때 정한다: 먼저 만든 같은 오류 이슈의 검토 대기 보고서가 있으면 그 요약·원인·개선 방향(근거·남은 의문은 넘기지 않음), 없으면 가장 최근 완료한 진단의 날짜와 내보낸 파일 경로(파일이 없으면 날짜만). 완료 기록은 7일이 지나 목록에서 사라져도 저장소에서 읽는다. 다시 진단의 입력에도 같은 규칙으로 들어간다.
  6. 재현도 다시 하기 체크는 재현이 없어 두지 않는다(42번).
- 42번에 넘기는 것: 다시 진단 성공 때 `saveReport`가 앞선 첨부 폴더를 지운다(`removeAttachments`). 42번이 새 첨부를 같은 진단 폴더에 옮기는 순서를 정할 때, 옛 폴더 삭제가 새 첨부를 지우지 않도록 맞춰야 한다.
- 실기 확인 못 함: 화면(알림 줄·바닥 줄 지시 입력·메뉴)과 실제 CLI 진단은 실행하지 않았고 정적 렌더링 테스트와 가짜 실행기로만 확인했다.
