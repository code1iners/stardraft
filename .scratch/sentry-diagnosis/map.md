# Sentry 오류 이슈 진단 보고서

Label: wayfinder:map
Created: 2026-11-12

## Destination

이 지도가 끝나면 **구현 착수용 스펙**(`.scratch/sentry-diagnosis/spec.md`)이 나온다.

스펙이 다루는 기능은 다음과 같다.

- Sentry를 Flow에 이은 두 번째 **프로바이더**로 추가한다.
- 등록한 Sentry 프로젝트에서 새로 생기거나 재발한 **오류 이슈**를 감지한다.
- **에이전트**가 매핑된 저장소를 읽고 `diagnosing-bugs` 절차에 따라 시뮬레이터·에뮬레이터·브라우저로 **재현**을 시도한다.
- 에이전트가 원인과 개선 방향을 담은 **진단 보고서**를 만든다.
- 사용자는 진단 보고서를 앱에서 검토하고, 원하면 마크다운 파일로 **내보낸** 뒤 **완료**한다.

2026-11-24에 목적지를 넓혔다. 다른 사람의 Flow 키로 바꿀 때 Flow 기록을 지우지 않고 **계정별로 보관**하는 변경도 이 스펙에 담는다([Flow 기록의 계정별 보관](issues/22-flow-records-per-account.md)).

스펙만 보고 티켓을 나눠 바로 구현에 들어갈 수 있으면 도착이다.

## Notes

- **도메인**: Sentry(sentry.io) 오류 모니터링, 기존 Flow 프로바이더, 로컬 저장소, 로컬 CLI 코딩 에이전트(Claude Code, Codex).
- **용어**: 저장소 루트의 [GLOSSARY.md](../../GLOSSARY.md)를 따른다. 이 지도에서 정한 용어는 **프로바이더**, **오류 이슈**, **재현**, **진단 보고서**, **진단 절차**, **진단 실패**, **내보내기**, **완료**이고, **초안**의 뜻도 넓혔다. Sentry의 "이벤트"(개별 발생)와 **오류 이슈**(묶음)를 섞어 쓰지 않는다.
- **티켓 유형별로 쓰는 스킬**
  - grilling 티켓: `grilling`, `domain-modeling`
  - prototype 티켓: `prototype`
  - research 티켓: `research`
  - 화면이 걸린 결정: `ui-design`을 함께 쓴다.
  - 재현 절차가 걸린 결정: `diagnosing-bugs`를 참고한다.
- **진행 방식**: 지도와 티켓은 차팅 세션에서 만들고, 각 티켓은 새 세션에서 하나씩 진행한다. research 티켓도 차팅 세션에서 실행하지 않았다.
- **문서 언어**: 이 지도의 모든 문서는 한국어로 쓴다.
- **조사 결과 위치**: 조사 결과는 이 폴더의 `research/`에 파일로 두고 티켓에서 링크한다.
- **현재 코드 사실**: 에이전트 실행은 읽기 전용이다. Claude Code는 `--tools Read,Glob,Grep`·`--restricted`·MCP 차단(`apps/desktop/src/core/agent/claude-code-executor.ts`), Codex는 셸 명령을 실행하되 권한 프로필(Seatbelt)로 읽기 범위를 제한하고 쓰기와 네트워크를 막는다(`apps/desktop/src/core/agent/codex-executor.ts`). 재현은 이 경계를 여는 일이라서 가장 무거운 결정이다.

### 차팅 중 확정된 전제

티켓 없이 정한 사항이다. 바꾸려면 지도를 다시 그려야 한다.

- **목적지 형태**: 구현은 지도 밖이고, 결과물은 스펙이다.
- **프로바이더**: Sentry는 Flow와 대등한 프로바이더다. 나중에 Slack·Gmail·Threads 등이 더 붙을 수 있다. 이번에는 Sentry를 붙이는 데 실제로 필요한 공통 경계만 정한다. 이후 프로바이더는 그 경계에 맞는지 점검만 하고 설계하지 않는다.
- **트리거 단위**: 새로 생긴 오류 이슈와 해결 후 재발한 오류 이슈마다 진단을 한 번 한다. 이벤트 단위로는 진단하지 않고, 수동 진단 요청도 두지 않는다.
- **진단 대상**: 등록한 Sentry 프로젝트의 오류 이슈 중 환경(예: `production`)과 레벨(예: `error` 이상) 필터를 통과한 것이다. Sentry 배정 여부는 보지 않는다.
- **저장소 찾기**: Flow처럼 Sentry 프로젝트와 로컬 저장소를 잇는 **저장소 매핑**을 쓴다.
- **결과물과 행선지**: 진단 보고서는 앱에서 검토하고 마크다운 파일로 내보낼 수 있다. 외부에 게시하지 않는다.
- **재현 책임**: 앱은 재현 환경을 준비하지 않는다. 에이전트에게 `diagnosing-bugs` 절차와 재현 도구 사용을 허용한 **지침**을 넘기고, 에이전트가 자기 도구로 재현을 시도한다. 결과는 성공·실패·불가 중 하나로 보고서에 적는다.
- **Sentry 종류**: 공식 sentry.io만 지원한다. 서버 주소 설정은 두지 않는다(차팅 때 "서버 주소만 열어 둔다"로 잘못 적었던 것을 [계정 연결 티켓](issues/04-sentry-connection-and-mapping.md)에서 바로잡음).
- **프로바이더는 모두 선택**: Flow를 포함해 어떤 프로바이더도 필수가 아니다(같은 티켓에서 정함).

## Decisions so far

<!-- 닫힌 티켓마다 한 줄: 관련성을 판단할 만큼의 요지 + 링크 -->

- [Flow 전용 구조에서 프로바이더 공통 경계 후보 조사](issues/03-provider-seam-codebase-research.md): 공통으로 쓸 수 있는 것은 실행기 포트뿐이고 나머지는 Flow 묶음 타입에 묶여 있다. 경계 후보는 A(묶음에 종류 추가)·B(대기열의 실행 관리를 공통으로 떼고 프로바이더 어댑터)·C(실행기 포트만 공유) 셋이다. 이와 별도로 대기열 직렬 실행·Flow 키 멈춤·계정 리셋이 Sentry 쪽에 미치는 영향도 적었다.
- [Sentry 오류 이슈 감지와 인증 조사](issues/01-sentry-detection-auth-research.md): 조직 단위 이슈 목록 API를 폴링해 감지할 수 있다(신규는 `firstSeen` 체크포인트, 재발은 `is:regressed`). 인증은 개인 토큰에 `org:read`+`event:read`이고 조직 토큰은 쓸 수 없다. 환경·레벨·프로젝트 필터는 서버에서 걸 수 있고, 진단 데이터는 `events/latest/` 한 번으로 받는다. 지역별 `regionUrl`과 rate limit은 주의해야 한다.
- [재현에 필요한 에이전트 실행 권한 조사](issues/02-agent-reproduction-permissions-research.md): 두 CLI 모두 macOS Seatbelt로 쓰기 범위와 네트워크를 좁힐 수 있다. Codex는 이미 OS 수준에서 셸 경유 비밀 읽기를 막고, Claude는 샌드박스를 켜야만 막힌다. MCP(Playwright)는 샌드박스 밖에서 돈다. 환경 변수가 그대로 넘어가는 문제와 `mcp__*` deny 구조도 바꿔야 한다. 정리한 선택지는 A~F다.
- [Sentry 계정 연결, 진단 대상 필터, 저장소 매핑 설정](issues/04-sentry-connection-and-mapping.md): 개인 토큰 하나를 safeStorage로 저장하고, 문제가 생기면 Sentry 감지만 멈춘다. 여러 조직을 허용하며 프로젝트는 옵트인으로 등록하고 `id`를 키로 쓴다. 환경·레벨 필터는 프로젝트마다 두고(기본 `production`, `error`·`fatal`), 등록 시각을 기준 시각으로 잡는다. 설정은 `settings.json`에 두므로 Flow 리셋에도 남는다. 화면은 `Sentry` 칸을 새로 두고 매핑은 `저장소` 칸에 모은다. sentry.io만 지원하고, 온보딩에서 Flow 필수를 풀어 모든 프로바이더를 선택으로 둔다.
- [재현 실행의 보안 경계](issues/05-reproduction-security-boundary.md): 샌드박스로 가두지 않고, 저장소마다 켠 **재현 허용** 아래에서 내 개발 환경을 APFS 복제 사본(`.git` 제외)으로 그대로 쓴다. 사본의 `.env`는 저장소별 **재현용 환경 파일**이고 그 값의 노출은 받아들인다. 셸·네트워크를 열고, 사용자의 MCP 정의만 가져와 에이전트가 직접 조작한다(기본 `자동` + 위험 도구 deny, `직접 선택` 가능). 상한 20분, 새로 켜진 시뮬레이터만 정리. [ADR 0003](../../docs/adr/0003-reproduction-opens-agent-boundary.md).
- [저장소 매핑이 없는 Sentry 프로젝트의 오류 이슈 처리](issues/06-unmapped-sentry-project.md): 추측하지 않는다. 자동 선택·경로 추정 없이 **저장소 매핑 필요**로 남기고, 그 프로젝트에 매핑을 저장하면 자동으로 재개한다. 오류 이슈 하나에만 고르는 경로는 두지 않는다. Sentry 매핑은 프로젝트 하나에 저장소 하나이고 같은 저장소를 여러 프로젝트에 매핑할 수 있다. 매핑된 폴더가 사라지면 **저장소 확인 필요**로 멈춘다.
- [재현용 MCP 불러오기와 위험 도구 목록 조사](issues/10-reproduction-mcp-research.md): Claude는 `--restricted`에서 사용자 MCP가 전혀 실리지 않으므로 앱이 설정 파일을 읽어 `--mcp-config`로 넘겨야 한다. Codex는 `--ignore-user-config`를 유지한 채 `-c mcp_servers.*`로 넘길 수 있다. `${VAR}` 인증과 최소 환경 변수가 충돌하고, Codex는 승인 `never`에서 조작 도구가 막힐 수 있으며, Codex의 MCP 프로세스는 그룹 SIGKILL을 견딘다. deny는 Claude glob, Codex 서버별 `disabled_tools`로 걸고, 우회되는 도구가 있다.
- [진단 보고서의 형식과 저장 위치](issues/07-diagnosis-report-format.md): 결론 먼저(요약·재현·원인과 확신도·개선 방향·근거·남은 의문, 메타데이터는 아래) 형식이다. 오류 이슈·실행 정보와 "불가(허용 안 됨·시간 초과)"는 앱이, 나머지는 에이전트 결과 스키마가 채운다. 파일로 만드는 것은 선택 동작 **내보내기**(`~/Documents/Stardraft/Reports/Sentry/`, `YYYY-MM-DD-<slug>-<shortId>.md`, 덮어쓰지 않음)이고, 끝내는 것은 **완료**(최소 기록만 남김, Sentry 상태는 안 바꿈)다. 첨부는 이미지·로그 10개·20MB까지.
- [프로바이더 공통 경계 결정](issues/08-provider-seam-decision.md): 후보 B를 골랐다. `DraftQueue`를 공통 **생성 대기열**(직렬·우선순위·재시도·멈춤·취소)과 **대상 어댑터**(Flow = 기존 묶음, Sentry = 새 모듈)로 나눈다. `RunKind`에 `'diagnosis'`를 더하고(재현 허용이 꺼지면 읽기 전용으로 낮춤), 지침은 어댑터가 만들며 사용자 추가 지침은 Flow에만 붙인다. Sentry는 전용 저장 포트와 표를 갖고, 대기열 키는 `(kind, targetId)`이며, 완료 기록은 Sentry 표에 둔다(`minimal_record`는 그대로). `ReviewSnapshot`에는 `diagnoses`를 따로 더한다. 멈춤은 전역(에이전트)과 어댑터별(프로바이더 연결) 두 층이다. [ADR 0004](../../docs/adr/0004-generation-queue-with-provider-adapters.md).
- [Sentry 설정 칸·저장소 매핑·온보딩 화면 시안](issues/09-sentry-settings-ui-prototype.md): **작업 폴더와 Flow 자동 선택을 없앤다**. 저장소는 매핑으로만 정하고, 매핑이 없으면 Flow 멘션도 기다린다. 온보딩 필수는 에이전트 연결 하나이고, 필수/선택 두 묶음으로 보인다. Sentry 칸은 요약 줄에 편집 모달(필터+저장소)을 둔다. 저장소 칸은 `Flow`·`Sentry` 탭으로 나눈 같은 모양의 매핑과 저장소별 재현 허용을 둔다. 재현 도구 권한은 에이전트 칸의 `재현` 탭에 둔다. 앱의 시트를 모두 화면 가운데 모달로 바꾼다.
- [재현용 MCP 적용 방식 결정](issues/11-reproduction-mcp-wiring.md): 재현 허용이 켜진 진단 실행에만, 실행하는 CLI 자신의 MCP 정의(Claude user·local·`.mcp.json`, Codex `config.toml`)를 싣는다. 플러그인 MCP와 claude.ai 커넥터는 싣지 않는다. `${VAR}`는 참조된 이름만 로그인 셸에서 읽어 통과시키고 평문 값은 명령줄에 싣지 않는다. 서버마다 도구를 모두 허용(Codex `approve`)하고, 셸로는 못 하는 피해를 막는 고정 deny 목록을 건다. `직접 선택`은 켠 서버 이름만 저장한다. Codex MCP는 CLI를 죽이기 직전에 자손 그룹을 끝낸다. 버전 하한은 그대로이고, 빠진 서버는 보고서 실행 정보에 적는다.
- [진단 실행 큐의 동시 실행과 우선순위](issues/12-diagnosis-run-queue.md): 직렬을 버리고 최대 n개를 동시에 돌린다. n은 설정의 슬라이더(1~5, 기본값 1)로 고른다. 종류별 제한은 "재현하는 진단은 한 번에 하나"뿐이다. 칸은 `resume` > `user` > `auto` 그대로이고 감지된 진단은 `auto`, 사용자가 요청한 진단은 `user`에 서며 선점은 없다. 재시도는 Flow와 같은 규칙(일시적 실패 1회)이다. 전역 실패 때 함께 돌던 실행은 끊지 않는다. 취소 뒤 다음 재현 진단은 시뮬레이터가 꺼진 뒤 시작하고, 앱 종료는 최대 5초만 기다리며 남은 사본은 다음 시작 때 지운다.
- [작업 폴더·자동 선택 폐지의 Flow 전환](issues/13-flow-without-work-folders.md): Flow 묶음 상태를 **저장소 매핑 필요**와 **저장소 확인 필요** 둘로 나누고, 매핑을 저장하거나 폴더가 돌아오면 자동으로 재개한다. 묶음 하나에만 저장소 고르기는 남기고(후보에서 작업 폴더 무리만 뺌) 고른 저장소는 나중 매핑보다 먼저 쓴다. 저장소가 정해지지 않은 초안은 다시 만들기·지시를 막는다. 기존 사용자는 안내 없이 넘어가며 `workFolders` 키는 읽지 않고 남긴다. 걸려 있던 묶음은 첫 시작 때 다시 판정하고, 자동 선택으로 만든 초안은 그대로 둔다. 자동 선택·작업 폴더 코드는 모두 걷어 낸다.
- [병렬 작업 수 설정 화면 시안](issues/14-concurrency-setting-ui-prototype.md): 설정값 이름을 **병렬 작업 수**로 정했다(옛 "동시 실행 수"). 에이전트 칸에 `병렬 작업` 탭을 더해 눈금 없는 슬라이더(1~5)와 현재 값, 한도 안내 한 줄, 두 줄 표(초안 · 진단 최대 n개 / 재현하는 진단 그중 1개)를 둔다. 표의 이름 옆 툴팁이 뜻과 재현 예외의 이유를 알리고, 값을 줄이면 "진행 중인 n개가 끝나면 맞춥니다"를 보인다. 화면에는 "프로바이더" 대신 "서비스"를 쓰고 특정 서비스 이름에 묶인 문구를 피한다. 슬라이더와 툴팁은 새 패턴이다.
- [Sentry 실행 상태의 저장 위치](issues/15-sentry-run-state-storage.md): Sentry 표는 같은 `state.db`에 두고, `sentry_`로 시작하는 표는 Flow 계정을 바꿀 때 지우지 않는다. 그때 대기열에서는 Flow 초안만 뺀다. Sentry 토큰을 바꿔도 실행 상태는 그대로다. 연결을 끊으면 토큰만 지우고 감지를 멈춘다. 프로젝트 등록을 풀면 진단을 취소하고 체크포인트·중복 억제 기록을 지우되 보고서와 완료 최소 기록은 남긴다. 본문은 표에, 첨부는 앱 데이터 폴더 `diagnoses/<진단 id>/`에 둔다. 원격 저장소(R2)는 쓰지 않는다.
- [따라잡기와 중복 억제](issues/16-catch-up-and-dedupe.md): **신규**는 등록한 환경에서 처음 보인 것이고, 따라잡기는 최근 7일까지만 하며 개수 상한은 없다. 7일 넘게 놓친 재발과 `escalating`은 진단하지 않는다. 체크포인트는 프로젝트마다 두고 조회 시작 시각으로 옮기며 겹치게 조회한다. 중복 억제 키는 신규가 오류 이슈 id, 재발이 `(오류 이슈 id, 재발을 일으킨 이벤트 id)`이고 진단 간격은 없다. 줄 서 있거나 실행 중인 진단이 있으면 재발을 흡수하고, 검토 대기 중이면 새 진단을 따로 만든다. 폴링은 5분 주기이고 `429`면 `X-Sentry-Rate-Limit-Reset`까지 Sentry 감지만 미룬다.
- [`diagnosing-bugs` 절차의 전달 방식](issues/17-diagnosing-bugs-delivery.md): 스킬 설치를 가정하지 않는다(Claude `--restricted`는 스킬을 끈다). 앱이 무인 진단용으로 다시 쓴 **진단 절차**를 코드 상수로 두고 지침에 넣는다. 원문의 1~4단계와 비밀 가리기만 남기고 수정·정리 단계는 뺀다. 사람에게 묻는 대신 남은 의문에 적는다. 사본 안에서 코드를 고쳐 가설을 확인할 수 있고, 루프를 못 만들어도 코드 읽기로 끝까지 쓰되 재현 없이는 확신도 `high`를 피한다. 재현 시도는 10분쯤에서 끊는다. 성공은 같은 예외가 같은 자리에서 난 것이다. 읽기 전용 진단은 지침과 스키마에서 재현을 뺀다. 보고서는 한국어로 쓴다.
- [진단 실패와 데이터 부족의 처리](issues/18-diagnosis-failure-handling.md): 데이터가 부족해도 항상 진단하고, 이벤트 데이터는 시작할 때 받는다(못 받으면 실패가 아니라 Sentry 쪽 멈춤). 보고서 없이 끝난 진단은 사유가 붙은 **진단 실패**로 남아 [다시 시도]·[완료]를 받고, 새 재발이 오면 교체된다. 재현하는 진단은 상한 5분 전에 사용자에게 [계속 진행](10분씩, 합계 60분)·[멈추기]를 묻고, 답이 없으면 멈춘다. 멈출 때 Claude에게는 실행 중 메시지로 보고서를 마무리시키고(5분), Codex는 끊는다. 시간 초과 실패에는 [재현 없이 다시 시도]가 있다. 재현 실패·불가 보고서는 같은 검토 대기다. 시작 직전에 해결·보관·삭제된 오류 이슈는 조용히 뺀다. 상태는 일곱 개다.

## Out of scope

- Sentry 이슈 댓글이나 Flow로 진단 보고서를 게시하는 것.
- Slack·Gmail·Threads 등 다른 프로바이더 추가.
- 이벤트 단위 진단, 수동 진단 요청.
- 진단 결과에 따른 자동 수정이나 PR 생성.
- 앱이 재현 환경(시뮬레이터 부팅, 브라우저 설치 등)을 직접 준비하는 것.
- 자가 호스팅 Sentry 지원(서버 주소 설정 포함).
- 진단 보고서를 링크로 공유하거나 첨부를 원격 저장소(Cloudflare R2 등)에 올리는 것. 공유 기능을 만들 때 다시 본다([저장 위치](issues/15-sentry-run-state-storage.md)).
