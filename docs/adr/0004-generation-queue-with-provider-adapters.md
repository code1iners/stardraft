# 프로바이더는 공통 생성 대기열 아래의 대상 어댑터로 붙인다

Stardraft의 감지 → 초안 대기열 → 검토는 모두 Flow 타입 `MentionBundle` 하나를 주고받았다. 담당 업무 초안도 별도 타입 없이 이 묶음에 선택 필드를 더하는 방식으로 붙었다. Sentry를 두 번째 프로바이더로 붙이면서 이 선례를 따르지 않기로 했다.

초안 대기열(`DraftQueue`)에서 프로바이더와 무관한 부분을 떼어 공통 **생성 대기열**로 두고, 대상마다 다른 부분은 **대상 어댑터**로 받는다. 공통 부분은 실행 자리 관리(병렬 작업 수), 우선순위, 대기열 저장, 실행 직전 에이전트 확인, 일시적 실패 재시도, 전역 실패 멈춤, 취소다. 어댑터가 맡는 부분은 대상 준비(지침·입력·출력 스키마·저장소·시간 상한·실행 종류), 결과 읽기, 저장·실패·저장소 확인 필요 기록이다. Flow 어댑터는 기존 묶음 모듈을 감싸고, Sentry 어댑터는 새로 만든다. 대기열은 대상을 `(종류, ID)`로만 안다. 각 어댑터는 자기 저장 포트와 표, 자기 검토 스냅숏 배열을 갖는다.

멈춤은 두 층으로 나눈다. 에이전트를 쓸 수 없으면 전부 멈춘다. 프로바이더 연결 문제(Flow 키 거부, Sentry 토큰 문제, 도달 불가)는 그 어댑터의 대상만 멈춘다. 그래서 한 프로바이더의 계정 문제가 다른 프로바이더의 진행을 막지 않는다.

생성 대기열은 처음에 직렬로 정했다가, 설정한 수만큼 동시에 돌리는 것으로 바꿨다(기본값 1은 직렬과 같다). 대기열은 종류를 가리지 않고 꺼내되, 재현하는 진단만 한 번에 하나로 묶는다. 시뮬레이터와 dev 서버 포트가 한 벌이라 겹치면 재현 결과가 틀려지기 때문이다. 순서를 종류별로 나누거나 실행 중인 것을 끊는 선점은 두지 않는다.

## Considered Options

- **대상 종류 확장(담당 업무 선례)**: `MentionBundle`에 `errorIssue?`를 더하고 같은 묶음·대기열·검토 화면을 쓴다. 새 코드는 가장 적다. 그러나 가장 큰 Flow 파일들에 종류 분기가 퍼지고, `mention_bundle`의 Flow 열이 `NOT NULL`이라 Sentry 값을 억지로 채워야 한다. Flow 키가 없으면 대기열 전체가 멈추는 동작도 그대로 남는다. 프로바이더가 늘수록 유니온이 계속 커진다.
- **실행기 포트만 공유**: Sentry가 감지·저장·대기열·화면을 모두 따로 갖는다. Flow 회귀 위험은 가장 낮다. 대신 재시도·멈춤·취소·대기열 저장을 프로바이더마다 중복하고, 두 대기열이 같은 CLI 에이전트를 동시에 돌린다. 이것을 막으려고 공용 줄을 두면 결국 생성 대기열이 된다.

## Consequences

- `DraftQueue`를 나누는 동안 Flow 회귀 위험이 있다. 기존 `draft-queue.test.ts`가 대기열 인터페이스를 거쳐 Flow 동작을 검증하므로 그 테스트를 유지한 채 나눈다. 위험 지점은 우선순위·`resume` 재진입, 저장된 대기열 복원, 멈춤 까닭 일반화, `draft_queue` 이관이다.
- `draft_queue`에 대상 종류 열을 더하는 이관이 필요하다.
- 답변 초안 전용 규칙(쉬운 말 문체, 게시, `minimal_record`)은 Flow 어댑터 안에 남는다. 다른 프로바이더는 자기 지침·문체·종착 상태를 따로 정한다.
- 병렬 작업 수가 1이면 20분짜리 진단이 줄지어 Flow 초안을 늦출 수 있다. 사용자가 병렬 작업 수를 올려 푼다.
- 동시에 도는 실행은 같은 로그인의 사용량 한도를 함께 쓴다.
- 다음 프로바이더는 어댑터 하나와 저장 포트·스냅숏 배열을 더해 붙인다. 대기열 정책을 바꾸면 모든 프로바이더에 함께 적용된다.

## 구현 뒤 확인 (2026-11-26)

구현(28·33·37번)은 이 결정과 어긋나지 않는다. 다만 결정이 말하지 않은 두 가지가 구현에서 생겼다.

- **계정을 바꾸는 동안의 종류별 멈춤**: "멈춤은 두 층"(전역·어댑터)과 다른 장치다. 계정을 바꾸는 동안 한 종류(Flow)의 대상만 멈추는 장치(`suspendKind`)이고, 앱 종료를 한 종류에만 적용한 것이라 실패 멈춤 층이 아니다([33번](../../.scratch/sentry-diagnosis/issues/33-flow-records-per-account.md)).
- **어댑터 멈춤의 범위**: Sentry 어댑터는 일시적 실패(네트워크·5xx·429)와 토큰 문제에서만 멈추고, 기다려도 안 풀리는 실패(403, 최신 이벤트 404 등)는 그 진단만 진단 실패로 둔다. 멈추면 대기열 맨 앞에서 다른 진단까지 막기 때문이다([37번](../../.scratch/sentry-diagnosis/issues/37-read-only-diagnosis.md)).
- Sentry 어댑터는 `DraftQueue`의 `extraAdapters`와 대상 단위 메서드로 붙어 있어, 이름이 초안 대기열인 모듈이 진단도 다룬다. 공통 생성 대기열 분리를 더 밀지 않은 것이다.
