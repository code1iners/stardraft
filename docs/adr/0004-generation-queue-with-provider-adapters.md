# 프로바이더는 공통 생성 대기열 아래의 대상 어댑터로 붙인다

Stardraft의 감지 → 초안 대기열 → 검토는 모두 Flow 타입 `MentionBundle` 하나를 주고받았다. 담당 업무 초안도 별도 타입 없이 이 묶음에 선택 필드를 더하는 방식으로 붙었다. Sentry를 두 번째 프로바이더로 붙이면서 이 선례를 따르지 않기로 했다.

초안 대기열(`DraftQueue`)에서 프로바이더와 무관한 부분을 떼어 공통 **생성 대기열**로 두고, 대상마다 다른 부분은 **대상 어댑터**로 받는다. 공통 부분은 직렬 실행, 우선순위, 대기열 저장, 실행 직전 에이전트 확인, 일시적 실패 재시도, 전역 실패 멈춤, 취소다. 어댑터가 맡는 부분은 대상 준비(지침·입력·출력 스키마·저장소·시간 상한·실행 종류), 결과 읽기, 저장·실패·저장소 확인 필요 기록이다. Flow 어댑터는 기존 묶음 모듈을 감싸고, Sentry 어댑터는 새로 만든다. 대기열은 대상을 `(종류, ID)`로만 안다. 각 어댑터는 자기 저장 포트와 표, 자기 검토 스냅숏 배열을 갖는다.

멈춤은 두 층으로 나눈다. 에이전트를 쓸 수 없으면 전부 멈춘다. 프로바이더 연결 문제(Flow 키 거부, Sentry 토큰 문제, 도달 불가)는 그 어댑터의 대상만 멈춘다. 그래서 한 프로바이더의 계정 문제가 다른 프로바이더의 진행을 막지 않는다.

## Considered Options

- **대상 종류 확장(담당 업무 선례)**: `MentionBundle`에 `errorIssue?`를 더하고 같은 묶음·대기열·검토 화면을 쓴다. 새 코드는 가장 적다. 그러나 가장 큰 Flow 파일들에 종류 분기가 퍼지고, `mention_bundle`의 Flow 열이 `NOT NULL`이라 Sentry 값을 억지로 채워야 한다. Flow 키가 없으면 대기열 전체가 멈추는 동작도 그대로 남는다. 프로바이더가 늘수록 유니온이 계속 커진다.
- **실행기 포트만 공유**: Sentry가 감지·저장·대기열·화면을 모두 따로 갖는다. Flow 회귀 위험은 가장 낮다. 대신 재시도·멈춤·취소·대기열 저장을 프로바이더마다 중복하고, 두 대기열이 같은 CLI 에이전트를 동시에 돌린다. 이것을 막으려고 공용 줄을 두면 결국 생성 대기열이 된다.

## Consequences

- `DraftQueue`를 나누는 동안 Flow 회귀 위험이 있다. 기존 `draft-queue.test.ts`가 대기열 인터페이스를 거쳐 Flow 동작을 검증하므로 그 테스트를 유지한 채 나눈다. 위험 지점은 우선순위·`resume` 재진입, 저장된 대기열 복원, 멈춤 까닭 일반화, `draft_queue` 이관이다.
- `draft_queue`에 대상 종류 열을 더하는 이관이 필요하다.
- 답변 초안 전용 규칙(쉬운 말 문체, 게시, `minimal_record`)은 Flow 어댑터 안에 남는다. 다른 프로바이더는 자기 지침·문체·종착 상태를 따로 정한다.
- 다음 프로바이더는 어댑터 하나와 저장 포트·스냅숏 배열을 더해 붙인다. 대기열 정책을 바꾸면 모든 프로바이더에 함께 적용된다.
